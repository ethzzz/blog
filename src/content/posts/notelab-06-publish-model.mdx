## 知识地图

```text
编辑态  xxx                     B 端读写，随时可脏
   │
   │  publish：整份复制（不是逐字段合并）
   ▼
发布态  xxx_published           C 端匿名只读，只有这一份
   │
   │  unpublish：直接 remove 这个键
   ▼
C 端启动/定时拉取 → 本地缓存 → 组件消费

关键：C 端读不到编辑态，所以「改了没发布」= 线上不变，这是特性不是 bug。
```

## 一、为什么值得多存一份

最省事的方案是 C 端直接读编辑态键，代码少一个分支。它的问题在**发布时机不可控**：

- B 端每次保存都是一次整包覆盖写，中间态天然存在（表单分步填、批量导入先跑一半）；
- 前台是匿名可见的，任何人任何时刻都可能撞上那个中间态；
- 更糟的是**没有回滚点**。编辑态一直在被覆盖，出了事你只能"再改回去"，而改回去的依据已经丢了。

分成两份之后，三个收益立刻拿到：

| 能力 | 编辑态单份 | 编辑/发布两份 |
|---|---|---|
| 半套配置不外泄 | ❌ 靠人克制 | ✅ 结构上读不到 |
| 回滚 | ❌ 只能手工改回 | ✅ 上一份快照还在（或重新发布旧内容） |
| 灰度/择时发布 | ❌ 保存即生效 | ✅ 发布动作独立，可挑时间 |
| 权限边界 | ❌ C 端接口要能读全量 | ✅ C 端只读一个键，写权限彻底无关 |

代价说清楚：**内容有两份，会出现"我改了，怎么线上没变"**。这不是技术问题，是心智问题，我的处置是在 B 端页面顶部常驻显示「当前线上版本：未发布变更 N 项」，把这层差异显式化。藏起来才是事故源头。

## 二、复制的语义：整份复制，不做字段合并

```java
// publish：把编辑态整份塞进发布键
public void publish() {
    var cfg = UiConfigService.getConfig();
    cfg.put("xxx_published", xxxService.of(cfg));   // of() 里已含懒 seed
    UiConfigService.save(cfg);
    UiConfigService.invalidate();
}

// unpublish：直接摘掉这个键，C 端读到空
public void unpublish() {
    var cfg = UiConfigService.getConfig();
    cfg.remove("xxx_published");
    UiConfigService.save(cfg);
    UiConfigService.invalidate();
}
```

必须是**整份复制**，理由和第五节"全量提交"是同一个：字段级合并会让"发布"变成"叠加"，删掉的一项会因为在旧快照里存在而复活。整份复制的语义只有一句：**发布后的线上内容，与此刻编辑器的内容完全一致，不多不少。**

`unpublish` 的语义也要定死：它不是"回到上一版"，而是**下线**。回到上一版的做法是"编辑态改回旧内容再发布"，或者你另存历史快照键。把这两个动作混在一起，早晚会在真实事故里按错。

## 三、C 端只读那一个键，且匿名

C 端接口只暴露快照，且**不带鉴权**（因为前台内容本来就该公开）：

```java
@GetMapping("/api/c/xxx/content")     // 匿名可读
public Resp<JsonNode> content() {
    var published = UiConfigService.getConfig().get("xxx_published");
    return Resp.ok(published == null ? EmptyDoc.of() : published);   // 未发布 = 空文档
}
```

「未发布时返回空」这条是安全边界，也是最好的验收点：**未发布状态下请求这个接口，所有切片必须是空**。如果它返回了内容，说明匿名接口指到了编辑态——那是数据外泄，不是显示 bug。我在 [第五篇](/blog/posts/notelab-05-admin-module-pipeline/) 的六条断言里留了这条，这里是它的原理。

## 四、缓存：正确性问题先于性能问题

C 端每次渲染都打后端显然不行，所以有本地缓存。缓存引出的三个坑，按危险程度排序：

1. **权限内容不能被缓存成公共结果**。这条路径之所以安全，正是因为 C 端只读公开快照。哪天你要在 C 端读"按用户不同"的内容，缓存 key 必须带上身份维度——和语义缓存那个坑是同一个（见 [面试宝典 AI 工程篇 9b](/blog/posts/interview-guide-22-ai-engineering/)）。
2. **发布后多久生效**要明确。我的做法是短 TTL + `invalidate()` 后强制回源，并把这个时长写进文档而不是留在代码里；用户能接受"发布后最多 N 秒可见"，但不能接受"我不知道什么时候可见"。
3. **失败要能用旧值**。回源失败时继续用缓存，而不是白屏——这是 [第三篇](/blog/posts/notelab-03-ai-capability/) 里"AI 是旁路不能拖垮主流程"的同一条原则：**外部依赖的失败不能变成主链路的失败**。

## 五、发布动作要在 UI 上诚实

三个我后来强制加的约定：

- 发布按钮旁显示**脏摘要**（哪些切片与线上不一致、各多少条），让人知道自己在发布什么；
- 发布成功后回读一次 C 端接口做**闭环确认**，而不是只看接口的 200；
- `unpublish` 走二次确认，并在文案里写明"前台会立刻变成空"，不要用一个模糊的"下架"。

这三条本质都是**把不可见的状态变得可见**，和第五篇的脏标记整份比对是同一种工程品味。

## 小结

- 分离的动机不是流程漂亮，而是「中间态不能外泄」+「要有回滚点」。
- 发布 = 整份复制；撤销 = 摘键下线（不是回到上一版）。语义要提前定死并写进文案。
- C 端只读快照、匿名、未发布返回空——这三条同时是功能设计与安全边界。
- 缓存的三条铁律：身份进 key、生效时长要明说、回源失败用旧值。
- UI 必须显式呈现"编辑态 ≠ 线上态"，否则分离带来的困惑会大于收益。

## 练习

1. 给你的后台加一个"与线上不一致"的脏摘要（哪怕只是一行文字），并在页面上验证：改一项不发布 → 摘要计数 +1 → 前台接口返回不变。
2. 写两条断言并跑通：未发布时 C 端接口所有切片为空；publish 后 C 端内容与编辑器逐字段一致。
3. 故意把 `publish` 改成字段级合并，构造一次"删掉的项在发布后复活"，然后解释为什么整份复制不会出这个问题。
4. 把回源失败的降级做出来：断掉后端 → C 端仍显示缓存内容，并在控制台能看到一条明确的降级日志。
