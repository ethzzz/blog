> [!NOTE]
> 这是 **notelab 分组**的第七篇。[第四篇](/blog/posts/notelab-04-deploy-and-verify/) 讲的是"怎么证明改动真的上线了"（状态码、字节大小、CSS 类、截图四层证据）。这篇正好相反：**盘点那些会主动骗你的检查**——它们返回成功、输出漂亮，但结论是假的。
> 每一条都是我真的信过一次之后才发现的，不是设想出来的风险。

> [!TIP]
> 「绿灯必须有证据」这件事固化成流水线，就是[测试与质量门禁](/blog/posts/engineering-roadmap-12-testing-gates/)；视觉回归那条另见[前端工程化的发布回滚](/blog/posts/engineering-roadmap-13-release-rollback/)。

## 知识地图

```text
「通过」信号的两种失效方向
├── 假绿（报了成功但事实不成立）  ← 危险，因为你不会再查
│     1 上一次构建的日志残留   2 同步脚本静默 return   3 同名的假包
│     6 大文件写入未落盘       7 无头浏览器截出一堆同图
└── 假红（报了失败但事实成立）    ← 浪费时间，容易被误当成回归
      4 .next/types 陈旧 TS2307    5 既有噪声淹没本次改动
```

## 一、假绿：`tail` 日志里的 `BUILD SUCCESS`

`tail` 构建日志看到 `BUILD SUCCESS` 就认为这次构建过了——**它可能是上一次留下的**。日志文件是追加的，而失败的那次构建往往在写"最终结果"之前就断了，于是尾部仍然停着上一次的成功行。

替代做法：判据取**脚本自己的收尾输出**（我这边是"构建完成 / 同步完成"这类唯一标记），并且比对日志文件的时间戳是否晚于本次操作开始时间。

## 二、假绿：同步脚本说「已是最新」

最阴的一次。部署脚本第一步是 `git pull --ff-only`，如果没有新对象就直接 `return`——**不构建、不重启**。于是"已是最新"这个输出会让人以为已经上线，而生产其实还跑着上一次的产物。只要中途有人手动 pull 过、或另一个流程同步过，这个分支就会命中。

三条同时成立才算真上线，我把它固化成一段查生产的命令：

```bash
git log -1 --format='%h %cd %s' --date=iso   # ① HEAD 是不是我要的那个 commit
stat -c '%y' .next/BUILD_ID                   # ② 构建时间必须晚于 commit 时间
grep -rl "<本次改动特有的中文串>" .next/static/chunks | head -3   # ③ 特征串必须在产物里
pm2 list                                      # ④ 进程 uptime 必须晚于构建
```

第 ③ 条最值钱：**挑一个只有本次改动才会出现的字符串**（一句新加的提示文案就行）去产物里搜。它同时证明"代码进了产物"和"产物是新的"，而且完全不依赖你对构建流程的记忆。

## 三、假绿：`npx tsc` 拉到一个同名的假包

在没有 `node_modules` 的仓库里跑 `npx tsc`，不会去装 `typescript`——它会从 registry 找一个**叫 `tsc` 的包**（那是个 2.0.4 的老古董），跑完返回 0。整个类型检查根本没发生，但看起来"通过"了。

我的规矩改成：**类型检查只在装了依赖的地方跑**，并且先确认执行的是谁：

```bash
node -e "console.log(require.resolve('typescript'))"   # 路径必须在你的 node_modules 里
```

拿不到就换一台机器跑，或者干脆用仓库自带的构建命令——**任何"环境不一致"的预检结果都不该进结论**。

## 四、假红：`.next/types` 里的陈旧校验文件

反方向也踩过：改了路由目录结构之后，服务器上的 `tsc --noEmit` 报一堆 `TS2307`，指向的是已经不存在的页面。根因是 `.next/types/validator.ts` 还是旧的，它引用的模块路径已经变了。

正确顺序是 **先构建再检查**：`pull` → `npm run build`（重建 `.next/types`）→ 再 `tsc --noEmit`。当时我差点去删 `.next` 甚至回滚代码——两者都不需要。**框架生成的类型文件是构建产物，不是事实来源**；拿它当基准就会出现这种假红。

## 五、假红（也是假绿）：既有噪声淹没本次改动

老仓库里跑类型检查，输出里永远躺着几条与本次无关的历史报错：引用已删页面的 `TS2307`、缺第三方类型声明的 `TS7016`。两种坏结果同时发生：新错误被淹没，或者你习惯性地"这些一直都在"而放走了真问题。

做法很简单，我一直提醒自己执行：**按路径过滤，只看自己改的文件**。

```bash
tsc --noEmit 2>&1 | grep -E "src/app/(admin/)?你的目录"
```

如果要判断"有没有引入新问题"，就比对**条数**而不是看有没有输出：改动前后各跑一次，条数不变才算没恶化。

## 六、假绿：大文件写入静默不落盘

写一个几百行的文件，工具返回成功，构建时才发现它是空的或者只有前半截——**体积大的单次写入有概率静默失败**。从那以后我对"写完就信"这件事过敏：

```bash
ls -la path/to/file && wc -l path/to/file
```

一行成本。**任何生成出来的文件都要用它的可观测属性（字节数、行数、末尾几行）证明它存在**，而不是用写入操作的返回值。

## 七、假绿：无头浏览器截出一堆"长得一样"的图

用 CDP 控制本机 Chrome 做视觉验收，最坑的一次是：五个路由的截图内容一模一样，我差点以为是模板复用出问题。真凶是本机的 `HTTPS_PROXY` 被 Chrome 子进程继承，页面全部没联网，每张图都是"未连接到互联网"。

四条硬规矩：

- **必须加 `--no-proxy-server`**，否则你的代理环境会污染每一次导航；
- **必须取 `/json/list` 里 `type === 'page'` 的 `webSocketDebuggerUrl`**。用 `/json/version` 返回的那个连上去是 browser 级 endpoint，发 `Page.enable` 会报 `-32601`——症状看起来像 CDP 版本不兼容，其实是连错了对象；
- **每个脚本用独立的 `--user-data-dir`**，重跑前清掉。否则上一个脚本留下的 localStorage / cookie 会让"这次的结果"变成上次的结果；
- 截图之后**要验证差异**：同一批截图的哈希如果全等，先怀疑环境而不是页面。

## 八、还有一条通用的：200 不代表内容对

状态码只说明"有人应答"。`/blog/xxx/` 返 200 但页面是空的、接口返 200 但字段是默认值，都见过。判据要往下压一层：状态码 + **内容特征**（特有文案、CSS 类是否进产物、字节数量级）。第四篇里那四层证据（状态码、字节大小、CSS 类、截图）就是为这件事写的，这里不重复，只强调一句：**只看状态码的验收等于没有验收**。

## 元规则

把上面七条抽成一句可以复用的判据：**一个"通过"信号可信，当且仅当你能指出它绑定的证据文件与时间戳**。

- 日志 → 文件 mtime 是否晚于本次操作；
- 构建产物 → 特征串是否存在、BUILD_ID 时间是否新于 commit；
- 进程 → uptime 是否晚于构建；
- 类型检查 → 执行的是哪个路径的编译器；
- 截图 → 哈希是否互不相同、是否禁用了代理。

指不出证据的绿灯，一律当黄灯处理。

## 小结

- 假绿比假红危险：假红会让你再查一遍，假绿会让你直接收工。
- 三类反复出现的原因：**陈旧状态**（日志、types、缓存、代理）、**静默分支**（"已是最新"就 return、写入不落盘）、**同名误导**（假 `tsc`、browser 级 endpoint）。
- 判据要落在产物与时间戳上，不要落在"操作返回成功"上。
- 这些检查大多不复杂，复杂的是**承认自己刚才那条绿灯其实没有证据**。

## 练习

1. 挑一个你手上项目的部署脚本，找出它所有"提前 return"的分支，并给每个分支补一条独立的生产核实命令。
2. 用"特有中文串 + 产物搜索"的方式，为你最近一次改动写一条上线断言，并把它记进部署笔记。
3. 故意在没有依赖的仓库里跑 `npx tsc`，观察它拉到什么包、返回什么码，然后写出你会怎么在 CI 里防住这类假绿。
4. 给你的视觉验收脚本加上"截图哈希互不相同"的断言，跑一次带 `HTTPS_PROXY` 的对照，看它能不能抓出环境故障。
