## 做到什么算过

网关类技术的验收标准是"敢让它挡在流量前面"。五条：

1. 能把一个**真实服务**接进网关：域名 → 路由 → 后端，并能解释这条链路每一跳。
2. 能配**灰度、限流、超时重试**，并说清各自失效的场景（比如限流为什么挡不住慢请求累积）。
3. 能做鉴权（JWT / OIDC / Key），并守住边界：**认证在网关，授权在服务**。
4. 能写一个 **Wasm 插件**并上线（Go，含测试与灰度发布），而不是只跑通 demo。
5. 能观测：按路由看 QPS/延迟/错误率，并能从一条 5xx 追到具体上游。

## 三层结构

| 层 | 解决什么 | 篇目 | 过关标志 |
|---|---|---|---|
| **L1 会用** | 环境、核心概念、路由、服务发现 | 01–04 | 能把服务接进来并打通 |
| **L2 会治理** | 流量治理、安全认证、可观测、AI 网关 | 05–08、12 | 能配灰度/限流/鉴权并验证 |
| **L3 会扩展** | Wasm 插件、Console 运维、选型、生产实践 | 09–11、13–15 | 能写插件、能给出选型结论 |

按起点选读法：

- **A. 没用过网关**：01 → 02 → 03 → 04。
- **B. 用过 Nginx**：02 → 03，对照着看（`location` 对应路由、`upstream` 对应服务发现），再进 05。
- **C. 要做流量治理**：05 → 06 → 07。
- **D. 要写插件**：08（Wasm 基础）→ 09（Go 开发）→ 10（实战）。

## 前置知识

- **必备**：Linux 基础、Docker、HTTP 协议

## 环境准备

```bash
# 本地实验环境（二选一）

# 方案 1：Docker Compose（最简单，适合快速体验）
curl -fsSL https://higress.io/standalone/get-higress.sh | bash -s -- -a

# 方案 2：Kubernetes（生产级，推荐）
# 需要先准备 K8s 集群（minikube/kind/云厂商 K8s）
helm repo add higress https://higress.io/helm-charts
helm install higress higress/higress -n higress-system --create-namespace

# 验证
kubectl get pods -n higress-system
# 应该看到 higress-controller、higress-gateway、higress-console 等 Pod
```

## 毕业前自检（整条路线）

- [ ] 能画出请求链路：客户端 → 网关（路由匹配 → 插件链 → 上游选择）→ 服务
- [ ] 路由配置能按域名/路径/Header 匹配，且知道优先级规则（冲突时谁生效）
- [ ] 配过一次灰度：按权重或 Header 分流，并用两个版本的实际响应验证
- [ ] 配过限流，并用压测证明超限时确实被拒（不是"配了但没生效"）
- [ ] 鉴权只做认证，业务权限留在服务里，能说清为什么
- [ ] 能按路由看到 QPS、P99、5xx 率，并从一条 5xx 追到上游
- [ ] 写过一个 Wasm 插件：有单元测试、能灰度、能回滚
- [ ] 能给出"什么规模该用网关、什么规模直接 Nginx"的判断依据
- [ ] 做过一次插件或路由配置的回滚演练
