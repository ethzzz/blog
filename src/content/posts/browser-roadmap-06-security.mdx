## 同源策略：限制的是"读"，不是"发"

同源 = 协议 + 域名 + 端口 三者完全一致。

关键认知：**跨域请求能发出去，只是响应不能被 JS 读取**。所谓的"跨域报错"发生在**读响应**这一步。

例外：`<img>`、`<script>`、`<link>`、`<form>` 这些"天然跨域"的标签不受限制——这也正是 JSONP 与 CSRF 存在的土壤。

## CORS：什么时候会有两次请求

```text
简单请求（GET/POST + 仅安全头 + 特定 Content-Type）
  └── 直接发，带 Origin，看响应头的 Allow-Origin

非简单请求（PUT/DELETE、application/json、自定义头）
  └── 先发 OPTIONS 预检 → 服务端允许 → 再发真实请求
```

简单请求的三个条件（必须**同时**满足）：方法属于 `GET/HEAD/POST`；只带安全头（`Accept`、`Accept-Language`、`Content-Language`、`Content-Type` 等）；`Content-Type` 只能是 `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded`。

> 所以 `fetch(url, { method:'POST', headers:{'Content-Type':'application/json'} })` **一定会预检**——这是最常见的"多一次 OPTIONS"来源。

### 带 cookie 的三条硬规则

```js
// 前端
fetch('https://api.example.com/me', { credentials: 'include' });

// 服务端
Access-Control-Allow-Origin: https://app.example.com   // ❌ 不能是 *
Access-Control-Allow-Credentials: true
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 600                            // 预检结果缓存 10 分钟
```

三条规则缺一不可：

1. `Allow-Origin` 必须是**具体来源**，不能 `*`（浏览器直接拒绝）；
2. 必须有 `Allow-Credentials: true`；
3. 预检响应里不能用 `*` 通配头（`Allow-Headers/Methods` 要列具体值）。

`Max-Age` 值得配：不配的话每个非简单请求都要多一次 OPTIONS（移动网络下等于多 200–400ms）。

**常见误解**：CORS 是**浏览器**的规则，服务端日志里能看到请求成功，但前端读不到——所以"Postman 能通、浏览器不行"是正常的。

## XSS：三种注入路径

| 类型 | 注入点 | 例子 |
| --- | --- | --- |
| **存储型** | 数据入库后渲染 | 评论里写 `<img src=x onerror=steal()>` |
| **反射型** | URL 参数直接回显 | 搜索页把 `q` 原样输出 |
| **DOM 型** | 前端自己把不可信数据塞进 DOM | `el.innerHTML = location.hash` |

前端能做的四件事：

```js
// 1) 默认用 textContent / 框架的插值（React/Vue 默认转义）
el.textContent = userInput;                       // ✅

// 2) 必须插 HTML 时，先净化
import DOMPurify from 'dompurify';
el.innerHTML = DOMPurify.sanitize(userInput);     // ✅

// 3) 别把用户数据拼进 URL 协议位
location.href = userInput;                        // ❌ javascript:alert(1)
// ✅ 白名单协议
const u = new URL(userInput, location.origin);
if (!['http:', 'https:'].includes(u.protocol)) throw new Error('非法协议');

// 4) 富文本只允许白名单标签
```

`innerHTML` 是最常见的入口。**只有在内容可控（自己写的模板）时才能用**，任何来自用户/接口的字符串都要净化。

## CSRF：为什么 SameSite 救了一半

CSRF 的本质：**别的站点诱导用户浏览器带着 cookie 发请求**。

```html
<!-- attacker.com 上的图片，用户一访问就发出 POST -->
<form action="https://bank.com/transfer" method="POST" id="f">
  <input name="to" value="attacker"><input name="amount" value="10000">
</form>
<script>document.getElementById('f').submit()</script>
```

三层防御：

| 手段 | 说明 | 现状 |
| --- | --- | --- |
| `SameSite=Lax`（默认） | 跨站 POST 不带 cookie | 挡住大部分场景，**现代浏览器默认值** |
| CSRF Token | 服务端下发，提交时必须带上 | 老系统的标准做法 |
| 校验 `Origin` / `Referer` | 服务端拒绝异常来源 | 简单有效，建议都做 |

因为 `SameSite=Lax` 已成默认，纯跨站表单攻击基本失效；但**`SameSite=None` 的场景（第三方嵌入）仍然需要 Token**。

## 点击劫持与 CSP

```html
<!-- 禁止被 iframe 嵌入 -->
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'
```

一份"能落地"的 CSP（先报告，再收紧）：

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-<随机>' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https://cdn.example.com;
  connect-src 'self' https://api.example.com;
  font-src 'self' https://cdn.example.com;
  report-uri /csp-report
```

落地顺序（一口吃不下）：

1. 先上 `Content-Security-Policy-Report-Only` + `report-uri`，收集两周违规；
2. 把真实用到的域加白；
3. 再切到强制模式；
4. 逐步去掉 `'unsafe-inline'`（用 nonce/hash）。

`style-src 'unsafe-inline'` 在现实项目里很难去掉（大量行内样式与 CSS-in-JS），**这已经是明显好于"完全没有 CSP"的状态**，不必追求满分。

## 第三方脚本：供应链风险

埋点、客服、AB 测试的脚本都在你的**主域**下执行，能读你的 DOM、cookie、localStorage。

- 用 `SRI` 校验固定版本：`<script src="..." integrity="sha384-..." crossorigin>`;
- 给 iframe 沙箱：`sandbox="allow-scripts"`（别加 `allow-same-origin`，两者同时存在等于没沙箱）；
- 用 CSP 的 `script-src` 限定来源；
- 第三方必须能"随时撤掉"——不要让它成为首屏阻塞资源（见 01 篇 `async` 的坑）。

---

## 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 带 cookie 报 CORS | `Allow-Origin: *` | 改成具体来源 + `Allow-Credentials` |
| 每个请求都多一次 OPTIONS | `Max-Age` 没配 / 用了自定义头 | 配 `Max-Age: 600`，减少自定义头 |
| Postman 通、浏览器不通 | CORS 是浏览器策略 | 检查响应头，不是请求 |
| 用户输入含 `<` 显示成标签 | 用了 `innerHTML` | `textContent` 或 DOMPurify |
| CSP 上线后页面白屏 | 内联脚本被拦 | 用 nonce；或先 Report-Only |
| iframe 嵌入后 cookie 丢失 | `SameSite=Lax` 不发送 | 第三方场景用 `None; Secure` + Token 防 CSRF |
| 图片 src 被设置成 `javascript:` | 未校验协议 | 白名单 `http/https` |

## 验收清单

- [ ] 能判断一个请求会不会触发预检，并说出原因
- [ ] 带 cookie 的跨域：`Allow-Origin` 是具体值 + `Allow-Credentials: true` + 列具体头
- [ ] 项目里 `innerHTML` 都有净化（或内容完全可控）
- [ ] 会话 cookie 是 `HttpOnly` + `Secure` + 明确 `SameSite`
- [ ] 有 `X-Frame-Options` 或 `frame-ancestors`
- [ ] 有 CSP（哪怕是 Report-Only），且知道下一步怎么收紧
- [ ] 第三方脚本有来源限制，且不阻塞首屏

## 练习

1. **数一次预检**：用 `Content-Type: application/json` 发一个 POST，在 Network 里找到 OPTIONS，加上 `Max-Age` 后再发，确认预检被缓存。  
   *自检*：能解释"为什么简单请求不预检"。
2. **复现一次 XSS**：在本地页面用 `innerHTML` 渲染 `<img src=x onerror="alert(1)">`，再换 `textContent` 与 DOMPurify 对比。  
   *自检*：三种写法的表现差异能说清。
3. **写一份 CSP Report-Only**：只收集不拦截，跑一天看 violations，列出你项目实际需要放行的域。  
   *自检*：能说出"为什么不能一上来就强制"。
