> [!NOTE]
> Worker 不是"性能优化按钮"。它只解决一件事：**把不碰 DOM 的重计算从主线程挪走**。挪之前先量两件事——计算耗时、传输耗时；后者常常比前者更大。

---

## 1. 只有一类任务值得上 Worker

判断标准两条，**必须同时满足**：

1. **计算超过 50ms**（低于这个，通信开销就把它抵消了）；
2. **不碰 DOM**（Worker 里没有 DOM、没有 `window`、没有 `document`）。

| 适合 | 不适合 |
| --- | --- |
| 大 JSON / CSV 解析 | 任何 DOM 操作 |
| 图片处理（`OffscreenCanvas`）、缩放/滤镜 | 很轻的计算（低于 10ms） |
| 加密 / 哈希 / 压缩 | 需要每帧同步的交互 |
| 复杂 diff、语法高亮、Markdown 渲染 | 频繁小任务（通信比计算贵） |
| 大量数据排序 / 聚合 | 依赖 `window`/`document` 的库 |

真实例子里最有价值的是**首屏大 JSON 解析**：2MB 接口响应在主线程解析要 100ms+，搬到 Worker 后主线程完全不受影响，首屏不再被这一段卡住。

先量一下，再决定要不要搬：

```js
// 在 Console 里就能跑：测一段计算有多重
const t0 = performance.now();
const rows = JSON.parse(bigJson);
console.log('parse', (performance.now() - t0).toFixed(1), 'ms', rows.length, 'rows');
```

低于 50ms 的任务搬过去，收益大概率被 `postMessage` 的序列化抵消。

## 2. 通信成本：免费的是"转移"，不是"克隆"

```js
// ❌ 结构化克隆：复制一份，10MB 数据可能耗 30–80ms，而且占用双份内存
worker.postMessage(bigArrayBuffer);

// ✅ Transferable：转移所有权，几乎零成本；主线程这边立刻失效
worker.postMessage(bigArrayBuffer, [bigArrayBuffer]);
console.log(bigArrayBuffer.byteLength); // 0 —— 已经分离，不能再读写
```

可转移的类型：

| 类型 | 典型场景 |
| --- | --- |
| `ArrayBuffer` | 二进制文件、大 JSON 的 UTF-8 字节 |
| `MessagePort` | 建立独立通道（`MessageChannel`） |
| `ImageBitmap` | 图片解码结果，可与 `OffscreenCanvas` 配合 |
| `OffscreenCanvas` | 把画布控制权交给 Worker |
| `ReadableStream` / `WritableStream` | 流式处理 |

一个完整的"传二进制、回结果"流程：

```js
// 主线程
const res = await fetch('/api/export');
const buf = await res.arrayBuffer();
worker.postMessage({ id: 1, buf }, [buf]);

// worker
self.onmessage = (e) => {
  const { id, buf } = e.data;
  const text = new TextDecoder().decode(buf);
  const rows = JSON.parse(text);          // 重计算在 Worker
  const summary = rows.map((r) => r.id);  // 只回传需要的字段
  self.postMessage({ id, summary });      // 回传结果会被克隆，所以越小越好
};
```

**两条经验**：传"原始二进制"而不是"解析后的对象"；回传"结果摘要"而不是"完整数组"。频繁传大对象会让 Worker 变成负优化。

## 3. 三种 Worker

| 类型 | 创建方式 | 隔离 | 用途 |
| --- | --- | --- | --- |
| **Dedicated** | `new Worker(url)` | 与创建者一对一 | 最常见 |
| **Shared** | `new SharedWorker(url)` | 多个标签共享 | 少见，多标签共享连接 |
| **Service Worker** | `navigator.serviceWorker.register` | 拦截网络 | 离线/缓存（05 篇），**不能用于计算** |

```js
// Dedicated + 模块化（现代构建工具都支持）
const worker = new Worker(new URL('./image.worker.ts', import.meta.url), {
  type: 'module',
});
```

⚠️ `type: 'module'` 在构建工具里**必须**用 `new URL(..., import.meta.url)` 的写法，不能拼字符串路径——否则打包器无法静态分析，产物里找不到这个文件（Vite/Webpack 都一样）。这是"本地 dev 正常、构建后 404"的第一大原因。

## 4. Worker 池：别为每个任务 new 一个

每次 `new Worker` 都要启动一个新的 JS 上下文，成本约几毫秒到几十毫秒。批量任务应该复用：

```ts
// src/lib/worker-pool.ts
export function createPool(url: URL, size = Math.min(4, navigator.hardwareConcurrency ?? 4)) {
  const workers = Array.from({ length: size }, () => new Worker(url, { type: 'module' }));
  const idle: Worker[] = [...workers];
  const queue: Array<(w: Worker) => void> = [];

  const acquire = () =>
    new Promise<Worker>((resolve) => {
      const w = idle.pop();
      if (w) resolve(w);
      else queue.push(resolve);
    });

  const release = (w: Worker) => {
    const next = queue.shift();
    if (next) next(w);
    else idle.push(w);
  };

  return {
    async exec<T>(payload: unknown, transfer: Transferable[] = []): Promise<T> {
      const w = await acquire();
      try {
        return await new Promise<T>((resolve, reject) => {
          const onMessage = (e: MessageEvent) => {
            w.removeEventListener('message', onMessage);
            w.removeEventListener('error', onError);
            e.data.ok ? resolve(e.data.data) : reject(new Error(e.data.error));
          };
          const onError = (e: ErrorEvent) => {
            w.removeEventListener('message', onMessage);
            w.removeEventListener('error', onError);
            reject(e.error ?? new Error(e.message));
          };
          w.addEventListener('message', onMessage);
          w.addEventListener('error', onError);
          w.postMessage(payload, transfer);
        });
      } finally {
        release(w);
      }
    },
    destroy: () => workers.forEach((w) => w.terminate()),
  };
}
```

池大小的默认值是 `hardwareConcurrency`，但**不要开满**：浏览器自身也要用线程，`min(4, cores)` 更稳。

### 4.1 请求-响应配对

Worker 是单线程队列，但**多条消息可能交错返回**（尤其是有 `await` 时）。所以协议里必须带 `id`：

```ts
// 单 Worker 版本的配对
const pending = new Map<number, (v: unknown) => void>();
let seq = 0;

worker.onmessage = (e) => {
  const { id, data } = e.data;
  pending.get(id)?.(data);
  pending.delete(id);
};

function call(payload: unknown) {
  const id = ++seq;
  return new Promise((resolve) => {
    pending.set(id, resolve);
    worker.postMessage({ id, payload });
  });
}
```

没有 `id` 的协议，在并发调用下会"张冠李戴"，而且很难复现。

## 5. OffscreenCanvas：把绘制也搬走

```js
// 主线程：把 canvas 控制权转移给 Worker
const canvas = document.querySelector('canvas');
const offscreen = canvas.transferControlToOffscreen();
worker.postMessage({ canvas: offscreen }, [offscreen]);

// worker
let ctx;
self.onmessage = (e) => {
  if (e.data.canvas) {
    ctx = e.data.canvas.getContext('2d');
    draw();
  }
};
function draw() {
  ctx.fillStyle = '#2b6cb0';
  ctx.fillRect(0, 0, 200, 200);
}
```

适用场景：图表重绘、粒子动画、图片滤镜。注意 `transferControlToOffscreen` 只能调用一次，之后主线程不能再 `getContext`。

## 6. SharedArrayBuffer：需要跨源隔离

```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

两个头缺一不可，否则 `SharedArrayBuffer` 不可用。代价很实在：开了 COEP 后，**所有跨域资源都要带 `Cross-Origin-Resource-Policy` 或 CORS**——第三方图片、iframe、CDN 字体都可能被拦。

```js
// 主线程
const sab = new SharedArrayBuffer(1024 * 1024);
const view = new Int32Array(sab);
worker.postMessage({ sab });

// worker：用 Atomics 安全读写
Atomics.store(view, 0, 42);
Atomics.notify(view, 0);
```

`Atomics.wait` 在主线程被禁止（会卡住 UI），只能在 Worker 里用。除非真需要多线程共享内存（音视频、大数组并行），不要开 COOP/COEP。

---

## 7. 何时不该用：三个反例

1. **为了"并行请求"**：HTTP 本身就是并行的，Worker 不会更快。
2. **为了"渲染不卡"**：渲染必须在主线程，Worker 只能分担计算。
3. **把 10ms 的计算搬过去**：一次 `postMessage` 往返 + 序列化，净亏。

---

## 8. 背压：别把 Worker 变成新的瓶颈

主线程一股脑 `postMessage` 一千个任务，Worker 队列会堆到几十 MB，内存与延迟一起涨。需要"控制并发 + 控制批次"：

```js
// 主线程：每批 50 条，等上一批回执再发下一批
async function sendInBatches(worker, rows, size = 50) {
  for (let i = 0; i < rows.length; i += size) {
    const batch = rows.slice(i, i + size);
    await new Promise((resolve) => {
      worker.onmessage = resolve;             // 等这一批的结果
      worker.postMessage({ batch });
    });
  }
}

// 或者用信号量控制"同时在飞"的数量
async function withLimit(tasks, limit = 4) {
  const queue = [...tasks];
  const runners = Array.from({ length: limit }, async () => {
    while (queue.length) await queue.shift()();
  });
  await Promise.all(runners);
}
```

流式场景（大文件解析、逐块压缩）更适合"边传边算"，而不是攒一整个 ArrayBuffer：

| 方式 | 内存峰值 | 适用 |
| --- | --- | --- |
| 一次性传完整 Buffer | 高（双份） | 小于几十 MB |
| 分块传输（`ReadableStream` / 切片） | 低 | 大文件、可流式处理 |
| `SharedArrayBuffer` | 低（共享） | 需要并行读写同一块内存 |

分块传 `ArrayBuffer` 时注意：每次 `postMessage(buf.slice(a, b), [chunk])` 都要新建切片，切片本身也是拷贝——所以块不要太小（建议 ≥1MB）。

## 9. 调试 Worker

| 需求 | 做法 |
| --- | --- |
| 看 Worker 的 `console.log` | DevTools Console 里来源会标 `worker.js`，也可在 Sources 里选 Worker 上下文 |
| 断点 | Sources → 左侧 `Threads`/Workers 面板，选中 Worker 文件下断点 |
| 看 Worker 的异常 | 主线程 `worker.onerror` + Worker 内 `self.onerror` 都要接 |
| 量 Worker 启动成本 | `Performance` 面板里搜 Worker 的 script 请求与 `Evaluate Script` |

```js
// 错误必须两头接，否则 Worker 崩了主线程毫无感知
worker.addEventListener('error', (e) => console.error('worker error', e.message));
// worker 内
self.addEventListener('error', (e) => {
  self.postMessage({ ok: false, error: String(e.message) });
});
```

## 10. 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| Worker 加载 404 | 用了字符串路径，打包器没处理 | `new URL('./x.worker.ts', import.meta.url)` |
| Worker 里报 `document is not defined` | 代码依赖 DOM | DOM 操作留主线程，只传数据 |
| 传大对象后主线程卡顿 | 结构化克隆复制 | Transferable 或减小传输量 |
| 并发调用结果错乱 | 消息没有 id 配对 | 加 id + pending Map |
| Worker 内存一直涨 | 没 `terminate`，或任务积压 | 卸载时 terminate，用池控制并发 |
| SAB 报未定义 | 缺 COOP/COEP | 加两个头，并处理跨域资源 |
| 用了 Worker 反而更慢 | 任务太小 / 传输太大 | 先量 50ms 阈值与传输耗时 |
| dev 正常、prod 白屏 | Worker 产物未随构建输出 | 检查产物目录里是否有独立 worker 文件 |

## 11. 验收清单

- [ ] 能判断一个任务"该不该"搬 Worker（>50ms 且不碰 DOM）
- [ ] 传输用 `Transferable`，或在传之前把数据缩到最小
- [ ] Worker 用 `new URL(..., import.meta.url)` 创建，构建后能正常加载
- [ ] 有请求-响应配对机制（id），且组件卸载时 `terminate`
- [ ] 批量任务用池，不要每个任务都新建 Worker
- [ ] 知道 SharedArrayBuffer 需要 COOP/COEP 及其代价
- [ ] 有"搬之前/搬之后"的主线程长任务对比数字
- [ ] Worker 的错误在主线程有兜底

## 12. 练习

1. **量一次搬移收益**：把 2MB JSON 的解析分别放在主线程与 Worker，用 Performance 记录主线程长任务时长。  
   *自检*：主线程长任务应接近消失，总耗时可能只降一点——能解释这个差别。
2. **对比克隆与转移**：同一个 50MB `ArrayBuffer` 分别用克隆与 Transferable 传递，测耗时。  
   *自检*：能给出两个数字，并说明"转移后原对象为什么是 0 字节"。
3. **写一个 Worker 池**：并发发起 20 个解析任务，对比"每任务 new Worker"与"4 个 Worker 复用"的总耗时与内存。  
   *自检*：能说出启动成本与并发上限的权衡。
4. **做一个会报错的 Worker**：用字符串路径创建 Worker，构建后观察 404，再改成 `new URL` 修好。  
   *自检*：能在产物目录里指出 Worker 文件被单独打出来的位置。
5. **用 OffscreenCanvas 画一次**：把粒子动画搬到 Worker，对比主线程长任务与动画帧率。  
   *自检*：能说明为什么 `transferControlToOffscreen` 之后主线程不能再取 context。
