## 三种更新，代价差 100 倍

一次样式变化，浏览器可能只做其中一步：

| 阶段 | 做什么 | 典型耗时 | 触发条件 |
| --- | --- | --- | --- |
| **Layout（重排）** | 重算位置与尺寸 | 慢，可能整棵树 | 改 `width/height/top/left/font-size/padding/display` |
| **Paint（重绘）** | 重新生成绘制指令 | 中 | 改 `color/background/border-radius/box-shadow` |
| **Composite（合成）** | GPU 直接挪图层 | 最快 | 改 `transform` / `opacity`（在合成层上） |

口诀：**能只改合成，就不要碰布局**。

---

## 属性代价对照表

| 属性 | 触发 | 备注 |
| --- | --- | --- |
| `transform: translate/scale/rotate` | Composite | 最便宜，优先用它做位移/缩放动画 |
| `opacity` | Composite | 同上 |
| `filter`（部分） | Composite/Paint | 视实现，仍比布局便宜 |
| `color` / `background-color` | Paint | 大元素上仍可能明显 |
| `box-shadow` | Paint | 大面积阴影很贵，尤其是动画里 |
| `width/height/padding/margin` | Layout | 影响兄弟/父节点，可能整页重排 |
| `top/left`（非 absolute） | Layout | **改用 `transform` 代替** |
| `font-size` | Layout | 文本重排最贵之一 |
| `display: none ↔ block` | Layout | 会移除/重建子树 |

一个常见误区：

```css
/* ❌ 每帧都触发布局 */
.panel { transition: left .3s; }
.panel.open { left: 240px; }

/* ✅ 每帧只做合成 */
.panel { transition: transform .3s; }
.panel.open { transform: translateX(240px); }
```

## 强制同步布局：把 1ms 变成 60ms

浏览器本来会把"写样式"和"读布局"批量处理。但你一旦**在同一个任务里交替读写**，它就必须立刻算一遍布局：

```js
// ❌ 布局抖动：每次循环都强制重算
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px';   // 读 → 写 → 读 → 写…
}

// ✅ 先读后写（一次布局解决）
const widths = items.map((el) => el.offsetWidth);
items.forEach((el, i) => { el.style.width = widths[i] + 10 + 'px'; });
```

会触发"强制布局"的读操作（记住这几个高频的）：

`offsetTop/Left/Width/Height`、`clientWidth/Height`、`scrollTop/Left`、`getBoundingClientRect()`、`getComputedStyle()`、`window.innerHeight`（部分情况）。

排查办法：Performance 面板里看到 **`Recalculate Style` / `Layout` 出现紫色三角警告**，就是它。

## 合成层：便宜的来源，也是内存杀手

满足某些条件时，元素会被提升为独立的合成层（GPU 纹理）：

```css
.promote {
  will-change: transform;      /* 提前告诉浏览器"我要动" */
  /* 或者 */
  transform: translateZ(0);    /* 老写法，副作用大 */
}
```

**代价**：每个合成层都是一张 GPU 纹理，占显存/内存。全屏大小的层约 **4MB**（1920×1080×4 字节）。

```css
/* ❌ 这个写法等于给列表里每一项都开一个层 */
.list-item { will-change: transform; }
```

100 个列表项 × 每层几百 KB → 内存暴涨，**低端机直接闪退**。真实事故里见过 1.2G。

正确用法：

- **只在交互开始前加，结束后移除**（或干脆不加，直接用 `transform` 动画）；
- 针对性强作用域：只给"真正会动的那一个元素"；
- 用 DevTools → Layers 面板确认层数（超过 20 个就该警惕）。

`contain` / `content-visibility` 是更安全的替代：

```css
.card { contain: layout paint; }        /* 限制布局/绘制影响范围 */
.long-list-item { content-visibility: auto; contain-intrinsic-size: 0 120px; }
```

`content-visibility: auto` 让屏幕外的内容**跳过渲染**，长列表首屏能省几百毫秒——但必须给 `contain-intrinsic-size`，否则滚动条会乱跳（导致 CLS）。

## 常见坑

| 现象 | 机制 | 解法 |
| --- | --- | --- |
| 动画掉帧 | 用 `left/top` 做位移 → 每帧布局 | 改 `transform` |
| 滚动时页面抖 | `content-visibility` 没给预估尺寸 | 补 `contain-intrinsic-size` |
| 内存暴涨/闪退 | 合成层过多（`will-change` 滥用） | 只在需要时加，用 Layers 面板核查 |
| 循环里改样式很慢 | 读写交替导致强制布局 | 先批量读、再批量写 |
| 首屏大图卡顿 | 大尺寸 `box-shadow` / `filter: blur` | 用图片替代、或减少作用面积 |
| 列表滚动卡 | 一次性渲染上千节点 | 虚拟滚动（见 09 篇） |

## 练习

1. **对比两种动画**：同一个位移分别用 `left` 与 `transform` 实现，用 Performance 录制 3 秒，比较 FPS 与 Layout 次数。  
   *自检*：`left` 版本每帧都有 Layout（紫色），`transform` 版本几乎没有。
2. **制造布局抖动**：写上面那个"读 `offsetWidth` 再写 width"的循环（100 个元素），记录耗时；改成先读后写再测。  
   *自检*：能给出两次耗时差，并从 Performance 里指出强制布局的位置。
3. **数一次合成层**：给 50 个元素加 `will-change: transform`，用 Layers 面板看内存变化，再删掉。  
   *自检*：能说出"每层多少 MB、总共多吃了多少内存"。
