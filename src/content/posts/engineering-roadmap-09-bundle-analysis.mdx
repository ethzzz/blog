## 没有预算的优化，一定会反弹

第一次做体积优化时我砍掉了 400KB，颇有成就感。三个月后回到 1.8MB——因为**没有任何东西阻止别人继续加**。

体积优化和减肥一样：**单次努力没用，机制才有用**。这篇讲两件事：怎么量（分析），怎么锁（预算）。

---

## 一、先学会看

### 三种工具的差别

| 工具 | 输入 | 特点 | 适合 |
| --- | --- | --- | --- |
| `rollup-plugin-visualizer` | 构建统计 | Vite/Rollup 原生，能看 chunk 组成、gzip 体积 | **Vite 项目首选** |
| `source-map-explorer` | 产物 + sourcemap | 按**源码归属**算面积，能精确到"这 80KB 来自哪个文件" | 深挖单个大 chunk |
| `webpack-bundle-analyzer` | stats.json | Webpack 生态标准，交互式 treemap | Webpack 项目 |

```bash
# Vite：构建时生成可交互报告
pnpm add -D rollup-plugin-visualizer
```

```ts
// vite.config.ts
import { visualizer } from 'rollup-plugin-visualizer';

export default defineConfig({
  plugins: [visualizer({ filename: 'dist/stats.html', gzipSize: true, brotliSize: true })],
});
```

```bash
# source-map-explorer：看某个 chunk 里究竟是谁占的
npx source-map-explorer 'dist/assets/*.js' --gzip
```

### 看三个数字，不是看一个

打开报告先看这个顺序：

1. **最大的单 chunk**（超过 250KB 未压缩就要查）；
2. **重复依赖**（同一个库出现多个版本，最常见的隐形浪费）；
3. **首屏关键路径**（HTML 里直接引用的 JS/CSS 总量，这个才影响 LCP）。

> 一个常见误判：报告里的面积是**未压缩体积**。`echarts` 未压缩 3MB、gzip 后 330KB。**判断线上影响要看 gzip/brotli 后的数字**。

## 二、按 ROI 排序的六种手段

### 1. 换库（收益最大，风险中等）

| 老方案 | 替代 | 体积变化（gzip 估算） |
| --- | --- | --- |
| `moment`（含 locale） | `dayjs`（+ 2 个插件） | 230KB → 7KB |
| `lodash`（全量） | `lodash-es` 按需 / 手写 | 70KB → 5–15KB |
| `axios` | 原生 `fetch` 封装 | 13KB → 0 |
| `classnames` | 模板字符串 | 1KB → 0 |

收益最大，但要评估 API 差异与团队熟悉度。**新项目从一开始就别引入 moment。**

### 2. 按需引入（收益中等，成本极低）

```ts
// ❌ 整个库进来
import { DatePicker } from 'antd';

// ✅ 现代库本身支持 tree-shaking，但要确保 import 是静态可分析的
// antd v5 已默认支持；老版本需要 babel-plugin-import
```

图标库是重灾区：`import * as Icons from 'lucide-react'` 会把 1500 个图标全打进来。

### 3. 动态导入（收益取决于场景）

```ts
// 非首屏才需要的能力
const openEditor = async () => {
  const { Editor } = await import('./Editor');   // 独立 chunk
  return Editor;
};
```

判断标准：**用户 10 秒内用不到的东西，都不该在首屏 chunk 里**（地图、图表、富文本、导出、上传）。

### 4. 分包与预加载（不是减体积，是改顺序）

```ts
// 拆出稳定 vendor，提升缓存命中
manualChunks: { react: ['react', 'react-dom'] }

// 告诉浏览器"下一页大概率要用"，提前空转下载
<link rel="modulepreload" href="/assets/detail.js">
```

### 5. 资源瘦身

- 图片：WebP/AVIF + 合理尺寸（一张 2000px 的图塞进 300px 容器是最常见的浪费）；
- 字体：只保留需要的字重与字符子集（`fonttools subset`），中文字体尤其必须；
- 图标：优先 SVG sprite 而不是 icon font。

### 6. 压缩与传输

- JS/CSS 用 brotli（比 gzip 再小 15–20%），nginx 配 `brotli on;`；
- 确认 CDN 没有对已压缩产物二次压缩（无效且耗 CPU）。

## 三、把预算写进 CI：棘轮机制

`size-limit` 是最省事的方案：它按"实际加载的 chunk"算 gzip 体积，超了就失败。

```bash
pnpm add -D size-limit @size-limit/file
```

```json
// package.json
{
  "size-limit": [
    { "name": "首屏 JS", "path": "dist/assets/index-*.js", "limit": "150 kB" },
    { "name": "首屏 CSS", "path": "dist/assets/index-*.css", "limit": "30 kB" },
    { "name": "单个 chunk 上限", "path": "dist/assets/*.js", "limit": "250 kB" }
  ]
}
```

```yaml
# CI 里加一步（见 08 篇的 build job）
- run: pnpm exec size-limit
```

关键是**预算从"当前值"开始，只降不升**：

| 做法 | 效果 |
| --- | --- |
| 预算设成"理想值" | 第一天就红，团队直接注释掉这一步 |
| 预算设成"当前值 + 0%" | 谁加谁红，被迫先优化再加功能 |
| 每月 review 一次并下调 5% | 持续瘦身 |

这套机制叫**棘轮（ratchet）**：只允许往一个方向转。它是唯一能防反弹的办法。

## 四、性能预算不只是体积

体积只是手段，用户感知的是指标：

| 指标 | 目标（移动 4G） | 直接相关 |
| --- | --- | --- |
| **LCP**（最大内容绘制） | < 2.5s | 首屏 JS/CSS、图片、字体 |
| **INP**（交互到绘制） | < 200ms | 主线程长任务、大组件渲染 |
| **CLS**（布局偏移） | < 0.1 | 图片缺尺寸、字体切换、动态插入 |

体积预算卡住的是 LCP 的主要来源；INP 靠代码分割与长任务拆分（见[浏览器与性能那篇](/blog/posts/browser-roadmap-12-project-perf-budget/)）；CLS 靠显式尺寸。

## 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 报告里某库占 3MB，但线上没感觉 | 看的是未压缩体积 | 看 gzip/brotli 列 |
| 按需引入后体积没变 | 包是 CJS 的，摇不掉 | 换 ESM 版本（`lodash-es`） |
| 同一个库出现两份 | 版本冲突（依赖树里两个 major） | `pnpm why <pkg>` 定位，用 `overrides` 收敛 |
| 拆了 chunk 但首屏更慢 | 拆太碎，HTTP/1.1 请求数爆炸 | 合并小 chunk（>20KB 才值得单独拆） |
| size-limit 数字和报告对不上 | 它按"实际请求链"算，而非全量产物 | 以 size-limit 为准（更接近用户真实下载量） |
| 预算加了没人管 | 只在 CI 报警，没人在意 | 把"体积变化"写进 PR 模板，超标必须说明 |

## 验收清单

- [ ] 能给出首屏 JS 的 **gzip 后**体积，以及最大的 3 个模块名
- [ ] 项目里没有 moment / 全量 lodash / 全量图标库
- [ ] 非首屏能力（图表、编辑器、地图）走动态导入，且有独立 chunk
- [ ] 稳定三方包被拆成独立 chunk，改业务代码不改变其 hash
- [ ] CI 里有 `size-limit`，且预算是"当前值"而不是理想值
- [ ] 能说出你项目的 LCP 目标值和当前实测值

## 练习

1. **找到体积最大的三个模块**：用 visualizer 生成报告，按 gzip 排列，记录名字与大小。
   *自检*：三个模块加起来占首屏 JS 的比例 > 50%，说明找对了方向。
2. **做一次换库实验**：把 moment 换成 dayjs（只替换用到的 API），对比构建产物 gzip 体积。
   *自检*：给出前后数字，并说明为什么 locale 是 moment 体积的主要来源。
3. **给 CI 加预算并故意超标**：配一个把 `limit` 设成当前值 80% 的预算，推一次看是否变红，再调回。
   *自检*：能解释"预算设太严会被直接删掉"，以及棘轮为什么要从当前值开始。
