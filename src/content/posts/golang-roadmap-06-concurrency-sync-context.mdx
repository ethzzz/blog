> [!NOTE]
> Go 的谚语是"用通信来共享内存"，但现实里**计数器、缓存、连接池就是共享状态**，
> 硬用 channel 包一层反而更难读。这一篇的正事是：**什么时候用锁、什么时候用 atomic、取消信号怎么传**。

---

## 1. Mutex：临界区越小越好

```go
type Counter struct {
	mu sync.Mutex
	n  int
}

func (c *Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock() // defer 保证 panic 也能解锁
	c.n++
}

func (c *Counter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.n
}
```

四条纪律：

1. **锁保护数据，不保护代码**——同一个字段的所有访问都要经过同一把锁。
2. **临界区里不要做 IO、不要调用别人的回调**（可能在等锁时形成环）。
3. **不要复制含锁的结构体**（`go vet` 的 `copylocks` 会抓）：方法用指针接收者，传参用指针。
4. 加锁后立刻 `defer Unlock`，别在中间写几十行再加。

`RWMutex`：读多写少才划算（读锁可并行，写锁独占）。

```go
type Store struct {
	mu sync.RWMutex
	m  map[string]string
}

func (s *Store) Get(k string) (string, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	v, ok := s.m[k]
	return v, ok
}

func (s *Store) Set(k, v string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[k] = v
}
```

> 别盲目上 `RWMutex`：读极短时，读写锁的额外开销可能比普通 `Mutex` 还高。**基准测试说话**。

## 2. Once：只做一次的初始化

```go
type Client struct {
	once sync.Once
	conn *Conn
}

func (c *Client) Conn() *Conn {
	c.once.Do(func() {
		c.conn = dial() // 并发下也只会执行一次，其余调用会阻塞到它完成
	})
	return c.conn
}
```

比"手写 double-checked locking"安全得多：`Once` 内部保证了内存可见性与互斥。

## 3. atomic：只适合单个标量

```go
type Metrics struct {
	requests atomic.Int64
	errors   atomic.Int64
}

func (m *Metrics) OnRequest() { m.requests.Add(1) }
func (m *Metrics) OnError()   { m.errors.Add(1) }
func (m *Metrics) Snapshot() (int64, int64) {
	return m.requests.Load(), m.errors.Load()
}
```

- 适合：计数器、开关、指针替换（`atomic.Pointer[T]`）。
- 不适合：多个字段要一起变（比如"总数 + 成功数"必须一致）——那要用锁。
- Go 1.19+ 有 `atomic.Int64` 这类类型，比 `atomic.AddInt64(&x, 1)` 更清晰。

**典型误用**：以为 `n++` 是原子的。它不是——读、加、写三步，并发下会丢计数。用 `go test -race` 一试就现。

## 4. context：取消信号的唯一正确通道

```go
func handler(ctx context.Context) error {
	ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
	defer cancel() // ⚠️ 必须调用，否则定时器与父子关系泄漏

	select {
	case res := <-doAsync(ctx):
		return res
	case <-ctx.Done():
		return ctx.Err() // context.DeadlineExceeded 或 context.Canceled
	}
}
```

规则（来自官方文档 + 实战教训）：

1. **作为函数的第一个参数**，命名 `ctx`；
2. **不要存进 struct**，一路显式传；
3. **不要传 nil**，用 `context.TODO()`；
4. `WithValue` 只放"请求域"的数据（请求 ID、用户身份），**不放可选参数**；
5. 拿到 ctx 后**一定 defer cancel**，即使没有超时（`WithCancel` 也一样）。

取消是**向下传播**的：父 ctx 取消，所有派生的子 ctx 都收到 `Done()`。这正好配合 worker pool 里"每个阻塞点都 select ctx.Done()"。

```go
// HTTP 请求里拿到 ctx，一路传到数据库
func (s *Service) ListTasks(ctx context.Context) ([]Task, error) {
	rows, err := s.db.QueryContext(ctx, "select id, title from tasks") // 传 ctx，请求断开时自动取消查询
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	// ...
}
```

`context.Background()` 只用在 main/初始化；`context.TODO()` 表示"还没想好放哪"。

## 5. 竞态检测：不加 -race 的并发测试等于没测

```bash
go test -race ./...
go run -race ./cmd/server
```

`-race` 会插桩检测"两个 goroutine 无同步地读写同一块内存"，代价是慢 5–10 倍、内存翻几倍，**所以只在测试与本地调试开**。

典型报告长这样：

```
WARNING: DATA RACE
Write at 0x00c0000b4010 by goroutine 7:
  main.(*Counter).Inc()
Previous read at 0x00c0000b4010 by goroutine 6:
  main.(*Counter).Value()
```

它告诉你是**哪个写、哪个读、哪个 goroutine**——顺着看就能定位。

## 6. 三类常见死锁

**① 同一 goroutine 重复加锁（不可重入）**

```go
func (c *Counter) Bad() {
	c.mu.Lock()
	c.mu.Lock() // 永久阻塞：Go 的 Mutex 不可重入
}
```

**② 锁顺序不一致**

```go
// goroutine A: lock(a) → lock(b)
// goroutine B: lock(b) → lock(a)   ← 交叉就死
```

解法：**全局约定加锁顺序**（比如按 ID 排序后加锁），或干脆避免嵌套锁。

**③ channel 自锁**

```go
ch := make(chan int)
ch <- 1 // 无缓冲且没人接收 → 永久阻塞
```

无缓冲 channel 在同一个 goroutine 里先发后收，必然死锁。

## 7. 一个生产级的并发习惯清单

- [ ] 每个 goroutine 都有退出条件（ctx / 关闭信号 / 有限循环）。
- [ ] 所有对外阻塞调用都带 ctx（`QueryContext`、`NewRequestWithContext`）。
- [ ] 共享状态要么加锁，要么用 atomic，**没有第三种**。
- [ ] 含锁的结构体用指针传递；方法用指针接收者。
- [ ] `go test -race ./...` 是 CI 的必跑项。
- [ ] 用 `errgroup`（`golang.org/x/sync/errgroup`）管理"一组 goroutine 里有错就全体取消"的场景，比手写 WaitGroup + ctx 干净。

```go
g, ctx := errgroup.WithContext(ctx)
for _, url := range urls {
	url := url
	g.Go(func() error {
		return fetch(ctx, url) // 任一返回 error → ctx 取消，其余尽快退出
	})
}
if err := g.Wait(); err != nil {
	return err
}
```

## 8. 常见坑速查

| 坑 | 现象 | 做法 |
|---|---|---|
| `n++` 当原子操作 | 计数偏小、-race 报错 | `atomic.Int64` 或加锁 |
| 复制含 Mutex 的 struct | vet 报 `copylocks`；锁失效 | 用指针 |
| 锁里做 HTTP 调用 | QPS 掉、超时 | 先取数据、放锁、再请求 |
| 忘了 `defer cancel()` | ctx 泄漏、定时器堆积 | 拿到 ctx 立刻 defer |
| 把 ctx 存进 struct | 生命周期混乱 | 显式传参 |
| `WithValue` 传业务参数 | 类型不安全、没人知道从哪来 | 放进函数参数 |
| 只测 happy path | 竞态只在压力下出现 | `-race` + 并发测试 |
| 用 `time.Sleep` 等 goroutine | 测试偶发失败 | 用 channel 或 `require.Eventually` |

---

## 小结

- 锁保护**数据**，临界区越小越好，含锁结构体只传指针。
- `Once` 做一次性初始化，`atomic` 做单标量计数。
- `context` 是取消的唯一正确通道：第一个参数、一路传、必须 cancel。
- `-race` 是并发代码的入场券，不加等于没测。
- 死锁三大来源：重复加锁、锁顺序不一致、channel 自锁。

## 练习

1. 用 `Mutex` 与 `atomic.Int64` 各写一个计数器，起 100 个 goroutine 各加 1000 次，验证结果都是 100000；再故意用 `n++` 版本，看 `-race` 报告。
2. 用 `sync.Once` 实现懒加载的数据库连接，起 50 个 goroutine 同时调用，验证只 `dial` 了一次（打印计数）。
3. 给一个函数加 3 秒超时：分别在 1 秒返回、5 秒返回两种情况下测试，验证超时后 `ctx.Err()` 是 `DeadlineExceeded`。
4. 复现锁顺序死锁（两个 goroutine 交叉加两把锁），用 `pprof/goroutine` 或 `go test -timeout 5s` 观察到卡死，再改成一致顺序。
5. 用 `errgroup` 并发请求 10 个 URL，任一失败就整体快速失败，并打印实际用了几毫秒。
