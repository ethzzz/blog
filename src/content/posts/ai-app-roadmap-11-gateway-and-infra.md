> [!NOTE]
> 当你的 AI 功能从一个变成三个，问题就来了：三个功能各自调不同模型、各自的 Key、各自的账单、各自的限流——乱成一锅粥。网关就是把这一锅收拢成一个入口。这篇讲 MaaS 平台怎么选、token-plan 计费怎么读、自建网关怎么做、用量怎么统计。来自我走阿里云 MaaS 计费和自建网关的全部笔记。

## 1. MaaS 平台对比

MaaS（Model as a Service）平台就是模型托管方，国内主流选择：

| 平台 | 模型 | 优势 | 适合 |
| --- | --- | --- | --- |
| 阿里云百炼 | Qwen 全系 | 国内合规、模型全、生态全 | 国内产品首选 |
| 硅基流动 | 聚合多家开源 | 低价、聚合方便 | 个人项目、降本 |
| OpenAI Platform | GPT 全系 | 能力天花板、文档标杆 | 海外产品/能力对标 |
| 自部署 vLLM | 开源模型 | 数据不出门、无按量计费 | 有 GPU、隐私敏感 |

我的选型经验：

- **兼容性优先**：优先选 OpenAI 兼容接口的平台（Qwen、DeepSeek、硅基流动都兼容）。这样你的客户端（02 篇）换平台只改 BASE_URL 和 Key，代码不动。这是我敢在多家平台间比价的底气。
- **至少接入两家**：单一供应商 = 单点故障。我的网关支持按模型名路由到不同平台，主用 Qwen，OpenAI 系做备胎。
- **个人项目别急着自部署 GPU**：vLLM 自部署听起来美好，但一张 24G 显存的卡 + 运维 + 模型更新，综合成本远高于按量 MaaS，除非你有数据合规的硬约束。

## 2. token-plan 计费：读懂账单

MaaS 计费有三种主流形态，价格差异极大：

| 形态 | 机制 | 适合 |
| --- | --- | --- |
| 按量后付费 | 用多少付多少（每千 token 单价） | 起步期、用量不稳 |
| 免费额度 | 新用户/新模型赠送 token 或限时免费 | 迁移测试、灰度验证 |
| 资源包（token plan） | 预付费买固定额度，单价低 30%~50% | 用量稳定的成熟功能 |

踩坑记录（都在阿里云 MaaS 上真实发生）：

- **免费额度的陷阱**：额度常按"新用户 90 天"或"特定模型"限制。我灰度切换到新模型用免费额度跑得很爽，正式放量当天额度用尽、切回按量计价，单日成本是预估的三倍——**灰度用的价格 ≠ 放量后的价格，测算成本必须按正式价**。
- **资源包的余量不可退**：买大包省钱但用不完就浪费。我的做法是先按量跑一个月看真实消耗，再买接近 80% 用量的包，避免为"可能会用"买单。
- **不同模型价差可达 50 倍**：09 篇的模型分级之所以是省钱第一刀，就是因为旗舰模型的按量价格真的能把人吓到。

## 3. 自建网关

功能多了之后，我在服务端加了一层轻量网关（没有用现成开源网关，核心逻辑不过几百行）：

```
功能代码 → Gateway.chat(model, messages, opts) → 路由 → KeyPool → 平台
```

网关的职责清单：

```ts
export async function gatewayChat(req: GatewayRequest) {
  // 1. 鉴权：内部功能带服务凭证，拒绝裸调
  assertInternal(req.token);

  // 2. 配额检查：功能级日预算熔断（09 篇）
  await quota.check(req.feature);

  // 3. 路由：按模型名解析到具体平台
  const route = resolveRoute(req.model);

  // 4. 统一容错：重试/超时/降级（02 篇）在网关层收口
  const res = await withRetry(() => callPlatform(route, req));

  // 5. 记账：功能、模型、token、耗时、成功失败
  await ledger.record({ ...req.meta, ...res.usage, feature: req.feature });
  return res;
}
```

核心原则：**容错、记账、配额这些横切关注点在网关收口**，业务代码只管"我要什么模型、发什么消息"。我刚起步时每个功能自己写重试和记账，三处实现三种 bug——收口之后这类问题一次修完全局生效。

### 3.1 一个轻量网关的最小目录结构

给出我实际在用的网关代码组织方式，方便你起步：

```
src/gateway/
├── index.ts        # gatewayChat：鉴权→配额→路由→容错→记账 的主流程
├── routes.ts       # 模型名 → 平台/Key 池 的路由表，纯配置
├── key-pool.ts     # 02 篇的 KeyPool 原样复用
├── retry.ts        # 02 篇的 withRetry 原样复用
├── quota.ts        # 功能级日预算熔断（09 篇）
├── ledger.ts       # 调用记录落 SQLite
└── ledger.sql      # 建表语句
```

注意 `key-pool.ts` 和 `retry.ts` 都是 02 篇已经写好的代码——**网关不是新大陆，只是把前面各篇的零件按"横切关注点收口"的方式组装起来**。这也是这条路线把网关放在第 11 篇而不是第 2 篇的原因：没有前面的零件，网关就是空中楼阁。

路由表的设计值得多说一句：

```ts
// routes.ts —— 换平台/切模型只改这一个文件
export const ROUTES: Record<string, Route> = {
  "qwen-plus":  { platform: "dashscope", pool: "main" },
  "qwen-turbo": { platform: "dashscope", pool: "main" },
  "gpt-4o":     { platform: "openai",    pool: "backup" },
  // fallback 链：主路由失败自动降级到备胎
  "qwen-plus@fallback": { platform: "siliconflow", pool: "backup" },
};
```

好处是业务代码里的模型名（`gatewayChat({ model: "qwen-plus", ... })`）永远不用改，平台层面的迁移、比价、故障切换全部在配置层解决。我的百炼 → 硅基流动的一次降本迁移，改动量就是这个文件里的三行。

## 4. 可观测与用量统计

### 4.1 记什么

每次调用记一行：时间、功能名、模型、输入/输出 token、耗时、状态（成功/失败/降级/缓存命中）、请求指纹（hash）。SQLite 一张表就够，别上时序数据库。

### 4.2 三个必看报表

```sql
-- 按功能看成本：谁在烧钱
SELECT feature, SUM(total_tokens), COUNT(*) FROM calls
WHERE date >= date('now', '-7 day') GROUP BY feature ORDER BY 2 DESC;

-- 按模型看成本分布：分级策略有没有生效
SELECT model, COUNT(*), SUM(total_tokens) FROM calls GROUP BY model;

-- 失败率与降级率：质量哨兵
SELECT feature,
  SUM(CASE WHEN status='failed' THEN 1 ELSE 0 END) * 1.0 / COUNT(*) AS fail_rate
FROM calls GROUP BY feature;
```

我的看板只看三个数：**本周按功能成本 Top5、缓存命中率、失败率异常**（>2% 告警）。这三个数每周花五分钟扫一眼，就能覆盖 90% 的异常。

### 4.3 一次真实排障

有周我的账单环比涨了 4 倍。按功能报表一拉：翻译功能 token 暴涨。再按日期拆：某两天集中爆发。对日志发现：那两天一位用户在批量翻译超长文——每篇都因超时失败重试 3 次，重试也计费（5xx 重试会正常扣费）。修复：长文分段 + 失败重试前检查内容哈希缓存。**没有记账表，这个故事就只是"账单变贵了"的玄学。**

### 4.4 告警：让报表自己开口说话

报表是"人去看"，告警是"人来找你"，后者才是值班体验的关键。我的告警规则只有三条，全部基于 ledger 表做定时查询（一个 cron 任务每 10 分钟跑一次）：

1. **失败率告警**：任一功能最近 30 分钟失败率 > 5%，或降级触发次数 > 10 次。这条抓的是模型服务异常和 Key 失效。
2. **成本速率告警**：任一功能当日成本超过日均值的 3 倍。这条抓的是重试风暴、被刷、批处理失控——11 篇开头那个"账单涨 4 倍"的故事，如果有这条告警，发现时间会从周结算提前到当天中午。
3. **静默告警**：有真实流量的功能连续 2 小时零调用。这条最反直觉但救过我一次：缓存 key 的 bug 导致所有请求在网关前就异常返回，"零失败"看起来岁月静好，实际是根本没调用成功——**没有失败告警的系统不等于健康，没流量本身就是异常**。

告警通道用最普通的方案：服务端 webhook 推到我的即时通讯，每条告警带功能名、指标值、最近 10 条相关调用记录的链接。**告警必须附上下文**，否则半夜被叫起来的人第一件事是去翻日志，那告警的价值就折半了。

三条规则的阈值都调过至少两轮：第一轮全按拍脑袋设，跑两周，把没触发过的调灵敏、把天天误报的放宽，收敛到"一个月响两三次，每次都是真事"的状态。告警的工程哲学和测试一样：**你不在乎的告警等于没有告警，甚至更糟——它会训练你忽略所有告警。**

## 5. 多平台并存的成本策略

网关路由表建好之后，多平台并存就从"容灾手段"升级成了"成本武器"。我实际在用的三条策略：

**按任务分平台**：不同任务绑定不同平台的最优解。翻译绑定 Qwen（中文语感好、价格低），某类英文摘要任务走另一家（当时该家模型在那类任务上盲测更好）。路由表里写死，业务无感知。

**免费额度轮换**：新模型上线通常配免费额度，我的灰度评测（10 篇）固定用新模型免费额度跑——评测跑一轮几毛钱虽少，但一年下来评测、实验类请求全走免费额度，省下的也是真实成本。注意 2 节的教训：免费额度只用于非生产路径。

**年度比价**：每年固定做一次同档模型价格对照（1.2 万 chunk 级别的项目，半小时就能做完），把 main 路由指向性价比最优者。我在最近一次比价后把主力模型从 A 平台迁到 B 平台，同质量账单降了 35%，迁移工作量是 routes.ts 三行 + 一轮回归评测。

三条策略的共同前提是第 3 节的架构：**业务代码只声明模型名，平台细节全部收在网关**。没有这层抽象，比价和迁移永远是"下次一定"。

## 小结

- 优先选 OpenAI 兼容接口的 MaaS 平台，至少接两家互为备份；个人项目别急自部署 GPU。
- 计费三形态：按量起步、稳定后买资源包；测算成本永远按正式价，免费额度的价格不可信。
- 网关把鉴权、配额、路由、容错、记账收口成统一入口，业务代码只声明需求。
- 一张 SQLite 调用表 + 三个报表（功能成本 / 模型分布 / 失败率）= 足够的可观测性。
