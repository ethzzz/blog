## 作用域是"写在哪"，不是"谁调用我"

JS 用**词法作用域**（静态作用域）：变量在哪查找，由**代码书写位置**决定，与调用者无关。

```js
const a = 'outer';

function foo() {
  console.log(a);      // outer —— 看书写位置，不看谁调用
}

function bar() {
  const a = 'inner';
  foo();               // 仍然是 outer
}
bar();
```

对比动态作用域的语言（bash、早期 Lisp），`foo` 会打印 `inner`。**JS 不是**——这一条决定了闭包的行为（05 篇）。

查找路径：当前作用域 → 外层 → … → 全局。找不到就是 `ReferenceError`（不是 `undefined`）。

## var / let / const 的三层差别

| | `var` | `let` | `const` |
| --- | --- | --- | --- |
| 作用域 | **函数作用域** | 块级 | 块级 |
| 提升 | 提升并初始化为 `undefined` | 提升但**不初始化**（TDZ） | 同 let |
| 重复声明 | 允许 | 报错 | 报错 |
| 是否挂到 `window` | **是**（全局 `var`） | 否 | 否 |
| 可重新赋值 | 是 | 是 | 否（引用不可变，内容可变） |

### 暂时性死区（TDZ）

```js
console.log(x);   // ❌ ReferenceError: Cannot access 'x' before initialization
let x = 1;
```

`let/const` 的变量在**进入作用域时已存在**，但处于"未初始化"状态，访问就报错。这比 `var` 的 `undefined` 好——它能让你立刻发现"用在了声明之前"。

注意 TDZ 是**按位置**生效的：

```js
let y = 1;
{
  console.log(y);   // ❌ 报错：块内声明了 let y，所以在块内 y 从块开始就处于 TDZ
  let y = 2;
}
```

### 全局 `var` 会污染 `window`

```js
var a = 1;
let b = 2;
console.log(window.a, window.b);   // 1, undefined
```

在浏览器里这是真实的污染（会覆盖同名全局属性），模块作用域里不存在这个问题。**这也是"用 `let/const`"最实际的理由之一。**

## 提升：函数声明和函数表达式不一样

```js
foo();            // ✅ 能跑（函数声明整体提升，含函数体）
function foo() { console.log('decl'); }

bar();            // ❌ TypeError: bar is not a function
var bar = function () { console.log('expr'); };
```

`var bar` 提升的是变量名（值为 `undefined`），`bar()` 等于 `undefined()`，所以是 **TypeError** 而不是 ReferenceError。错误类型能帮你定位问题性质。

`const fn = () => {}` 同理，而且更糟：TDZ 会直接抛 ReferenceError。

## 循环里 var 的经典陷阱

```js
// ❌ 三个回调都打印 3
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));
}

// ✅ let 每轮新建绑定
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));   // 0 1 2
}
```

为什么 `var` 是 3：**只有一个 `i`**（函数作用域），循环结束时它是 3，回调在之后执行，读到的自然是 3。

`let` 的行为等价于：

```js
for (let i = 0; i < 3; i++) {
  let _i = i;             // 每轮新建一个块级绑定
  setTimeout(() => console.log(_i));
}
```

这也是"闭包捕获的是变量而不是值"的直接体现（05 篇展开）。

## 作用域的四种形态（顺便认全）

```js
// 1) 函数作用域
function f() { var x = 1; }

// 2) 块级作用域（let/const）
if (true) { let y = 1; }

// 3) 模块作用域（每个文件一个独立作用域，顶层不是全局）
//    —— 这是现代代码里最常用的一种，也是"不再需要 IIFE"的原因

// 4) 全局作用域（浏览器里是 window，Node 里是 globalThis）
```

老代码里常见的 IIFE 就是"在没有模块的年代造一个作用域"：

```js
(function () {
  var privateVar = 1;     // 外部拿不到
})();
```

现在直接用模块就够了——**别在新代码里写 IIFE 造作用域**。

## 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 循环里回调都拿到最后一个值 | `var` 函数作用域 | 改 `let`，或用 `forEach` 的形参 |
| `Cannot access 'x' before initialization` | TDZ | 把声明提前；或确认是否重复声明了同名 `let` |
| 函数调用报 `not a function` | `var` 提升为 `undefined` | 用函数声明，或把调用放到赋值之后 |
| 全局变量互相覆盖 | `var` 挂到 `window` | 用 `let/const` 或模块 |
| `if` 块里声明的变量外面拿不到 | `let` 块级作用域 | 把声明提到外层 |
| for 循环里 `const` 报错 | 每次迭代要重新赋值 | 循环变量用 `let`，或改用 `for...of` |

## 练习

1. **预测输出**：写一段"外层 `let a`、内层块再 `let a` 并在声明前打印"的代码，先猜再跑。  
   *自检*：能解释 TDZ 是"进入块就开始"而不是"到声明那一行才开始"。
2. **改造一段老代码**：把项目里一个用 `var` 的循环回调改成 `let`，再用 `var` + IIFE 复现旧行为，对比两者。  
   *自检*：能说出 IIFE 为什么也能修好（它给每轮造了独立作用域）。
3. **制造一次隐式全局污染**：在非严格模式下写 `x = 1`（不声明），看 `window.x` 是否存在；再加 `'use strict'` 观察报错。  
   *自检*：能说明"模块默认是严格模式"，所以这种 bug 在模块里不会出现。
