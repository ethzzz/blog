## 为什么还要学一个框架

React 解决的是「UI 怎么随状态变化」。但一个能上线的产品还需要：路由、服务端渲染、数据获取、表单提交、鉴权、缓存、构建与部署。Pages Router 时代，这些大多靠社区拼装；App Router 把其中大部分收进了框架，并且用 RSC（React Server Components）重新划了前后端的边界。

代价是：**心智模型变复杂了**。同一份代码，可能在构建期跑、在请求期跑、在浏览器跑；同一个页面，可能静态、可能动态、可能一半静态一半流式。很多团队上 Next.js 后遇到的生产事故，不是 API 不会用，而是不知道某段代码到底在哪一层执行。

## 三条贯穿全系列的主线

### 一、边界比 API 重要

`'use client'` 不是一个装饰器，它是一条**模块边界**：从这一行开始，导入图里的所有东西都会进入客户端 bundle。放错位置，要么把数据库客户端打进浏览器，要么让整棵树失去服务端渲染能力。后面第 03 篇会专门讲。

### 二、缓存是显式的，失效是设计出来的

Next.js 15 起 `fetch` 默认不缓存，Route Handler 默认不缓存；Next.js 16 推 `use cache`、`cacheLife`、`cacheTag` 这套显式缓存模型。框架不再替你做「聪明的决定」，你必须自己回答：这份数据能旧多久？谁负责让它失效？第 04 篇会把这条链路讲透。

### 三、服务端不是「另一个前端」

直接在 Server Component 里查数据库很爽，但连接池、事务、超时、鉴权、审计一个都跑不掉。第 07、08 篇会把服务端工程的基本功补上——这些才是全栈和前端的真正分水岭。

## 我带团队时最常见的五个翻车点

- **根布局写了 `'use client'`**：整站退化成客户端应用，SSR 只剩个空壳。
- **在深层组件里读 `cookies()`**：整条路由从静态变动态，构建日志里全是 ƒ，CDN 缓存全失效。
- **只做了写入、没做失效**：后台改了数据，前台半小时后还是旧的，最后靠重启服务「解决」。
- **把 Server Action 当公开 API**：它是可被直接调用的 HTTP 端点，没做鉴权就等于把写接口裸奔在公网。
- **本地 `next start` 正常，上线 502**：standalone 产物没带 `public/`、`.next/static`，或者反代没配流式响应。
