运营输入一段需求，得到一份包含字段、原文证据和待确认项的建议。审核时可以回看这些条件来源。点击「应用到表单」后先预演，再由运营员保存和提交；已有发布活动继续服务于模拟客户端。

## 1. 跑一遍完整输入和模糊输入

在「新草稿」选择默认配置，将最低版本先改为 `2.4.0`。保持其余字段不变，再把这段需求发给 AI：

```text
Link 2 教程，仅已激活，未完成新手引导，App 至少 2.5.0，开始 2026-12-01T00:00:00Z，下线 2026-12-04T12:00:00Z
```

1. 点击「生成建议」。在返回值中找到 `patch.minAppVersion` 和 `evidence.minAppVersion`，分别应为 `2.5.0` 和原文里的「至少 2.5.0」。
2. 点「应用到表单」再点「对比改动」。在默认时点，版本门槛提高后预计获胜群体移除了 u02。若先前发布过同优先级活动，用另一个优先级或先在测试环境下线该活动，确保演练结果可重现。
3. 改发「Link 2 教程，本周五下线」。建议应列出下线时间待确认。检查表单保存前的日期，已有值依旧需要按实际排期人工核对。
4. 应用一份建议、保存并提交审核。切换审核员后检查「修改与审核记录」，可以对照冻结的发布配置、原始需求和 AI 建议。服务器把 AI 建议单独保存为提案，并在对应修订的审计快照中记录提案 ID。人工修订后的配置仍以活动快照为准。

## 2. 把模型响应做成可以验证的契约

`assistant.mjs` 发送给模型的是运营需求与已审核的素材清单。返回 JSON 后，`normalize` 依次校验字段名称、原文证据、版本和时间格式，以及素材是否允许投放。缺少的字段生成对应问题，优先级和活动名称由表单提供。

```json
{
  "fields": [
    { "field": "model", "value": "LINK2", "evidence": "Link 2" },
    { "field": "minAppVersion", "value": "2.5.0", "evidence": "至少 2.5.0" }
  ],
  "headline": "查看设备使用指南"
}
```

将同一条响应的版本改成 `2.0.0`，保留「至少 2.5.0」作证据。校验应报 `MODEL_VALUE_NOT_SUPPORTED_BY_EVIDENCE`。把素材改成未审核的 `draft-sale`，应报 `UNAPPROVED_MODEL_ASSET`。这些反例说明位置正确的证据也需要和字段值核对。

解析器只接受教程中定义的表达，例如三段版本号和明确 UTC 时间，遇到更复杂的句式可以先提示运营补充。即使证据是原文子串，长句中的否定、转述与歧义仍要由审核员结合上下文判断。文案作为模型建议显示，发布前应核对价格、折扣和产品能力等承诺。

## 3. 换成真实模型并比对

保留数据库设置，在原 `.env` 把模式设成 `compatible`。服务端使用 Chat Completions JSON 模式，响应仍要经过业务校验。填配置前确认供应商提供兼容的 API 路径、模型和 JSON 模式。 [OpenAI 结构化输出与 JSON 模式](https://developers.openai.com/api/docs/guides/structured-outputs)

```dotenv
AI_PROVIDER=compatible
AI_BASE_URL=https://api.openai.com/v1/
AI_API_KEY=填自己的测试密钥
AI_MODEL=填支持 JSON 模式的模型 ID
```

重启后先跑第一节的两段输入，再在输入中加「仅 Link 2C」复测机型识别。遇到错误时查看接口错误码，排查上游响应、JSON 解析或证据校验。模型网络请求有 20 秒上限，测试时使用合成需求和素材，密钥只放服务端环境文件。

## 验收

- [ ] 生成建议只写入提案。应用建议并保存后，审核员能读取关联的原文和证据。
- [ ] 相对日期留待确认。伪造证据、版本与证据不一致或未审核素材会被拒绝。
- [ ] 改一项版本门槛可看到确切的新增或移除用户。
- [ ] 有真实模型密钥时，保留一条通过和一条失败样本，记录模型 ID 和提示词版本。
