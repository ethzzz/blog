## 一条主线：类型越窄越好，但只能在"确定"时收窄

TS 新手常犯两类错：

- **太宽**：到处 `any`，等于没写类型；
- **假装很窄**：`as User` 把 `unknown` 强行说成 `User`，编译通过、运行时炸。

真正要建立的习惯是：**边界处收宽（`unknown`），确认后收窄（守卫），永不断言**。这篇讲的就是这套工具。

---

## 三个"特殊"类型的分工

| 类型 | 含义 | 用在哪 |
| --- | --- | --- |
| `any` | 关闭检查 | **只在迁移期临时用**，且必须有 TODO |
| `unknown` | 未知，但**使用前必须收窄** | 所有外部输入：`JSON.parse`、`catch (e)`、`postMessage`、第三方回调 |
| `never` | 不可能存在的值 | 穷尽检查、`throw` 函数返回值、过滤联合类型 |

```ts
// any：进来就失控
function f1(x: any) { x.foo.bar(); }   // 编译通过，运行时可能炸

// unknown：不确认就不让用
function f2(x: unknown) {
  // x.foo;            // ❌ 报错
  if (typeof x === 'object' && x !== null && 'foo' in x) {
    // 这里 x 被收窄为 object & Record<'foo', unknown>
  }
}
```

`catch` 的变量在 `strict` + `useUnknownInCatchVariables` 下就是 `unknown`——**这是好事**，因为抛出的可能是 string、可能是 Error、也可能是任意值：

```ts
try { await save(); } catch (e) {
  const msg = e instanceof Error ? e.message : String(e);   // ✅ 必须显式判断
}
```

## 字面量类型：让类型携带"值"

```ts
type Status = 'idle' | 'loading' | 'success' | 'error';   // 不是 string，是四个具体值
let s: Status = 'idle';
s = 'done';      // ❌ 编译报错
```

配合 `as const` 把"值"固定下来：

```ts
const config = { mode: 'dark', retries: 3 };
// 推断：{ mode: string; retries: number }  ← 太宽，'dark' 丢了

const config2 = { mode: 'dark', retries: 3 } as const;
// 推断：{ readonly mode: "dark"; readonly retries: 3 }  ← 精确到字面量
```

`as const` 的两个作用：**字面量收窄** + **深度 readonly**。

## `satisfies`：校验但不改变推断

`as const` 的问题是它同时冻结了类型。而 `: Type` 注解的问题是**它会丢失具体推断**：

```ts
type Route = { path: string; auth: boolean };

// 用注解：items 的类型被抹成 Route[]，拿不到具体 path 字面量
const routesA: Route[] = [
  { path: '/home', auth: false },
  { path: '/admin', auth: true },
];
routesA[0].path;      // string（丢了 '/home'）

// 用 satisfies：既校验结构，又保留精确推断
const routesB = [
  { path: '/home', auth: false },
  { path: '/admin', auth: true },
] satisfies Route[];
routesB[0].path;      // "/home"（保住了）
```

判断规则：

- 只要**校验**（结构对不对）→ `satisfies`
- 要**当常量字典用**（值要参与类型推导）→ `as const satisfies X`（TS 4.9+）
- **不要**用 `as` 做校验：`as` 是"闭嘴"，不是"检查"

```ts
// 经典用法：配置表既要约束又要保留 key
const theme = {
  primary: '#3b82f6',
  danger: '#ef4444',
} as const satisfies Record<string, string>;

type ThemeKey = keyof typeof theme;   // "primary" | "danger"
```

## 数组、元组、readonly

```ts
const list: string[] = ['a'];           // 可变长同类型
const pair: [number, string] = [1, 'a']; // 元组：定长、定位置类型
const ro: readonly string[] = ['a'];     // 只读数组（不能 push）
```

元组真正的价值是**函数返回多值**：

```ts
function parse(input: string): [ok: true, value: number] | [ok: false, error: string] {
  const n = Number(input);
  return Number.isFinite(n) ? [true, n] : [false, `不是数字: ${input}`];
}

const [ok, result] = parse('12');
if (ok) result.toFixed(2);   // result 被收窄为 number
```

比 `{ ok: boolean; value?: number; error?: string }` 强得多——**后者永远需要判空两次**。

## 为什么新代码别用 `enum`

```ts
enum Status { Idle, Loading }        // 运行时产物：一个双向映射对象
const enum Fast { A }               // 编译期替换，但 isolatedModules/esbuild 不支持
```

三个问题：

1. **运行时体积**：`enum` 会生成真实对象（`{0:'Idle', Idle:0}`），还不能被 tree-shake；
2. **类型是名义的**：`Status.Idle` 不能直接和数字比较，跨文件传递容易失败；
3. **与 `const enum` 的坑**：`isolatedModules`（esbuild/swc/Vite 必需）下不支持，编译直接报错。

替代方案就是字面量联合 + `as const`：

```ts
const STATUS = { idle: 'idle', loading: 'loading' } as const;
type Status = (typeof STATUS)[keyof typeof STATUS];   // "idle" | "loading"
```

**唯一例外**：你在写需要位运算的权限标志（`1 << 0`），那种场景确实适合常量对象 + 位运算函数，也不需要 enum。

## 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| `Object is possibly 'null'` 到处出现 | 没做判空 | `if (!x) return`、可选链 + 默认值；别用 `!` |
| `as const` 后不能改属性 | 它同时加 `readonly` | 需要可变时用 `as const` 后在局部展开 `{...obj}` |
| `satisfies` 报"类型不满足"但看不出哪 | 嵌套深 | 先抽成类型别名，让报错定位到具体字段 |
| `JSON.parse` 返回值当对象直接用 | 返回 `any` | 立刻赋给 `unknown`，或直接过 schema（11 篇） |
| 枚举值在接口里变成字符串 | 反向映射理解错 | 改用字面量联合 |
| `catch (e)` 里 `e.message` 报错 | `e` 是 `unknown` | `e instanceof Error` 判断 |

## 验收清单

- [ ] 项目里 `any` 的数量可统计（`grep -rn ": any"`），每一处都有理由或 TODO
- [ ] 所有外部输入（响应、存储、URL、`postMessage`）落地时是 `unknown`，不是 `any`
- [ ] 常量表用 `as const satisfies`，能从中推导出 key 的联合类型
- [ ] 多返回值函数用元组，而不是三个可选字段
- [ ] 没有 `enum` / `const enum`（或能说出唯一例外）
- [ ] 能说清 `as`、`satisfies`、`as const` 三者的差别

## 练习

1. **对比推断结果**：分别写 `const a = { mode: 'dark' }`、`as const`、`: { mode: string }` 三个版本，用编辑器悬停看类型差异。  
   *自检*：能说出 `as const` 在 `mode` 上做了什么（字面量 + readonly）。
2. **用 `satisfies` 修一个真实问题**：给一份路由表或主题表加 `satisfies` 约束，同时保留 key 的字面量类型，用它做 `keyof typeof`。  
   *自检*：故意删掉一个必填字段，确认报错位置精确到那一行。
3. **替换一处 `as`**：找项目里 `as SomeType` 的用法，改成"`unknown` + 守卫/schema"，说明哪个版本能在字段改名时报警。  
   *自检*：能指出 `as` 只在"你比编译器更懂"时成立，而那种时候通常是错的。
