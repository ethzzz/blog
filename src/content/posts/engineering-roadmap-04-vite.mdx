## 快的本质：把"打包"从开发期挪走

Webpack 的开发服务器要先**把整个应用打包一遍**才能响应第一个请求——项目越大，冷启动越慢。

Vite 换了个思路：**开发期不打包**。

```text
浏览器请求 /src/main.tsx
  → Vite 把这一个文件转译成 ESM（esbuild，毫秒级）
  → 浏览器顺着 import 继续请求下一个文件
  → 按需转译，永远只处理"当前页真正用到"的模块
```

代价是：**请求数变多**（一个页面几百个模块请求）。所以 Vite 做了第二件事——**依赖预构建**。

## 依赖预构建：为什么不预构建就慢

你的源码有 100 个文件，但 `react`、`lodash-es` 这些依赖内部有**几千个模块**。如果不处理，浏览器要发几千个请求，瀑布流直接卡死。

预构建做两件事：

1. **CJS → ESM**：把 `react` 这种 CJS 包转成 ESM，浏览器才能直接 import；
2. **合并**：把 `lodash-es` 的几百个内部模块打成一个文件，请求数从几百降到 1。

产物缓存到 `node_modules/.vite/deps`，所以**第二次启动几乎瞬间完成**。

```bash
# 依赖变了但缓存没更新（常见于 link 本地包）
rm -rf node_modules/.vite   # 或 vite --force
```

`vite.config.ts` 里可以强制某些包参与/不参与预构建：

```ts
export default defineConfig({
  optimizeDeps: {
    include: ['lodash-es', 'echarts'],   // 动态 import 的包不会被自动扫描到，手动加
    exclude: ['my-local-lib'],           // 本地 link 的包别预构建，改了能立即生效
  },
});
```

> 判断是否命中预构建：浏览器 DevTools → Network，看 `node_modules/.vite/deps/react.js?v=xxxx` 这类带 hash 的请求，是否存在。

## 一份生产可用的配置

```ts
// vite.config.ts
import { defineConfig, loadEnv } from 'vite';
import react from '@vitejs/plugin-react';
import { fileURLToPath, URL } from 'node:url';

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), '');

  return {
    base: env.VITE_BASE ?? '/',        // 部署在子路径时必须改这个（如 /blog/）

    resolve: {
      alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) },
    },

    server: {
      port: 5173,
      proxy: {
        '/api': { target: 'http://localhost:8001', changeOrigin: true },
      },
    },

    build: {
      target: 'es2020',               // 决定语法降级程度
      sourcemap: 'hidden',            // 生成 map 但不写引用注释（上传监控平台，别发 CDN）
      chunkSizeWarningLimit: 600,     // KB，超过就提醒你该拆了
      rollupOptions: {
        output: {
          manualChunks: {
            react: ['react', 'react-dom'],
            vendor: ['axios', 'dayjs'],
          },
        },
      },
    },
  };
});
```

三点说明：

- **`base`**：部署到 `https://x.com/blog/` 就必须写 `/blog/`，否则所有资源 404（本博客就是这个坑）。
- **`build.target`**：`es2020` 覆盖 95%+ 现代浏览器；要兼容更老环境就得降到 `es2015` 并加 polyfill（Vite 不再内置 polyfill）。
- **`manualChunks`**：把稳定的三方包拆出来，改业务代码不会让用户重新下载 React。

## 环境变量：`import.meta.env` 的规矩

Vite 只把**以 `VITE_` 开头**的变量注入客户端，这是一道安全边界：

```bash
# .env.development
VITE_API_BASE=http://localhost:8001
VITE_FEATURE_NEW_UI=true

# .env.production
VITE_API_BASE=https://api.example.com
```

```ts
if (import.meta.env.VITE_FEATURE_NEW_UI === 'true') { /* ... */ }
console.log(import.meta.env.MODE);       // development / production
console.log(import.meta.env.PROD);       // boolean
```

⚠️ **注入是"文本替换"**，发生在构建期：

```ts
// 危险：变量会被原样替换进产物，等于把值写死在 JS 里
const key = import.meta.env.VITE_SECRET_KEY;
```

所以三条铁律：

1. **密钥绝不进 `VITE_` 前缀的变量**（构建后任何人都能在 JS 里搜到）；
2. 需要保密的配置走**服务端注入**（见 13 篇：运行期配置）；
3. `.env.local` 加进 `.gitignore`，`.env.example` 入库作为文档。

## 库模式：把组件库打成 npm 包

```ts
// vite.config.ts
export default defineConfig({
  build: {
    lib: {
      entry: 'src/index.ts',
      name: 'MyLib',
      formats: ['es', 'cjs'],           // 双格式，兼容 import 与 require
      fileName: (format) => `index.${format === 'es' ? 'mjs' : 'cjs'}`,
    },
    rollupOptions: {
      external: ['react', 'react-dom'],  // 宿主提供，不打进产物
      output: {
        globals: { react: 'React', 'react-dom': 'ReactDOM' },
      },
    },
  },
});
```

配 `package.json`：

```json
{
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.mjs", "require": "./dist/index.cjs" }
  },
  "peerDependencies": { "react": ">=18" },
  "sideEffects": false
}
```

`external` + `peerDependencies` + `sideEffects: false` 这三件套，决定了用户装你的库会不会出现"两份 React"和"摇不掉"。

## 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 改了本地 link 的包不生效 | 被预构建缓存了 | `optimizeDeps.exclude` 掉它，或 `--force` |
| 动态 `import()` 的包没被预构建，首屏卡 | 预构建只扫描静态入口 | `optimizeDeps.include` 手动加 |
| 部署到子路径后白屏 | `base` 没改 | 设 `base: '/子路径/'` |
| 生产报 `process is not defined` | 依赖里用了 Node 全局 | `define: { 'process.env.NODE_ENV': JSON.stringify(mode) }` |
| 某个 CJS 依赖 import 后是空对象 | 预构建没覆盖，或包没有 ESM 入口 | 加进 `optimizeDeps.include`；确认包的 `exports` |
| HMR 后状态丢失/整页刷新 | 组件没走 fast refresh（如默认导出匿名组件） | 导出具名组件；检查 `@vitejs/plugin-react` 是否生效 |
| SSR 时报 `window is not defined` | 模块顶层访问了浏览器 API | 移到 `onMounted`/`useEffect` 内，或 `typeof window !== 'undefined'` 守卫 |

## 从 Webpack 迁到 Vite：检查清单

- [ ] `base` 与部署路径一致（子路径最容易漏）
- [ ] `resolve.alias` 与 `tsconfig.paths` 对齐（Vite 不读 tsconfig 的 paths）
- [ ] `process.env.*` 全部替换成 `import.meta.env.*`
- [ ] 找出所有 CJS 依赖，加进 `optimizeDeps.include`
- [ ] `require()` 全部改成 `import`（Vite 不处理运行时 require）
- [ ] 静态资源引用从 `require('./a.png')` 改成 `new URL('./a.png', import.meta.url).href`
- [ ] 环境变量前缀从 `REACT_APP_` 换成 `VITE_`
- [ ] CI 里 `npm run build` 的产物目录仍是 `dist`（Vite 默认就是）
- [ ] 生产 sourcemap 策略确认（默认 `false`，建议改 `hidden` + 上传）

## 练习

1. **量化差异**：同一个中型项目分别用 Webpack 5 和 Vite 启动，记录冷启动时间与首次页面可交互时间。
   *自检*：给出两组数字，并解释 Webpack 的时间花在"预先打包全量"、Vite 花在"按需转译 + 预构建依赖"。
2. **观察预构建**：清空 `node_modules/.vite` 后启动，看终端输出的 "Pre-bundling dependencies"，然后在 DevTools 里找到 `deps/` 请求。
   *自检*：能指出被合并的包名，并说明合并前后的请求数差异。
3. **制造 base 事故**：把 `base` 从 `/` 改成 `/app/`，构建后直接用 `npx serve dist` 打开首页，观察资源 404，再改回来。
   *自检*：能解释"HTML 里资源路径是构建期写死的，不是运行时算的"。
