---

## 度量：实验室数据和真实用户是两回事

- **实验室**：Lighthouse、PageSpeed Insights，可复现，适合定位。
- **真实用户（RUM）**：LCP、INP、CLS 的 P75，才是业务真正体验到的。
- **服务端**：TTFB、数据库查询耗时、缓存命中率。

Next.js 自带的 `useReportWebVitals` 可以把指标打到自己的分析端点：

```tsx
// app/_components/web-vitals.tsx
"use client";

import { useReportWebVitals } from "next/web-vitals";

export function WebVitals() {
  useReportWebVitals((metric) => {
    navigator.sendBeacon(
      "/api/vitals",
      JSON.stringify({
        name: metric.name,
        value: metric.value,
        id: metric.id,
        path: location.pathname,
      }),
    );
  });
  return null;
}
```

先在真实流量上拿到基线，再谈优化目标。没有基线的「优化」都是自我感觉。

## 最大的杠杆：少发 JS

Next.js 最大的性能优势不是 SSR，而是 **Server Component 默认不进客户端 bundle**。

- 页面能留在服务端就留在服务端。
- `'use client'` 只加在真正需要交互的叶子。
- 大依赖（图表、编辑器、地图）用 `next/dynamic` 懒加载。
- 定期跑 bundle analyzer，看有没有意外被拖进客户端的库。

```tsx
import dynamic from "next/dynamic";

const Editor = dynamic(() => import("@/components/editor"), {
  loading: () => <EditorSkeleton />,
});
```

一个常见的体积杀手是 barrel file：`import { Button } from "@/components"` 可能把整个组件库的导入图都带进来。按路径精确导入，或者配置 `modularizeImports` / `optimizePackageImports`。

## 流式渲染：先给壳，再给数据

```tsx
// app/dashboard/page.tsx
import { Suspense } from "react";

export default function Dashboard() {
  return (
    <main>
      <Header />
      <Suspense fallback={<StatsSkeleton />}>
        <Stats />
      </Suspense>
      <Suspense fallback={<TableSkeleton />}>
        <RecentOrders />
      </Suspense>
    </main>
  );
}
```

`Stats`、`RecentOrders` 是 async Server Component，各自取数、各自流式返回。注意：

- **两个 Suspense 边界是并行渲染的**，不要把它们串行 `await` 在一个父组件里。
- 骨架要和真实内容尺寸接近，否则 CLS 飙升。
- 流式响应经过反代时，关闭 `proxy_buffering`。

### 消除请求瀑布

```ts
// ❌ 串行：三步各 200ms，总共 600ms
const user = await getUser(id);
const orders = await getOrders(user.id);
const stats = await getStats(user.id);

// ✅ 无依赖的并行
const [user, stats] = await Promise.all([getUser(id), getStats(id)]);
const orders = await getOrders(user.id);
```

RSC 里一个很容易忽视的点：**同一个 `await` 链上的兄弟组件也是串行的**。独立数据源拆到独立组件、独立 Suspense 边界里。

## 图片：LCP 的主战场

```tsx
import Image from "next/image";

<Image
  src={cover}
  alt={title}
  width={1200}
  height={630}
  sizes="(max-width: 768px) 100vw, 800px"
  priority={isAboveTheFold}
/>
```

规则：

- **首屏主图加 `priority`**，其余图片不要加，否则会抢带宽。
- 永远提供 `width` / `height` 或 `fill` + 容器尺寸，避免 CLS。
- `sizes` 写对，否则会下载过大的图。
- 图片走 CDN/对象存储，别让 Next 进程代理大文件。
- 动图优先视频（`<video>`）或压缩后的 WebP/AVIF。

## 字体：别让文字等字体

```ts
// app/layout.tsx
import { Noto_Sans_SC } from "next/font/google";

const sans = Noto_Sans_SC({
  subsets: ["latin"],
  weight: ["400", "500", "700"],
  display: "swap",
});
```

- 用 `next/font` 自托管，避免第三方字体域名的额外连接。
- 只加载需要的字重和子集，中文字体尤其要控制。
- `display: "swap"` 先显示系统字体，避免 FOIT。
- 变量字体优先，减少文件数量。

## 交互性能：INP 比加载更常被忽略

页面加载快了，点击还是卡，问题通常在主线程：

- 大列表渲染：虚拟化（`@tanstack/react-virtual`）。
- 输入联想：`useDeferredValue` 把重渲染降级。
- 大量状态更新：`startTransition` 标记非紧急更新。
- 长任务：拆分为多个 `requestIdleCallback` / `scheduler` 任务。
- 动画用 CSS transform/opacity，别在 JS 里逐帧改布局属性。

```tsx
const [query, setQuery] = useState("");
const deferredQuery = useDeferredValue(query);
const results = useMemo(() => search(deferredQuery), [deferredQuery]);
```

---

## 缓存也是性能

- 静态资源加长缓存 + 内容哈希（Next 构建产物自带）。
- 页面级缓存用 `use cache` / ISR，别每次请求都打数据库。
- 接口层加 Redis 缓存时，记得设计失效，别制造「数据永远旧」的新问题。
- CDN 缓存 HTML 要谨慎：带用户信息的页面绝不能进公共缓存。

## 性能预算

给团队定可执行的数字，而不是喊口号：

| 指标 | 建议目标 |
| --- | --- |
| LCP（P75） | 小于 2.5s |
| INP（P75） | 小于 200ms |
| CLS（P75） | 小于 0.1 |
| 首屏 JS（gzip） | 控制在 200KB 以内 |
| 单页数据请求 | 关键路径不超过 3 跳 |

把预算写进 CI：Lighthouse CI 或自建脚本，超过阈值就报警。性能是**守出来的**，不是某次专项优化出来的。

---

## 常见坑

- **无脑 `priority`**：首屏图片互相抢带宽，LCP 反而更差。
- **把所有组件标成客户端**：JS 体积翻倍，流式渲染失效。
- **只看 Lighthouse 分数**：实验室 100 分，真实用户依然卡。
- **在客户端传巨大数组**：RSC Payload 几百 KB，序列化和 hydrate 都慢。
- **滥用 `useMemo` / `memo`**：比较成本大于收益。
- **忽略第三方脚本**：统计、客服、A/B 脚本经常是 INP 罪魁祸首，用 `next/script` 的 `lazyOnload` / `afterInteractive` 管好。

## 练习（带自检）

1. **判断**：给一个页面（大图头图、长列表、一个折叠在下面的图表）。指出 LCP 元素是什么、为什么不是头图，以及哪个元素最可能造成 CLS。
2. **改错**：图片没写宽高导致 CLS 0.3；字体用默认加载导致文字先隐形后闪现。给出两处修法，并说明各自的代价（占位空间、`swap` 的字体跳动）。
3. **做出**：给首屏图加 `priority`、其余图懒加载、字体做子集化。用 Lighthouse 或 web-vitals 采集改前/改后的 LCP 与 CLS。
4. **量数据**：记录 P75（不是平均值），并说明为什么看 P75——给出你自己的两个页面各一个数字。
5. **故意搞坏**：把整页包进一个客户端组件（顶层 `'use client'`），观察 First Load JS 与 TTI 的变化，解释"为什么这不是性能优化能救回来的"。

**自检标准**：第 3 题能给出具体的秒数与分数对比；第 4 题能说出"P75 覆盖了大多数真实用户，平均值会被极快样本稀释"。

## 验收清单

- [ ] 首屏图用了 `next/image`、有 `priority`、有明确尺寸
- [ ] 非首屏图片全部懒加载，且给了尺寸或宽高比
- [ ] 字体做了子集化 + `display: swap`，没有长时间隐形文字
- [ ] 客户端组件的体积在预算内，且知道最大的三个依赖是什么
- [ ] 长列表做了分页或虚拟化（不是一次渲染 1000 行）
- [ ] 采集了真实用户指标（P75），而不是只看本地 Lighthouse
- [ ] 慢页面用流式或 PPR，首屏骨架出现时间早于数据返回

## 小结

性能优化是「减少要做的事」：少发 JS、少等一次网络、少渲染一帧。Next.js 提供了流式渲染、RSC、图片与字体优化这些工具，但用不用、用在哪，取决于你有没有度量。下一篇讲另一件决定项目能不能长期运行的事：错误处理与可观测性。
