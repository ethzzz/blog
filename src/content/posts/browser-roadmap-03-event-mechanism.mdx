## 1. 三阶段与三个"停止"

```text
        捕获阶段                目标阶段              冒泡阶段
window → document → ... → 事件源元素 → ... → document → window
```

```js
el.addEventListener('click', handler, true);   // 捕获（第三个参数 true，或 { capture: true }）
el.addEventListener('click', handler);         // 冒泡（默认）
```

`addEventListener` 的第三个参数还可以是对象，除了 `capture` 常用的还有 `once`、`passive`、`signal`——最后这个配合 `AbortController` 能一次性解绑所有监听，后面会用到。

### 1.1 三个 API，职责完全不同

| API | 阻止什么 | 不阻止什么 | 典型误用 |
| --- | --- | --- | --- |
| `e.stopPropagation()` | 事件继续向**其它元素**传播 | **同元素**上的其它监听器照常执行 | 以为能"独占"当前元素 |
| `e.stopImmediatePropagation()` | 连**同元素上后续**监听器一起阻止 | 已经执行过的监听器 | 顺手用了它，把别人的埋点也杀了 |
| `e.preventDefault()` | 浏览器**默认行为**（提交、跳转、右键菜单） | **完全不影响**传播 | 以为能阻止外层监听 |

一个可运行的验证，把三者的差别一次看清：

```html
<div id="outer">
  <button id="btn">点我</button>
</div>
<script>
  const outer = document.getElementById('outer');
  const btn = document.getElementById('btn');

  outer.addEventListener('click', () => console.log('outer 冒泡'), false);
  outer.addEventListener('click', () => console.log('outer 捕获'), true);
  btn.addEventListener('click', () => console.log('btn #1'));
  btn.addEventListener('click', (e) => {
    // 试着逐个打开，看输出变化
    // e.stopPropagation();
    // e.stopImmediatePropagation();
    // e.preventDefault();
    console.log('btn #2（调 API 的地方）');
  });
  btn.addEventListener('click', () => console.log('btn #3'));

  // 对照实验：用 stopPropagation 之后，outer 冒泡不打印，但 btn #3 仍然打印；
  // 用 stopImmediatePropagation 之后，btn #3 也不打印。
</script>
```

> 经验：业务代码里优先用"判断来源"（`e.target.closest()`）而不是 `stopPropagation`。一旦某个组件开始全局截断事件，排查其它组件的问题时你会非常痛苦。

### 1.2 `preventDefault` 什么时候会失效

- 监听是 `passive: true`（第 3 节）：浏览器明确忽略 `preventDefault`，控制台会给警告；
- 事件本身不可取消：`e.cancelable === false` 时调用无效（例如某些浏览器上报的 `scroll`、已完成的 `touchmove`）；
- 你调用得太晚：默认行为在事件派发过程中就执行了。

```js
document.addEventListener('click', (e) => {
  console.log('cancelable?', e.cancelable); // 通常 true
});
```

## 2. 事件委托：好用，但有五个坑

```js
// ✅ 1000 个列表项只挂 1 个监听器
list.addEventListener('click', (e) => {
  const item = e.target.closest('[data-id]');
  if (!item || !list.contains(item)) return;
  select(item.dataset.id);
});
```

一个完整可跑的版本（含动态新增节点）：

```html
<ul id="list">
  <li data-id="1"><span>A</span></li>
  <li data-id="2"><span>B</span></li>
</ul>
<button id="add">新增一项</button>
<script>
  const list = document.getElementById('list');

  list.addEventListener('click', (e) => {
    const item = e.target.closest('[data-id]');
    if (!item) return;          // 点在空白处
    console.log('选中', item.dataset.id); // 新增的项也自动生效
  });

  document.getElementById('add').addEventListener('click', () => {
    const li = document.createElement('li');
    li.dataset.id = String(list.children.length + 1);
    li.innerHTML = '<span>新增</span>';
    list.appendChild(li);       // 不需要为新节点再绑监听
  });
</script>
```

五个坑，按踩到的频率排序：

**① 不是所有事件都冒泡。** 这些不冒泡：`focus`、`blur`、`mouseenter`、`mouseleave`、`load`、`error`（资源）、`submit`（其实是冒泡的，容易记错）。要用冒泡版或捕获：

| 不冒泡 | 冒泡替代 |
| --- | --- |
| `focus` / `blur` | `focusin` / `focusout` |
| `mouseenter` / `mouseleave` | `mouseover` / `mouseout` |
| 资源 `load` / `error` | 用 `{ capture: true }` 在捕获阶段接 |

**② `e.target` 是真正被点的子元素。** `textContent`、`dataset` 都要在 `closest()` 返回的元素上取。忘了这点，点了 `<span>` 就取不到 `data-id`。

**③ 委托容器必须稳定。** SPA 路由重建列表容器后，挂在上面的监听随节点一起消失——这是"跳转回来点了没反应"的经典原因。要么挂在不会重建的父节点上，要么在组件卸载时解绑、挂载时重绑。

**④ Shadow DOM 会重定向事件目标。** 跨 shadow 边界时，`e.target` 被重定向为宿主元素（retargeting），`closest()` 找不到内部节点。要在 shadow root 内部再委托一层，或用 `e.composedPath()`：

```js
host.addEventListener('click', (e) => {
  const path = e.composedPath();       // 从真实目标到 window 的完整路径
  const inner = path.find((n) => n.dataset?.action);
  if (inner) handle(inner.dataset.action);
});
```

**⑤ 大量委托不等于零成本。** 每次点击都要跑一遍 `closest()`，在超深 DOM（嵌套 20 层）里也有开销。极深结构下用 `data-action` 直接判 `e.target.dataset`，别每次都遍历。

## 3. `passive`：滚动卡顿的常见解药

移动端滚动由**合成线程**驱动。但浏览器不确定你的 `touchmove` 回调会不会调 `preventDefault()`，所以必须等主线程执行完这个回调，才敢开始滚——回调里有 10ms 逻辑，手指就多 10ms 的延迟感。

```js
// 默认（在 window/document/body 上已被浏览器当成 passive）
window.addEventListener('touchmove', handler);

// ✅ 明确"我不会阻止默认行为" → 滚动可以立刻开始，不必等主线程
window.addEventListener('touchmove', handler, { passive: true });
```

Chrome 从 56 起，把 `touchstart` / `touchmove` / `wheel` 在 **window / document / body** 上的监听**默认设为 passive**。于是就有了这个经典现象：

```js
// ❌ 在 window 上无效：被动监听，preventDefault 被忽略，控制台有警告
window.addEventListener('touchmove', (e) => e.preventDefault());

// ✅ 显式声明非被动（请确认真的需要阻止滚动）
el.addEventListener('touchmove', (e) => e.preventDefault(), { passive: false });
```

更好的做法往往是**不用 JS 阻止滚动**，改用 CSS `touch-action`，让合成线程直接处理：

```css
/* 只允许纵向滚动，横向手势留给组件（如轮播） */
.carousel { touch-action: pan-y; }

/* 完全禁止手势（配合自定义拖拽） */
.draggable { touch-action: none; }
```

`touch-action` 在合成线程生效，不占主线程，比 `preventDefault` 干净得多。**只有需要"条件性"阻止时**（比如横向拖到边界才允许竖滚）才回到 `passive: false`。

## 4. 合成事件 vs 原生事件

React 17 起，事件不再挂在 `document`，而是挂在**根容器**（`createRoot` 的第一个参数）。这带来三个实际影响：

1. **顺序不同**：同一元素上，你在原生层注册的**捕获**监听先于 React 合成事件；React 的合成事件是在根容器上用原生冒泡模拟的。
2. **`e.stopPropagation()` 只作用于 React 的合成事件树**，阻止不了挂在容器外的原生监听——后者要在原生层 `stopPropagation`。
3. **多个 React 根共存时**，事件互不干扰：这正是 17 改挂载点的动机（微前端、渐进式迁移）。

```js
// 判断某元素属于哪个 React 根
const root = el.closest('[data-reactroot], #root');
```

另外两个常见记忆错误：`SyntheticEvent` 的对象池在 React 17 已移除，**不再需要** `e.persist()`；React 18 的自动批处理只影响 `setState` 的合并，与事件传播无关。

## 5. 中文输入法：必须处理 composition

输入中文时，用户按的每个拼音字母都会触发 `keydown` / `input`。如果在 `input` 里直接做搜索，会**拿拼音去查**（"nihao"），既浪费请求又体验糟糕。

```js
let composing = false;

input.addEventListener('compositionstart', () => { composing = true; });
input.addEventListener('compositionend', (e) => {
  composing = false;
  handleInput(e.target.value);   // 定稿后处理一次
});
input.addEventListener('input', (e) => {
  // 双保险：e.isComposing 在部分浏览器/场景下比自维护标记更可靠
  if (composing || e.isComposing) return;
  handleInput(e.target.value);   // 英文、粘贴、语音输入走这里
});
```

三个容易漏的细节：

- **Safari 的顺序差异**：`compositionend` 与最后一次 `input` 的先后在不同版本/输入法下不一致。双保险写法（自维护 `composing` + `e.isComposing`）能覆盖两种顺序。
- **React 受控组件的光标跳动**：合成期间如果把 `value` 回写（例如做格式化），光标会跳到末尾。合成期间只更新 state、不回写 DOM，`compositionend` 后再统一格式化。
- **粘贴与语音输入不触发 composition**，所以不能只在 `compositionend` 里处理，`input` 里的分支必须保留。

一个能直接用的搜索框版本：

```js
function debounce(fn, wait) {
  let t;
  return (...args) => {
    clearTimeout(t);
    t = setTimeout(() => fn(...args), wait);
  };
}

const search = debounce((kw) => {
  if (!kw.trim()) return;
  fetch(`/api/search?q=${encodeURIComponent(kw)}`);
}, 250);

let composing = false;
input.addEventListener('compositionstart', () => (composing = true));
input.addEventListener('compositionend', (e) => {
  composing = false;
  search(e.target.value);
});
input.addEventListener('input', (e) => {
  if (composing || e.isComposing) return;
  search(e.target.value);
});
```

## 6. 高频事件的性能处理

| 事件 | 触发频率 | 处理方式 |
| --- | --- | --- |
| `scroll` | 每帧多次 | 只读不算；`rAF` 合并；`passive: true` |
| `resize` | 拖拽时极高 | 防抖 100–200ms |
| `mousemove` / `pointermove` | 极高 | 节流到 `rAF`；只在拖拽期间监听 |
| `input` | 每次按键 | 防抖 200–300ms，注意 composition |
| `wheel` | 高 | `passive`；别在回调里同步读布局 |
| `deviceorientation` | 60Hz+ | 节流 + 只在需要时开启 |

`rAF` 合并比"每 N 毫秒执行"更贴合渲染节奏：

```js
let ticking = false;
window.addEventListener('scroll', () => {
  if (ticking) return;
  ticking = true;
  requestAnimationFrame(() => {
    updateHeader();     // 一帧最多算一次
    ticking = false;
  });
}, { passive: true });
```

现代写法可以用 `AbortController` 统一回收，避免组件销毁时漏解绑：

```js
const ac = new AbortController();

window.addEventListener('scroll', onScroll, { passive: true, signal: ac.signal });
window.addEventListener('resize', onResize, { passive: true, signal: ac.signal });

// 组件卸载时一行搞定
ac.abort();
```

## 7. 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| `preventDefault` 无效 | 被动监听（`passive: true`） | 显式 `{ passive: false }`，或改用 `touch-action` |
| 委托监听不到 `focus`/`hover` | 事件不冒泡 | 换 `focusin`/`mouseover`，或用捕获 |
| `stopPropagation` 后别人收不到 | 事件被截断 | 只在必要时阻止，优先判断来源 |
| 中文输入时搜索乱跳 | 没处理 composition | `compositionstart/end` + `e.isComposing` 双保险 |
| 中文输入后光标跳末尾 | 合成期间回写 `value` | 合成期间不回写 DOM |
| 移动端滚动"粘手" | `touchmove` 里有同步逻辑 | `passive` + 逻辑移到 `rAF` |
| 路由切换后点击失效 | 委托容器被重建 | 挂稳定父节点，或随组件重绑 |
| Shadow DOM 里委托失效 | 事件目标被重定向 | `e.composedPath()` 或 shadow 内部再委托 |
| 组件卸载后监听还在跑 | 忘了解绑 | `AbortController` + `{ signal }` |

## 9. 练习

1. **复现被动监听陷阱**：在 `window` 上加 `touchmove` 并 `preventDefault`，用移动端模拟看控制台警告；再加 `{ passive: false }` 对比。  
   *自检*：能解释"为什么浏览器默认不让 window 上的 touchmove 阻止滚动"，以及为什么 `touch-action` 更好。
2. **给委托加一个不冒泡事件**：用 `focus` 做委托（失败），再改 `focusin`（成功）。  
   *自检*：能列出至少 4 个不冒泡的事件名及各自的冒泡替代。
3. **输入法测试**：写一个带 debounce 的搜索框，用中文输入"你好"。  
   *自检*：不加 composition 守卫时请求数是 2–4 次（拼音），加守卫后应为 1 次；能说出 Safari 的顺序差异。
4. **量一次 passive 的收益**：在移动端模拟下，对比 `passive: true/false` 时 `touchmove` 回调的耗时与滚动手感。  
   *自检*：能说出"合成线程等待主线程"的具体链路。
5. **写一次 composedPath 委托**：在 shadow DOM 内部放一个带 `data-action` 的按钮，在外部用 `composedPath()` 接住点击。  
   *自检*：能解释为什么直接读 `e.target.dataset` 拿不到。
