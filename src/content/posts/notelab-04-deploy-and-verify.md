> [!NOTE]
> notelab 分组第四篇。前三篇讲的都是"怎么改"，这篇讲"改完之后，怎么证明线上真的是对的"。我的结论只有一句：**部署只是把字节搬上服务器，发布成功的唯一证据是验证**。这套自检三件套，是被两次假成功逼出来的。

## 知识地图

```
本地：commit + push
   ▼
服务器：git pull --ff-only
   ▼
构建：npm run build（前端）/ mvn package（后端）
   ▼
重启：pm2 restart（前端进程）/ java 进程重启
   ▼
验证三件套：
  ① HTTP 状态码 == 200
  ② 页面字节大小与上次发布同量级
  ③ 关键 CSS 类（如 opacity-55）真的进了生产 CSS
   ▼
视觉验收：系统 Chrome headless 截 SSR 渲染后的真实页面
```

## 一、标准链路，以及为什么 pull 必须 --ff-only

整条链路收敛到服务器上的几条命令：

```bash
ssh my-server
cd /root/notelab-c
git pull --ff-only
npm ci && npm run build
pm2 restart notelab-c
```

`--ff-only` 是这条链路里最重要的一个参数。没有它，当本地历史被 rebase 或 amend 过、和远端分叉时，pull 会静默生成一个 merge commit——把"我本机那半截没想清楚的旧代码"堂堂正正混进生产，而且构建还大概率能过。加了它，分叉时 pull 直接失败，逼你先处理历史再部署。

**宁可部署失败，也不部署一个来历不明的合并节点。** 部署失败是一分钟的事，回滚一个说不清来源的 merge commit 是半天的事。

后端仓库的链路略有不同：`mvn -DskipTests package` 之后重启 java 进程，别忘了一篇讲过的教训——构建输出重定向到文件再看退出码，接管道会把它吃掉。前端的两个进程由 pm2 守护，重启命令固定写进部署脚本，不敲第二遍：任何"发布日手抖"的命令都应该活在脚本里，而不是活在当天的记忆里。

## 二、验证一和验证二：状态码 + 字节大小

**第一项：HTTP 状态码必须真的等于 200。** 这条听着像废话，直到我踩了第五节的 CI 假 success。现在验证脚本是这么写的：

```bash
#!/bin/bash
set -e
url="$1"
code=$(curl -s -o /tmp/page.html -w '%{http_code}' "$url")
if [ "$code" != "200" ]; then
  echo "FAIL: expect 200, got $code"; exit 1
fi
echo "bytes: $(wc -c < /tmp/page.html)"
```

**第二项：页面字节大小与上次发布同量级。** 每次发布后把字节数记进 release.log，和上次比：

| 现象 | 字节大小信号 |
|---|---|
| 首页正常更新 | 与上次同量级，±10% 以内 |
| SSR 降级成骨架屏 / 白屏 | 骤降到几 KB |
| 404 页面被当成了首页返回 | 骤降到固定小值 |
| 误把调试数据渲染进页面 | 异常膨胀 |

它不是精确指标，但它是**最便宜的"页面没白"信号**——一条 `wc -c` 命令，就能在用户投诉之前发现一半的发布事故。反过来，200 加上字节数正常，也还有漏网的坑，这就是第三项存在的理由。

release.log 的记录也要脚本化：发布脚本最后一行追加 `date + commit hash + 字节数`，检查动作和记录动作写在同一处才不会被遗忘。人肉流程会褪色，脚本不会。

## 三、验证三：Tailwind 任意值类进没进生产 CSS

这个坑最阴：本地 dev 里 `opacity-55` 这类任意值类明明是好的，上线后样式就是没生效——类名根本没进生产 CSS 产物。dev 和 build 的 CSS 生成策略有差异，肉眼在本地看不出任何问题。

验证方式很直接：构建产物里 grep 类名。

```bash
cd /root/notelab-c
grep -o 'opacity-55' .next/static/css/*.css | head -1
# 有输出：类进了产物，安心
# 无输出：类没进产物，页面一定不对 → 直接回滚，别指望肉眼
```

Next.js 的 CSS chunk 是哈希文件名，所以用通配符扫全部。这个动作已经进了我的发布清单：**凡是用到任意值类或低频类的改动，发布后必须 grep 一次**。它把"上线后用户说样式不对"这种最难定位、反馈周期最长的故障，提前变成了一条可判定的命令。

为什么任意值类会漏？Tailwind 生产构建靠扫描源码决定生成哪些类，动态拼接的类名（比如 `opacity-${level}`）在源码里不存在完整字面量，扫描器看不见它。dev 环境按需即时生成的宽松策略掩盖了这一点——你在本地永远"看得到"样式，因为 dev 根本不是在生产模式下生成 CSS。根治办法是把会用到的任意值类完整写在源码某处、或进安全清单；发布后的 grep 则是最后一道保险丝。

## 四、视觉验收：系统 Chrome headless 截图

截图有两个流派：本地起 dev server 截，或者截线上真实页面。我坚持后者——**dev server 的数据源、环境变量、字体和线上都可能不同，截出来的"正确"不算数**。要截就截服务器 SSR 渲染后的真实产物。

不需要装 Playwright，系统自带的 Chrome 就够了（Git Bash 下的 Windows 路径写法）：

```bash
"/c/Program Files/Google/Chrome/Application/chrome.exe" \
  --headless=new --disable-gpu \
  --virtual-time-budget=8000 \
  --screenshot=verify.png --window-size=1440,900 \
  https://notelab.example.com/
```

两个参数的用意：`--virtual-time-budget=8000` 给 SSR 流式响应和首屏 JS 八秒执行预算，否则截到的是半渲染状态；`--window-size` 固定视口，保证不同天的截图横向可比。截完肉眼过一遍，重点看首屏和几个配置驱动的区块（Hero、爬塔入口）——它们是从 ui_config 读的，恰好是这套架构里最容易因为配置问题而变形的地方。

顺带说截图的存放：verify.png 存在本地临时目录，不进仓库。它是验证证据，不是资产——截图进了仓库，下一次构建就会把它打成产物的一部分，"验证物污染产物"的循环我见过一次，清理起来相当滑稽。

## 五、两个踩坑复盘

**坑一：CI 假 success。** 最早的验证脚本是 `curl https://... > /dev/null`，然后判断"命令没报错就是发布成功"。但 curl 对 404、500 默认都算成功——退出码 0，页面是错的，CI 亮着绿灯，我盯着绿灯睡觉去了。修复三件套：脚本加 `set -e`；curl 加 `-w '%{http_code}'` 显式比对状态码；任何不匹配都 `exit 1`。教训刻成一句话：**CI 的绿色只代表脚本退出码是 0，不代表页面是对的**。

同一个坑还有个变体：`curl -f` 能挡住非 2xx，但挡不住"200 但内容是错的"——比如网关层把上游 500 转成了 200 的错误页。这就是三件套要三项而不只一项的原因：状态码拦网络层错误，字节大小拦渲染层塌方，CSS 类 grep 拦构建差异。三层各拦一类问题，谁也不能替代谁。

**坑二：本地与服务器 node 版本不一致。** 本地 node 22、服务器 node 20，同一个 commit 构建出来的 CSS chunk 哈希对不上，某些类的生成行为也有差异——"本地验证过了、线上没过"就是这么来的，而且两次现象还不完全一样，排查时根本没往版本上想。对策：仓库里加 `.nvmrc` 固定版本，服务器部署脚本第一步 `nvm use`，版本不对直接中止构建。教训同样一句话：**构建产物是 node 版本的函数，版本不一致时，你验证的和上线的根本不是同一个东西**。

## 小结

- `git pull --ff-only`：宁可部署失败，不进来历不明的 merge commit。
- 三件套里前两项（状态码、字节大小）是通用底线，第三项（关键 CSS 类 grep）是前端特有的坑。
- 视觉验收截线上 SSR 产物，不截本地 dev server——数据源不同，正确性不可迁移。
- 两个坑的共同根因是**验证了错误的对象**：CI 验证的是退出码，本地验证的是另一个 node 版本的产物。
- 验证动作要可判定：一条命令、一个退出码，不靠"看着还行"。

## 练习

1. 把验证三件套写成一个 `verify.sh`，接受 URL 和期望的 CSS 类名做参数，任一项失败 exit 1，接到发布脚本末尾。
2. 给 release.log 加日期与 commit hash 字段，写一个对比脚本输出与上次发布的字节差异百分比。
3. 故意把服务器 node 切到错误大版本构建一次，diff 两份产物，亲眼看一次"版本漂移"。
4. 用 `--virtual-time-budget` 分别取 0 和 8000 各截一张图，对比半渲染与完整渲染的差别。
