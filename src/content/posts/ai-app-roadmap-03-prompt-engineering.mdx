> [!NOTE]
> Prompt 是 AI 应用里唯一"没有类型检查的代码"。改一个词，线上行为可能天翻地覆，而 git diff 里只显示一行字符串变化。这篇的核心观点：**把 Prompt 当一等公民的代码资产管理**——有版本、有测试、有变更记录。以下所有经验来自我知识库翻译/摘要功能的真实迭代史。

## 1. 系统提示词设计

### 1.1 我的四段式模板

看了几十篇"提示词圣经"之后，我沉淀下来一个稳定的结构，自己称为四段式：

```
[角色]   你是谁、为谁服务
[任务]   做什么、输出什么形式
[约束]   不做什么、边界在哪
[示例]   1-3 个输入输出对（可选）
```

真实例子——我知识库的摘要功能 system prompt（简化版）：

```
你是技术文档摘要助手。
任务：将输入的技术文章压缩为 3 条要点，每条不超过 30 字，
输出 JSON 数组：[{"point": "..."}]。
约束：
- 只使用原文出现的技术名词，不要引入新概念
- 原文没有的内容不要编造；信息不足时输出 []
```

设计原则（全部来自翻车教训）：

1. **任务动词要具体**。"帮我总结一下"→"压缩为 3 条要点，每条不超过 30 字"。越可验收，输出越稳。
2. **约束比指令更常被违反，所以放后面、逐条列**。模型的注意力对列表项更敏感。
3. **给失败出口**。"信息不足时输出 []"让模型有路可退，否则它会硬编。这句话帮我消灭了大约一半的幻觉摘要。
4. **别堆客套话**。"你是一个乐于助人的AI助手"对输出质量没有任何可测量的影响，纯浪费输入 token（01 篇说过，system 每轮都计费）。

### 1.2 一个反直觉的经验：Prompt 不是越长越好

我最早的摘要 Prompt 写了 2000 字，塞满了各种注意事项。后来逐步删到 300 字，输出质量反而更好、更稳定。原因有二：超长指令内部自相矛盾的概率大增（写着写着忘了前面说过什么）；约束越多模型越容易"平均化"各条约束，最后哪条都做得平庸。**每一句 Prompt 都应该能回答"删掉它输出会变差吗"，答不上来的就删。**

### 1.3 system prompt 的 token 预算

既然 system 每轮重发、按输入计费（01 篇），它就该有预算约束。我的规则：**system prompt 控制在 400 token 以内，例外必须说明理由**。预算约束带来的克制是真实的收益——你会开始用更短的句子表达同样的约束，而短句恰好是模型遵循度更高的形式。

超预算的常见原因和处理：塞了大量"注意事项"（合并同类项，五条注意事项通常能并成两条）；写了大段背景介绍（模型不需要知道你的产品愿景，只需要知道它的任务）；few-shot 例子放在了 system 里（挪到 messages 尾部，配合第 5 节的顺序策略效果更好，还方便按请求动态换例子）。把 2000 字删到 300 字的经历让我确信：**写 Prompt 的能力和删 Prompt 的能力，后者更稀缺。**

## 2. Few-shot：例子的选择比数量重要

few-shot 就是在 messages 里伪造几轮对话当示例：

```ts
const messages = [
  { role: "system", content: SYSTEM_PROMPT },
  { role: "user", content: "原文：React 的 useEffect 在渲染后异步执行……" },
  {
    role: "assistant",
    content: '[{"point":"useEffect 在渲染后异步执行"},{"point":"…"}]',
  },
  { role: "user", content: actualInput },
];
```

我的三条筛选标准：

1. **例子必须来自真实数据分布**。用编造的短例子，遇到真实长文时模型输出格式就漂移。我从历史真实文章里挑了 3 篇不同长度、不同结构的做样本。
2. **包含一个边界例子**。比如一篇"信息量极小"的文章，期望输出 `[]`——这一条例子教会模型"可以拒绝"。
3. **例子里的格式 100% 合法**。示例 JSON 少个引号，模型会学得一模一样。

注意成本：3 个 few-shot 例子如果各占 400 token，system 区块瞬间 1500+，每次调用都重复付费。**例子能压缩就压缩**，我最后把示例原文截断到每篇 200 字，效果几乎无损。

## 3. 思维链：有用的场景与浪费钱的场景

思维链（CoT）就是在 Prompt 里要求"先分析再作答"，或者给一个带推理的示例。

**有效场景**：判断类、比较类、多步计算类。比如我的"文章质量打分"功能，要求模型先列出优缺点再给分数，分数的稳定性明显提升——因为先写出来的分析会约束最后结论，等于给了模型一次自我校对。

**浪费钱场景**：抽取、翻译、格式转换。这类任务的中间推理没有任何信息增量，你只是在为多出来的输出 token 付费。我测试过让翻译功能"先分析句子结构再翻译"，质量零提升，成本 +80%。

一个折中技巧：需要 CoT 但不想暴露推理过程时，用两段式——第一次调用带 CoT，第二次调用把第一次的推理喂进去只取最终答案（或者用部分模型的 reasoning_content 字段，它通常不计入你的展示层，但注意有些平台推理 token 也计费）。

## 4. 提示词版本管理

这是我最想安利的一节。Prompt 改动导致的线上回归，我经历过两次大事故（摘要格式从 JSON 漂移成了 markdown，前端渲染全挂），之后我建立了这套流程：

### 4.1 Prompt 存代码仓库，当配置管理

```ts
// prompts/index.ts —— 集中存放，导出带版本号
export const SUMMARY_PROMPT_V3 = `你是技术文档摘要助手。
任务：将输入的技术文章压缩为 3 条要点……`;

export const PROMPTS = {
  summary: { current: SUMMARY_PROMPT_V3, fallback: SUMMARY_PROMPT_V2 },
} as const;
```

- 每次改动开 PR，diff 一目了然，其他工程师能 review
- 版本号进变量名，出问题可秒级回滚到 fallback
- 别放数据库然后在线编辑——除非你打算给 Prompt 也写权限管理和审批流

### 4.2 变更必跑评测集

我从历史文章里固定抽了 30 篇做评测集（10 篇常规 + 10 篇长文 + 10 篇信息量低的边界样本）。任何 Prompt 改动，先跑一遍这 30 篇，输出和上一版对比。10 篇内容会讲怎么把这个流程自动化，这里只强调纪律：**没有跑过评测集的 Prompt 变更，不配上生产。** 这句话跟"没有测试的代码不许合并"一样朴实。

### 4.3 一个真实的回归事故复盘

为了让你理解这套流程为什么值得，完整复盘我经历过的那次事故：

某天我为了让摘要"更有信息量"，在 Prompt 里加了一句"尽量提取数字和版本号"。改动本身方向没错，PR 里 diff 只有一行。但没跑评测集就直接发布了。结果：模型开始把"要点提取"理解成"信息罗列"，输出从 JSON 数组漂移成了带编号的文本，前端 Zod 校验全部失败，走降级路径——全站摘要变成了"正文前 200 字截断"的简版，持续了 11 个小时才发现。

这次事故之后的三个产出：一是 30 条固定评测集（当时一条都没有）；二是"改 Prompt 必跑评测"写进了团队约定；三是 Zod 失败率上了监控告警（11 篇会讲失败率报表）。一句话总结：**Prompt 的事故现场没有堆栈，评测集就是你的堆栈。**

## 5. 一份可抄的 Prompt 迭代节奏

最后给出我目前实际在用的迭代节奏，直接抄走即可：

1. **有想法先记进 issue**，写清楚"当前哪里不满意、期望什么行为"，附 1-2 个真实样本
2. **在分支上改 Prompt**，跑评测集对比新旧通过率，把对比结果贴进 PR
3. **通过率不降 + 目标样本改善**才合并，合并即生效（配置文件随代码部署）
4. **上线后一周内**人工抽看 10 条真实输出（10 篇的评审表），异常随时回滚到上一版本号

这个节奏让我的 Prompt 迭代从"凭感觉"变成了"看数据"，改动频率大概每周一次，但每一次都有据可查、可回滚。

## 5. Few-shot 的顺序与位置：一个容易忽略的变量

few-shot 还有一个几乎没人讨论但实测有影响的变量：**例子的排列顺序和位置**。模型对上下文开头和结尾的内容注意力最强（中间部分相对弱），这就是所谓的"lost in the middle"现象。由此得到两个实用推论：

第一，**最重要的例子放最后**——紧挨着真实输入的位置。我的三例布局是：常规例子、边界例子（可以拒绝的那种）、然后是与目标任务形态最接近的例子。调整这个顺序前后，我的摘要格式稳定率有肉眼可见的差别。

第二，**例子和真实输入之间要有明确的分隔信号**。我在最后一个 few-shot 例子之后加一行 user 消息"以下是待处理的实际内容"，再接真实输入。没有这个分隔时，偶尔会出现模型把真实输入当成第三个例子的续写，输出完全跑偏——这种偶发问题非常难排查，因为十次里可能只出现一次。

另外补充一个反直觉的观察：**当任务已经很明确时，加例子反而可能有害**。我发现当 few-shot 例子里恰好有某种句式特征（比如例子原文都是短句），模型处理长句时会不自觉地向例子的风格靠拢，损害了对真实输入的适配。所以例子不是越多越好，我的迭代方向一直是"从 5 个例子减到 3 个，再从 3 个减到 2 个加一行分隔说明"。每加一个例子都问一遍：它教会模型的，是任务本身，还是例子的偏见？

---

## 小结

- 系统提示词用四段式（角色/任务/约束/示例），动词具体、给失败出口、删掉所有可有可无的话。
- few-shot 例子来自真实数据分布，包含一个边界样本，格式绝对合法，并控制 token 体积。
- CoT 只对判断/多步类任务有用，抽取翻译类用了纯烧钱。
- Prompt 当代码管理：进仓库、走 PR、带版本、可回滚、变更必跑评测集。

---

## 练习

1. 把你现在正在用的一段 Prompt 改写成四段式，逐句问自己"删掉它输出会变差吗"，砍掉一半。
2. 为你的任务挑 3 个真实 few-shot 例子，其中 1 个必须是边界样本。
3. 建一个 `prompts.ts` 文件集中管理你的提示词，给当前版本标 v1。
4. 固定 10 条测试输入存成文件，作为你的第一个迷你评测集——第 10 篇会把它扩展成完整方案。
