交付前分别回答两个问题。AI 提取的字段和缺项对不对？这些配置经过审核后，线上接口会不会向预期用户展示正确 Banner？用独立的评测和端到端用例回答它们。

## 1. 固定评测样本再调模型

先将 `AI_PROVIDER` 设为 `mock`，在项目目录执行：

```bash
npm test
npm run eval
npm run smoke
```

纯规则测试检查版本、排期和素材。评测读 `eval-cases.json` 的五条基线，检查预期字段、样本中缺失的字段是否仍为空、应追问内容是否出现。冒烟测试起独立 MySQL 测试工作台，检查角色、预演、发布冲突、关联提案和下线回退。三个命令分别以非零退出码表示失败，可以接入 CI。

固定评测样本后，把供应商或模型 ID 改为真实配置再执行 `npm run eval`，保留两份 JSON 输出。归因时先核对 `wrong` 和 `invented`，再看 `questionOk`。保留最小复现输入、预期、实际输出、提示词版本和耗时。命中的文案可继续人工检查，尤其留意是否许诺了运营未提供的优惠。

给样本集加一次可控变化。复制一条通过案例，将 2.5.0 改为 2.10.0，再把「已激活」条件改成「含未激活」。先写裁决预期，再跑评测。增加一句不在识别规则中的口语表达，检查它是否触发待确认，或出现意外的肯定判断。把发现的问题保留成后续回归用例。

## 2. 用同一套场景演示两条流程

| 操作 | 要留的验收证据 |
| --- | --- |
| 手工和 AI 辅助各创建一次同样的活动 | 记录从读需求到提交审核的耗时和修改字段数。 |
| 两份草稿分别预演 | 对照同一份人工人员清单，统计误投候选和漏投候选。 |
| 审核员发布后用 u01、u02 查询 | u01 看到定向教程，u02 看到通用引导。 |
| 并行发布两条重叠同优先级活动 | 保留一个成功、一个 409 的接口结果及审计记录。 |
| 下线本次活动 | 在同一演练时点，u01 恢复看到通用引导。 |

对比耗时时固定同一个计时起止点。可以选几条新需求交叉演练，交换做手工流程和 AI 流程的顺序。这样记录能拆出生成、改动和审核各自花的时间，也能指出哪种需求更适合交给模型起草。

## 3. 在单机做一次私有内测

在测试主机或本机单独建运行目录，复制完整源码，执行 `npm ci`。为测试账号生成两把不同密钥，填进 `.env` 的 `OPERATOR_KEY` 和 `REVIEWER_KEY`。

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

设置 `APP_MODE=production` 后，程序检查两把密钥都至少 32 字符。由运维提供单独的 MySQL 数据库及服务账号，可使用同机回环地址。用非管理员账号运行 `node --env-file=.env server.mjs`，工作目录指向源码目录，并限制环境文件访问范围。服务默认监听回环地址。远端演练可通过 SSH 转发访问私有工作台：

```bash
ssh -N -L 8790:127.0.0.1:8790 你的测试主机
```

本机浏览器打开 `http://127.0.0.1:8790/`。先查健康接口，再用两个角色完成演示。需要长期运行时，由测试机上的服务管理器托管同一启动命令。此版使用合成数据、两个固定角色与一个投放位，适合封闭演练。

备份演练用 `mysqldump --single-transaction --no-tablespaces --set-gtid-purged=OFF` 导出 InnoDB 表。由数据库管理员建一个空恢复库，导入后修改独立实例的 `DB_NAME`，重新查刚才的活动、审计和关联 AI 建议。备份期间暂停表结构变动。业务上的紧急恢复优先演练下线本次活动，确认通用引导能继续投放。 [MySQL 备份工具](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)

## 毕业验收

- [ ] 从空工作目录完成依赖安装、初始化和运行，并保留 README 式启动记录。
- [ ] 演示一次 AI 生成、确认、预演、审核、发布与下线。
- [ ] 提供一份失败样本分析、一份并发发布记录、一份跑得通的评测结果。
- [ ] 在测试环境分别复验重启读回和独立数据库恢复。
