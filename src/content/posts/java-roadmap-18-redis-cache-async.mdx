> [!NOTE]
> 阶段十七把 task-center 的回归测试补齐了，其中一条用例断言「查询不存在返回 404」。这一篇把同一个查询放进缓存，于是测试要回答的问题变了：**命中缓存的时候，这条用例还能证明什么**。
>
> 全文只做两件能当场验证的事。一是用 Docker 起一个 Redis，把 `GET /api/tasks/{id}` 改成「查缓存 + 逻辑过期 + 互斥重建」，用 `redis-cli` 和两条并发 curl 看它究竟什么时候碰库。二是把「导出任务」做成先落表、再进线程池的异步任务：核心 2、队列 8、最大 4，用一批并发请求把 `CallerRunsPolicy` 逼出来，看它把活退回给 Tomcat 线程之后，接口到底付出了什么。
>
> 数字只出现在两类地方：配置值（线程池参数、TTL 是我定的）和某一次运行的输出。不承诺命中率、QPS、耗时，那些必须在同一台机器、同一份数据、同一个并发模型下自己测。中间件版本写死为 Redis 7.4、Spring Boot 3.x、JDK 21，换版本结论可能变。

## 一、先跑起来

先解决两个环境问题。缓存要有独立的 Redis，不能和本机开发用的实例混在一起，否则 `FLUSHDB` 一敲别人的数据就没了；异步导出要有真实的耗时窗口，否则线程池还没满，任务已经跑完，拒绝策略永远观察不到。

工程侧只加两个依赖。`task-center` 仍是 Maven 3.9 加 JDK 21，版本交给 Boot 3.x 的 BOM，不要自己写死：

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<!-- Lettuce 的连接池要它才生效；缺了它，spring.data.redis.lettuce.pool 会被静默忽略 -->
<dependency>
  <groupId>org.apache.commons</groupId>
  <artifactId>commons-pool2</artifactId>
</dependency>
```

第一条带来 `StringRedisTemplate`、`RedisTemplate` 和 Lettuce 客户端。第二条容易被忘：没有 `commons-pool2` 时，Boot 仍然能建连接工厂，只是**不会用连接池**，你写的 `max-active`、`min-idle` 全部无效，压测时表现为「连接数怎么调都不变」。

### 1. 一个容器，两个观察口

```yaml title="task-center/docker-compose.redis.yml"
services:
  redis:
    image: redis:7.4-alpine
    container_name: redis-lab
    command:
      - redis-server
      - --appendonly
      - "yes"
      - --maxmemory
      - 256mb
      - --maxmemory-policy
      - allkeys-lru
      - --requirepass
      - lab123456
    ports:
      - "6380:6379"
    volumes:
      - redis-lab-data:/data
volumes:
  redis-lab-data:
```

映射到 6380 是为了和你本机可能已有的 6379 隔开。`--maxmemory-policy allkeys-lru` 是学习环境下的自保：实验里出现无 TTL 的 key 也不会把内存吃光；生产上这等于「内存满时随机淘汰业务缓存」，要不要用它取决于你能不能接受缓存被淘汰——大多数读缓存可以，锁和队列不行，所以锁的 key 必须带 TTL，这一点后面会反复出现。

```bash
docker compose -f docker-compose.redis.yml up -d
docker compose -f docker-compose.redis.yml exec redis-lab \
  redis-cli -a lab123456 --no-auth-warning INFO server | head -6
```

输出：第一行是 `# Server`，随后能看到 `redis_version:7.4.x` 和 `tcp_port:6379`。容器内的端口永远是 6379，6380 只是宿主机的映射，两个数字别混。`--no-auth-warning` 只是压掉「用 -a 传密码不安全」的提示，生产上应该用 `REDISCLI_AUTH` 环境变量。

先手动验证一次「加锁」这件事在协议层是什么样：

```bash
docker compose -f docker-compose.redis.yml exec redis-lab \
  redis-cli -a lab123456 --no-auth-warning SET lock:demo token-a NX PX 3000
docker compose -f docker-compose.redis.yml exec redis-lab \
  redis-cli -a lab123456 --no-auth-warning SET lock:demo token-b NX PX 3000
docker compose -f docker-compose.redis.yml exec redis-lab \
  redis-cli -a lab123456 --no-auth-warning PTTL lock:demo
```

输出：第一条 `OK`，第二条 `(nil)`，第三条是一个小于 3000 的毫秒数（剩余存活时间）。这三行说明了两件事：`NX` 是「不存在才写」，`PX` 是「同时设过期」，两个语义在同一条命令里完成；第二条失败时没有覆盖已有值，也没有改动它的 TTL。

### 2. 查询走缓存：逻辑过期与互斥重建

要改的第一个文件是缓存里存什么。不能只存 `Task` 的 JSON，因为「逻辑过期」需要把业务过期时间写进 value 里，让读的人自己判断新旧。

```java title="task-center/src/main/java/com/demo/taskcenter/cache/CachedTask.java"
package com.demo.taskcenter.cache;

import com.demo.taskcenter.task.Task;

/**
 * task 为 null 表示「这个 id 确实不存在」，即空值缓存，用来挡穿透。
 * softExpireAt 是业务意义上的过期时刻，和 Redis 的物理 TTL 无关。
 */
public record CachedTask(Task task, long softExpireAt) {
}
```

锁单独成一个组件，因为后面导出任务、定时任务都会用到它。三个方法对应三件事：抢锁、续期、比对 token 之后删除。

```java title="task-center/src/main/java/com/demo/taskcenter/cache/RedisLock.java"
package com.demo.taskcenter.cache;

import java.time.Duration;
import java.util.List;
import java.util.UUID;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.stereotype.Component;

@Component
public class RedisLock {

    /** 比较 token 再删除：GET 与 DEL 合成一个原子步骤，避免删掉别人的锁 */
    private static final DefaultRedisScript<Long> UNLOCK = new DefaultRedisScript<>("""
            if redis.call('get', KEYS[1]) == ARGV[1] then
              return redis.call('del', KEYS[1])
            end
            return 0
            """, Long.class);

    /** 续期同样要校验 token，否则会把已经易主的锁续上 */
    private static final DefaultRedisScript<Long> RENEW = new DefaultRedisScript<>("""
            if redis.call('get', KEYS[1]) == ARGV[1] then
              return redis.call('pexpire', KEYS[1], ARGV[2])
            end
            return 0
            """, Long.class);

    private final StringRedisTemplate redis;

    public RedisLock(StringRedisTemplate redis) {
        this.redis = redis;
    }

    /**
     * SET key value NX PX ttl 一条命令完成，不存在「先设值、再设过期」的空档。
     * 返回 token 表示抢到，返回 null 表示别人持有。
     */
    public String tryLock(String name, Duration ttl) {
        String token = UUID.randomUUID().toString().replace("-", "");
        Boolean ok = redis.opsForValue().setIfAbsent(key(name), token, ttl);
        return Boolean.TRUE.equals(ok) ? token : null;
    }

    public boolean renew(String name, String token, Duration ttl) {
        Long renewed = redis.execute(RENEW, List.of(key(name)), token, String.valueOf(ttl.toMillis()));
        return renewed != null && renewed == 1L;
    }

    public boolean unlock(String name, String token) {
        Long removed = redis.execute(UNLOCK, List.of(key(name)), token);
        return removed != null && removed == 1L;
    }

    private String key(String name) {
        return "lock:" + name;
    }
}
```

读路径是这一篇的核心。三条分支对应三种时间状态：新鲜、逻辑过期、没有。注意它**没有**给读请求加同步排队：逻辑过期分支在抢不到锁时直接返回旧值。

```java title="task-center/src/main/java/com/demo/taskcenter/cache/TaskCacheService.java"
package com.demo.taskcenter.cache;

import com.demo.taskcenter.task.Task;
import com.demo.taskcenter.task.TaskMapper;
import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import java.time.Duration;
import java.util.concurrent.ThreadLocalRandom;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.support.TransactionSynchronization;
import org.springframework.transaction.support.TransactionSynchronizationManager;

@Service
public class TaskCacheService {

    private static final Logger log = LoggerFactory.getLogger(TaskCacheService.class);

    private static final String PREFIX = "task:v1:detail:";
    /** 空值缓存必须短：它挡穿透，但也会让「刚创建的数据」短暂查不到 */
    private static final Duration NULL_TTL = Duration.ofSeconds(30);
    /** 物理过期 = 逻辑过期 + 这段余量，保证逻辑过期那条分支永远能走到 */
    private static final long HARD_EXTRA_MS = 25L * 60L * 1000L;
    private static final Duration LOCK_TTL = Duration.ofSeconds(3);

    private final StringRedisTemplate redis;
    private final ObjectMapper json;
    private final TaskMapper mapper;
    private final RedisLock lock;
    private final long softTtlMs;

    public TaskCacheService(StringRedisTemplate redis,
                            ObjectMapper json,
                            TaskMapper mapper,
                            RedisLock lock,
                            @Value("${app.cache.soft-ttl-ms:300000}") long softTtlMs) {
        this.redis = redis;
        this.json = json;
        this.mapper = mapper;
        this.lock = lock;
        this.softTtlMs = softTtlMs;
    }

    public Task findById(long id) {
        String key = PREFIX + id;
        CachedTask cached = read(key);
        if (cached != null && cached.softExpireAt() > System.currentTimeMillis()) {
            log.debug("cache hit id={} remainMs={}", id, cached.softExpireAt() - System.currentTimeMillis());
            return cached.task();
        }
        if (cached != null) {
            log.info("cache stale id={}", id);
            return rebuild(id, key, cached.task());
        }
        log.info("cache miss id={}", id);
        return rebuild(id, key, null);
    }

    /**
     * stale 非 null 时走「逻辑过期」：抢不到锁就返回旧值，请求不排队。
     * stale 为 null 时走「互斥重建」：抢不到锁短暂停顿后再读一次，仍没有就降级查库。
     */
    private Task rebuild(long id, String key, Task stale) {
        String lockName = "cache:detail:" + id;
        String token;
        try {
            token = lock.tryLock(lockName, LOCK_TTL);
        } catch (RuntimeException e) {
            // Redis 不可用时锁也拿不到，这里直接降级，不把异常抛给接口
            log.warn("lock unavailable id={} fallback to db", id, e);
            return mapper.findById(id);
        }
        if (token == null) {
            if (stale != null) {
                log.info("cache stale served id={} rebuilding elsewhere", id);
                return stale;
            }
            pauseBriefly();
            CachedTask retried = read(key);
            if (retried != null) {
                return retried.task();
            }
            log.warn("cache rebuild skipped id={} fallback to db", id);
            return mapper.findById(id);
        }
        try {
            CachedTask doubleCheck = read(key);
            if (doubleCheck != null && doubleCheck.softExpireAt() > System.currentTimeMillis()) {
                return doubleCheck.task();
            }
            return loadAndStore(id, key);
        } finally {
            try {
                if (!lock.unlock(lockName, token)) {
                    // 走到这里说明业务耗时超过了 LOCK_TTL，锁已经易主
                    log.warn("cache rebuild lock lost id={}", id);
                }
            } catch (RuntimeException e) {
                log.warn("cache rebuild unlock failed id={}", id, e);
            }
        }
    }

    private Task loadAndStore(long id, String key) {
        Task task = mapper.findById(id);
        long now = System.currentTimeMillis();
        long softExpireAt = now + (task == null ? NULL_TTL.toMillis() : softTtlMs);
        Duration physicalTtl = task == null
                ? NULL_TTL
                : Duration.ofMillis(softTtlMs + HARD_EXTRA_MS
                        + ThreadLocalRandom.current().nextLong(60_000L));
        try {
            redis.opsForValue().set(key, json.writeValueAsString(new CachedTask(task, softExpireAt)),
                    physicalTtl);
        } catch (JsonProcessingException | RuntimeException e) {
            // 缓存写失败只记日志：这次请求还能返回，下一次再回填
            log.warn("cache write failed key={}", key, e);
        }
        log.info("cache filled id={} found={} physicalTtlMs={}", id, task != null,
                physicalTtl.toMillis());
        return task;
    }

    public void evict(long id) {
        try {
            redis.delete(PREFIX + id);
        } catch (RuntimeException e) {
            log.warn("cache evict failed id={}", id, e);
        }
    }

    /** 事务提交后再删：提交前删会被并发读用旧值重新填回去 */
    public void evictAfterCommit(long id) {
        if (!TransactionSynchronizationManager.isSynchronizationActive()) {
            evict(id);
            return;
        }
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                evict(id);
            }
        });
    }

    private CachedTask read(String key) {
        try {
            String raw = redis.opsForValue().get(key);
            return raw == null ? null : json.readValue(raw, CachedTask.class);
        } catch (JsonProcessingException | RuntimeException e) {
            // 反序列化失败当未命中处理：宁可查库，也不要让脏 value 一直报错
            log.warn("cache read failed key={}", key, e);
            return null;
        }
    }

    private void pauseBriefly() {
        try {
            Thread.sleep(30L + ThreadLocalRandom.current().nextLong(20L));
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

等过 20 秒再并发查两次，看逻辑过期分支：

```bash
sleep 21
curl -s http://127.0.0.1:8081/api/tasks/1 > /dev/null &
curl -s http://127.0.0.1:8081/api/tasks/1 > /dev/null &
wait
```

输出示例：日志里出现一行 `cache stale id=1`，随后是 `cache filled id=1 found=true ...`；另一个请求可能是 `cache stale served id=1 rebuilding elsewhere`。两次都出现 `cache stale` 也正常——第一个重建在第二个请求到达前就结束了，这恰好说明逻辑过期的代价很小。要稳定复现「返回旧值」的分支，可以在 `loadAndStore` 前临时加一段睡眠，或者在 `redis-cli` 里手工把软过期时间改早。

### 3. 异步导出：先落表，再排队

导出不是一个 tick 能做完的事，所以先给它一张表。状态机的四个状态不是为了好看，是为了让「谁在执行」「失败了几次」「能不能重试」都能用一条 SQL 查出来。

```sql
-- task-center/src/main/resources/db/migration/V4__export_task.sql
CREATE TABLE export_task (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  status      VARCHAR(16)     NOT NULL DEFAULT 'PENDING',
  attempts    INT             NOT NULL DEFAULT 0,
  file_path   VARCHAR(200)    NULL,
  last_error  VARCHAR(300)    NULL,
  created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP
                              ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_export_status (status, attempts)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

Mapper 里最关键的是 `markRunning` 的 WHERE 条件：它同时承担「认领」和「状态迁移」两件事，返回影响行数为 0 就说明这个任务已经被别人领走或已经结束。这一条条件更新比一把会过期的锁更可靠——它的原子性由数据库的 UPDATE 保证，而且不会因为进程停顿而失效。

```java title="task-center/src/main/java/com/demo/taskcenter/export/ExportTaskMapper.java"
package com.demo.taskcenter.export;

import java.util.List;
import org.apache.ibatis.annotations.Insert;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Options;
import org.apache.ibatis.annotations.Param;
import org.apache.ibatis.annotations.Select;
import org.apache.ibatis.annotations.Update;

@Mapper
public interface ExportTaskMapper {

    @Insert("INSERT INTO export_task(status, attempts) VALUES('PENDING', 0)")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int insert(ExportTask task);

    @Select("""
        SELECT id, status, attempts, file_path, last_error, created_at
        FROM export_task WHERE id = #{id}
        """)
    ExportTask findById(@Param("id") long id);

    /** 认领：只有 PENDING/FAILED 且次数没用完的行能被改成 RUNNING */
    @Update("""
        UPDATE export_task
        SET status = 'RUNNING', attempts = attempts + 1
        WHERE id = #{id} AND status IN ('PENDING', 'FAILED') AND attempts < 3
        """)
    int markRunning(@Param("id") long id);

    @Update("""
        UPDATE export_task SET status = 'SUCCEEDED', file_path = #{filePath}
        WHERE id = #{id}
        """)
    int markSucceeded(@Param("id") long id, @Param("filePath") String filePath);

    @Update("""
        UPDATE export_task SET status = 'FAILED', last_error = #{error}
        WHERE id = #{id}
        """)
    int markFailed(@Param("id") long id, @Param("error") String error);

    @Select("""
        SELECT id FROM export_task
        WHERE status IN ('PENDING', 'FAILED') AND attempts < #{maxAttempts}
        ORDER BY id LIMIT #{limit}
        """)
    List<Long> findRetryable(@Param("maxAttempts") int maxAttempts, @Param("limit") int limit);
}
```

线程池的四个参数是这一篇的第二个主角。`setQueueCapacity(8)` 才是真正的并发闸门：线程池的执行顺序是「核心线程 → 队列 → 扩到最大线程 → 拒绝」，队列没满之前不会创建第 3 个线程，这一点和很多人的直觉相反。

```java title="task-center/src/main/java/com/demo/taskcenter/config/AsyncConfig.java"

import java.util.concurrent.ThreadPoolExecutor;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.annotation.EnableAsync;
import org.springframework.scheduling.annotation.EnableScheduling;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

@Configuration
@EnableAsync
@EnableScheduling
public class AsyncConfig {

    private static final Logger log = LoggerFactory.getLogger(AsyncConfig.class);

    @Bean("exportExecutor")
    public ThreadPoolTaskExecutor exportExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(2);
        executor.setMaxPoolSize(4);
        executor.setQueueCapacity(8);
        executor.setThreadNamePrefix("export-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy() {
            @Override
            public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
                // CallerRunsPolicy 本身不打印任何东西，必须自己记一行，否则拒绝是静默的
                log.warn("export pool saturated, run on caller thread={} active={} queue={}",
                        Thread.currentThread().getName(), e.getActiveCount(), e.getQueue().size());
                super.rejectedExecution(r, e);
            }
        });
        executor.setWaitForTasksToCompleteOnShutdown(true);
        executor.setAwaitTerminationSeconds(30);
        executor.initialize();
        return executor;
    }
}
```

```java title="task-center/src/main/java/com/demo/taskcenter/export/ExportService.java"
package com.demo.taskcenter.export;

import com.demo.taskcenter.task.Task;
import com.demo.taskcenter.task.TaskMapper;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.Paths;
import java.util.List;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.scheduling.annotation.Async;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;
import org.springframework.stereotype.Service;

@Service
public class ExportService {

    private static final Logger log = LoggerFactory.getLogger(ExportService.class);
    private static final int MAX_ATTEMPTS = 3;

    private final ExportTaskMapper mapper;
    private final TaskMapper taskMapper;
    private final ThreadPoolTaskExecutor exportExecutor;
    private final long pageDelayMs;

    public ExportService(ExportTaskMapper mapper,
                         TaskMapper taskMapper,
                         @Qualifier("exportExecutor") ThreadPoolTaskExecutor exportExecutor,
                         @Value("${app.export.page-delay-ms:0}") long pageDelayMs) {
        this.mapper = mapper;
        this.taskMapper = taskMapper;
        this.exportExecutor = exportExecutor;
        this.pageDelayMs = pageDelayMs;
    }

    public long submit() {
        ExportTask task = new ExportTask();
        mapper.insert(task);
        return task.getId();
    }

    public ExportTask detail(long id) {
        return mapper.findById(id);
    }

    @Async("exportExecutor")
    public void run(long exportId) {
        dispatch(exportId);
    }

    public void dispatch(long exportId) {
        if (mapper.markRunning(exportId) == 0) {
            log.info("export skipped id={} 已被领走或已结束", exportId);
            return;
        }
        try {
            Path file = writeCsv(exportId);
            mapper.markSucceeded(exportId, file.getFileName().toString());
            log.info("export done id={} file={} thread={}", exportId,
                    file.getFileName(), Thread.currentThread().getName());
        } catch (Exception e) {
            String message = e.getClass().getSimpleName() + ": " + e.getMessage();
            mapper.markFailed(exportId, message);
            ExportTask current = mapper.findById(exportId);
            log.warn("export failed id={} attempts={} thread={}", exportId,
                    current == null ? -1 : current.getAttempts(), Thread.currentThread().getName());
        }
    }

    /** 进程重启、队列丢失、失败重试都靠这张表捞回来；认领那一步保证重复投递不会重复执行 */
    @Scheduled(fixedDelay = 5_000L)
    public void sweep() {
        List<Long> due = mapper.findRetryable(MAX_ATTEMPTS, 5);
        for (Long id : due) {
            exportExecutor.execute(() -> dispatch(id));
        }
    }

    private Path writeCsv(long exportId) throws IOException {
        Path dir = Paths.get("./data/exports").toAbsolutePath().normalize();
        Files.createDirectories(dir);
        StringBuilder csv = new StringBuilder("id,title,done,priority\n");
        int offset = 0;
        while (true) {
            List<Task> page = taskMapper.page(null, null, "id", 100, offset);
            if (page.isEmpty()) {
                break;
            }
            for (Task task : page) {
                csv.append(task.getId()).append(',')
                        .append('"').append(task.getTitle().replace("\"", "\"\"")).append('"').append(',')
                        .append(Boolean.TRUE.equals(task.getDone()) ? 1 : 0).append(',')
                        .append(task.getPriority()).append('\n');
            }
            offset += page.size();
            sleepPageDelay();
        }
        Path file = dir.resolve("task-export-" + exportId + ".csv");
        Files.writeString(file, csv.toString(), StandardCharsets.UTF_8);
        return file;
    }

    private void sleepPageDelay() {
        if (pageDelayMs <= 0) {
            return;
        }
        try {
            Thread.sleep(pageDelayMs);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

## 二、机制

第一节跑出来的两个现象——「缓存能跳过查库」和「拒绝策略会让 Tomcat 线程干活」——都不是配置的副作用，而是两条明确的机制。这一节把它们拆开。

### 1. 缓存命中的三条路径与三个时间

把 `findById` 的分支画成图，比读代码更快看出谁在什么时候碰库：

```text
GET /api/tasks/1
  │
  ├─ Redis GET task:v1:detail:1
  │    │
  │    ├─ 有值，且 softExpireAt 还没到 ────────────▶ 直接返回（0 次查库、0 次加锁）
  │    │
  │    ├─ 有值，但 softExpireAt 已过 ─┬─ tryLock 成功 ─▶ 查库、写回、返回新值
  │    │                              └─ tryLock 失败 ─▶ 返回旧值（请求不排队）
  │    │
  │    └─ 没有值 ─────────────────────┬─ tryLock 成功 ─▶ 双检、查库、写回
  │                                   └─ tryLock 失败 ─▶ 停顿后重读，仍无则降级查库
  │
  └─ Redis 超时或报错 ────────────────────────────▶ 当作未命中，继续查库（降级）
```

图里其实有三个不同的时间，混在一起就会出 bug：

| 时间 | 存在哪 | 谁来判断 | 作用 |
| :-- | :-- | :-- | :-- |
| 逻辑过期 `softExpireAt` | value 的 JSON 字段里 | 应用代码 | 决定「要不要重建」，过期期间仍可返回旧值 |
| 物理 TTL | Redis 的 key 元数据里 | Redis 自己 | 决定「什么时候彻底删掉」，兜底防止脏数据永久停留 |
| 锁的 TTL | 锁 key 的元数据里 | Redis 自己 | 决定「进程崩溃后多久能有人接手」 |

**物理 TTL 必须严格大于逻辑过期**，否则 key 会在逻辑过期之前被删掉，「返回旧值 + 后台重建」这条分支永远走不到，整套设计退化成普通的互斥重建。代码里 `HARD_EXTRA_MS` 就是这个余量：25 分钟远大于一次重建需要的毫秒级时间，留这么长是为了让逻辑过期成为唯一的过期判断者，物理 TTL 只负责兜底。

**逻辑过期的收益是「请求不等」。** 普通互斥重建在热点 key 过期的那一瞬间，只有一个请求能重建，其余请求要么阻塞等待（线程被占住），要么降级查库（库被打）。逻辑过期把「等」换成「先给旧值」，代价是这段时间读到的是陈旧数据。所以它只适合「能容忍几十秒陈旧」的数据：任务详情可以，账户余额不行。

**空值缓存挡的是穿透。** `CachedTask` 的 `task` 为 `null` 时照样写进 Redis，TTL 30 秒。它防的是「同一个不存在的 id 被反复请求」——每次未命中都查库，库就成了缓存。代价有两个：内存里多了一批 null；如果这个 id 后来真的被创建，最多 30 秒内仍返回 404。自增主键场景下后者几乎不会发生，业务唯一键场景下要在创建后主动 `evict`。

**降级不是可选项。** 代码里五处 Redis 交互——读、写、删、抢锁、解锁（外加看门狗里的续期）——各自兜了异常：读失败当未命中，抢锁失败直接查库，解锁失败只记日志。这不是容错洁癖：Redis 是加速层，它挂了应该是「接口变慢」，不是「接口全 500」。反过来，如果业务不能接受变慢，那要在网关层限流，而不是在这里假装缓存永远可用。

### 2. `SET NX PX` 与 Lua：原子性到底保了什么

先看一段不能用的写法：

```java
// 反例：两条命令，中间有明显空档
Boolean ok = redis.opsForValue().setIfAbsent("lock:job", token);
if (Boolean.TRUE.equals(ok)) {
    redis.expire("lock:job", Duration.ofSeconds(10));   // 这两行之间进程崩了会怎样？
}
```

如果进程在 `setIfAbsent` 成功之后、`expire` 之前被杀掉，这把锁就**永远不过期**。之后所有实例都抢不到它，业务彻底卡死，只能人工 `DEL`。这就是「先 SETNX 再 EXPIRE」被淘汰的原因，而不是因为它的性能差。

`SET key value NX PX 3000` 把「判断不存在」「写值」「设过期」放进同一条命令。Redis 执行命令是串行的：Redis 6 之后网络读写用了多线程，但**命令执行仍然在单线程里一条一条来**，所以一条命令要么完整生效，要么完全没发生，中间不会插进别的客户端的命令。这就是原子的全部含义——不是什么高级特性，是「一条命令」这个粒度本身。

Lua 脚本拿到的是同一个保证，只是把「一组命令」包装成「一条命令」。`EVAL` 执行期间 Redis 不处理其他客户端的命令，所以 `GET` 比 token、`DEL` 这两步不会被切开：

```lua
-- 解锁：先比对 value，再删除；两件事必须一次完成
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
end
return 0
```

没有这段脚本会怎样？A 的锁在 3 秒后过期，B 抢到了锁；这时 A 的业务跑完，执行 `DEL lock:xxx`，删掉的是 **B 的锁**。C 紧接着抢到锁，于是 B 和 C 同时写同一份数据。所以 value 必须是唯一标识（代码里是去横线的 UUID），解锁必须比对后删除，不能只发一个 `DEL`。

代价也要说清楚：Lua 脚本运行期间整个 Redis 实例阻塞，脚本越慢，全站越慢。所以脚本里不要放大循环、不要做 `KEYS` 扫描。另外 `EVAL` 每次都要传脚本体，`DefaultRedisScript` 配合 `redis.execute` 会自动走 `EVALSHA`，脚本没缓存时才回退到 `EVAL`。

续期在同一套规则里： `PEXPIRE` 之前必须先比对 token，否则 A 会把 B 的锁续上，B 以为自己在持锁，其实随时会被 A 的 `DEL` 端掉：

```lua
-- 续期：token 对得上才延长，返回 1 表示续期成功
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('pexpire', KEYS[1], ARGV[2])
end
return 0
```

## 三、穿透、击穿、雪崩：三种故障的分界

三个词经常被混着用，其实触发条件完全不同，解法也不能互换。

| 故障 | 触发条件 | 现象 | 主要解法 | 代价 |
| :-- | :-- | :-- | :-- | :-- |
| 穿透 | 请求的 key 在库里根本不存在 | 每次都不命中，每次查库 | 空值缓存、布隆过滤器、参数校验 | 内存占用、误判、创建后短暂 404 |
| 击穿 | 某一个热点 key 刚好过期 | 瞬时并发全部打到库的同一条 SQL | 互斥重建、逻辑过期 | 前者让请求等，后者读到旧值 |
| 雪崩 | 大量 key 同时过期，或 Redis 整体不可用 | 库的 QPS 整体抬升，连接池耗尽 | TTL 抖动、多级缓存、熔断降级 | 实现复杂度、内存翻倍 |

**穿透**的根因不是缓存没生效，而是「缓存对不存在的 key 无能为力」——查不到就没有东西可缓存。空值缓存是最省事的解法，本文已经实现。布隆过滤器解决的是同一个问题，但用的是另一条路：把所有可能存在的 id 预先把进一个位数组，查询前先问一句「这个 id 可能存在吗」。

布隆过滤器有两条必须记住的性质。**第一，误判方向是单向的**：它说「不存在」，那一定不存在，可以放心拒绝；它说「存在」，可能只是几个哈希位被别的元素碰巧置成了 1，实际并不存在，请求照样会打到库。所以它只能减少穿透，不能消灭穿透，也不是用来替代空值缓存的。**第二，标准布隆过滤器不能删除元素**：位是多个元素共享的，清掉一个元素的位会把别人的判断一起弄错。数据要删只能整表重建（定期离线重建、双缓冲切换），或者换成计数布隆过滤器（每个位改成计数器，代价是内存成倍）。

对 task-center 来说，`id` 是自增主键，恶意请求会扫 `1`、`2`、`3` 一直到无穷，空值缓存的 30 秒 TTL 足以把它们挡在库里之外；如果以后加了「按工单号查」，工单号是外部可控的字符串，就该在入口做格式校验，再考虑布隆过滤器。

**击穿**只针对热点。判断标准很具体：某一个 key 的访问量占了这个接口的绝大部分，它一过期，库里立刻出现一个尖峰。本文给了两种解法，取舍写在代码注释里：互斥重建保证读到的都是新值，但要有人等；逻辑过期保证没人等，但要接受几十秒的旧值。真实项目里通常是**两者都用**：逻辑过期做主路径，互斥重建兜「缓存彻底没有」的冷启动。

**雪崩**是规模问题，不是单点问题。两个来源：一是大批 key 的 TTL 设成同一个值（比如凌晨批量预热、全部 30 分钟），到点一起失效；二是 Redis 或网络整体故障，所有请求同时降级到库。前者靠抖动：本文 `loadAndStore` 里给物理 TTL 加了 0 到 60 秒的随机量，让过期时间散开。后者靠架构：本地缓存（Caffeine）扛第一层、Redis 第二层、库最后一层；再配合熔断，Redis 不可用时限制回源并发，而不是把全部流量放给数据库。

一个常被忽略的边界：**加锁只能保护「重建」，保护不了「整体不可用」**。Redis 挂了的时候，`tryLock` 自己也会失败，这时候锁不是答案，限流和降级才是。

## 四、缓存与数据库的一致性

这是缓存里唯一没有标准答案的部分。先明确一件事：**缓存和数据库不可能强一致**，除非你不缓存，或者把读也放进数据库事务里。能追求的只有「窗口多短、脏数据能活多久」。

四种常见顺序，各自的窗口：

| 顺序 | 脏数据窗口 | 风险 | 适用 |
| :-- | :-- | :-- | :-- |
| 先删缓存，再写库 | 删除到提交之间 | 并发读把旧值回填，直到 TTL 才自愈 | 写少、能容忍陈旧 |
| 先写库，再删缓存 | 提交到删除完成之间 | 删除失败则旧值长期存在 | 最常用，配合重试 |
| 先写库，再写缓存 | 同上，且更长 | 并发写会互相覆盖成旧值 | 几乎不推荐 |
| 写库 + 删缓存 + 延迟再删 | 两次删除之间 | 延迟时间靠猜，第二次删也可能失败 | 冲突概率高的热点 key |

「先删缓存再写库」的问题在第一节的代码里已经有对应：读请求在「缓存已删、事务未提交」这个窗口里查库，读到的是**旧值**，然后把它回填进缓存；事务提交后，缓存里躺着的是旧值，直到 TTL 到期。这个窗口在写事务较长时会被放大。要缩它，只能让删除发生在提交之后——本文的 `evictAfterCommit` 就是干这个的：

```java
    @Transactional(rollbackFor = Exception.class)
    public Task update(long id, TaskSaveReq req) {
        Task task = mapper.findById(id);
        if (task == null) {
            throw new BusinessException(ErrorCode.TASK_NOT_FOUND);
        }
        task.setTitle(req.title().trim());
        task.setPriority(req.priority() == null ? task.getPriority() : req.priority());
        task.setDueAt(req.dueAt());
        task.setRemark(req.meta().remark());
        task.setEstimateMinutes(req.meta().estimateMinutes());
        mapper.update(task);
        cacheService.evictAfterCommit(id);   // 注册到 afterCommit，而不是现在就删
        return task;
    }
```

即便这样，还剩一个窗口。写缓存和删除是两个动作，它们和「读库」的相对顺序决定后果：删除发生在写缓存之后，删除会把它清掉，无害；读库发生在提交之后，读到的是新值，也无害。真正有害的只有一种顺序——**读请求在提交前读到旧值，写缓存却发生在删除之后**，旧值就这样留在缓存里，直到 TTL 到期或下一次删除。这就是**延迟双删**要对付的场景：

```java
        // 延迟双删：提交后删一次，过一段时间再删一次，覆盖「先读后写」的回填窗口
        cacheService.evictAfterCommit(id);
        delayExecutor.schedule(() -> cacheService.evict(id), 500L, TimeUnit.MILLISECONDS);
```

它的局限和它的名字一样直白：500 毫秒是猜的，读请求如果卡了 800 毫秒才回填，第二次删除照样漏；多实例部署时，第二次删除只在一个实例上排队，别的实例的回填它管不到；删除本身失败（Redis 抖动）时没有任何补偿。所以延迟双删只是「降低概率」，不是「保证正确」。

要真正收敛，就得放弃「业务代码负责删缓存」这个前提，改成订阅数据变更：MySQL 的 binlog 通过 Canal / Debezium 投递出去，由消费者删缓存或刷新缓存。好处是删缓存的时机由数据变更驱动，不依赖每个人记得写 `evict`；代价是多一个组件、多一条链路、多一段延迟，而且 binlog 消费失败要能重放。

更彻底的做法是把「写库」和「通知」放进同一个事务，也就是 Outbox：

```sql
CREATE TABLE outbox_event (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  aggregate    VARCHAR(40)     NOT NULL,
  aggregate_id BIGINT UNSIGNED NOT NULL,
  event_type   VARCHAR(60)     NOT NULL,
  payload      JSON            NOT NULL,
  status       VARCHAR(16)     NOT NULL DEFAULT 'PENDING',
  attempts     INT             NOT NULL DEFAULT 0,
  created_at   DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_outbox_pending (status, id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

```java
    @Transactional(rollbackFor = Exception.class)
    public void complete(long id) {
        Task task = mapper.findById(id);
        task.setDone(true);
        mapper.update(task);
        // 业务表与 outbox 在同一个事务里：要么都在，要么都不在
        outboxMapper.insert("TASK", id, "TASK_COMPLETED", "{\"id\":" + id + "}");
    }
```

关键点是「同一事务」四个字。不在事务里发消息，就会出现「库回滚了，消息已经发出去了」；在事务里发 HTTP 或 MQ，就会出现「消息发出去了，事务回滚了」。Outbox 把「要不要发」变成一行可以一起提交的数据，投递则交给一个可重试的轮询任务：取出 `PENDING` 的行、发送、成功改成 `SENT`、失败累加 `attempts`。投递是至少一次，消费方必须幂等。

`outboxMapper.insert` 就是一条四列的 `INSERT`，没有别的逻辑。上面的 payload 用字符串拼接，是因为 `id` 是 `long`，拼进去不构成注入；换成标题一类外部字符串，就必须交给 Jackson 序列化，不能拼。

结论不要写成「先写库再删缓存是对的」。准确的说法是：**在允许短暂陈旧的读多写少场景，写库后删缓存（+ 提交后删 + 抖动 TTL）是默认选择；冲突概率高的热点数据加延迟双删降低概率；跨服务、跨存储的一致性用 binlog 或 Outbox 收敛到最终一致；需要强一致的那部分数据，不要缓存。**

## 五、分布式锁：原子、令牌、续期与超时

上一节讲了 `SET NX PX` 为什么必须是一条命令。这一节把锁的其余部分补齐，因为它们每一个都对应一类线上事故。

**第一，value 必须是唯一标识。** 用固定字符串（比如 `"1"`）当 value，解锁时就无法区分「我的锁」和「别人的锁」。代码里用 UUID，每次抢锁都换一个。

**第二，解锁必须比对后删除。** 这一点已经用 Lua 解决。不要用「先 `GET` 判断等于自己的 token，再 `DEL`」的两步写法，那和 `SETNX` 加 `EXPIRE` 是同一类错误：两步之间锁可能已经过期并易主。

**第三，锁的 TTL 与业务的执行时间是一对矛盾。** TTL 太短，业务没跑完锁就没了，另一个实例进来，两个实例同时写；TTL 太长，进程崩溃后要等很久才有人能接手。经验值是「正常耗时的若干倍」，但这不是保证。

**第四，续期（watchdog）不是万能药。** 它解决的是「业务比预期慢」，解决不了「进程被暂停」：

```java title="task-center/src/main/java/com/demo/taskcenter/cache/LockWatchdog.java"
package com.demo.taskcenter.cache;

import java.time.Duration;
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.ScheduledFuture;
import java.util.concurrent.TimeUnit;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;

@Component
public class LockWatchdog {

    private static final Logger log = LoggerFactory.getLogger(LockWatchdog.class);

    private final RedisLock lock;
    private final ScheduledExecutorService scheduler =
            Executors.newSingleThreadScheduledExecutor(r -> {
                Thread thread = new Thread(r, "lock-watchdog");
                thread.setDaemon(true);
                return thread;
            });

    public LockWatchdog(RedisLock lock) {
        this.lock = lock;
    }

    /** 每 ttl/3 续一次；返回的句柄要在业务结束后 cancel，否则会一直续下去 */
    public ScheduledFuture<?> watch(String name, String token, Duration ttl) {
        long period = Math.max(ttl.toMillis() / 3, 50L);
        return scheduler.scheduleAtFixedRate(() -> {
            try {
                if (!lock.renew(name, token, ttl)) {
                    // 续期失败说明锁已经易主，业务必须尽快停下，而不是继续写
                    log.warn("lock lost name={}", name);
                }
            } catch (RuntimeException e) {
                // scheduleAtFixedRate 遇到异常会静默停掉后续执行，必须在这里接住
                log.warn("lock renew failed name={}", name, e);
            }
        }, period, period, TimeUnit.MILLISECONDS);
    }
}
```

看门狗能覆盖的只有「业务慢」这一种情况。**它覆盖不了 stop-the-world**：JVM 做一次长 GC、虚拟机被挂起、容器被 CPU 限流，都可能让持锁进程在 TTL 内一次都没续上；等它醒来，锁早已易主，而它并不知道。所以锁的边界必须写清楚：**分布式锁只降低并发冲突的概率，不提供互斥保证。** 真正的保证要落在数据层——唯一索引、条件更新（`markRunning` 的 `WHERE ... AND status IN (...)`）、版本号。这也是为什么导出服务**根本不需要锁**：认领那一步由数据库完成，重复投递不会重复执行。

**第五，Redlock 的争议。** 单实例 Redis 做锁，在主从切换时可能丢锁（主节点写完还没同步就挂了，从节点升主，锁消失）；Redlock 用多个独立节点投票来降低这个概率，但它的正确性依赖时钟假设，在 GC 停顿和网络分区下的表现一直有争议。多节点场景要单独评估，不要因为「五个节点」就认为它更强。

**第六，锁的粒度比锁的实现更重要。** 锁 `cache:detail:1` 和锁 `cache:detail` 是两种系统：前者只影响一个 key 的重建，后者让所有详情查询串行。宁可多加几个 key，也不要一把大锁。

## 六、缓存实现：Spring Cache 的边界、序列化与 key 命名

Spring 提供了 `@Cacheable` 这一层抽象，看起来可以省掉本文手写的几十行。它确实适合简单场景，但有四个边界必须先知道，否则会写出一段「看起来在缓存、实际每次查库」的代码。

```java
    // 常见的写法：注解很干净，但四个边界都藏在框架里
    @Cacheable(cacheNames = "task", key = "#id", unless = "#result == null")
    public Task findById(long id) {
        return mapper.findById(id);
    }
```

**边界一：自调用不生效。** `@Cacheable` 靠代理实现，和 `@Transactional`、`@Async` 是同一个机制（阶段十三讲过）。同类里 `this.findById(id)` 调用不经过代理，注解完全不执行，连日志都没有。这条几乎占了「注解不生效」问题的一半。

**边界二：异常不会被缓存，空结果却会。** 方法抛异常时不会写入任何东西，这是对的；但正常返回 `null` 时，`null` 照样会被写进缓存，而且用的是这个 cacheName 的统一 TTL。要挡穿透就得让空值活得更短，而 `@Cacheable` 的 TTL 只能通过 `RedisCacheManager` 的 `RedisCacheConfiguration` 全局或按 cacheName 配置，做不到「null 30 秒、正常 5 分钟」这种按值区分——除非给空值单开一个 cacheName，把复杂度又推回配置里。

**边界三：`sync = true` 只在单 JVM 内互斥。** 它保证同一时刻只有一个线程去加载同一个 key，用的是本地锁。多实例部署时每个实例都会各自加载一次，起不到第一节「互斥重建」的作用。

**边界四：`@CacheEvict` 的时机。** 默认在方法返回后执行，和事务提交没有关系；`beforeInvocation = true` 更早。要「提交后删」还是得自己注册 `afterCommit`，或者用 `@TransactionalEventListener`。

所以本文的选择是：**读路径手写**（因为要逻辑过期、要空值与正常值不同 TTL、要降级），**写路径用 `evictAfterCommit`**。选型不是「手写更高级」，而是注解表达不了这三个需求。

序列化的选择比想象中重要，因为它决定了三件事：`redis-cli` 里能不能看懂、升级类会不会炸、换语言还能不能用。

| 序列化器 | 存进去的样子 | 优点 | 代价 |
| :-- | :-- | :-- | :-- |
| `JdkSerializationRedisSerializer` | 二进制，带类名 | 默认就能用，对象直接存 | 不可读、体积大、类结构一变就反序列化失败、跨语言不可用 |
| `GenericJackson2JsonRedisSerializer` | JSON，多一个 `@class` 字段 | 可读、自动带类型 | 依赖类名，改包名会失效；反序列化回 `Object` 时按类名找类 |
| `StringRedisTemplate` + 手写 JSON | 纯 JSON | 完全可控、可读、跨语言 | 要自己管类型和 null |

本文用第三种：`StringRedisTemplate` 加 `ObjectMapper`。理由很实在——出问题时能直接 `redis-cli GET task:v1:detail:1` 看到内容，而不用写一段 Java 去反序列化；`CachedTask` 是显式类型，不需要 `@class` 那种隐式契约；`null` 由 `CachedTask.task` 字段表达，不依赖序列化器对 null 的特殊处理。

key 的命名是低成本的纪律，写错了要等到排查时才痛：

- **带业务前缀和版本**：`task:v1:detail:1`。版本号是给「结构变了要整体作废」用的，改 value 结构时把 `v1` 改成 `v2`，老 key 自然过期，不用写迁移脚本。
- **不要用 `KEYS *`**：它是 O(N) 且阻塞整个实例。排查用 `--scan --pattern`，代码里根本不该出现 `keys`。
- **单 value 控制在几十 KB 以内**：大 key 会拖慢网络传输，也会让删除、过期产生尖峰。列表数据不要整体塞进一个 key，按 id 拆。
- **锁和缓存用不同前缀**：`lock:` 与 `task:` 分开，方便按前缀做容量统计和清理。
- **TTL 是必填项，不是可选项**：没有 TTL 的 key 在内存满时会被 LRU 淘汰，行为不可预测；显式给 TTL，至少能算出「最坏情况脏多久」。

## 七、@Async、有限线程池与异步任务的可靠性

`@Async` 只需要一个注解，但它的默认值几乎必然要改。

**先搞清楚「默认」是哪一个。** Spring Boot 3 在一个 `Executor` bean 都没有时，会自动配 `applicationTaskExecutor`，它也是 `ThreadPoolTaskExecutor`，但默认值是核心 8、最大线程 `Integer.MAX_VALUE`、队列 `Integer.MAX_VALUE`——队列几乎无界，等于把「拒绝」这件事关掉了，任务只会一直排队。更隐蔽的是：一旦你自己定义了任意一个 `Executor`（比如本文的 `exportExecutor`），这份自动配置会整体退让，此时不带名字的 `@Async` 会退回 `SimpleAsyncTaskExecutor`——每次提交新建一个线程，不复用、不设上限，提交速度超过完成速度就会一路涨到把内存和文件句柄吃光，Spring 会打一条容易被略过的警告。所以「有没有线程池」不是重点，「用的是哪一个」才是：`@Async` 永远把 bean 名字写清楚。

**四个参数怎么定。** 执行顺序是：核心线程 → 队列 → 扩到最大线程 → 拒绝。这条顺序决定了一个反直觉的事实：`queueCapacity` 才是并发闸门，`maxPoolSize` 只在队列满了之后才起作用。

| 参数 | 本文取值 | 决定了什么 | 调大的代价 |
| :-- | :-- | :-- | :-- |
| `corePoolSize` | 2 | 常驻线程数，队列空时也保留 | 空闲时也占内存 |
| `queueCapacity` | 8 | 排队上限，满之前不扩线程 | 内存、排队延迟、任务「看起来提交成功」但其实等了很久 |
| `maxPoolSize` | 4 | 队列满后的临时扩容上限 | 瞬时并发高，下游压力大 |
| 拒绝策略 | `CallerRunsPolicy` | 满了之后怎么办 | 见下 |

**`CallerRunsPolicy` 的副作用必须说清。** 它的语义是「谁提交，谁执行」：不丢任务，不抛异常，但把工作退回到调用者线程。在 Web 请求里，调用者就是 Tomcat 工作线程——第一节的日志里 `thread=http-nio-8081-exec-3` 就是证据。后果有三层：

1. **接口响应时间变成导出时间。** 原来提交即返回的接口，在池满时响应时间直接等于整段导出的时间。
2. **Tomcat 线程被占，整体吞吐下降。** Tomcat 的线程数是有限的（默认 200），导出占用的线程无法处理其他请求；如果导出很慢，就可能把整个应用的请求队列拖满。
3. **背压是有效的，但没有上限。** 它的好处是「系统变慢而不是丢数据」，坏处是这个变慢会传导到所有接口，包括跟导出无关的那些。

选它的前提是「丢任务比变慢更糟」。反过来，如果导出可以丢（比如可以由用户重试），`AbortPolicy` 加一个明确的 429 或 503 反而更诚实；如果希望「排队等一会儿」，`DiscardOldestPolicy` 要先想清楚丢掉的最老任务由谁负责。

**优雅停机。** `setWaitForTasksToCompleteOnShutdown(true)` 加 `setAwaitTerminationSeconds(30)` 让容器关闭时先做完手上的任务。没有这两行，发布时正在跑的导出会被直接杀掉，数据库里留下 `RUNNING` 状态的行。所以要有一个兜底：`updated_at` 超过一定时间还是 `RUNNING` 的，视为失败并回收。

**异常去哪了。** `@Async` 方法返回 `void` 时，抛出的异常不会传播给调用方，默认只打一条日志。要拿到异常，要么返回 `CompletableFuture`，要么实现 `AsyncUncaughtExceptionHandler`。本文的 `dispatch` 把异常全部就地捕获并落成 `FAILED` 状态，就是因为「异步方法的异常没人接」这件事在排障时极其费时。

**线程池不是任务可靠性的答案。** 线程池只保证「提交之后有线程执行」，不保证「提交成功」。进程崩溃、发布重启、队列积压后丢弃，任何一个都会让内存里的任务消失。所以任务必须先落表，再进池：

```text
提交接口                     export_task 表                线程池
   │                              │                          │
   ├─ INSERT status=PENDING ──────▶│                          │
   ├─ @Async run(id) ─────────────┼─────────────────────────▶│ 排队/执行
   │                              │                          │
   │                     dispatch 认领：UPDATE ... WHERE status IN ('PENDING','FAILED')
   │                              │  affected=1 ──▶ 执行 ──▶ SUCCEEDED / FAILED
   │                              │  affected=0 ──▶ 跳过（别人领走了）
   │                              │
   └─ 定时 sweep 每 5 秒 ─────────▶│ 捞出 PENDING/FAILED 且 attempts 小于 3 的行，重新投递
```

这张图解释了为什么「认领」这一步用条件更新而不是加锁：**它顺带解决了重复投递**。`sweep` 可能和第一次提交同时把同一个 id 塞进池里，两个线程都会执行 `dispatch`，但只有一个能让 `markRunning` 返回 1，另一个直接放弃。锁做不到这一点——锁会过期、会丢，而 `WHERE status IN (...)` 永远不会。

重试要有上限和退避。本文的重试是「每 5 秒捞一次」，实现简单，但对「上游服务挂了」这类故障不够：三次尝试可能在 15 秒内烧完，然后任务永久失败。生产上更常见的是在表里加 `next_retry_at`，用指数退避把间隔拉开，并且把失败原因分成人可读的几类（参数错、下游超时、磁盘满），只有「可重试」的那几类才继续重试。

Outbox 是同一套思路的延伸：导出的可靠性靠 `export_task`，跨服务通知的可靠性靠 `outbox_event`。两者的共同点都是「把意图先写成一行数据，再让一个可重试的循环去执行它」，区别只是前者的执行者是线程池，后者是消息投递器。**永远不要在同一事务里做远程调用**：事务会回滚，消息不会。

## 八、前端视角：localStorage 与 Redis

把两者放在一起对照，不是为了说「Redis 更高级」，而是因为它们解决的是不同的问题，混用会导致完全错误的直觉。

| 维度 | localStorage | Redis（本文的用法） |
| :-- | :-- | :-- |
| 作用域 | 单个浏览器、单个域名，只对当前用户可见 | 所有实例共享，跨用户、跨请求 |
| 失效 | 只能手动删，或用户清缓存 | TTL + 业务逻辑过期，两层都可以主动控制 |
| 并发 | 同一页面基本无并发写 | 多线程、多实例同时读写 |
| 容量与淘汰 | 几 MB，超了直接抛错 | 由 `maxmemory` 决定，可配置淘汰策略 |
| 重建 | 没有「重建」概念，取不到就重新请求 | 需要互斥重建，否则同一瞬间所有人一起查库 |

一个具体的差别能说明问题。前端把用户信息存进 localStorage，多个标签页之间是共享的，但**跨用户的隔离是天然的**（每个浏览器就是一个人）。Redis 里存的是所有人的数据，key 少写一个 `userId`，就会让 A 看到 B 的任务——这不是缓存问题，是越权问题，阶段十六的归属校验就是防这个的。

第二个差别是「失效」的语义。localStorage 里没有 TTL，前端常见的做法是存一个 `expiresAt` 字段，读的时候自己判断——这个模式正好就是本文的逻辑过期。区别在于：浏览器里判断过期之后直接重新请求即可，因为只有一个客户端；Redis 里判断过期之后，可能有几千个客户端同时判断出过期，于是必须有互斥重建或者逻辑过期来吸收这个尖峰。

第三个差别是并发写。localStorage 的写入基本是「最后写赢」，没有并发冲突的概念；Redis 的 `INCR`、`SET NX` 是原子的，但「读出来改完写回去」不是原子的，这一点和数据库的读-改-写完全一样，需要锁或者 Lua。

第四个差别是容量心态。前端习惯「反正只有几 MB，能省则省」，后端习惯「反正 Redis 有内存，先塞进去」。两边都错：Redis 的内存是钱，而且被淘汰时没有任何业务感知。大 key、无 TTL 的 key、把整个列表塞一个 key，这三件事在任何项目里都会被追溯到。

## 这条链路在真实项目里的位置

把这一篇的改动放回一次真实迭代，顺序和阶段十四、十五是同一套：需求先于数据，数据先于契约，契约先于实现，验证先于上线。

**这一步不做什么，同样要写清楚。** 不做多级缓存（本地 Caffeine 留给真实的高并发场景）；不做 binlog 订阅（Outbox 的投递器先用手写轮询，需要时再换）；不做分布式事务（只承诺最终一致）；不调 Tomcat 线程数（那是阶段十九的事）。

**测试怎么写。** 阶段十七建立的三层测试在这一步各有用处。缓存逻辑用单元测试，Mockito 把 `StringRedisTemplate` 和 `TaskMapper` 换成 mock，**断言命中时一次库都不查**——这是缓存唯一能被自动证明的价值：

```java title="task-center/src/test/java/com/demo/taskcenter/cache/TaskCacheServiceTest.java"
package com.demo.taskcenter.cache;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.mockito.Mockito.mock;
import static org.mockito.Mockito.verifyNoInteractions;
import static org.mockito.Mockito.when;

import com.demo.taskcenter.task.Task;
import com.demo.taskcenter.task.TaskMapper;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.ValueOperations;

class TaskCacheServiceTest {

    private final StringRedisTemplate redis = mock(StringRedisTemplate.class);
    @SuppressWarnings("unchecked")
    private final ValueOperations<String, String> valueOps = mock(ValueOperations.class);
    private final TaskMapper mapper = mock(TaskMapper.class);
    private final RedisLock lock = mock(RedisLock.class);
    private final ObjectMapper json = new ObjectMapper();

    private TaskCacheService service;

    @BeforeEach
    void setUp() {
        when(redis.opsForValue()).thenReturn(valueOps);
        service = new TaskCacheService(redis, json, mapper, lock, 300_000L);
    }

    @Test
    void cacheHitSkipsDatabaseAndLock() throws Exception {
        Task task = new Task();
        task.setId(1L);
        task.setTitle("cache hit");
        task.setDone(false);
        String raw = json.writeValueAsString(
                new CachedTask(task, System.currentTimeMillis() + 60_000L));
        when(valueOps.get("task:v1:detail:1")).thenReturn(raw);

        Task result = service.findById(1L);

        assertEquals("cache hit", result.getTitle());
        verifyNoInteractions(mapper);
        verifyNoInteractions(lock);
    }
}
```

异步那条链路不能用 mock 证明：`@Async` 的代理、线程池的拒绝、状态机的迁移，都要在真实容器里跑。切片测试提交 18 个导出，断言最终 18 行都是 `SUCCEEDED`、`attempts` 都是 1，再用 `Awaitility` 等状态收敛。**能证明「不重复执行」的，只有数据库里那行 `attempts = 1`**，日志不算。

下一步是 [部署、日志与线上排查](/blog/posts/java-roadmap-19-deploy-and-troubleshoot/)：这一篇引入的线程名、`export_task` 表和 Redis 超时，正是那一步要观察的东西——线程池满了看什么指标，导出失败从哪张表查，缓存降级率怎么统计。

## 常见坑

| 现象 | 根因 | 处理 |
| :-- | :-- | :-- |
| `@Cacheable` 完全不生效 | 同类自调用，没经过代理 | 拆到另一个 Bean，或注入自身代理；与 `@Transactional` 同一类问题 |
| 缓存永远命中不了 | key 前缀或序列化不一致，两次请求写读的不是同一个 key | 用 `--scan --pattern` 核对实际 key；统一用 `StringRedisTemplate` |
| 缓存里的值和库不一致，且不自愈 | 写库后没删缓存，或删除失败没重试 | `evictAfterCommit` + 短 TTL 兜底；热点加延迟双删 |
| 删了缓存依然读到旧值 | 删除发生在事务提交前，并发读回填了旧值 | 删除注册到 `afterCommit`；或用 binlog / Outbox 驱动 |
| 锁删掉了别人的 | 解锁只发了 `DEL`，没比对 token | Lua 里先 `GET` 比对再 `DEL` |
| 锁永不过期，业务永久卡死 | `SETNX` 与 `EXPIRE` 分两条命令，中间进程崩溃 | 用 `SET key value NX PX ttl` 一条命令；锁必须带 TTL |
| 业务跑过 TTL，两个实例同时写 | 锁过期而业务未结束 | 看门狗续期 + 数据层幂等（唯一索引、条件更新），锁不能当保证 |
| 线程数莫名上涨 | 用了默认 `SimpleAsyncTaskExecutor` | 自定义 `ThreadPoolTaskExecutor`，给四个参数和线程名前缀 |
| 池满了接口变慢但没报错 | `CallerRunsPolicy` 把任务退回 Tomcat 线程 | 接受背压，或换 `AbortPolicy` 返回 503；监控 `caller thread` 日志 |
| 发布后导出任务卡在 `RUNNING` | 停机没等待任务，或线程被杀 | `awaitTerminationSeconds` + 按 `updated_at` 回收超时的 `RUNNING` |
| 失败任务无限重试 | 没有 `attempts` 上限和退避 | 上限 + `next_retry_at` + 失败原因分类 |
| 消息发了但数据回滚 | 在事务里做远程调用 | Outbox：同事务落一行，投递器重试 |
| Redis 挂掉导致接口 500 | 缓存操作没有降级 | 短超时 + 捕获异常当未命中；限流保护数据库 |

## 验收清单

- [ ] `redis-cli INFO server` 显示 `redis_version:7.4.x`，且 `SET lock:demo token-b NX PX 3000` 返回 `(nil)` 而不是覆盖原值。
- [ ] 连续两次 `GET /api/tasks/1`，第二次日志有 `cache hit`，且 `PTTL task:v1:detail:1` 明显大于 `softExpireAt - now`（物理 TTL 大于逻辑过期）。
- [ ] 等过 `soft-ttl-ms` 再查一次，日志里出现 `cache stale`，而 `EXISTS task:v1:detail:1` 仍为 1（key 还在，只是软过期），说明走的是逻辑过期而不是「key 被删后重建」。
- [ ] `redis-cli DEL task:v1:detail:1` 后并发查两次，日志里只有一次 `cache filled`，另一次是 `fallback to db` 或直接命中。
- [ ] 更新一条任务后 `GET` 能读到新值，紧接着 `EXISTS task:v1:detail:1` 为 0，下一次 `GET` 才把它重建（删除发生在提交之后）。
- [ ] 18 个并发 `POST /api/exports` 全部返回 200，日志里至少有一行 `export pool saturated`，且该行之后的 `export done` 的 `thread` 是 `http-nio-...`。
- [ ] `GET /api/exports/{id}` 的 `attempts` 为 1、`status` 为 `SUCCEEDED`；把导出目录改成不可写后重新提交，能看到 `FAILED` 与 `last_error`，五秒后 `attempts` 变成 2。
- [ ] 停掉 Redis 后 `GET /api/tasks/1` 仍返回 200（降级查库），日志里有 `cache read failed`，接口耗时变长但没有 500。

## 练习

1. **把空值缓存改成布隆过滤器。** 启动时用 `TaskMapper` 查出所有 id 灌进一个位数组，查询前先判断。**自检：** 请求一个从没存在过的 id，布隆过滤器返回「不存在」时不会出现 `cache miss` 日志；手工把某个 id 从库里删掉但不重建过滤器，请求它会被判定为「可能存在」并继续走缓存路径——这条正好证明误判方向是单向的。
2. **复现「删掉别人的锁」。** 先把 `LOCK_TTL` 改成 1 秒，并在 `loadAndStore` 前加一段 `Thread.sleep(1500)`；用两个并发请求触发重建。**自检：** 第二个请求会打印 `cache rebuild lock lost`；把解锁换成一个裸 `DEL`，同一实验会看到两次 `cache filled` 都成功，说明锁失效后没有任何保护——这就是为什么数据层还要幂等。
3. **把 `CallerRunsPolicy` 换成 `AbortPolicy`。** 重跑 18 个并发。**自检：** 第 13 个及之后的请求不再返回 200，日志里出现 `TaskRejectedException`，Tomcat 线程不再被占用；两种策略下最终成功的导出数量不同，用这一点解释「不丢」和「不慢」为什么不能同时要。
4. **测量逻辑过期的陈旧窗口。** 把 `soft-ttl-ms` 设成 5 秒，写一个循环：每秒更新一次任务标题，同时每秒读一次详情，记录读到旧标题的最大持续次数。**自检：** 读数里会出现连续几次旧值，且都落在「逻辑过期之后、重建完成之前」；把 `soft-ttl-ms` 调大后，陈旧次数减少但重建次数也减少，用这两组数说明取舍。
5. **给重试加 `next_retry_at`。** 表里加一列，`findRetryable` 改成按它过滤，`markFailed` 时写入「当前时间 + 2 的 attempts 次方秒」。**自检：** 连续失败三次的时间间隔逐次变长（查 `created_at` 与三次 `updated_at` 的差值），第四次不再被 `sweep` 捞出，`attempts` 停在 3。

## 小结

- 缓存的三条读路径对应三个时间：逻辑过期决定重建，物理 TTL 兜底删除，锁 TTL 决定崩溃后多久能接手；物理必须大于逻辑。
- 穿透靠空值缓存与布隆过滤器（误判单向、不可删除），击穿靠互斥重建或逻辑过期，雪崩靠 TTL 抖动、多级缓存与降级。
- 一致性别追求「某顺序绝对正确」：写库后删缓存 + 提交后删 + 抖动 TTL 是默认，延迟双删只降低概率，跨服务用 binlog 或 Outbox 收敛。
- 锁的三件套：`SET NX PX` 一条命令、value 用唯一 token、Lua 比对后删除；续期覆盖不了 GC 停顿，互斥保证最终要落在数据层。
- Spring Cache 的四个边界（自调用、异常与空值、`sync` 只在单 JVM、淘汰时机）决定了什么时候该手写。
- `@Async` 必须配自定义线程池；`queueCapacity` 才是并发闸门，`CallerRunsPolicy` 用「变慢」换「不丢」。
- 任务先落表再进池，认领用条件更新，重试有上限与退避；线程池保证执行，任务表保证存在。
- 本步在 task-center 留下 `TaskCacheService`、`RedisLock`、`ExportTask` 与 `exportExecutor`；下一步部署与排查会直接观察它们。
