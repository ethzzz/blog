> [!NOTE]
> 这是 **notelab 分组**的第二篇。上一篇把本地环境跑通了，这篇回答一个更上位的问题：一套自托管知识库，为什么要拆成三个仓库？配置到底存在哪、谁能写、谁能读？这些结论是我重构两次、推翻自己两次之后才稳定下来的，不是一开始设计好的。

## 知识地图

```
notelab-b（B 端管理后台，Next.js + antd）
    │
    │ 写（唯一的写入口，带校验）
    ▼
notelab-java（Spring Boot 3.4）
    │
    ├──▶ MySQL.ui_config（单键存储 + 白名单 + 懒 seed）
    │
    │ 读（只读透传 + 发布快照）
    ▼
notelab-c（C 端前台，Next.js）
```

分工一句话：**B 端负责生成，C 端负责消费，Java 负责兜底**。所有"谁来改数据"的问题，都用这句话裁决。

## 一、为什么拆三仓

最早的 NoteLab 是一个大仓库，前后端全塞在一起。拆的导火索很具体：B 端管理后台要引入 antd，构建产物从 200KB 涨到 1.2MB，而 C 端前台对首屏性能是有要求的——两者的依赖策略、发布节奏、甚至部署目标都开始打架。

| 维度 | 单仓 monorepo | 三仓分离 |
|---|---|---|
| 构建互扰 | B 端引入重型依赖拖累 C 端构建 | 各建各的，互不影响 |
| 发布节奏 | 改一行菜单文案要全量构建 | 后台想发就发，前台想发就发 |
| 权限边界 | 只能仓库级控制 | B 端可以单独收紧协作权限 |
| 代价 | — | 跨仓改动要人肉对齐（第四节讲） |

拆仓不是免费的，代价就是最后一行：**一个功能横跨三仓时，版本对齐从"编译器保证"退化成"人肉保证"**。这个代价是否值得，取决于三端有没有独立的发布节奏——我们有，所以拆。如果你的一体化小项目没有这个问题，不必跟风。

还有一个没写进表里的好处：心智负担。monorepo 时代我每次打开仓库，都要在几个技术栈混杂的目录树里重新定位自己——改 C 端首页时 IDE 里晃着 antd 的依赖提醒，改 B 端表单时构建又顺手把 C 端也编了一遍。拆开后每个仓库只干一件事，`git log` 读起来也干净：这个仓库的历史只回答一个领域的问题。排查问题时"问题在哪个仓库"这个判断本身，就淘汰了一半的错误方向。

## 二、ui_config：一张表、一个键

所有 UI 配置（站点信息、首页 Hero、爬塔玩法参数……）都存一张表：

```sql
CREATE TABLE IF NOT EXISTS ui_config (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  config_key   VARCHAR(64) NOT NULL UNIQUE,
  config_value JSON        NOT NULL,
  updated_at   DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

设计取舍集中在"单键"上：比如 `spire` 这一个键，存整棵玩法配置树，而不是每个参数拆一行。

```json
{
  "g_site": { "title": "NoteLab", "icp": "..." },
  "gc_hero": { "enabled": true, "subTitle": "一个自托管知识库" },
  "spire": { "maxLevel": 100, "dailyReward": 50, "shop": [] }
}
```

单键的好处很实在：B 端一次保存就是一次事务；后端做发布快照只需要复制一行；回滚就是把旧行写回去。坏处是**并发覆盖**——两个管理员同时编辑，后保存的会整体覆盖先保存的，字段级合并根本不存在。我的裁决：管理后台就一两个人用，覆盖可以接受，快照兜底就够了。哪天协作人数上来了，再拆行不迟。

键名前缀是刻意的约定：`g_` 开头是全局键，`gc_` 开头是只给 C 端消费的键。肉眼看键名就知道这个配置会影响谁，排查问题时省一半脑子。这些键在后端启动时还有一步"懒 seed"——首次读取发现没有就写入默认值，幂等，重启多少次都不动已有数据。

顺带回答一个常被问到的问题：为什么不用 JSON 文件存配置放在仓库里，非要走数据库？因为配置的变更方是「人在后台点保存」，不是「开发者改代码」。文件方案意味着每次调参数都要发一版，而 ui_config 的改动不经过构建、不经过发布，B 端保存即生效——这正是三仓分工想要的效果：内容运营和代码发布彻底解耦。代价是配置结构失去了类型约束，全靠 B 端表单和后端校验两层兜着；这个取舍在当前规模下我认为是划算的，等配置项多到表单维护不动，再考虑 schema 化。

## 三、读写分离：B 端是唯一写入口

这条规则是被事故教育出来的，先讲规则再讲事故（第五节）。

- **notelab-b**：唯一的写入口。保存走后端校验（结构、取值范围、白名单），通过才落库。
- **notelab-c**：只读。请求时拉配置、本地缓存，**代码里没有任何写路径**。
- **notelab-java**：两边暴露同一组接口，写接口做校验和快照，读接口做透传。

后端 Controller 的定位是"透传 + 快照"，不掺业务逻辑：

```java
@GetMapping("/api/config/{key}")
public Resp<JsonNode> get(@PathVariable String key) {
    return Resp.ok(configService.get(key));    // 读：透传
}

@PutMapping("/api/admin/config/{key}")
public Resp<Void> save(@PathVariable String key, @RequestBody JsonNode value) {
    configService.assertAllowed(key);          // 白名单校验
    configService.snapshot(key);               // 改前先快照
    configService.save(key, value);            // 写：校验后落库
    return Resp.ok();
}
```

`snapshot` 这一步值得单独强调：保存前把旧值整行复制进快照表，出问题时一条 SQL 就能回滚。它便宜到没有理由不做——这也是单键设计带来的红利，快照的对象就是一行 JSON，不存在"快照到一半"的问题。

接口的权限也是分裂的：读接口给 C 端用，匿名可读——配置本来就是前台要渲染的内容，没有保密的必要；写接口挂在管理员鉴权后面，走 RBAC 过滤。另外校验做两层：B 端表单负责体验层的即时校验，后端负责权威校验。前端校验是给用户看的，后端校验是给数据兜底的，两层不能互相替代——因为总有人绕过前端直打接口，多数时候那个人就是我自己在调试。

## 四、跨仓改动怎么对齐：双登记

拆仓最大的代价在这里。给后台新增一个"爬塔配置"页面，要同时改两个仓库：

```ts
// notelab-b：lib/page.ts —— 页面路由登记
export const PageRoutes = {
  '/admin/spire': { title: '爬塔配置', auth: true },
};
```

```java
// notelab-java：菜单种子数据 —— 菜单登记（启动时懒 seed，幂等）
menuSeed.add(new MenuItem("/admin/spire", "爬塔配置", "spire:read"));
```

两边都是登记制：Java 侧 MenuTree 管菜单可见性（走 RBAC 过滤，没权限的用户连菜单都看不到），B 端 PageRoutes 管页面可达性。**漏掉任何一边，故障症状都不一样**：漏 Java 侧，菜单里看不到入口，但手输 URL 能进；漏 B 端侧，菜单点了 404。

我在 PR 模板里放了一条检查项：改了任意一侧登记，另一侧的 PR 是否已关联。仪式感很土，但比记忆可靠。

更进一步的做法是对账脚本：定期拉取两侧的登记集合做差集，输出只在单侧存在的键，跑在 CI 里。它把「漏登记」从上线后的 404 工单，提前到合并前的红灯。人肉检查项负责快速拦截，脚本负责兜底，两者缺一不可。

## 五、两个踩坑记录

**坑一：C 端直接改配置，写脏了一棵树。** 早期为了"预览即时生效"，我在 C 端开发时顺手写过一段直接 update ui_config 的调试代码，提交时忘了删。上线后某个操作绕过 B 端校验写回了一棵结构不完整的树，C 端读出来直接渲染白屏。修复只花十分钟（快照回滚），但结论刻下来了：**配置的写路径必须物理上只有一个，C 端仓库里连调试用的写代码都不该存在**。后来 C 端的配置模块只导出 `readConfig()`，类型层面就没有写方法，想绕都绕不了。

复盘时我还发现一个放大因素：C 端当时对配置解析没有任何防御，JSON 结构不对就一路解构下去，炸在最深的渲染层，报错信息完全对不上因。后来 C 端读配置统一走一层 normalize——结构不对就用默认值顶上，同时打一条告警日志。写路径唯一化是治本，读路径防御化是治重症，两层都要有。

**坑二：白名单静默丢键。** 后端保存接口维护了一张键白名单，不在名单里的键直接丢弃、返回 success。某次 B 端新增了 `gc_footer` 键，忘了同步后端白名单——保存永远"成功"，前台永远读不到，两边还都觉得自己是对的，排查了整整一晚上。静默丢键比报错恶劣得多：报错当场修，静默丢键要等用户发现页面少了东西才暴露。修复方式是把丢弃改成显式报错 `unsupported config key`，白名单不一致在第一时间炸出来，而不是攒成大雷。

## 小结

- 三仓分工：B 端生成、C 端消费、Java 兜底；配置只有一个写入口。
- ui_config 单键存储，换来快照和回滚的简单，代价是并发覆盖——当前规模下可以接受，规模变了再改。
- Controller 只做透传、校验、快照三件事，业务逻辑不进这一层。
- 跨仓改动靠双登记对齐，任何一侧漏登记都有明确的故障症状，PR 检查项兜底。
- 两个坑的共同教训：**静默失败是这个架构最大的敌人**，宁可报错，不可吞掉。

## 练习

1. 给 `ui_config` 的 save 接口加乐观锁：请求带 `expected_updated_at`，不一致返回 409，用两个终端模拟并发覆盖。
2. 实现快照表和回滚接口：`POST /api/admin/config/{key}/rollback` 接受快照 id，回滚前再做一次"回滚前的快照"。
3. 故意在 B 端注册一个后端白名单外的键，观察保存接口的报错路径，确认它不再静默。
4. 给双登记写一个对账脚本：拉取 B 端 PageRoutes 和 Java 侧 MenuTree 的键集合，输出差集，接到 CI 里跑。
