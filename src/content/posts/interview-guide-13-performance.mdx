## 指标体系

### Q1: 有哪些常见的性能指标？⭐ 🔥

**答：**

| 指标 | 全称 | 含义 | 优秀标准 |
|:--|:--|:--|:--|
| FCP | First Contentful Paint | 首次内容绘制 | < 1.8s |
| **LCP** | Largest Contentful Paint | 最大内容绘制（加载体验） | < 2.5s |
| **INP** | Interaction to Next Paint | 交互到下一帧绘制（2024 取代 FID） | < 200ms |
| **CLS** | Cumulative Layout Shift | 累计布局偏移（视觉稳定性） | < 0.1 |
| TTFB | Time To First Byte | 首字节时间（服务端响应） | < 800ms |
| FP | First Paint | 首次绘制（可能只是背景色） | - |
| 白屏时间 | - | 用户看到第一个像素前的时间 | - |

**Core Web Vitals（核心 Web 指标）= LCP + INP + CLS**，Google 搜索排名因素。

```javascript
// FID 为什么被 INP 取代？
// FID 只测量"第一次交互的输入延迟"，忽略处理耗时和绘制耗时
// INP 测量页面整个生命周期内所有交互的响应性，取最差值（P98）
// INP = 输入延迟 + 处理时间 + 渲染延迟（全部计入）
```

## Core Web Vitals 逐项治理（本节是全篇的核心，只报指标不说治理是背书）

### Q2b: LCP 慢，怎么拆解归因？⭐⭐⭐ 🔥

**答：** 先把 LCP 拆成四段，再看是哪一段拖后腿——**不拆就直接说「图片压缩一下」是猜**。

```
LCP = ① TTFB（服务器首字节）
    + ② 资源加载延迟（发现 LCP 资源的时间 - TTFB）
    + ③ 资源加载时长（下载耗时）
    + ④ 元素渲染延迟（下载完到真正绘制：JS 阻塞、CSS 阻塞、字体阻塞）
```

| 卡在哪一段 | 判断依据 | 对应手段 |
|:--|:--|:--|
| ① TTFB | 所有请求都慢，`server-timing` 显示后端耗时高 | CDN/边缘缓存、SSR 缓存、接口聚合、服务端优化 |
| ② 加载延迟 | LCP 图片地址藏在 JS 里，要等 bundle 执行完才发请求 | HTML 直出图片地址、`preload`、`fetchpriority="high"` |
| ③ 加载时长 | 图片/字体文件本身很大 | AVIF/WebP、响应式尺寸、CDN、Brotli |
| ④ 渲染延迟 | 资源下好了但首屏被 JS 长任务或 CSS 阻塞 | 拆长任务、关键 CSS 内联、`font-display: swap` |

**追问：「LCP 元素到底是哪一个？」**
答：不一定是最大的图。DevTools Performance 面板里 LCP 标记会直接标出元素；常见是首屏大图、`h1` 大标题、视频封面。**改错元素是最常见的无效优化**——优化了一张不算 LCP 的图，指标当然不动。

### Q2c: INP 高，怎么优化？⭐⭐⭐ 🔥

**答：** INP = **输入延迟** + **事件处理耗时** + **呈现延迟（下一帧绘制）**，三段要分别治。

| 段 | 根因 | 手段 |
|:--|:--|:--|
| 输入延迟 | 主线程被长任务占着，点击排队 | 拆长任务（`scheduler.yield()` / `setTimeout` 分片）、把计算移入 Worker、减少第三方脚本 |
| 事件处理耗时 | 事件回调里做了重活（同步渲染大列表、复杂计算） | 事件处理里只记录，渲染交给 `startTransition` / `requestAnimationFrame`；输入用 `useDeferredValue` 降级 |
| 呈现延迟 | 处理完还要重排重绘、合成 | 不在交互里读写布局（防强制同步布局）、动画走 `transform/opacity`、减少同时变更的 DOM 数量 |

```javascript
// 典型反例：输入即同步过滤 5 万条数据 → INP 直接爆
input.addEventListener('input', (e) => {
  list.innerHTML = render(filter(hugeData, e.target.value));  // 同步重活
});

// ✅ 拆解：立刻回显输入，重活让出主线程
input.addEventListener('input', (e) => {
  const q = e.target.value;
  queueMicrotask(() => updateListAsync(q));   // 或 startTransition / rAF
});
```

**追问：「INP 为什么取 P98 而不是平均？」**
答：因为交互体验是「最差那一次决定感受」。平均会把少数卡死体验稀释掉；P98 是「几乎最坏情况」的近似，且规避了极端离群值。**这也是为什么优化 INP 要看长尾而不是均值**。

### Q2d: CLS 怎么治理？⭐⭐

**答：** CLS 只有三个主要来源，逐个堵：

| 来源 | 表现 | 修复 |
|:--|:--|:--|
| 图片/视频无尺寸 | 图加载完把下面内容顶下去 | 显式 `width/height` 或 `aspect-ratio`（现代浏览器按宽高比预留空间） |
| 字体切换（FOIT/FOUT） | 自定义字体加载完文字跳一下 | `font-display: swap` + `size-adjust`/`ascent-override` 对齐度量，或 `preload` 关键字体 |
| 动态插入内容 | 广告位/公告条/懒加载占位突然出现 | 预留固定高度容器，**绝不把内容插到已有内容上方** |

```css
/* 关键：给媒体预留空间，是 CLS 最廉价的一招 */
.cover { aspect-ratio: 16 / 9; width: 100%; }

/* 字体度量对齐，减少 swap 时的抖动 */
@font-face {
  font-family: 'Brand';
  src: url('/brand.woff2') format('woff2');
  font-display: swap;
  size-adjust: 96%;
}
```

**追问：「CLS 只统计用户输入后的 500ms 内吗？」**
答：不是「只统计」，是**排除**：`hadRecentInput` 为 true 的布局偏移不计入（用户自己触发的交互导致的位移不算「意外」）。所以「点击展开菜单导致内容下移」不该被算 CLS，而「图片加载把按钮挤走」要算。

## 加载性能优化

### Q3: 从输入 URL 到页面展示，有哪些优化点？⭐⭐⭐ 🔥

**答：** 这是一道"串联所有知识"的大题，按阶段答：

```
输入 URL → DNS → TCP/TLS → HTTP 请求 → 服务器处理 → 响应 → 解析渲染

各阶段优化手段：
┌─────────────┬──────────────────────────────────────┐
│ DNS         │ dns-prefetch 预解析                   │
│ TCP/TLS     │ preconnect 预连接、TLS1.3、HTTP/2     │
│ HTTP 请求   │ CDN、缓存（强缓存/协商缓存）、         │
│             │ Gzip/Brotli、减少请求数（合并/雪碧图） │
│ 服务器      │ SSR、接口聚合（BFF）、数据库优化       │
│ 资源体积    │ 压缩、Tree Shaking、代码分割、         │
│             │ 图片 WebP/AVIF、按需加载              │
│ 解析渲染    │ defer/async、关键 CSS 内联、           │
│             │ 减少重排重绘、GPU 加速                │
└─────────────┴──────────────────────────────────────┘
```

```html
<!-- 资源提示（Resource Hints）-->
<link rel="dns-prefetch" href="//api.example.com">
<link rel="preconnect" href="//cdn.example.com" crossorigin>
<link rel="preload" href="/fonts/main.woff2" as="font" crossorigin>
<link rel="prefetch" href="/next-page.js">  <!-- 空闲时预取下一页 -->
```

### Q3b: preload / prefetch / preconnect / modulepreload 怎么选？⭐⭐ 🔥

**答：** 资源提示是「向浏览器调度器表达意图」，用错了不是没效果，而是**负优化**。先分清优先级语义：

| 提示 | 语义 | 优先级 | 典型场景 |
|:--|:--|:--|:--|
| `dns-prefetch` | 只做 DNS 解析 | 极低 | 第三方域名兜底（成本几乎为零） |
| `preconnect` | DNS + TCP + TLS 全建好 | 低 | 马上要请求的关键第三方源（字体/CDN/API） |
| `preload` | **当前页必需**，提前高优下载 | 高（随 `as` 类型） | LCP 图片、关键字体、被 JS 晚发现的资源 |
| `prefetch` | **未来导航可能用**，空闲下载 | 最低 | 下一页的 chunk |
| `modulepreload` | preload + 解析 + 递归预加载依赖图 | 高 | ESM 入口及其 import 链 |

```html
<!-- preload 必须写 as，否则按最低优先级下载且可能重复请求 -->
<link rel="preload" href="/hero.avif" as="image" fetchpriority="high">
<link rel="preload" href="/font.woff2" as="font" type="font/woff2" crossorigin>

<!-- modulepreload：连依赖一起预热，Vite 构建产物自动注入 -->
<link rel="modulepreload" href="/assets/index-a1b2.js">
```

**三个高频坑（追问必考）：**

1. **preload 了但没用上**：控制台警告 `was preloaded but not used within a few seconds`。preload 是强制下载，资源 3 秒内没被消费就是白占带宽——只 preload「确定首屏要用」的资源。
2. **字体 preload 忘写 `crossorigin`**：字体请求默认匿名 CORS 模式，不带 `crossorigin` 会**下载两次**（preload 一次、实际使用一次）。
3. **preconnect 开太多**：每条连接占着 socket 和拥塞窗口预热成本，超过 4~6 个域名收益递减；只留给「10 秒内一定会请求」的源，其余用 dns-prefetch。

**追问：「`fetchpriority` 和 preload 什么关系？」**
答：preload 解决「**何时发现**」（把请求提前），fetchpriority 解决「**排多高**」（同批请求里的相对优先级）。LCP 图片两个一起用：`<link rel="preload" as="image" fetchpriority="high">` + `<img fetchpriority="high">`；反过来，非首屏大图可以 `fetchpriority="low"` 给关键资源让路。HTTP/2 下它们最终映射为流的优先级权重。

### Q4: script 标签的 defer 和 async 区别？⭐ 🔥

```html
<script src="a.js"></script>          <!-- 同步：阻塞解析，顺序执行 -->
<script src="b.js" async></script>    <!-- 异步下载，下载完立即执行（打断解析，顺序不定）-->
<script src="c.js" defer></script>    <!-- 异步下载，HTML 解析完后按顺序执行 -->

/*
时间线对比：
普通:   解析──停─下载─执行─解析──停─下载─执行─解析
async:  解析────解析────解析（下载完就插队执行）
defer:  解析────解析────解析│DOMContentLoaded前统一执行

使用建议：
- 无依赖的统计脚本 → async
- 有依赖顺序的业务脚本 → defer
- 都不加 → 阻塞渲染，尽量避免
*/
```

### Q7: 首屏白屏时间怎么优化？⭐⭐⭐ 🔥

```
白屏时间构成：DNS + TCP + TTFB + HTML下载 + CSS/JS下载解析

优化手段（按投入产出比排序）：

1. 静态资源上 CDN（TTFB 大幅下降）
2. 开启 Gzip/Brotli（体积降 60-80%）
3. 强缓存 + 文件 hash（二次访问秒开）
4. 路由懒加载 + 分包（减小首屏 JS）
5. 骨架屏 / Loading（体验兜底，非真优化）
6. SSR / SSG（HTML 直出，FCP 最快）
   - SSG：构建时生成（博客、官网）
   - SSR：请求时渲染（个性化内容）
   - 流式 SSR / 岛屿架构：更快 TTFB + 局部 hydration
7. 预渲染（prerender）：SSG 的轻量替代
8. 关键 CSS 内联到 <head>，非关键 CSS 异步加载
9. 接口预请求：HTML 内联 script 提前发起首屏接口，
   与 JS 下载并行，省掉串行等待
10. 客户端缓存首屏数据（localStorage），
    先渲染缓存再静默刷新（SWR 模式）
```

## 渲染性能优化

### Q8: 浏览器渲染流程？哪里会阻塞？⭐⭐ 🔥

```
HTML → DOM 树
              ↘
               Render 树 → Layout（布局）→ Paint（绘制）→ Composite（合成）
              ↗
CSS  → CSSOM

阻塞点：
1. CSS 阻塞渲染：CSSOM 构建完才能合成 Render 树
2. CSS 间接阻塞 JS：JS 执行前要等前面的 CSS 下载完
3. JS 阻塞解析：同步 script 会暂停 HTML 解析
4. Layout 抖动：JS 频繁读写几何属性触发强制同步布局
```

### Q9: 重排和重绘？如何减少？⭐⭐ 🔥

```javascript
// 重排（Reflow/Layout）：几何变化 → 重新计算布局（贵）
// 重绘（Repaint）：外观变化不影响布局（较贵）
// 合成（Composite）：仅 transform/opacity → GPU 处理（最便宜）
// 关系：重排必重绘，重绘不一定重排

// 触发重排的操作：
// - 改变窗口大小、字体
// - 增删 DOM、元素位置/尺寸变化
// - 读取几何属性（offsetTop/clientWidth/getComputedStyle）
//   ← 高频坑！读取会强制刷新布局队列（强制同步布局）

// ❌ 布局抖动（Layout Thrashing）
for (let i = 0; i < 1000; i++) {
  const el = document.getElementById(`item-${i}`);
  el.style.width = el.offsetWidth + 10 + 'px';  // 读写交替，1000 次强制布局
}

// ✅ 读写分离：先批量读，再批量写
const widths = els.map(el => el.offsetWidth);   // 集中读
els.forEach((el, i) => el.style.width = widths[i] + 10 + 'px');  // 集中写

// ✅ requestAnimationFrame 分批写
function batchUpdate() {
  els.forEach(el => el.style.transform = 'translateX(10px)');
}
requestAnimationFrame(batchUpdate);

// 其他手段：
// - transform/opacity 代替 top/left（走合成层，不重排）
```

### Q10: 长列表（10 万条数据）如何渲染？⭐⭐⭐ 🔥

```
虚拟列表（Virtual List）核心思想：
只渲染可视区域 + 上下缓冲区的 DOM（约 20-30 个），
滚动时动态替换内容和位置。

┌─────────────┐ ← 外层容器（撑开总高度：10万 × 行高）
│  (占位)      │ ← transform: translateY(偏移)
│ ┌─────────┐ │
│ │ 可视区   │ │ ← 只渲染这一屏的条目
│ │ item 51 │ │
│ │ item 52 │ │
│ │ ...     │ │
│ └─────────┘ │
│  (占位)      │
└─────────────┘

核心计算：
startIndex = Math.floor(scrollTop / itemHeight)
endIndex = startIndex + Math.ceil(viewportHeight / itemHeight)
visibleData = list.slice(startIndex - buffer, endIndex + buffer)
offsetY = startIndex * itemHeight
```

```javascript
// 简易实现（固定行高）
function VirtualList({ container, itemHeight, total, renderItem }) {
  const viewportH = container.clientHeight;
  const visibleCount = Math.ceil(viewportH / itemHeight);
  const buffer = 5;

  container.addEventListener('scroll', () => {
    const scrollTop = container.scrollTop;
    const start = Math.max(0, Math.floor(scrollTop / itemHeight) - buffer);
    const end = Math.min(total, start + visibleCount + buffer * 2);

    // 只更新可视数据 + 偏移
    renderItems(start, end);
    content.style.transform = `translateY(${start * itemHeight}px)`;
  });
}
// 现成方案：vue-virtual-scroller、react-window、react-virtuoso
// 不定高场景：预估高度 + 渲染后实测缓存高度（react-virtuoso 内置）
```

### Q10b: Web Worker 怎么用？什么时候值得开线程？⭐⭐⭐ 🔥

**答：** Worker 是主线程之外的**独立线程**，有自己的事件循环，**不能碰 DOM**，与主线程靠消息通信。适合「计算密集、可异步、结果晚一点到也行」的活：

| 适合丢给 Worker | 不适合 |
|:--|:--|
| 大数组排序/过滤/聚合（万级以上） | 需要读写 DOM 的逻辑 |
| 解析大 JSON / CSV、加解密、压缩 | 小计算（通信开销 > 计算本身） |
| 图片处理（配 OffscreenCanvas）、音视频编解码 | 强依赖主线程状态、要同步拿结果 |
| 埋点批量序列化、diff 计算 | 频繁小消息来回（每帧 postMessage） |

```javascript
// main.js
const worker = new Worker(new URL('./heavy.worker.js', import.meta.url), { type: 'module' });
worker.postMessage({ list: hugeArray });
worker.onmessage = (e) => render(e.data);

// heavy.worker.js
self.onmessage = (e) => {
  const result = heavyCompute(e.data.list);
  self.postMessage(result);
};
```

**核心考点：数据怎么传（三种方式，成本差几个数量级）**

```javascript
// 1. 结构化克隆（默认）：深拷贝，大对象会卡主线程「发送」这一刻
worker.postMessage({ buf: bigArrayBuffer });          // 拷贝 100MB ≈ 卡几十 ms

// 2. Transferable：所有权转移，零拷贝，原线程立即失效
worker.postMessage({ buf: bigArrayBuffer }, [bigArrayBuffer]);
// 发送后主线程 bigArrayBuffer.byteLength === 0，防止双写

// 3. SharedArrayBuffer：共享内存，真·多线程
// 需要跨源隔离头（COOP/COEP），配合 Atomics 做同步，复杂度最高
```

**追问链：**

- **「开了 Worker 为什么不快反而更慢？」**
  答：三笔账：① 序列化/克隆成本——传 10MB 对象默认深拷贝，光发送就卡主线程，必须 Transferable 或传「索引/参数」让 Worker 自己取数；② 线程启动成本——new Worker 要加载脚本，高频小任务应复用常驻 Worker 池而不是用完即弃；③ 结果回传也要克隆一次。**经验阈值：单次计算 < 10ms 别开 Worker，通信开销吃掉收益**。
- **「Worker 里能发请求吗？能用什么 API？」**
  答：能 fetch/XHR/WebSocket/IndexedDB，有 `self`、`performance.now()`；没有 window/document/localStorage。DedicatedWorker 之外还有 SharedWorker（多页签共享，调试麻烦）和 ServiceWorker（拦截请求，见网络篇）。
- **「怎么优雅地封装？」**
  答：用 comlink 把 postMessage 包装成 `await worker.heavyCompute(list)` 的 RPC 形式（Proxy + 消息 id 配对），避免手写 onmessage 状态机；Vite 用 `new Worker(new URL(...), { type: 'module' })` 原生支持打包。

### Q11: 防抖和节流在性能优化中的应用？⭐ 🔥

```javascript
// 防抖（debounce）：停止触发 n 秒后才执行（结果导向）
// 场景：搜索联想、窗口 resize 后重算、表单校验
function debounce(fn, delay = 300) {
  let timer = null;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

// 节流（throttle）：每 n 秒最多执行一次（频率导向）
// 场景：scroll 滚动加载、mousemove、射击游戏
function throttle(fn, interval = 200) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= interval) {
      last = now;
      fn.apply(this, args);
    }
  };
}

// 选择口诀：
// 只关心最终结果 → 防抖（搜索框）
// 需要持续响应但要限频 → 节流（滚动条）
```

### Q11b: 动画为什么用 requestAnimationFrame？requestIdleCallback 有什么坑？⭐⭐

**答：** 关键是理解一帧里各时机的位置：

```
一帧（60Hz ≈ 16.7ms）的事件循环：
宏任务 → 微任务 → rAF 回调 → 样式计算/布局/绘制 → （有空闲）rIC 回调
```

```javascript
// ❌ setTimeout 做动画：不与刷新率对齐
// 屏幕 60Hz 但你 10ms 一次 → 一半计算白做；屏幕 120Hz → 动画显得慢
// 且后台标签页 setTimeout 仍被节流到 1s，回来动画跳变
setInterval(() => { el.style.left = x++ + 'px'; }, 16);

// ✅ rAF：浏览器在「下一次重绘前」统一回调
// - 与屏幕刷新率对齐（120Hz 屏自动 120fps）
// - 后台标签页自动暂停，省电
// - 同一帧多个 rAF 合并成一次布局/绘制
function tick() {
  el.style.transform = `translateX(${x++}px)`;
  requestAnimationFrame(tick);
}
requestAnimationFrame(tick);
```

**requestIdleCallback 的三个坑：**

1. **不保证执行**：一直忙就永远不回调，必须带 `{ timeout: 2000 }` 兜底，否则埋点上报可能永远发不出去。
2. **回调里别改 DOM**：空闲期在绘制之后，改 DOM 会把布局推到下一帧，造成掉帧；要做 DOM 变更应在回调里再套一层 rAF。
3. **deadline.timeRemaining() 通常只有几 ms**：任务要自己切片，用 `deadline.didTimeout` 区分「真空闲」和「超时强制执行」。Safari 长期不支持，生产代码要 rIC + setTimeout 降级。

**追问：「rAF 里能读布局吗？」**
答：能，而且是**最佳读取点**——rAF 回调在一帧的布局/绘制之前，此时读 `offsetTop` 拿到的是上一帧的稳定布局，不会触发强制同步布局；「rAF 里读、下一段 rAF 里写」是 fastdom 库的核心思路。

### Q12b: V8 垃圾回收机制？和内存泄漏是什么关系？⭐⭐⭐ 🔥

**答：** 先给结论：**GC 回收的是「不可达」对象，泄漏的对象全都「可达」——所以泄漏永远等不来 GC**。这是把 Q12 的排查和 GC 原理串起来的一句话。

**分代回收（核心设计）：**

```
新生代（Young Generation，几 MB）
  ├─ 存活率低的临时对象：函数局部变量、中间结果
  ├─ 算法：Scavenge（复制式）
  │   From 空间 ──存活对象复制──> To 空间，然后整体翻转
  │   两次 Scavenge 还活着 → 晋升老生代
  └─ 特点：频繁、快（只扫新生代）

老生代（Old Generation，可达 GB 级）
  ├─ 存活率高的对象：全局缓存、闭包持有的大对象、晋升对象
  ├─ 算法：Mark-Sweep（标记-清除）+ Mark-Compact（标记-整理）
  │   标记：从根（全局/栈/句柄）遍历，可达的打标
  │   清除：回收未标记对象 → 产生碎片
  │   整理：存活对象向一端移动 → 消除碎片（贵，按需触发）
  └─ 特点：低频、慢 → 必须增量/并发化
```

**为什么老生代不能全停顿标记？——Orinoco 项目的三招：**

| 技术 | 做法 | 解决什么 |
|:--|:--|:--|
| 增量标记（Incremental） | 标记拆成小段，穿插在 JS 执行间隙 | 避免一次停顿几百 ms |
| 并发标记（Concurrent） | 辅助线程在后台标记，主线程不停 | 大堆标记不占主线程 |
| 并行清除/整理（Parallel） | 多个辅助线程一起清扫 | 缩短停顿尾部 |

配合**写屏障（Write Barrier）**：增量标记期间 JS 改了引用关系，记录下来补标，保证不漏。

**追问链：**

- **「新生代为什么用复制而不是标记清除？」**
  答：新生代对象「朝生夕死」，存活率极低（通常 `<10%`）。复制算法只搬存活对象、天然无碎片，成本与存活量成正比；标记清除要扫全空间，成本与总量成正比。老生代存活率高，复制要搬的对象太多，才改用标记清除。**算法选择是被存活率决定的**——这句是加分点。
- **「GC 会造成卡顿吗？怎么观测？」**
  答：会，Major GC 的停顿仍可能到几十 ms。Performance 面板里黄色长条若标注 `Minor GC` / `Major GC` 即 GC 耗时；频繁 Minor GC 说明临时对象分配过猛（每帧 new 大数组），优化方向是对象复用/池化，而不是「调 GC 参数」——浏览器不暴露 GC 调参，`--expose-gc` 只用于排查。
- **「WeakMap 为什么能防泄漏？强引用和弱引用差在哪？」**
  答：GC 判定可达性时**忽略弱引用**：WeakMap 的键没有其它强引用时，键值对整体可回收。所以「DOM 节点 → 附属数据」用 WeakMap 存，节点移除后数据自动释放；用 Map 存则节点被 Map 强引用，永远回收不了——这正是 Q12 游离 DOM 泄漏的机制解释。

### Q16: SSR 为什么能提升首屏？有什么代价？⭐⭐⭐

## 防劣化：性能预算怎么落地（资深面的真考题）

一次性优化谁都会做，**能阻止性能回退才是工程能力**。面试官问「优化后怎么保证不退化」，答「我在 CI 加了检查」不算完，要给出阈值来源与卡口位置。

```json
// 1. 体积预算：写进 CI，超标即失败（bundlesize / size-limit）
{
  "size-limit": [
    { "path": "dist/assets/index-*.js", "limit": "180 kB" },
    { "path": "dist/assets/vendor-*.js", "limit": "300 kB" }
  ]
}

// 2. 指标预算：Lighthouse CI 断言（对关键路由逐页跑）
{
  "ci": {
    "assert": {
      "assertions": {
        "largest-contentful-paint": ["error", { "maxNumericValue": 2500 }],
        "cumulative-layout-shift": ["error", { "maxNumericValue": 0.1 }],
        "total-byte-weight": ["warn", { "maxNumericValue": 1500000 }]
      }
    }
  }
}
```

**阈值从哪来（这问必须答得上）：**

1. 拿**线上 P75** 作基线，不要让实验室分数当基线（实验室永远更好看）；
2. 按页面类型分档（首页严、后台宽），每档留 10~20% 迭代余量；
3. 预算只增不减需要评审——**允许提升预算，但必须写明原因**，否则预算形同虚设。

**卡口位置的选择：**

| 卡口 | 优点 | 局限 |
|:--|:--|:--|
| 本地 pre-commit | 反馈快 | 可被 `--no-verify` 绕过 |
| PR CI 检查 | 强约束、留痕 | 每次都要等构建 |
| 合并后监控告警 + 自动回滚 | 兜底最后一道 | 已经影响用户 |

> 组合用法最现实：**体积预算卡 PR（硬）、Lighthouse 跑主干（软告警）、RUM 指标看板做周度趋势**。

## 常见坑速查表

| 现象 | 根因 | 解法 |
|:--|:--|:--|
| 优化完 LCP 没变 | 优化了非 LCP 元素，或卡在 TTFB/渲染延迟 | 先用 Performance 面板确认 LCP 是哪个元素、卡在哪一段 |
| 实验室分数很好，线上指标差 | 实验室是干净环境 + 主力机型 | 以 RUM 的 P75 为准，按机型分档看 |
| 首屏 JS 变小了但 LCP 变差 | 多了一次串行请求（拆得太碎） | 控制 chunk 数量，关键路径资源 preload |
| 加了 `will-change` 反而更卡 | 合成层过多，显存/合成开销上升 | 只在动画期间加，或干脆不用 |
| 图片懒加载后 CLS 反而升高 | 未预留占位尺寸 | `aspect-ratio` 或 width/height |
| 上报监控后页面变慢 | 上报本身同步执行/频率过高 | `sendBeacon` + 批量 + 采样 + 空闲上报 |
| 虚拟列表滚动白屏 | buffer 太小、滚动事件未节流 | 增加缓冲区、rAF 对齐滚动计算 |
| 性能预算总是刚过线 | 阈值定得贴着现状 | 设预算时留 10~20% 余量，否则每次迭代都红灯 |
| 字体被下载了两次 | preload 没写 `crossorigin`，与实际请求模式不一致 | `<link rel="preload" as="font" crossorigin>` |
| 开了 Worker 反而更卡 | 大对象默认结构化克隆，发送/回传各卡一次 | Transferable 转移 ArrayBuffer，或只传参数让 Worker 自取数据 |
| preload 的资源控制台报警告 | 预加载了 3 秒内没用上的资源 | 只 preload 首屏确定要用的；其余改 prefetch |

## 深水区追问（2026 补充）

**Q：长任务都拆到 50ms 以下了，为什么 INP 还是超标？**

答：50ms 只是「不算 long task」的门槛，不是「交互够快」的门槛——INP 要求从输入到下一次绘制在 200ms 内，而一次交互后面往往还排着好几个小任务和一次渲染。三个常被忽略的点：① `setTimeout(fn, 0)` 有 4ms 最小间隔钳制，拆成 20 段就白送 80ms，应该用 `scheduler.yield()` / `scheduler.postTask()` / 微任务分片；② 拆得太碎总耗时会变长（每次让出都有调度开销），还可能被浏览器重新合并、或饿死低优先级任务；③ 真正的呈现延迟在渲染阶段——回调里改了 500 个 DOM，让出主线程也救不了，要减少同时变更的节点，或用 `content-visibility` 把屏外内容排除出渲染。

**Q：不定高虚拟列表的三个硬边界是什么？**

答：① **滚动锚定**：行高实测后总高度变化会让当前滚动位置漂移，必须按「上方高度差」回补 `scrollTop += newOffset - oldOffset`，否则用户看到内容整体上跳。② **快速滚动 / 拖动滚动条**：一步跨过几百行，缓冲区来不及渲染就是白屏，要么按 `scrollTop` 估值直接渲染目标区（不等测量），要么先铺骨架占位。③ **行内异步高度**（图片、可折叠面板）：测量必须可重入，用 `ResizeObserver` 监听条目变化，而不是只在挂载时量一次。附加一条：`transform` 位移与 `scrollTop` 混用时要统一坐标系，否则 `1px` 取整误差会累积成跳动。

**Q：除了游离 DOM，还有哪些「隐形持有」会让内存只涨不跌？**

答：① 观察者没断开：`PerformanceObserver`、`ResizeObserver`、`IntersectionObserver` 都持有回调闭包，卸载时不 `disconnect()` 就把 DOM 一起留住（`longtask` 观察者最容易被忘）。② 全局缓存没有上限：模块级 `Map` 存接口结果、图片 blob、路由级 store，不设 LRU 就是泄漏。③ 闭包捕获大对象：回调里只用了一个字段，整个大数组却被环境一起捕获。④ 排查前先手动 GC：拍快照前点一次垃圾桶（或开 `--js-flags=--expose-gc`），否则快照里全是待回收垃圾，Comparison 视图会骗人。

**Q：SPA 软导航之后，LCP / CLS 还准吗？上报要注意什么？**

答：不准。LCP 的候选只在一次硬导航内产生，路由切换后不会重算，所以「路由级 LCP」要自建：每次软导航重置观察器，记录新页面的最大元素绘制并自定义上报，别直接抄首屏指标。另外三个污染源：① `visibilityState` 为 `hidden` 时采集的指标，在 bfcache 恢复场景会失真，要按 `NavigationType.back_forward` 过滤；② 后台标签页的定时器被节流、`Date.now()` 与实际渲染无关，时长一律用 `performance.now()` 算；③ 采样偏差——只有能跑 JS 的设备才有数据，崩溃与极慢机型反而缺失，报出来的 P75 会系统性偏乐观（数值比真实更好），必须拿 CrUX 交叉校验。

## 复习卡片

> [!TIP]
> **快速复习清单**
>
> 1. **Core Web Vitals**：LCP < 2.5s、INP < 200ms、CLS < 0.1（INP 已取代 FID）
> 2. **测量**：web-vitals 库 + PerformanceObserver；Lab（Lighthouse）vs Field（RUM）
> 3. **URL 到展示**：DNS 预解析 → preconnect → CDN/缓存 → 分包 → 渲染
> 4. **defer vs async**：defer 顺序执行于解析后；async 下载完就执行
> 5. **代码分割**：路由懒加载 + manualChunks + 大库独立缓存
> 6. **图片**：WebP/AVIF、srcset、loading=lazy；LCP 图 preload + fetchpriority
> 7. **白屏优化**：CDN + Gzip + 缓存 + 懒加载 + SSR/SSG + 接口预请求
> 8. **重排重绘**：读写分离防布局抖动；transform/opacity 走合成层
> 9. **长列表**：虚拟列表，只渲染可视区 + buffer
> 10. **防抖节流**：结果导向用防抖，限频用节流
> 11. **内存泄漏**：定时器/监听/闭包/游离 DOM；Heap Snapshot 对比排查
> 12. **包体积**：Tree Shaking + 按需引入 + 大依赖替换 + 可视化分析
> 13. **案例回答**：STAR + 量化数据 + 沉淀，务必提前准备 1-2 个
> 14. **资源提示**：preload 当前页必需（写 as + crossorigin）、prefetch 未来导航、preconnect 关键源
> 15. **Worker**：计算密集才开；大 buffer 用 Transferable 零拷贝；小计算通信开销反而亏
> 16. **动画时机**：rAF 对齐刷新率、后台自动暂停；rIC 要 timeout 兜底、别在里面改 DOM
> 17. **V8 GC**：新生代 Scavenge 复制、老生代标记整理 + 增量并发；泄漏对象可达，GC 救不了
