> [!NOTE]
> 存储选型的核心不是"哪个新用哪个"，而是三个问题：**要不要随请求发给服务端、能不能异步、数据有多敏感**。先把这三问答完，表都不用看。

---

## 1. 一张表选存储

| 方案 | 容量 | 读写 | 阻塞主线程 | 生命周期 | 跨标签 | 随请求发送 |
| --- | --- | --- | --- | --- | --- | --- |
| **cookie** | 约 4KB/条 | 同步 | 是（很小，可忽略） | 可设过期 | 是 | **是**（同站请求自动带） |
| **localStorage** | 约 5MB | **同步** | **是** | 永久（除非清） | 是（`storage` 事件） | 否 |
| **sessionStorage** | 约 5MB | 同步 | 是 | 标签页关闭即清 | 否（每标签独立） | 否 |
| **IndexedDB** | 配额制，通常数百 MB | **异步** | 否 | 永久（可被清理） | 是（需自行同步） | 否 |
| **Cache Storage** | 配额制 | 异步 | 否 | 永久（Service Worker 管） | 是 | 否 |
| **OPFS** | 配额制 | 异步（Worker 内可拿同步句柄） | 否 | 永久 | 否 | 否 |
| **内存变量** | 受页面限制 | 同步，最快 | 否（本来就快） | 页面刷新即失 | 否 | 否 |

三条选型原则：

1. **要随请求发给服务端** → cookie，且只放会话标识，别放业务数据（每条请求都带，4KB 会显著抬高请求头）；
2. **小、同步读、不敏感** → localStorage（主题、语言、最近一次筛选条件）；
3. **大、结构化、不能卡主线程** → IndexedDB（列表缓存、草稿、离线数据）。

一句话版本：**localStorage 是"同步的小抽屉"，IndexedDB 是"异步的仓库"，cookie 是"自动随信寄出的便签"。**

## 2. localStorage 为什么会卡住首屏

```js
// 这行代码在主线程上同步执行，期间页面完全无法响应
const cache = JSON.parse(localStorage.getItem('bigCache'));
```

成本有三层，很多人只意识到第一层：

- **读 + 反序列化是同步的**：2MB 的 JSON 字符串，`getItem` 本身几毫秒，`JSON.parse` 轻松 30–80ms（低端机更久）；
- **写入更贵**：`setItem` 要序列化、落盘、并通知其它标签，大对象时能到几十毫秒，且**同步**；
- **连带伤害**：`storage` 事件会在其它标签触发，如果那些标签也解析大 JSON，**一次写入会同时卡住好几个标签**。

一个可复现的测量（在 Console 直接跑）：

```js
function measure(label, fn) {
  const t0 = performance.now();
  fn();
  console.log(label, (performance.now() - t0).toFixed(1), 'ms');
}

const big = JSON.stringify(
  Array.from({ length: 20000 }, (_, i) => ({ id: i, title: `任务 ${i}`, done: i % 3 === 0 })),
);
console.log('数据大小', (big.length / 1024 / 1024).toFixed(2), 'MB');

measure('setItem', () => localStorage.setItem('bigCache', big));       // 几十 ms 起
measure('getItem+parse', () => JSON.parse(localStorage.getItem('bigCache'))); // 同样几十 ms
localStorage.removeItem('bigCache');
```

一个真实事故：首屏 `App` 初始化时读一个 2MB 的 localStorage 缓存，低端安卓机白屏约 800ms；换成 IndexedDB 后降到 60ms 以内。**注意：换 IndexedDB 不是"变快了"，而是"不再挡住渲染"**——数据还是异步取，但首屏可以先画壳。

原则：**单条不超过几十 KB，且不要在主线程关键路径上做大 JSON 解析。** 超过这个量级，直接上 IndexedDB。

另外记住 localStorage 的两个硬限制：

- **只存字符串**，存对象必须手动 `JSON.stringify`（也就必然有解析成本）；
- **配额按 origin 计**，写满抛 `QuotaExceededError`，必须 `try/catch`，否则用户"存不进去"而你的代码以为成功了。

## 3. cookie 的属性直接决定安全与登录

```http
Set-Cookie: sid=abc123; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=604800
```

| 属性 | 作用 | 漏了会怎样 |
| --- | --- | --- |
| `HttpOnly` | JS 读不到（`document.cookie` 里没有它） | XSS 能直接偷走会话 |
| `Secure` | 只在 HTTPS 发送 | 明文网络可被截获 |
| `SameSite=Lax` | 跨站**顶层 GET 导航**才带 | 现代浏览器默认按 Lax 处理，但显式写更稳 |
| `SameSite=Strict` | 任何跨站请求都不带 | 从外部链接进来时"看起来没登录"，体验差 |
| `SameSite=None` | 跨站都带，**必须配 `Secure`** | 第三方嵌入场景必需（iframe 登录态） |
| `Domain` | 允许子域共享 | 写错会导致子域拿不到会话 |
| `Max-Age` / `Expires` | 过期时间 | 不写就是会话 cookie，关浏览器即失效 |
| `Partitioned` | 按顶层站点分区存储（CHIPS） | 第三方 cookie 被限制后的替代方案之一 |

**前端无法设置 `HttpOnly`**——这是服务端的事。`document.cookie = 'sid=...'` 写出来的 cookie 永远能被 JS 读取，所以**永远不要用 JS 写会话 cookie**。

```js
// ❌ 前端写会话：XSS 一行 document.cookie 就能偷走
document.cookie = `sid=${token}; path=/`;

// ✅ 服务端下发，前端只管发请求时带上凭据
await fetch('/api/me', { credentials: 'include' });
```

### 3.1 同域 vs 跨域

| 场景 | 需要什么 |
| --- | --- |
| 同域（`app.example.com` 调自身 `/api`） | `SameSite=Lax` 足够 |
| 跨子域（`app.example.com` 调 `api.example.com`） | cookie 设 `Domain=.example.com`；仍算同站，`Lax` 可 |
| 真跨站（`app.com` 调 `api.io`） | `SameSite=None; Secure` + `credentials: 'include'` + 服务端 CORS 白名单 |
| 第三方 iframe 内 | `SameSite=None; Secure`，并考虑 `Partitioned` |

跨站时服务端 CORS 必须满足两条，缺一不可：

```js
// Node/Express 示例
app.use((req, res, next) => {
  res.setHeader('Access-Control-Allow-Origin', 'https://app.example.com'); // 不能是 *
  res.setHeader('Access-Control-Allow-Credentials', 'true');
  res.setHeader('Access-Control-Allow-Headers', 'Content-Type');
  if (req.method === 'OPTIONS') return res.sendStatus(204);
  next();
});
```

> `Access-Control-Allow-Origin: *` 与 `credentials: 'include'` 是互斥的——带凭据的请求要求服务端**明确点名**来源。这就是"我明明配了 CORS 还是不带 cookie"的第一大原因。

## 4. IndexedDB：唯一能放心放大数据的地方

原生 API 是事件式的，心智负担高。先看一个能用的最小封装（生产建议直接用 `idb`）：

```js
function openDB(name, version, upgrade) {
  return new Promise((resolve, reject) => {
    const req = indexedDB.open(name, version);
    req.onupgradeneeded = () => upgrade(req.result);
    req.onsuccess = () => resolve(req.result);
    req.onerror = () => reject(req.error);
  });
}

function run(db, store, mode, fn) {
  return new Promise((resolve, reject) => {
    const tx = db.transaction(store, mode);
    const result = fn(tx.objectStore(store));
    tx.oncomplete = () => resolve(result?.result);
    tx.onerror = () => reject(tx.error);
    tx.onabort = () => reject(tx.error);
  });
}
```

建库与索引（**索引必须建，否则按字段查就是全表扫描**）：

```js
const db = await openDB('app', 1, (d) => {
  if (d.objectStoreNames.contains('tasks')) return;
  const store = d.createObjectStore('tasks', { keyPath: 'id' });
  store.createIndex('byStatus', 'status');
  store.createIndex('byUpdatedAt', 'updatedAt');
});
```

批量写要放在**同一个事务**里——这是性能差一个量级的关键：

```js
// ❌ 每条约一个事务：每笔都要提交、落盘
for (const t of tasks) await run(db, 'tasks', 'readwrite', (s) => s.put(t));

// ✅ 一个事务写 1000 条
await run(db, 'tasks', 'readwrite', (s) => {
  for (const t of tasks) s.put(t);
});
```

为什么差这么多？IndexedDB 的事务是**原子提交**：一次事务一次落盘，N 次事务就 N 次。1000 条数据下，前者可能是后者的 20–50 倍耗时。

按索引查 + 游标分页（避免一次 `getAll` 拉全表）：

```js
// 按状态查（走索引）
const done = await run(db, 'tasks', 'readonly', (s) => s.index('byStatus').getAll(IDBKeyRange.only('done')));

// 分页：先跳过前 N 条，再取 pageSize 条
function page(db, skip, size) {
  return new Promise((resolve, reject) => {
    const out = [];
    const req = db.transaction('tasks').objectStore('tasks').openCursor();
    let advanced = false;
    req.onsuccess = () => {
      const cur = req.result;
      if (!cur) return resolve(out);
      if (!advanced && skip > 0) {
        advanced = true;
        cur.advance(skip);
        return;
      }
      out.push(cur.value);
      if (out.length < size) cur.continue();
      else resolve(out);
    };
    req.onerror = () => reject(req.error);
  });
}
```

注意 `onupgradeneeded` 是**唯一能改结构**的地方：加字段、加索引、迁移数据都在这里做，并且要按版本号逐级迁移，不能假设用户从 v1 直升 v5。

## 5. Cache Storage：给资源用的仓库

它不是给你存业务数据的，是给 **Service Worker** 缓存请求/响应用的：

```js
// 在 Service Worker 里
const cache = await caches.open('static-v3');
await cache.addAll(['/app.css', '/app.js', '/logo.svg']);

self.addEventListener('fetch', (event) => {
  if (event.request.destination !== 'style' && event.request.destination !== 'script') return;
  event.respondWith(
    caches.match(event.request).then((hit) => hit ?? fetch(event.request)),
  );
});
```

版本号写在缓存名里（`static-v3`），升级时删旧缓存：

```js
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(keys.filter((k) => k !== 'static-v3').map((k) => caches.delete(k))),
    ),
  );
});
```

## 6. 多标签同步

```js
// ① storage 事件：同源其它标签收到，发送方自己收不到
window.addEventListener('storage', (e) => {
  if (e.key === 'theme') applyTheme(e.newValue);
  if (e.key === null) logout();          // e.key 为 null 表示 clear()
});

// ② BroadcastChannel：能传对象，发送方自己收不到（同名 channel 的其它实例能收到）
const ch = new BroadcastChannel('app');
ch.postMessage({ type: 'theme', value: 'dark' });
ch.onmessage = (e) => applyTheme(e.data.value);
```

三个细节值得记住：

- **发送方自己收不到**：`storage` 和 `BroadcastChannel` 都是如此。需要"自己 + 别人都执行"时，本地调用一次再广播。
- **`storage` 只在值真的变化时触发**：写入相同字符串不触发。
- **`storage` 是同步触发的**：其它标签若在回调里解析大 JSON，会把那些标签一起卡住（见第 2 节）。

登录态同步的完整写法（退出登录让所有标签一起退）：

```js
const authChannel = new BroadcastChannel('auth');

export function logoutEverywhere() {
  clearLocalSession();                 // 本标签立即执行
  authChannel.postMessage({ type: 'logout' }); // 通知其它标签
}

authChannel.onmessage = (e) => {
  if (e.data?.type === 'logout') clearLocalSession();
};
```

> 会话放 cookie 时天然跨标签共享，不必自己同步；只有把会话放 localStorage 时才需要这套机制——而把 token 放 localStorage 本身就是个安全问题（XSS 可读），所以更好的答案是：**会话放 `HttpOnly` cookie，前端只同步"用户信息"这类非敏感缓存。**

## 7. 容量与配额清理

```js
// 查询用量与配额
const { usage, quota } = await navigator.storage.estimate();
console.log(`已用 ${(usage / 1024 / 1024).toFixed(1)}MB / 配额 ${(quota / 1024 / 1024).toFixed(0)}MB`);

// 申请持久化（是否弹窗、是否自动授予，取决于浏览器与站点参与度）
if (navigator.storage?.persist) {
  const granted = await navigator.storage.persist();
  console.log('持久化存储:', granted);
}
```

- **配额是共享的**：同源下 localStorage（独立小配额）+ IndexedDB + Cache Storage 共用一份总配额，通常按可用磁盘的比例给。
- **写满会抛错**：IndexedDB 抛 `QuotaExceededError`，localStorage 抛同名异常，必须 `try/catch` 并降级（内存缓存 / 提示清理）。
- **浏览器会主动清理**：存储压力下，**未持久化**的 IndexedDB / Cache 可能被整站清掉。关键数据要么申请持久化，要么以服务端为准。

缓存要自己设上限，别指望用户清理：

实现"超限淘汰最旧"，最省事的方式是给每条记录打时间戳，启动时清一次：

```js
const KEEP = 200;

// 写入时带上时间戳（供淘汰排序用）
const putCache = (db, record) =>
  run(db, 'tasks', 'readwrite', (s) => s.put({ ...record, updatedAt: Date.now() }));

// 启动时调用：超过上限就按 updatedAt 删掉最旧的
async function evictOld(db, keep = KEEP) {
  const all = await run(db, 'tasks', 'readonly', (s) => s.getAll());
  if (all.length <= keep) return 0;
  const victims = all
    .sort((a, b) => a.updatedAt - b.updatedAt)
    .slice(0, all.length - keep);
  await run(db, 'tasks', 'readwrite', (s) => {
    for (const v of victims) s.delete(v.id);
  });
  return victims.length;
}
```

规则越简单越不容易出 bug：**启动清一次 + 写入打时间戳**，足够应付绝大多数"缓存越用越大"的问题。

## 8. 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 首屏白屏几百毫秒 | 主线程解析大 JSON（localStorage） | 换 IndexedDB，或把解析移到 Worker |
| 隐私模式/无痕下写入失败 | 配额极小或直接抛错 | `try/catch` + 降级到内存 |
| 跨域请求不带 cookie | `SameSite` 或 CORS 配置 | `SameSite=None; Secure` + `credentials:'include'` + 服务端点名 origin |
| 配了 CORS 仍不带 cookie | `Allow-Origin: *` 与凭据互斥 | 改成明确来源 + `Allow-Credentials: true` |
| 子域登录态不同步 | cookie 没设 `Domain` | 设 `.example.com` |
| 多标签退出不同步 | 用 localStorage 存 token | 改 `HttpOnly` cookie，或 `storage`/`BroadcastChannel` 广播 |
| 关了浏览器缓存就没了 | 用了 sessionStorage | 换 localStorage / IndexedDB |
| 批量写 IndexedDB 很慢 | 每条一个事务 | 同一事务批量写 |
| 按字段查询很慢 | 没建索引 | `createIndex`，并用 `index()` 查询 |
| 升级后老数据读不出 | `onupgradeneeded` 里没做迁移 | 按版本逐级迁移，改结构必须提版本号 |

## 10. 练习

1. **量一次 localStorage 成本**：存一个 2MB 的 JSON，分别测 `setItem` 与 `getItem + JSON.parse` 的耗时。  
   *自检*：能给出两个具体数字，并说明为什么这会拖慢首屏（提示：同步 + 主线程）。
2. **改成 IndexedDB 并量化**：把同一份数据搬到 IndexedDB，测读写耗时，同时录一次 Performance 看主线程是否被长任务占住。  
   *自检*：能解释"异步并不更快，但不阻塞渲染"。
3. **对比单事务与多事务写入**：1000 条数据分别用"每条一个事务"和"一个事务写完"，各测 3 次。  
   *自检*：能给出倍数差异，并说明原因（原子提交次数）。
4. **构造跨域 cookie 失败再修好**：两个本地端口模拟跨域，先用默认 cookie 请求（不带），再补 `SameSite=None; Secure` 与服务端 CORS（带上）。  
   *自检*：能说出"为什么 `Allow-Origin: *` 时浏览器拒绝带 cookie"。
5. **写一个多标签退出**：两个标签打开同一页面，用 `BroadcastChannel` 让 B 标签随 A 标签退出。  
   *自检*：能解释为什么 A 标签要在本地先执行一次，而不是只靠广播。
