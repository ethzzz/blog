> [!NOTE]
> demo 到产品之间隔着一条鸿沟：demo 只要在自己电脑上跑通一次，产品要在所有人、所有时段、所有内容上稳定运行且账单可控。这篇以我知识库里的三个真实功能——文章翻译、自动摘要、摘要卡片生成——为例，讲产品化的四个支柱：场景拆解、成本控制、缓存、灰度。

## 1. 三个真实场景的落地拆解

### 1.1 文章翻译

看似最简单的功能，落地细节最多：

- **分段翻译而非整篇翻译**。整篇长文一次翻译：输出易被 max_tokens 截断、中途格式漂移无法恢复、失败要全部重来。我按 Markdown 标题切块逐段翻译，失败只重试该段。
- **保留格式的 Prompt 设计**：明确要求"保持 Markdown 语法原样，代码块与行内代码不翻译"。这句约束帮我省掉了大量格式修复逻辑。
- **术语表**：翻译技术文章，专名（如 "Serverless"、"Edge Runtime"）保持原文是底线。我在 system prompt 里挂了一个 20 词的术语表，问题直接消失。
- **成本**：qwen-plus 处理一篇 3000 字文章约 0.02 元（2025 年中的价格），缓存命中后二次访问为 0。这个数字让"全站自动翻译"变成可以拍板的决策。

### 1.2 自动摘要

- **构建时生成**（我的选择）：文章发布时异步生成摘要存库，读时零延迟零成本。代价是新文章要等几分钟才有摘要，UI 显示"生成中"。
- 请求时生成只有内容动态（用户评论摘要等）时才值得，账单和 P99 延迟都难看。
- 摘要任务可以走低价模型，质量足够且成本再降一个量级——**模型分级**是成本控制第一刀。

### 1.3 摘要卡片生成

把文章变成可分享的图片卡片。这里 AI 只负责"产出结构化数据"（05 篇的 JSON mode + Zod），排版渲染是纯前端活（Canvas/SVG 绘制）。**AI 负责内容、前端负责呈现**，这是多数"生成类"功能的正确分工——别让模型直接输出 HTML/SVG，校验困难且难改样式。

### 1.4 挑场景的三个筛选标准

比"怎么落地"更前置的问题是"这个功能值不值得做"。我总结出三个筛选标准，三条全过再动手：

1. **输入输出频率高**。翻译/摘要是每篇文章都要跑的高频动作，一次开发长期受益；如果一个功能一个月用两次，demo 完就可以归档了。
2. **容错空间大**。摘要差一点、翻译风格略有出入，用户能接受；但"AI 自动回复客户邮件"这种容错极低的场景，出错成本远大于收益，新手别碰。
3. **有明确的"好"的标准**。能写出评测断言的功能（05/10 篇）才做得起来；"AI 帮我写得更有灵性"这种标准，你连好坏都判断不了，迭代无从谈起。

反过来，我砍掉过的功能也值得说：AI 自动打标签（模型打的标签跟自己的分类体系对不上，人工修的成本比手打还高）、AI 站内搜索（RAG 方案对 200 篇的小站是高射炮打蚊子，关键词搜索够用）。**克制是产品化的一部分，不是每个能用 AI 的地方都该用 AI。**

## 2. 成本控制

### 2.1 三级模型策略

| 任务类型 | 模型档 | 理由 |
| --- | --- | --- |
| 摘要、标签、分类 | 轻量（turbo/mini） | 任务简单，质量差异可忽略 |
| 翻译、问答 | 中档（plus） | 质量与成本平衡 |
| 复杂推理、Agent | 旗舰（max） | 只在高价值路径用 |

这个策略让我整体账单降到"全用旗舰"的 15% 左右。

### 2.2 预算护栏

**必须有硬性的用量熔断**。我的网关层（11 篇会展开）实现了两层：

```ts
// 日预算熔断：超了直接拒绝新请求
if (todaySpent >= dailyBudget) {
  throw new Error("DAILY_BUDGET_EXCEEDED");
}
// 单请求护栏：max_tokens 显式限制，防失控输出
const body = { max_tokens: 2000, /* ... */ };
```

熔断触发后走降级（02 篇的降级表），而不是让账单裸奔。我的警戒线设为月预算的 5%/天——任何异常（重试风暴、被刷）都能在当天被拦住，而不是月底看账单才知道。

### 2.3 防滥用

公开的 AI 接口必须限流：按 IP + 用户维度的速率限制（每分钟 3~5 次）、单请求输入长度上限、异常用户标记。被刷过一次之后，这几行代码你永远不会嫌多。

## 3. 结果缓存

AI 输出对确定性输入是（基本）确定的，所以**缓存命中率就是利润率**。我的三级缓存：

| 层 | 载体 | key | 生命周期 |
| --- | --- | --- | --- |
| L1 内容哈希 | SQLite | hash(model + promptVer + 输入文本) | 永久 |
| L2 会话内 | 内存 Map | hash(消息) | 会话 |
| L3 相似请求 | — | embedding 近邻（可选） | 审慎使用 |

关键设计：

- **key 里必须带 prompt 版本号**（03 篇的 PROMPTS.summary.current）。否则改了 Prompt 读到的还是旧逻辑的缓存，排查起来要命。
- **缓存命中也计数上报**，这样账单分析时能分清"没花钱"和"花了钱"的调用占比。
- 相似请求缓存（问题 A 和问题 B 是同一个意思就返回同答案）在 FAQ 场景很香，但要小心召回错误答案，我的建议是 v1 不做。

我的翻译功能上线三个月，缓存命中率 68%，账单直接砍三分之二——**热门内容天然高复用，缓存是 AI 应用最被低估的省钱手段。**

## 4. 灰度开关

每个 AI 功能都要有独立的开关和降级路径：

```ts
interface FeatureFlags {
  aiSummary: boolean;     // 总开关
  aiSummarySample: number; // 灰度比例 0~1
}

function enabled(flag: boolean, sample: number, uid: string): boolean {
  if (!flag) return false;
  // 按用户哈希稳定抽样，同用户体验一致
  return (hash(uid) % 100) / 100 < sample;
}
```

我的止血清单（按优先级）：

1. **功能级开关**：某功能异常，秒级关掉该功能，其余不受影响
2. **模型级开关**：某模型服务异常，一键切备用模型（改配置即可，别写死）
3. **全局熔断**：预算爆炸/内容事故，全局降级为非 AI 形态（02 篇降级表）

开关要用配置中心或环境变量，**改开关不需要发版**。凌晨两点出问题的时候，你会感谢这个决定。

## 5. 产品化上线检查清单

最后把全篇内容收拢成一张可以打印贴墙的检查清单。每个 AI 功能上线前，我按顺序过一遍，全部打勾才放行：

**功能与体验**
- [ ] 失败路径全部定义了降级动作，且降级对用户可理解（02 篇降级表）
- [ ] 等待超过 3 秒的环节有进度/预期提示（"约需 30 秒"）
- [ ] 结果可编辑或可重新生成（用户对 AI 输出永远要有掌控感）

**成本与滥用**
- [ ] 模型分级配置到位，非高价值路径不用旗舰模型
- [ ] max_tokens 显式设置，输入长度有上限
- [ ] 日预算熔断已接入，阈值为人月预算的 5%
- [ ] 接口限流（IP + 用户维度）已启用
- [ ] 缓存已启用且 key 带 prompt 版本号

**灰度与回滚**
- [ ] 功能独立开关 + 灰度比例，改配置不发版
- [ ] 备用模型路由已配置（11 篇 routes.ts）
- [ ] 评测集通过率 ≥ 基线，评测报告已归档（10 篇）

**安全与合规**
- [ ] 输入输出双向审核已接入（12 篇）
- [ ] 发送出站的数据过了一遍脱敏分级
- [ ] 敏感动作没有交给模型自动执行

这份清单的前身是我在不同功能上重复犯过的错——每次出事就加一条。它现在大概有 30 条，上面是提炼后的核心 15 条。清单思维听起来笨，但在"AI 功能出问题的方式千奇百怪"这个领域，笨办法恰恰是最可靠的办法。

## 6. 从数据反推功能演进：两个真实案例

产品化不是上线即终点，上线后的数据决定功能往哪走。两个我自己的演进案例：

**翻译功能的演进**：上线两个月后看 ledger 报表（11 篇），发现 70% 的翻译请求集中在每周刚发布的新文章上，且同一篇文章平均被访问 3.4 次——说明读者会反复回到新文章。于是我把"构建时生成"升级为"发布即预热"：文章发布的钩子里立刻触发翻译任务进队列，读者第一次打开时大概率已命中缓存。这个改动没动任何 Prompt，纯粹是数据驱动的时序优化，缓存命中率从 52% 提到 81%。

**摘要功能的演进**：人工抽评（10 篇）发现大量"要点太泛"的反馈集中在随笔类文章——随笔没有明确的"要点"可提。数据给出的答案不是改 Prompt，而是**承认场景边界**：随笔类文章自动降级为"首段引用"展示，不走模型。 功能变简单了，满意度反而上升。AI 产品化的一半功课是知道**哪些内容不该用 AI**，这个判断最好由数据而不是热情来做。

两个案例共同的教训：上线后每周看一次功能级数据（调用量、命中率、反馈率），比任何"我觉得应该优化 XX"的直觉都靠谱。功能不是设计出来的，是被数据喂养出来的。

### 3.1 缓存失效策略：什么时候必须清

缓存不能只加不清。三类事件触发我的缓存失效：**prompt 版本变更**（key 里带版本号天然隔离，旧版本缓存自然过期不用主动清）；**内容更新**（文章编辑后，对应的内容哈希变了，key 自然 miss——这是内容哈希方案的隐性优点，不需要任何失效逻辑）；**批量作废**（术语表更新这类全局变更，需要按 prompt 版本号批量删除缓存行，一条 DELETE 的事）。仔细看会发现，选对了 key 的设计，"失效"这个问题几乎被架构消解了——这是我在缓存设计上最喜欢的一课：**好的 key 设计让失效策略退化为无操作**。唯一需要人工介入的场景是"改了模型但想保留旧缓存做对比"，这时按模型名过滤即可，别删，留着当评测素材。

## 小结

- 产品化四支柱：场景拆解、成本控制、结果缓存、灰度开关，缺一个都别上线。
- 模型分级（轻量/中档/旗舰）+ 预算熔断 + 接口限流 = 账单可控三件套。
- 缓存 key 必须带 prompt 版本号；热门内容复用率高，缓存命中率就是利润率。
- 每个 AI 功能独立开关 + 模型级切换 + 全局熔断，且改开关不发版。

## 练习

1. 为你的一个 AI 功能写"场景拆解卡"：输入、输出、失败路径、降级动作、成本估算。
2. 实现内容哈希缓存（含 prompt 版本号），跑一批重复请求验证命中率。
3. 加上日预算熔断 + 功能开关，人为把预算调到 0.001 验证熔断链路。
4. 用按用户哈希做 20% 灰度，观察一周错误率后再放量——把这个流程走一遍，形成习惯。
