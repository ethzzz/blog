## React 基础

### Q1: React 的核心思想是什么？⭐

**答：**

1. **声明式编程**：UI = f(state)，状态驱动视图
2. **组件化**：将 UI 拆分为独立、可复用的组件
3. **单向数据流**：数据从父组件流向子组件
4. **虚拟 DOM**：高效更新真实 DOM
5. **跨平台**：React Native、React DOM、React Canvas

```jsx
// 声明式
function Counter({ initialCount }) {
  const [count, setCount] = useState(initialCount);
  
  return (
    <button onClick={() => setCount(count + 1)}>
      Count: {count}
    </button>
  );
}

// 命令式（jQuery 风格）
$('#btn').click(function() {
  count++;
  $('#count').text('Count: ' + count);
});
```

### Q2: JSX 是什么？为什么要使用？⭐

**答：**

JSX 是 JavaScript 的语法扩展，允许在 JS 中编写 HTML 结构。

```jsx
// JSX
const element = <h1 className="title">Hello, World!</h1>;

// 编译后
const element = React.createElement(
  'h1',
  { className: 'title' },
  'Hello, World!'
);

// 最终生成虚拟 DOM 对象
{
  type: 'h1',
  props: {
    className: 'title',
    children: 'Hello, World!'
  }
}
```

**JSX 的优势：**
- 结构清晰，接近 HTML
- 编译时检查，减少错误
- 性能更好（编译优化）

## Fiber 架构

### Q3: 什么是 Fiber？为什么需要 Fiber？⭐⭐⭐ 🔥

**答：**

Fiber 是 React 16 引入的新协调引擎，核心目标是**增量渲染**。

**问题背景：**
- React 15 的 Stack Reconciler 是同步递归的
- 大组件树更新时会阻塞主线程，导致掉帧

**Fiber 的解决方案：**

```
React 15 (Stack Reconciler)     React 16+ (Fiber)
┌─────────────────────┐        ┌─────────────────────┐
│    同步递归更新      │        │   可中断的异步更新   │
│    (不可中断)       │        │   (时间切片)        │
│                     │        │                     │
│   ██████████████    │        │   ███ ███ ███ ███   │
│   (长时间阻塞)      │        │   (分片执行)        │
└─────────────────────┘        └─────────────────────┘
```

**Fiber 节点结构（按用途分组）：**

```javascript
const fiber = {
  // 1. 身份
  tag: WorkTag,            // FunctionComponent / ClassComponent / HostComponent / HostRoot ...
  key: null,               // diff 用的稳定标识
  type: 'div',             // 元素类型或组件函数
  stateNode: domNode,      // 对应的真实 DOM / 类实例

  // 2. 树结构：用链表把树串起来，替代递归调用栈
  return: parentFiber,     // 父节点
  child: firstChildFiber,  // 第一个子节点
  sibling: nextFiber,      // 下一个兄弟节点
  index: 0,

  // 3. 状态
  pendingProps: {},        // 本次渲染的新 props
  memoizedProps: {},       // 上次提交的 props
  memoizedState: {},       // 函数组件：Hook 链表头；类组件：state
  updateQueue: [],         // 更新队列（setState / useState 的更新）

  // 4. 副作用
  flags: 0,                // 本节点的副作用位掩码：Placement / Update / Deletion / Passive ...
  subtreeFlags: 0,         // 子树副作用冒泡，commit 时可跳过整棵干净子树
  deletions: [],           // 被删除的子节点（挂在父节点上）

  // 5. 优先级与双缓存
  lanes: 0,                // 本节点的更新优先级（bitmask）
  childLanes: 0,           // 子树里还有哪些 lane 待处理
  alternate: otherFiber,   // 双缓存里的另一棵树
};
```

三个最容易讲错的字段：

- **`memoizedState` 不是"组件的 state 对象"**。函数组件里它指向第一个 Hook 节点，Hook 之间用 `next` 串成链表；`useState` 的值存在 Hook 自己的 `memoizedState` 上。
- **`flags` 是位掩码不是布尔**。一次提交可能同时"插入 + 更新"，用按位或叠加；React 16 叫 `effectTag`，17 起改名 `flags`。
- **`deletions` 挂在父节点**。被删的子 fiber 不在自己的 `flags` 上标，而是收集进父节点的 `deletions` 数组，commit 时统一删除。

**遍历：把递归改成「链表 + 循环」**

Stack Reconciler 用递归，调用栈由 JS 引擎管理，跑起来就停不下；Fiber 把树展开成 `child`/`sibling` 链表，用循环逐个处理节点，**每轮循环结束都是一个可中断点**：

```javascript
let nextUnitOfWork = root.current.alternate; // 从根开始

function workLoop() {
  while (nextUnitOfWork && !shouldYield()) {  // 时间片用完就让出主线程
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  if (!nextUnitOfWork) commitRoot(root);      // 整棵树算完才提交
}

function performUnitOfWork(fiber) {
  const child = beginWork(fiber);             // ↓ 向下：diff、生成子 fiber、打 flags
  if (child) return child;

  let node = fiber;
  while (node) {
    completeWork(node);                       // ↑ 向上：创建 DOM、冒泡 subtreeFlags
    if (node.sibling) return node.sibling;    // 有兄弟就转去兄弟
    node = node.return;                       // 没有就回父节点
  }
  return null;
}
```

两个方向要分清：

- **`beginWork` 是前序**：处理当前节点，算出它的子节点；
- **`completeWork` 是后序**：子节点都处理完才回到父节点，这时才创建/更新 DOM、把 `subtreeFlags` 往上冒泡。

**为什么这样就可中断**：暂停时只需要保存一个 `nextUnitOfWork` 指针，恢复时从它继续；递归做不到，因为调用栈里没有可以被外部保存的中间状态。这也是"Fiber 是一个虚拟调用栈"这句话的真正含义。

**渲染流程：render 可中断，commit 不可中断**

```text
render 阶段（可中断、可丢弃、不许有副作用）
  beginWork ↓  逐节点 diff，生成 workInProgress 子树，打 flags
  completeWork ↑ 创建 DOM 实例、冒泡 subtreeFlags
  ↓ 整棵树完成
commit 阶段（同步、一次跑完）
  ① before mutation  读 DOM（getSnapshotBeforeUpdate）、调度 passive effects
  ② mutation         真正增删改 DOM、执行 layout effect 的销毁函数
  ③ layout           执行 useLayoutEffect 创建、componentDidMount/Update、ref 赋值
                     root.current = finishedWork（双缓存交换）
  ↓ 浏览器绘制
  ④ passive effects  useEffect 在绘制后异步 flush
```

四条边界，面试最常追问：

| 问题 | 答案 |
| --- | --- |
| 为什么 commit 不能中断 | DOM 已经改了一半，中断会让用户看到中间态；且 layout effect / ref 必须与 DOM 一致 |
| `useLayoutEffect` 在哪 | commit 的 layout 阶段，同步执行，**会阻塞绘制** |
| `useEffect` 在哪 | 绘制之后异步执行（passive effect），不挡首屏 |
| render 为什么不能写副作用 | render 可能被重复执行（StrictMode 开发期会双调用）或被高优更新打断后重来 |

```jsx
function Demo() {
  useLayoutEffect(() => console.log('layout')); // commit 内，同步
  useEffect(() => console.log('passive'));      // 绘制后，异步
  console.log('render');                        // render 阶段，可能执行两次（开发期）
}
// 首次挂载的稳定顺序：render → layout → passive
```

**双缓存：current 与 workInProgress**

内存里同时存在两棵 Fiber 树：

- `current`：屏幕上正在显示的树；
- `workInProgress`（wip）：render 阶段正在构建的树；
- 两者通过 `alternate` 互指，节点可以复用，不是每次新建。

```javascript
// 简化：commit 的最后一步就是换根
root.current = finishedWork;
```

好处有三个：渲染过程中屏幕上的树始终完整可用；中断或放弃只需丢掉 wip，不影响已显示内容；下次更新可以复用上一棵树的节点与部分计算结果。

**调度：Scheduler 与 Lane 各管什么**

```text
优先级来源（Lane） → 调度器（Scheduler）→ 时间切片执行 render → commit
```

- **Scheduler**：React 自己实现，基于 `MessageChannel`，默认约 5ms 一个时间片（会根据是否有待处理输入动态调整），用 `shouldYield` 决定是否让出；**没有用 `requestIdleCallback`**，因为 rIC 的触发频率不可控，React 需要在高优更新到来时立刻抢占。
- **Lane**：Fiber 内部的 31 位 bitmask，表示"这次更新属于哪一档"。`SyncLane` 通常同步执行、不走 Scheduler；`startTransition` 走 transition lane，可以被高优更新打断。

**常见误区（很容易被追问打穿）**

| 说法 | 问题 | 正确表述 |
| --- | --- | --- |
| "Fiber 就是虚拟 DOM" | 混淆了元素描述与运行时结构 | VDOM 是 React 元素（描述 UI）；Fiber 是协调用的工作单元与状态载体 |
| "有了 Fiber，所有更新都异步" | 忽略了 SyncLane 与 legacy root | 只有并发 root 下的可打断 lane 才走时间切片；同步更新仍然一口气执行 |
| "Fiber 用 requestIdleCallback 切片" | 实现细节记错 | 用的是 Scheduler（MessageChannel） |
| "commit 阶段也可以被打断" | 把 render 的特性套到 commit | 只有 render 可中断，commit 一轮跑完 |
| "useEffect 在 commit 同步执行" | 混淆 layout / passive | `useLayoutEffect` 同步；`useEffect` 绘制后异步 |
| "每个组件每次更新都新建 Fiber" | 忽略了双缓存 | 通过 `alternate` 复用节点，commit 时交换根 |
| "优先级就是 5 级" | 把 Scheduler 当成 Fiber | Scheduler 5 级用于调度；Fiber 用 Lane 表示可合并的优先级 |

**追问链（Fiber 真正的考点）：**

- **「render 和 commit 分别能做什么，为什么这么分？」⭐⭐⭐**
  答：render（`beginWork`/`completeWork`）只做计算：生成 wip 树、diff 出 `flags`，可中断、可丢弃；commit（`commitRoot`）不可中断：一次跑完 DOM 变更、layout effect、`componentDidMount/Update`，再让浏览器绘制。根因是 DOM 操作没有中间态可回滚——改了一半就停下，用户会看到半个界面。所以"Fiber 能中断"严格说只适用于 render；`useLayoutEffect` 里写死循环照样卡死页面。
- **「双缓存 Fiber 树是什么？」**
  答：`current`（屏幕上的）与 `workInProgress`（构建中的）两棵树通过 `alternate` 互指；render 改 wip，commit 末把 `root.current` 指向 wip，完成交换。中断时丢掉 wip 即可，屏幕不受影响。
- **「Lane 模型解决了什么？」**
  答：优先级与批次。React 15 用 `expirationTime`（单值，比较粗），17+ 换成 31 位 bitmask：一次更新可以带多个 lane，按位运算合并；高优（输入）可以打断低优（大列表）渲染；`entangle` 让同一批更新一起提交。
- **「为什么不用 generator 实现可中断？」**
  答：生成器虽然能 `yield`，但它的中间状态不透明，React 需要"随时丢弃当前树、用新优先级重来"以及"复用已完成的部分"，用显式链表 + 指针更容易控制；此外还要在让出时判断是否有更高优先级的更新，生成器做这件事会很别扭。
- **「高优更新打断后，低优已经算完的工作会浪费吗？」**
  答：不一定。wip 树和 `alternate` 会保留已完成节点，恢复时能复用；但优先级不匹配或结构变化时，部分子树要重算。`childLanes` 用来快速判断"这棵子树里还有没有待处理的更新"，避免白跑。
- **「`flags` 和 `subtreeFlags` 为什么都要？」**
  答：`flags` 回答"我自己要做什么"，`subtreeFlags` 回答"我的子树里有没有活"。commit 时如果某棵子树的 `subtreeFlags` 为 0，就能整棵跳过，不用逐节点检查。
- **「`createRoot` 和 `ReactDOM.render` 的 Fiber 有区别吗？」**
  答：都有 Fiber。区别在 root 模式：`createRoot` 是并发 root，更新可以按 lane 切片、被打断；legacy 的 `ReactDOM.render` 走同步路径，Fiber 仍然存在，但不会做时间切片。
- **「Suspense 和 Fiber 什么关系？」⭐**
  答：Suspense 依赖 Fiber 的可中断能力：子树抛出一个 thenable 时，React 捕获它、把该子树标记为挂起、先提交 fallback，等 Promise resolve 后重新渲染；整个过程不需要阻塞主线程。能说到"捕获 promise + 挂起 + 重放"即可，不必背源码。

**面试话术（先给 30 秒版，再按追问展开）**

> "Fiber 是 React 16 的协调引擎。它把递归不可中断的调用栈，换成用 `return/child/sibling` 串起来的链表，每个节点是一个工作单元，循环处理，时间片用完就保存指针让出。render 阶段只算不提交、可中断可丢弃；commit 阶段同步改 DOM、跑 layout effect，不能中断。两棵 Fiber 树通过 `alternate` 做双缓存，commit 末交换根；优先级用 Lane 的 31 位 bitmask 表示，Scheduler 用 `MessageChannel` 做约 5ms 的时间切片。"

#### 追问：Fiber 优先级到底是「5 级」还是 Lane？

面试里很容易答成「5 级：立即/用户交互/普通/低延迟/非必要」，但这只是 **Scheduler 的优先级**，不是 Fiber 内部的全貌。

| 层 | 表示 | 作用 |
|---|---|---|
| Scheduler | 5 个优先级（Immediate / UserBlocking / Normal / Low / Idle） | 决定时间切片顺序 |
| Fiber | Lane（31 位 bitmask） | 表示更新优先级，可合并、可打断 |

更准确的答法：

> "Scheduler 层有 5 个优先级，用来决定时间切片；Fiber 内部用 Lane 表示更细的优先级，按位运算合并。`startTransition` 走 transition lane，可被高优先级打断；commit 阶段同步、不可中断。"

**追问**：5 级和 Lane 怎么对应？→ 大致对应，但不是一一映射；`SyncLane` 通常同步执行，不走 Scheduler；一个更新可以同时带多个 lane。**别说成「Fiber 只有 5 级」**。

## Hooks

### Q4: 常用 Hooks 有哪些？⭐ 🔥

**答：**

```jsx
import {
  useState,      // 状态管理
  useEffect,     // 副作用
  useContext,    // 上下文
  useRef,        // DOM/变量引用
  useCallback,   // 函数缓存
  useMemo,       // 计算缓存
  useReducer,    // 复杂状态
  useLayoutEffect, // 同步副作用
  useImperativeHandle, // 暴露方法
} from 'react';

// 1. useState
const [count, setCount] = useState(0);
const [user, setUser] = useState({ name: '', age: 0 });

// 2. useEffect
useEffect(() => {
  // 副作用逻辑
  const timer = setInterval(() => {}, 1000);
  
  return () => {
    // 清理函数
    clearInterval(timer);
  };
}, [dependency]); // 依赖数组

// 3. useContext
const theme = useContext(ThemeContext);

// 4. useRef
const inputRef = useRef(null);
<input ref={inputRef} />;
inputRef.current.focus();

// 5. useCallback
const memoizedCallback = useCallback(() => {
  doSomething(a, b);
}, [a, b]);

// 6. useMemo
const memoizedValue = useMemo(() => computeExpensiveValue(a, b), [a, b]);

// 7. useReducer
const [state, dispatch] = useReducer(reducer, initialState);
dispatch({ type: 'increment' });
```

### Q5: useEffect 和 useLayoutEffect 的区别？⭐⭐

**答：**

| 特性 | `useEffect` | `useLayoutEffect` |
|:--|:--|:--|
| 执行时机 | 浏览器绘制**后** | DOM 更新**后**，绘制**前** |
| 阻塞 | 异步，不阻塞 | 同步，阻塞绘制 |
| 使用场景 | 大多数副作用 | 需要读取/修改 DOM 布局 |

```jsx
// useEffect：不阻塞渲染
useEffect(() => {
  console.log('useEffect'); // 绘制后执行
}, []);

// useLayoutEffect：阻塞渲染
useLayoutEffect(() => {
  console.log('useLayoutEffect'); // 绘制前执行
  // 适合需要同步测量的场景
  const rect = divRef.current.getBoundingClientRect();
}, []);

// 执行顺序
// render -> useLayoutEffect -> 浏览器绘制 -> useEffect
```

**使用场景：**

```jsx
// useLayoutEffect：避免闪烁
function Tooltip({ target }) {
  const [position, setPosition] = useState({ top: 0, left: 0 });
  const tooltipRef = useRef(null);
  
  useLayoutEffect(() => {
    // 在绘制前计算位置，避免闪烁
    const rect = target.getBoundingClientRect();
    setPosition({
      top: rect.bottom + 8,
      left: rect.left
    });
  }, [target]);
  
  return <div ref={tooltipRef} style={position}>...</div>;
}
```

### Q6: useCallback 和 useMemo 的区别？⭐⭐ 🔥

**答：**

```jsx
// useCallback：缓存函数
const memoizedFn = useCallback(() => {
  doSomething(a, b);
}, [a, b]);

// useMemo：缓存计算结果
const memoizedValue = useMemo(() => computeExpensiveValue(a, b), [a, b]);

// 等价关系
useCallback(fn, deps) === useMemo(() => fn, deps)
```

**使用场景：**

```jsx
// useCallback：避免子组件不必要的重渲染
const Parent = () => {
  const [count, setCount] = useState(0);
  
  // ❌ 每次渲染都创建新函数，子组件会重渲染
  const handleClick = () => console.log('clicked');
  
  // ✅ 缓存函数引用
  const handleClickMemo = useCallback(() => {
    console.log('clicked');
  }, []);
  
  return <Child onClick={handleClickMemo} />;
};

const Child = React.memo(({ onClick }) => {
  console.log('Child rendered');
  return <button onClick={onClick}>Click</button>;
});

// useMemo：缓存昂贵计算
const ExpensiveComponent = ({ items }) => {
  // ❌ 每次渲染都重新计算
  const sorted = items.sort((a, b) => a.price - b.price);
  
  // ✅ 只在 items 变化时计算
  const sortedMemo = useMemo(() => {
    return [...items].sort((a, b) => a.price - b.price);
  }, [items]);
  
  return <List items={sortedMemo} />;
};
```

### Q7: useRef 的用途？⭐⭐

**答：**

```jsx
// 1. 获取 DOM 元素
function InputFocus() {
  const inputRef = useRef(null);
  
  const focusInput = () => {
    inputRef.current.focus();
  };
  
  return (
    <>
      <input ref={inputRef} />
      <button onClick={focusInput}>Focus</button>
    </>
  );
}

// 2. 保存可变值（不触发重渲染）
function Timer() {
  const [count, setCount] = useState(0);
  const intervalRef = useRef(null);
  
  useEffect(() => {
    intervalRef.current = setInterval(() => {
      setCount(c => c + 1);
    }, 1000);
    
    return () => clearInterval(intervalRef.current);
  }, []);
  
  const stop = () => clearInterval(intervalRef.current);
  
  return <div>{count}</div>;
}

// 3. 保存上一次的值
function usePrevious(value) {
  const ref = useRef();
  
  useEffect(() => {
    ref.current = value;
  }, [value]);
  
  return ref.current;
}

// 使用
const prevCount = usePrevious(count);
```

## Hooks 原理与陷阱（这一段才是中高级的分水岭）

### Q7b: 为什么 Hooks 不能写在条件/循环里？⭐⭐⭐ 🔥

**答：** 因为 Hooks 的状态不是存在组件上，而是**存在 fiber 的链表里，靠调用顺序对齐**。

```
mount 阶段（首次渲染）
fiber.memoizedState → hook1 → next → hook2 → next → hook3 → null
                        ↑        ↑        ↑
调用顺序：           useState  useEffect  useRef
```

每次渲染时，React 沿着 `memoizedState` 链表**按顺序**读取每个 hook 的状态。如果某次渲染少调了一个 hook（因为写在 if 里），链表指针就会错位——第二个 hook 读到第一个的状态，`useState` 拿到 `useEffect` 的 effect 对象。这不是「React 不让你这么写」，而是**顺序即身份，没有 key 可对齐**。

```jsx
// ❌ 条件调用：第一次渲染 cond=true，第二次 false，链表错位
if (cond) {
  const [a, setA] = useState(0);
}
const [b, setB] = useState(1);

// ✅ 规则：所有 hook 无条件、按固定顺序、在顶层调用；
//    条件逻辑放到 hook 内部或返回值上
const [a, setA] = useState(0);
if (!cond) { /* 用不用 a 是另一回事，hook 必须调 */ }
```

**追问：「那自定义 hook 里的 hook 算不算违反规则？」** 答：不算——只要自定义 hook 本身无条件调用、且以 `use` 开头（让 lint 插件能识别），它内部的 hook 也天然按固定顺序执行。

### Q7c: 什么是「闭包陷阱」（stale closure）？⭐⭐⭐ 🔥

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const timer = setInterval(() => {
      console.log(count);      // ❌ 永远是 0
      setCount(count + 1);     // ❌ 永远加不到 1 以上
    }, 1000);
    return () => clearInterval(timer);
  }, []); // 空依赖：effect 只跑一次，捕获了首次渲染的 count=0

  return <div>{count}</div>;
}
```

**根因**：函数组件每次渲染都是**一次全新的函数调用**，闭包捕获的是「这一次渲染的变量快照」。空依赖的 effect 只执行一次，回调里捕获的就是首次渲染的 `count`（=0）。组件重渲染不会改写已有闭包里的变量。

**三种解法（按推荐度）：**

```jsx
// ① 函数式更新：不依赖外部快照值（最优）
setCount(c => c + 1);

// ② useRef 保存最新值（需要读取但不想重建 effect）
const countRef = useRef(count);
useEffect(() => { countRef.current = count; });

// ③ 把依赖写全，effect 重建（代价是清理/重建频繁）
useEffect(() => { /* ... */ }, [count]);
```

**追问：「哪些场景最容易踩？」** 答：① 定时器/轮询；② WebSocket 消息回调里读 state；③ 事件监听回调（`addEventListener` 注册一次但需要读最新 state）；④ 防抖节流函数的参数。这类「长生命周期回调 + 短生命周期变量」的组合就是闭包陷阱的高发区。

### Q7d: setState 是同步还是异步？批处理怎么变了？⭐⭐⭐

**答：** 在 React 18 之前，`setState` 的「异步」只是**批处理**的表现：在 React 合成事件和生命周期里会合并成一次渲染，在 `setTimeout`/原生事件里是同步立即渲染。**React 18 起自动批处理覆盖所有场景**（包括 Promise 回调、setTimeout、原生事件），只有 `flushSync` 能强制同步刷。

```jsx
// React 18：这两次 set 会合并成一次渲染
setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);   // 同一个微任务批次，只渲染一次
}, 0);

// 需要立刻拿到 DOM 更新后同步执行（慎用，会打断批处理）
import { flushSync } from 'react-dom';
flushSync(() => setCount(c => c + 1));
```

**追问：「连续 setState 三次，值会变成 3 吗？」** 答：取决于写法——`setCount(count + 1)` 三次都基于同一快照，最终 +1；`setCount(c => c + 1)` 三次基于前一次结果累积，最终 +3。**这是同一道题的两个知识点：批处理 + 函数式更新**。

### Q7e: React 18 的并发特性怎么用？⭐⭐⭐

```jsx
// useTransition：把「非紧急更新」标记为可打断
const [isPending, startTransition] = useTransition();

function onSearch(keyword) {
  setKeyword(keyword);              // 紧急：输入框必须立刻响应
  startTransition(() => {
    setResults(search(keyword));    // 非紧急：可被后续输入打断
  });
}

// useDeferredValue：给「派生的重计算」降级
const deferredQuery = useDeferredValue(query);
const list = useMemo(() => filterHugeList(deferredQuery), [deferredQuery]);
```

**追问链：**

- **「transition 和 debounce 有什么区别？」** 答：debounce 是**延迟**（等用户停下再算），transition 是**让路**（立刻开始算，但一有紧急更新就丢弃重来）。所以 transition 不会让结果变慢，只是保证输入不卡；debounce 会牺牲响应时效。搜索框这类「输入必须跟手、结果可以稍慢」的场景，transition 更合适，且不需要猜延迟时长。
- **「`useDeferredValue` 什么时候真的有用？」** 答：只在「子组件渲染成本高、且数据能从当前 props 派生」时有用。如果渲染很便宜，它只是多一层状态反而更慢——这是典型的「看起来高级但不该用」的 API。

**追问链（性能题的天花板在这里）：**

- **「怎么证明某个组件在无谓重渲染？」⭐⭐⭐**
  答：三步：① React DevTools Profiler 录一段交互，看 flame chart 里哪些组件「渲染了但 props 没变」；② 打开「Highlight updates」直观看到闪烁范围；③ 开发期加 `why-did-you-render` 打印具体是哪个 prop 导致比较失败（通常是内联对象/函数、或 `children` 每次新建）。**能说出「先测再改」的顺序，比背 8 条优化手段值钱。**
- **「什么时候不该用 memo/useMemo？」**
  答：当组件渲染成本很低（几百个 DOM 节点以内）、父组件很少重渲染时，`memo` 的比较开销 + 缓存维护成本可能高于收益。判断标准是「有没有实测到重渲染热点」，而不是「代码里看到子组件就包 memo」。这也是 React 官方一直强调 memo 不能到处撒的原因。
- **「React Compiler 会取代这些手写优化吗？」**
  答：方向上是。React Compiler 在编译期自动插入 memoization，把手写的 `useMemo/useCallback/memo` 变成编译器职责。但它要求代码符合规则（纯函数、不在渲染期改外部状态），违反规则的部分会被跳过。所以「理解闭包与依赖」依然是必要的——**编译器只能优化语义正确的代码**。

## 常见坑速查表

| 现象 | 根因 | 解法 |
|:--|:--|:--|
| 定时器里读到的 state 永远是最初值 | 闭包陷阱（effect 只挂载一次） | 函数式更新 / ref 同步最新值 |
| 条件渲染时 hook 报「Rendered fewer hooks than expected」 | hook 写在 if/循环里，链表错位 | hook 提到顶层，条件逻辑内移 |
| 无限重渲染 | effect 依赖里放了每次新建的对象/函数 | 依赖拆到原始值，或把对象创建提到外面 useMemo |
| 改列表顺序后输入框内容串了 | 用 index 当 key | 用稳定唯一 id 当 key |
| `setState` 后立刻读 state 拿不到新值 | 批处理 + 快照语义 | 在 useEffect/回调里读，或用函数式更新 |
| 弹窗定位闪一下才归位 | 用 useEffect 测量 DOM | 换 useLayoutEffect 在绘制前算完 |
| Context 一改整棵树都重渲染 | Provider value 每次新建对象 | value 用 useMemo，或按域拆多个 Context |
| SSR 报 `window is not defined` | 渲染期访问浏览器 API | 移到 useEffect / 动态 import `ssr: false` |
| StrictMode 下 effect 执行两次 | 开发期故意双调用以暴露副作用 | 清理函数写完整，别关 StrictMode |

## 深水区追问（2026 补充）

**Q：RSC 和 SSR 是两件事，区别到底在哪？**

SSR 是**同一棵组件树渲染两遍**：服务端产出 HTML，客户端把同一份组件代码再跑一遍做 hydration，所以组件代码仍然要进客户端 bundle。RSC 是**两种组件**：服务端组件只在服务端执行（可以直接 `async/await` 查库、读文件，但不能用 hooks、不能绑事件），产出的是序列化的 RSC payload（Flight 格式）流式下发；客户端组件才打进 bundle 并参与 hydration。所谓 `'use client'` 划的是**模块边界**而不是某个组件——一个文件标了它，这个文件引用的东西统统进客户端图。收益是服务端组件的依赖不进 bundle；代价是两套运行模型，且跨边界的 props 必须可序列化。

**Q：`useSyncExternalStore` 解决的是什么「撕裂」？为什么 `useEffect` 订阅会出问题？**

并发渲染允许一次渲染**中途被打断、丢弃、重来**。用 `useEffect` + `useState` 订阅外部 store 时，effect 在提交之后才跑，而 store 可能在渲染过程中已经变了：同一次提交里 A 组件是在渲染早期读到 v1、B 组件是重渲染后读到 v2，最终 UI 内部不一致——这就是 tearing。`useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot)` 在**渲染期间同步读快照**，并在 store 变化时强制同步重渲染，保证一次提交内所有读取都来自同一版本。两个坑：`getSnapshot` 必须返回**稳定引用**（每次 new 一个对象会无限重渲）；SSR 必须提供 `getServerSnapshot`，否则服务端渲染直接报错。

**Q：并发渲染下，哪些「写在渲染函数里的假设」会失效？**

① 渲染可能执行多次或被丢弃，所以**不能在 render 里改外部变量、发请求、写 ref**（被丢弃的那次也会留下痕迹）；② StrictMode 双调用只是把这个风险提前暴露，生产环境一样会因为打断而重放；③ `useState(fn)` 的初始化函数必须是纯的，它可能在渲染被丢弃时白跑；④ transition 里的更新可能被后续高优更新**整体覆盖**，不要在里面做「读完 DOM 再写状态」的时序依赖；⑤ 需要唯一 id 用 `useId`，不要用 `Math.random()`（hydration 对不上）。一句话：渲染阶段只做「从 props/state 算出 UI」，其余全部挪到 effect 或事件回调。

**Q：React Compiler 的取舍在哪？哪些代码它不会（也不该）优化？**

它做的是**编译期自动插 memo 缓存**：把 `useMemo` / `useCallback` / `memo` 的职责收归编译器，前提是组件满足 Rules of React（渲染纯、props 与 state 不可变、hook 无条件调用）。一旦检测到违反（渲染期改 props、render 里读 `ref.current`、依赖里藏了可变捕获），该组件会 **bailout**：不优化但照常运行，也可以显式写 `"use no memo"` 跳过。代价不在运行时而在工程侧：构建时间变长、调试栈里多出缓存调用、旧代码混用时容易出现「编译器认为没变、手写 useMemo 认为变了」的心智负担。它能消掉的是「重复渲染」，消不掉「一次渲染本身很贵」——那还是得靠虚拟化、拆组件、少 DOM。
