## 一句话本质

这个项目的技术含量不在"页面数量"，在三件事：**身份与路由的装配顺序**（决定刷新会不会 404）、**权限的两层落点**（路由级与按钮级各自在哪实现、后端如何兜住越权）、**可运维性**（有指标的优化、能还原的栈、能回滚的发布）。做到了这三件，它就是一个"会架构、能救火、有数字"的作品；缺任何一件，它就是一堆 Element Plus 页面。

## 原理拆解

### 1. 三阶段的依赖顺序不可交换

```text
阶段一  身份与骨架     登录 / token / 动态路由装配 / 布局与标签页 / 权限指令
   ↓       决定"页面能不能进来"，返工代价最高，必须先定
阶段二  业务闭环       字典 / CRUD 表格 / 表单校验分层 / 批量与跨页选择 / 导出
   ↓       决定"需求能不能持续交付"，是前 6 章的练兵场
阶段三  可运维         性能基线与优化 / 错误边界与 chunk 恢复 / 测试门禁 / 构建与回滚
           决定"能不能上线、能不能讲"，也是面试里最稀缺的部分
```

顺序不可交换的具体理由：

- 先做业务页面，动态路由改造时要把每个页面的注册方式重写一遍（我见过两次这样的返工，成本都在一周以上）；
- 没有阶段一的权限指令，阶段二的按钮权限就变成"每个页面自己 `v-if`"，之后没法统一审计；
- 性能与错误兜底必须在业务形态稳定后做，否则优化对象会变（但**剖析与埋点要在阶段二就开始**，不然阶段三无基线）。

### 2. 每阶段"完成"的判定

| 阶段 | 交付物 | 判定证据（不是"我觉得好了"） | 最常见的返工 |
|---|---|---|---|
| 一 | 登录 + 动态路由 + 布局 + 双层权限 | 用两个不同角色账号跑通：菜单不同、按钮显隐不同、直接敲无权限 URL 进 403、刷新任意深层路由不 404 | 通配 404 路由注册早于 `addRoute`，导致所有动态路由永远匹配到 404 |
| 二 | 2 个完整业务模块（用户 + 一条业务域） | 每个模块能查/增/改/删/批量/导出，字典驱动状态字段，校验失败与接口失败都有可见反馈 | 选中态存 DOM（翻页即丢）、把字典值写死在页面里 |
| 三 | 指标文档 + 兜底体系 + CI 门禁 + 发布流程 | 有优化前后数字与测法；断网/删 chunk 两个故障场景能自愈；PR 上违规 import 会被拦 | 只做了 `errorHandler` 就以为兜住了（不做局部边界，仍是整页白屏） |

## 技术选型对照

| 维度 | 本方案：Vue 3 + Pinia + Router 4 + Element Plus | React + Zustand + Next | 直接采用 RuoYi-Vue3 |
|---|---|---|---|
| 从零到能演示 | 2–3 周（骨架代码本章给全） | 3–4 周（要自己拼表格、权限、请求层） | 2–3 天（菜单、字典、代码生成器都有） |
| 后端配合成本 | 需要 `getInfo` + `getRouters` 两个接口 | 同上，或全在前端配路由表 | 零：与 RuoYi 后端天然对齐 |
| 权限模型表达力 | 后端下发菜单 + 前端指令双保险，边界清晰 | 通常前端路由表 + `accessApi`/中间件，SSR 下更自然 | 同款双保险（本方案的参照物） |
| 首屏与包体 | 路由级 chunk + `manualChunks`，可控但要自己做（第 13 章） | Next 的路由分割更自动，但后台项目常因 RSC 复杂度得不偿失 | 默认打包较全，体积偏大，裁剪需读源码 |
| 二开自由度 | 高：所有基础设施都在自己手里，能讲清每行为什么这样写 | 高，但要额外处理 Element Plus 与 SSR 的兼容 | 低到中：要迁就它的约定（Shiro 权限字符、菜单表结构、多环境配置） |
| 面试叙事价值 | 最高：能答"刷新为什么 404""按钮权限在哪层生效""chunk 失效怎么恢复" | 高，但 Vue 岗位问不到这些细节 | 低：容易被追问"这部分是框架自带的吧" |
| 服务端渲染/SEO | 不适用（后台不需要，若需要见第 18 章 Nuxt） | Next 天然支持，管理后台里常是多余复杂度 | 不支持，需换技术栈 |
| 长期维护 | 取决于分层规范与测试门禁（第 14、15 章） | 取决于同类的规范落地 | 升级跟上游，改自己代码要处理合并冲突 |

结论按场景给：

- **给 Vue 岗位准备作品集** → 本方案。理由是最后一行：基础设施自己写过一遍，才撑得住第二轮追问。
- **公司要 3 个月内上线一套内部系统** → 直接用 RuoYi-Vue3（或同类脚手架），别自己造。这时候自研是负资产。
- **团队主栈是 React 或需要 SEO/服务端** → React + Next，别混栈做后台。
- **已经有一套 Vue 2 老后台** → 不要全量重写，按 RuoYi-Vue3 的结构把新模块写成 Vue 3，用微前端或 iframe 做过渡；等模块边界清晰后再逐域替换（这类渐进迁移的取舍属于工程化路线里微前端与构建配置的范畴，此处不展开）。

## 阶段一：登录 + 动态权限路由 + 布局

**请求层**（`api/request.ts` 的关键三段，其余照常规）：

```ts
const service = axios.create({ baseURL: import.meta.env.VITE_APP_BASE_API, timeout: 15_000 })

service.interceptors.request.use((config) => {
  const token = getToken()
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

let reloginPrompted = false

service.interceptors.response.use(
  (res) => {
    const { code = 200, msg, data } = res.data ?? {}
    if (code === 200) return data
    if (code === 401) handleUnauthorized()
    else ElMessage.error(msg || '请求失败')
    return Promise.reject(new Error(msg || `code ${code}`))
  },
  (error) => {
    if (error.response?.status === 401) handleUnauthorized()
    else if (!axios.isCancel(error)) ElMessage.error(error.message || '网络异常')
    return Promise.reject(error)
  },
)

// 并发 5 个 401 只弹一次：单点标志位 + 清理后跳转
function handleUnauthorized() {
  if (reloginPrompted) return
  reloginPrompted = true
  ElMessageBox.confirm('登录状态已过期，请重新登录', '提示', { confirmButtonText: '重新登录' })
    .then(async () => {
      await useUserStore().logout()
      location.href = `/login?redirect=${encodeURIComponent(location.pathname + location.search)}`
    })
    .finally(() => { reloginPrompted = false })
}
```

**用户 store**（setup store，权限字符与角色都放这里）：

```ts
export const useUserStore = defineStore('user', () => {
  const token = ref(getToken())
  const profile = ref<UserProfile | null>(null)
  const permissions = ref<string[]>([])
  const roles = ref<string[]>([])

  async function login(payload: LoginPayload) {
    const data = await apiLogin(payload)
    token.value = data.access_token
    setToken(data.access_token)
  }

  async function getInfo() {
    const data = await apiGetInfo()
    profile.value = { userName: data.userName, nickName: data.nickName, avatar: data.avatar }
    permissions.value = data.permissions ?? []
    roles.value = data.roles ?? []
  }

  async function resetAll() {
    removeToken()
    token.value = ''
    profile.value = null
    permissions.value = []
    roles.value = []
    usePermissionStore().reset()              // 必须一起清，否则下次登录拿到旧路由
    useDictStore().clear()
  }

  return { token, profile, permissions, roles, login, getInfo, logout, resetAll }
})
```

**权限 store：把后端菜单树转成路由**（`component` 字符串 → 动态 import）：

```ts
const modules = import.meta.glob('@/views/**/index.vue')

function loadComponent(name: string) {
  if (name === 'Layout') return () => import('@/layout/index.vue')
  if (name === 'ParentView') return () => import('@/layout/components/ParentView.vue')
  const loader = modules[`/src/views/${name}/index.vue`]
  if (!loader) {
    // 后端把组件路径配错了：不要让整个路由装配失败，只让这一个菜单坏
    reportError(new RouteComponentError(name), { phase: 'route-assembly', component: name })
    return () => import('@/views/error/500.vue')
  }
  return loader as () => Promise<unknown>
}

export const usePermissionStore = defineStore('permission', () => {
  const menuTree = shallowRef<MenuItem[]>([])
  const loaded = ref(false)

  async function generateRoutes() {
    const routers = await apiGetRouters()
    menuTree.value = routers
    return routers.map(toRouteRecord)
  }

  function toRouteRecord(item: MenuItem): RouteRecordRaw {
    return {
      path: item.path,
      name: item.routeName ?? item.path,
      component: loadComponent(item.component),
      redirect: item.redirect,
      meta: { title: item.meta.title, icon: item.meta.icon, perms: item.perms, keepAlive: item.meta.noCache !== 1 },
      children: item.children?.map(toRouteRecord),
    } as RouteRecordRaw
  }

  function reset() { menuTree.value = []; loaded.value = false }

  return { menuTree, loaded, generateRoutes, reset }
})
```

用 `import.meta.glob` 而不是模板字符串动态 import，是因为 `import('@/views/' + name + '/index.vue')` 在 Vite 里要靠静态分析确定范围：模板字符串能工作但会把整个目录切成大量 chunk 并失去类型；`glob` 的显式映射**同时避免了"路径拼错时报错信息完全看不出原因"**（这是 RuoYi 前端那张表里"页面空白"一行的根因）。

**守卫：本章必须完整可运行的一段**（`router/guard.ts`）：

```ts
import type { Router, RouteLocationNormalized } from 'vue-router'

const WHITE_LIST = ['/login', '/404', '/403']

export function setupGuard(router: Router) {
  router.beforeEach(async (to: RouteLocationNormalized) => {
    const userStore = useUserStore()
    const permissionStore = usePermissionStore()

    if (!userStore.token) {
      return WHITE_LIST.includes(to.path) ? true : { path: '/login', query: { redirect: to.fullPath } }
    }

    if (to.path === '/login') return { path: '/' }

    if (permissionStore.loaded) {
      return hasRoutePermission(to, userStore.permissions) ? true : { path: '/403' }
    }

    try {
      if (!userStore.profile) await userStore.getInfo()
      const routes = await permissionStore.generateRoutes()
      routes.forEach((record) => router.addRoute(record))

      // 通配兜底必须最后注册，否则它会先吃掉所有动态路由
      if (!router.hasRoute('notFound')) {
        router.addRoute({ path: '/:pathMatch(.*)*', name: 'notFound', redirect: '/404' })
      }

      permissionStore.loaded = true
      return { ...to, replace: true }             // 重放导航：让刚注册的路由参与本次匹配
    } catch (err) {
      reportError(err, { phase: 'route-bootstrap' })
      await userStore.resetAll()
      return { path: '/login', query: { redirect: to.fullPath } }
    }
  })

  router.afterEach((to) => {
    document.title = to.meta.title ? `${to.meta.title} · 管理台` : '管理台'
  })
}
```

这段有四个"写错就出事故"的点，逐条对号：

1. **Vue Router 4 用返回值控制导航**：`true`/`undefined` 放行、路由对象重定向、`false` 取消。老代码里的 `next({...to, replace: true})` 在 4 里仍可用，但同一个守卫里 `next()` 与 return 混用会触发"next 被调用多次"警告——统一用 return。
2. **`{ ...to, replace: true }` 不能省**：`addRoute` 之后当前导航的路由匹配结果已经算好了（是 404 或未匹配），不重放就会停在空页面。这是"刷新后 404/白屏"最主流的修法。
3. **通配 404 必须在动态路由之后注册**：`addRoute` 是插到匹配表末尾的，先注册的通配路由会一直命中，症状是"菜单点了都没反应"。
4. **失败分支必须清 token 并重置 permission**：否则半装配状态留在内存里，重登之后路由缺一半。

配套还差两处装配代码（容易漏）：

```ts
// main.ts：等首跳完成再挂载，避免首帧渲染时动态路由未装好导致 Layout 空白
router.isReady().then(() => app.mount('#app'))
```

```ts
// directive/hasPermi.ts：按钮级权限，无权限直接从 DOM 移除
export const hasPermi: Directive = {
  mounted(el: HTMLElement, binding: DirectiveCommand) {
    const required = normalize(binding)                  // 字符串或数组
    if (required.length && !checkPermi(required)) {
      el.parentNode?.removeChild(el)
    }
  },
}
```

`removeChild` 的写法要记住一条限制：指令移除元素后**不会因权限变化自动恢复**，所以权限在会话内变更时必须重新登录或整块重渲染（用第 16 章的边界 `key` 手法）。另外这条指令只是体验，越权必须由后端拒（接口返回 403）——这是清单里必须验的一条。

## 阶段二：字典 + CRUD + 校验 + 批量

**字典**（`composables/useDict.ts`，缓存 + 缺失补拉 + 退出清理）：

```ts
export function useDict(...types: string[]) {
  const store = useDictStore()
  const result = reactive<Record<string, DictItem[]>>({})

  types.forEach((type) => {
    result[type] = store.itemsOf(type)        // 命中缓存直接返回；未命中触发一次异步拉取并写入缓存
  })

  return result
}
```

三条验收要点：**页面里不许出现 `'0': '正常'` 这类硬编码**；字典被后台修改后要有"刷新缓存"入口（否则症状就是"改了后台页面还是旧值"）；退出登录必须清缓存（换个账号看别人的字典标签是常见的越权信息泄露）。

**CRUD 的编排层**（`composables/useTable.ts`，管状态与竞态，不管 UI）：

```ts
export function useTable<T>(fetcher: (q: Query) => Promise<PageResult<T>>, init: Partial<Query> = {}) {
  const query = reactive<Query>({ pageNum: 1, pageSize: 20, ...init })
  const rows = shallowRef<T[]>([])                      // 第 13 章：大列表不深代理
  const total = ref(0)
  const loading = ref(false)
  const error = shallowRef<Error | null>(null)
  let seq = 0

  async function load() {
    const my = ++seq
    loading.value = true
    error.value = null
    try {
      const res = await fetcher({ ...query })
      if (my !== seq) return                            // 第 12 章：丢弃过期响应
      rows.value = res.rows
      total.value = res.total
    } catch (err) {
      if (my !== seq) return
      error.value = err as Error                        // 失败保留旧数据，界面走空态 + 重试
    } finally {
      if (my === seq) loading.value = false
    }
  }

  const debouncedLoad = useDebounceFn(load, 250)        // 搜索框走防抖，分页器走即时
  return { query, rows, total, loading, error, load, debouncedLoad, reload: load }
}
```

**校验分层**（第 06 章的工程版）：`rules` 只管字段级（必填、长度、正则）；跨字段（结束时间晚于开始时间）用 `validator` 且必须写 `trigger: 'blur'`；业务唯一性与状态机校验放提交前拦截，失败要落到具体字段——做法是把后端返回的错误映射到 `serverErrors`，再传给对应 `el-form-item` 的 `error` 属性。提交时才跑全表 `validate()`，字段级变更只跑 `validateField`（第 13 章的性能口径在这里落地）。

**批量与跨页选择**：选中态存 `useSelection`（以 `row-key` 为单位的 `ref<Set<string>>`，整体替换而非原地 `add`），表格翻页/筛选后仍保留；提交前做三件事——数量上限检查、后端预校验（哪些可删）、失败明细回显。**"批量删除返回 200 但只删了 3 条"是这类系统的固定事故**，所以清单里要求后端返回逐条结果、前端必须显示失败原因。

**导出**（`useExport.ts`）：请求声明 `responseType: 'blob'` 之后必须先嗅探内容——后端出错时常常仍返回 200 加一段 JSON 错误体，于是你拿到的是一个"伪装成文件的 JSON"，直接落盘就是一个打不开的 xlsx：

```ts
async function download(params: ExportQuery, filename: string) {
  const blob = await request<Blob>({ url: '/biz/order/export', method: 'post', data: params, responseType: 'blob' })
  if (blob.type.includes('application/json')) {                 // 错误体伪装成文件
    const text = await blob.text()
    ElMessage.error(JSON.parse(text).msg || '导出失败')
    return
  }
  saveBlob(blob, filename)
}
```

## 翻车现场

**一、上线后所有人点某个菜单没反应，菜单能展开、页面空白**

- 症状：新角色登录后，部分菜单点击无变化，控制台干净。
- 根因：通配 404 路由在动态路由之前注册（阶段一第 4 点），永远命中它并被重定向到 404，而 404 页被写成了"无提示的空白布局"。
- 修法：把通配路由挪到 `addRoute` 循环之后并加 `hasRoute` 防重复注册；同时 404 页必须有可见文案——**"静默失败"是这类问题拖一整天的原因**。

**二、"字典改了没生效"演变成一次数据一致性疑云**

- 症状：运营在后台改了字典项，前端页面标签仍是旧值；有人怀疑接口缓存，去查了后端。
- 根因：`useDict` 把字典缓存在 store + `localStorage`，只有登录时拉一次，没有失效入口。
- 修法：字典缓存加 `updatedAt` 与"刷新缓存"按钮；`localStorage` 版本号和后端字典版本号对齐，不一致则丢弃本地缓存。
- 复盘定下的规矩：**任何本地缓存都必须有失效路径**，写不出失效路径的缓存就不要缓存在本地。

**三、发布后 20 分钟白屏告警，最后确认是两个问题叠在一起**

- 症状：一部分用户报"页面加载失败"提示，一部分报"整页空白刷新也没用"。
- 根因：旧 chunk 被删（第一类）+ 一个新版接口字段改名导致列表渲染抛错（第二类），且当时只有 `errorHandler` 没有局部边界，所以第二类是整页白。
- 修法：保留上一版产物 30 分钟 + 版本探测自愈；接口字段变更走"后端兼容两版 + 前端可选链 + 缺字段时降级列"三步；补 `AppBoundary` 分层。
- 复盘定下的规矩：**每次发布必须同时观察"chunk 类错误占比"和"单一 TypeError 的 fingerprint 突增"**，这两类混在一起时用影响面与错误类型分布区分最快（第 16 章的 30 分钟 checklist 第 3、8 分钟那两步）。

## 复习卡片

- **Q：动态路由装配后为什么要 `return { ...to, replace: true }`？** A：本次导航的路由匹配已在 `addRoute` 之前算完，不重放就会停在未匹配/404 状态，表现为刷新后白屏。
- **Q：通配 404 为什么要最后注册？** A：`addRoute` 按注册顺序参与匹配，先注册的通配路由会一直命中，导致所有动态路由打不开。
- **Q：前端权限和后端权限的分工？** A：路由级由后端下发菜单决定可见范围，按钮级用指令移除 DOM 只是体验，越权必须由后端接口拒绝。
- **Q：`keep-alive` 下页面数据为什么是旧的？** A：`onMounted` 不再执行，要在 `onActivated` 里重新取数；缓存超上限后被淘汰则恢复完整生命周期。
- **Q：阶段三为什么必须在业务稳定后做？** A：性能与错误兜底的优化对象会随业务形态变化，但剖析埋点与版本探测必须提前就位，否则拿不到基线。
- **Q：这个项目的可交付证据是什么？** A：22 条验收清单（每条带验证方法）+ 一份指标文档 + 一条被 CI 拦住的违规 import 记录。

## 小结

- 三阶段的划分依据是**返工代价**：路由与权限最先定，业务其次，可运维最后但埋点最早。
- 守卫与 `addRoute` 的那 20 行是这类后台的技术核心，四个雷（返回值语义、导航重放、通配时机、失败清理）踩任何一个都会变成线上事故。
- 权限是两层：后端下发路由决定"能不能进"，指令决定"能不能点"，接口 403 决定"到底安不安全"。
- 22 条清单里五条直接对应总览的尺子；勾不满就别对外说完成——**清单的价值是把"我觉得好了"变成可判定语句**。
- 面试里最值钱的不是页面数量，而是"哪个决定是我做的、哪个事故是我修的、哪个数字是我测的"。

2. 故意制造三类崩溃各一次（`setup` 抛错、渲染里读 `undefined`、`setTimeout` 里抛错），记录：用户分别看到什么、控制台与上报里分别有什么、被哪一层接住；再按第 16 章补齐缺失的层，重跑一遍。
3. 交付物：完整跑完 `## 22 条验收清单`，并把结果落成一份文档——每条写明"通过/未通过 + 验证方式 + 证据（截图、日志片段或测试文件名）"；同时产出 10 分钟 STAR 讲述稿一份，其中 A3 段必须有至少三个可被追问的数字及其测法。
