## `.d.ts` 是什么：只有形状，没有实现

```ts
// math.d.ts
export function add(a: number, b: number): number;
```

它只描述"有什么、类型如何"，没有函数体。用途三类：

1. **给 JS 库补类型**（库自己不带类型）；
2. **描述非 JS 资源**（`*.css`、`*.svg` 的 import）；
3. **给编译产物配类型**（`tsc --declaration` 自动生成）。

---

## `declare` 的四种形态

```ts
// 1) 声明值：告诉 TS "运行时存在这个东西"
declare const VERSION: string;
declare function init(opts: Record<string, unknown>): void;
declare class LegacyClient { connect(): void }

// 2) 声明模块：给"没有类型的包"或"非代码文件"用
declare module 'untyped-lib';                      // 整个模块当 any
declare module '*.svg' {
  const src: string;
  export default src;                             // 精确一点
}
declare module 'legacy' {
  export interface Options { url: string }
  export function create(o: Options): void;
}

// 3) 声明全局：给 window 挂属性
declare global {
  interface Window { __APP_CONFIG__?: { apiBase: string } }
  var __BUILD_ID__: string;
}
export {};   // ⚠️ 有这句才是"模块"，declare global 才合法

// 4) 声明命名空间：只为描述旧库结构
declare namespace jQuery { interface AjaxSettings { url?: string } }
```

⚠️ 最常见的坑：**在 `.ts` 里写 `declare global` 却忘了 `export {}`**，TS 会把文件当成脚本（全局作用域），`declare global` 报错。

## 给无类型库写声明：从最小到准确

```ts
// types/untyped-lib.d.ts
declare module 'untyped-lib' {
  export interface Options {
    /** 请求超时（毫秒） */
    timeout?: number;
    /** 是否自动重试 */
    retry?: boolean;
  }

  export interface Response<T = unknown> {
    data: T;
    status: number;
  }

  export function request<T = unknown>(url: string, options?: Options): Promise<Response<T>>;

  const _default: { request: typeof request };
  export default _default;
}
```

写声明的顺序：

1. **先让它能编译**（`declare module 'x';` 一行搞定）；
2. **再按实际用法补**（用到哪个函数补哪个，不要试图一次写全）；
3. **最后加注释**（JSDoc 会显示在编辑器提示里，这是文档）。

判断"我写的对不对"：在编辑器里悬停函数名，看提示是否与库文档一致。

## `@types` 生态与 `types` 字段

```bash
pnpm add -D @types/node @types/lodash
```

- 当库本身不带类型时，社区会在 `@types/<pkg>` 维护；
- TS 默认**自动加载** `node_modules/@types/*` 下的全局声明；
- `compilerOptions.types: ["node", "vite/client"]` 会**限制只加载这些**（写了就收窄了，别乱写）。

`typeRoots` 则是改"去哪里找 `@types`"，通常不需要动。

## Module Augmentation：扩第三方类型

```ts
// src/types/express.d.ts
import 'express';

declare module 'express-serve-static-core' {
  interface Request {
    requestId?: string;
    user?: { id: string; role: 'admin' | 'user' };
  }
}
```

要点：

1. **必须 `import` 原模块**（否则你是在"新建模块"而不是"扩展模块"）；
2. 扩展的是**接口**（`type` 不能合并）；
3. 路径要与库内部的实际模块名一致（`express-serve-static-core` 而不是 `express`）——这一点查库的 `.d.ts` 才知道。

## 全局注入：环境变量与构建常量

```ts
// src/env.d.ts
interface ImportMetaEnv {
  readonly VITE_API_BASE: string;
  readonly VITE_FEATURE_NEW_UI?: string;
}
interface ImportMeta {
  readonly env: ImportMetaEnv;
}
```

没有这段，`import.meta.env.VITE_X` 永远是 `any`，拼错名字也不报错——**这是 Vite 项目最常见的一处类型漏洞**。

同理，`declare const __BUILD_ID__: string;` 对应构建时 `define` 注入的常量。

## `skipLibCheck`：关掉的是什么

```jsonc
{ "skipLibCheck": true }
```

它跳过**所有 `.d.ts` 文件之间的类型兼容性检查**（不跳过你自己代码的类型检查）。

| 打开 | 关掉 |
| --- | --- |
| 检查快（大型项目能快 30–50%） | 能发现第三方类型定义之间的冲突 |
| 第三方 d.ts 有版本冲突时不会红 | 两个 `@types` 版本不兼容会让你修不了 |

现实结论：**99% 的项目应该打开**。第三方类型冲突应该用 `overrides` 统一版本解决，而不是让 `tsc` 天天报错。

代价是真实的：你**不会**发现"某个库的 d.ts 与你的 TS 版本不兼容"这类问题，直到运行时炸。

## 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| `declare global` 报"只能在模块里用" | 文件被当成脚本 | 加 `export {}` |
| 扩 `express` 类型不生效 | `declare module 'express'` 不匹配内部模块名 | 改成 `express-serve-static-core` |
| 声明文件不生效 | 没包含在 `include` 或 `typeRoots` 里 | 放进 `src/types` 并确保被 include |
| `Cannot find module './x.css'` | 没有资源声明 | `declare module '*.css'` |
| `@types` 装了却提示找不到全局 | `types` 字段把它排除了 | 从 `types` 里加上，或删掉该字段 |
| 自己的 d.ts 与源码重名冲突 | 同一模块声明两次 | 删掉手写的，让 `tsc` 生成 |

## 验收清单

- [ ] 项目里所有无类型依赖都有声明（或用了 `declare module 'x'` 兜底并记了 TODO）
- [ ] `ImportMetaEnv` 声明完整，`import.meta.env.X` 拼错会报错
- [ ] 全局注入（`Window` / `declare const`）都放在 `src/types/*.d.ts`
- [ ] 扩展第三方类型时 import 了原模块，且模块名与库内部一致
- [ ] 知道 `skipLibCheck` 关掉的是什么，且能说出代价
- [ ] 发布的库由 `tsc --declaration` 生成 d.ts，而不是手写

## 练习

1. **给一个无类型库补声明**：找一个只有 JS 的小包（或自己写一个 `.js` 文件），写 `declare module` 让它有类型提示，验证编辑器能跳转出参数类型。  
   *自检*：故意把 `export default` 写成 `export =`，观察 import 写法有什么变化。
2. **补 `ImportMetaEnv`**：故意把 `VITE_API_BASE` 写成 `VITE_API_BASEE`，确认编译报错（在此之前通常是 `any` 不报错）。  
   *自检*：能说明"没有声明时 env 是 any"是团队最常见的类型漏洞之一。
3. **做一次 module augmentation**：给 `Window` 加一个 `__APP_CONFIG__`，并让读取处获得类型提示。  
   *自检*：能指出"忘了 `export {}` 会怎样"。
