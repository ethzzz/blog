## 1. 评测集：质量保障的地基

评测集就是一组固定的"输入 + 期望"对，用来在你改动之后重跑对比。它的来源比想象中丰富：

1. **历史真实数据**：从真实使用记录里抽。我的摘要评测集 30 篇文章全部来自博客历史文章，覆盖不同长度/语言/结构。
2. **线上坏例**：用户反馈的每个 bad case，修复后收进评测集（第 4 节细讲）。这是评测集最珍贵的增量来源。
3. **边界构造**：故意构造的极端输入——空文本、纯代码文章、超长文、多语言混杂。这些是线上必然会出现的。

### 1.1 多少条够用

经验值：**30~100 条**。少于 30 条，随机波动就能淹没真实差异；超过 100 条，跑一轮的时间和成本开始劝退（我的 30 条用 qwen-plus 跑一轮约 3 分钱，几乎免费，但如果你测 Agent 类要多轮调用的功能，条数就要掂量）。

结构上必须分层，以我的摘要评测集为例：

| 层 | 数量 | 目的 |
| --- | --- | --- |
| 常规样本 | 12 | 主流程质量 |
| 长文样本 | 6 | 截断、格式漂移 |
| 边界样本（信息量低/纯代码/空文） | 8 | 防幻觉、防崩溃 |
| 历史坏例 | 4+（持续增加） | 防回归 |

### 1.2 期望怎么写

不是每条都要"标准答案"——那太贵了。三种可行的期望形式，从松到紧：

- **结构断言**：输出是合法 JSON、字段齐全、要点 3~5 条、每条 ≤ 30 字。全部可以代码判断，100% 自动化。
- **要点断言**：输出必须包含（或不得包含）某些关键信息。如"翻译结果必须保留 `AbortController` 术语原文"。子串/正则可判。
- **评分断言**：用另一个 LLM 当裁判打分（LLM-as-judge），比如"忠实度 1~5 分，≥4 通过"。有噪声，但规模化评估唯一可行的方式。

**能自动判断的绝不人肉**。我的摘要评测里结构断言和要点断言覆盖 80%，LLM 裁判只管最后 20% 的"读起来通不通顺"。

## 2. 自动回归流水线

核心是一个评测脚本：

```ts
// eval/run.ts
const cases = await loadEvalCases(); // 固定 30 条
let pass = 0;
const failures: EvalFailure[] = [];

for (const c of cases) {
  const output = await robustJsonCall(SummaryCard, [
    { role: "system", content: PROMPTS.summary.current },
    { role: "user", content: c.input },
  ]);
  const result = judge(c, output); // 结构断言 + 要点断言 + LLM 评分
  if (result.ok) pass++;
  else failures.push({ id: c.id, reason: result.reason, output });
}

console.log(`通过率 ${pass}/${cases.length}（基线 90%）`);
fs.writeFileSync("eval-report.json", JSON.stringify(failures, null, 2));
```

接入方式按项目体量两档：

- **个人项目**：git pre-push hook 跑一遍，基线以下不许推（03 篇的纪律自动化版）
- **多人协作**：CI 上跑，报告作为制品上传，PR 页面直接看通过率和逐条 diff

**基线思维**很重要：不要追求 100%（总有抖动样本），设定基线（如 90%），改动后显著低于基线就拦住。同时记录每次改动后的通过率曲线——这是我判断"这三个月质量是在变好还是变坏"的唯一依据。

一个坑：LLM 输出有随机性，同一条样本两次跑结果可能不同。缓解办法：temperature 压到 0.1 以下 + 每条样本跑 2 次取交集（成本翻倍但稳定性大增，只在关键版本发布前做）。

### 2.1 评测脚本的工程细节

把评测脚本写好有几个容易忽略的细节，直接影响它能不能长期用下去：

- **样本与代码分离**：评测集存 `eval/cases.json`（或按层拆多个文件），脚本只读不写。改脚本不应该动样本，改样本不应该动脚本。
- **输出必须可 diff**：评测报告除了通过率，要把每个失败样本的"输入摘要 / 期望 / 实际输出 / 失败原因"落成 JSON 或 Markdown。两个人看同一份报告，结论应该一致——做不到就是报告没写清楚。
- **耗时与成本打印**：跑一轮花了几秒、花了多少钱，写进报告末尾。这两个数字决定你"愿不愿意经常跑"，一个跑一次要十分钟几块钱的评测集，结局一定是没人跑。
- **随机性样本标记**：对已知输出不稳定（temperature 较高的场景）的样本，在样本里标 `"flaky": true`，统计时单列，避免它污染主基线的判断——这和前端 flaky test 的处理思路一模一样。

我的脚本从初版到现在改过四轮，但骨架没变：读样本 → 调用 → 断言 → 落报告。这个骨架值得你花一小时亲手搭一遍，它是后面所有质量工作的容器。

## 3. 人工评估：抽样评审表

自动化评不出的东西——"这个摘要读起来自然吗"、"这个翻译像人话吗"——需要人。我的做法很轻：

- **每周抽 10 条**线上真实输出（按时间随机，别挑着看），一张 Google Sheet 式的评审表
- 三个维度打分：**忠实**（有没有编造）、**准确**（任务完成度）、**可读**（表达质量），各 1~5 分
- 总分 < 12 的标记坏例，进第 4 节的分析流程

半年下来的经验：人工评估的价值一半在打分，另一半在**强迫你每周看真实输出**。很多问题（比如某类文章的摘要总是空泛）是看报表永远发现不了、盯着看十分钟就能发现的。

## 4. 坏例分析：归因到三层

每个坏例都要归因，否则修了也白修。我的三层归因框架：

| 层 | 典型症状 | 修复手段 |
| ---| --- | --- |
| Prompt 层 | 输出格式漂移、漏字段、过度发挥 | 改 Prompt + few-shot（03 篇），改完跑回归 |
| 模型层 | 事实错误、能力不足、换模型后批量劣化 | 换模型档位；模型层问题别用 Prompt 硬怼 |
| 工程层 | 截断、编码错误、缓存串了、超时 | 修代码；02/04/09 篇的所有内容 |

归因的实用技巧：**同一输入换模型再跑一次**。换模型后问题消失 → 模型层；依然失败 → Prompt/工程层。再检查输出原文有没有工程异常（截断标记、乱码）→ 区分 Prompt 和工程。三分钟定位，比盯着 Prompt 发呆半天强。

修复后的闭环动作：**坏例进评测集（1.2 的第 4 层）+ 修复方案写进案例记录**。两年下来这份记录成了我最值钱的私有文档——它就是这个 AI 功能的"病历本"。

## 5. 换模型的评估流程

换模型（升级版本、更换供应商）是质量保障里最惊险的常规操作，因为它影响的不是单条 Prompt 而是所有功能。我现在的换模型流程已经完全仪式化，这里完整给出：

**第一步：双模型跑同一评测集。** 网关（11 篇）的价值在这里体现：模型名一改，评测脚本零改动。新老模型各跑一遍 30 条样本，产出逐条对照表。

**第二步：分级对比结果。** 我把差异样本分三类统计——一致通过、一致失败、结果翻转。前两类不用管，**只盯结果翻转的样本**：老对新错是回归，必须逐条归因；老错新对是白赚的改善，记入更新日志。

**第三步：翻转样本归因。** 大部分翻转能归到三类：指令遵循强度不同（新模型对某条约束更敏感或更迟钝）、风格漂移（事实正确但表达变化，前端解析要确认兼容）、能力差异（长上下文或推理能力不同）。归因结果决定动作：指令类差异改 Prompt 适配，风格类差异跑一遍前端渲染回归，能力类差异评估是否值得整体迁移。

**第四步：小流量先行。** 评测集通过后也不直接全量，走 09 篇的灰度开关切 10% 流量观察三天，失败率和人工抽评无异常再放量。我的迁移节奏一般是评测 1 天 + 灰度 3 天 + 全量，一周内完成，从不赌。

这套流程跑过四次模型迁移（Qwen 系内升级两次、跨厂商一次、降本迁移一次），只有一次在灰度期发现问题回滚——那次是新模型对某个枚举值的输出习惯不同，导致 05 篇的校验失败率异常。**评估流程的意义不是保证不出问题，而是保证问题被拦在全量之前。**

## 6. 质量保障的投入节奏：别一开始就全上

最后回答一个现实问题：质量体系要建到多细？我的答案是**跟着痛感走，分四档渐进**，不要一上来就把本篇全部内容铺开：

- **第 0 档（demo 期）**：什么都不建，只保留一条纪律——把每次失败样本存进一个文件夹。这个文件夹就是你未来评测集的种子。
- **第 1 档（有真实用户后）**：建 20~30 条评测集 + 跑分脚本（第 1、2 节）。投入大约一个下午，回报是改 Prompt 不再裸奔。
- **第 2 档（功能超过三个）**：接入自动回归 hook/CI（基线拦截）+ 每周 10 条人工抽评。从此"哪个功能最近变差了"有数据可依。
- **第 3 档（多人协作/商业化）**：LLM 裁判规模化评估 + 换模型完整流程（第 5 节）+ 坏例归因制度。这时质量保障已经是一个正式的工程职能。

我自己是从第 2 档直接开始的——因为事故（格式漂移事件）痛得早。如果重来一次，我会从第 0 档的老老实实做起：那个"存失败样本的文件夹"成本为零，却是整个体系里唯一不可事后补建的东西，因为坏例是实时发生的，错过了就没了。评测集可以随时补，**坏例的记忆无法重建**。

---

## 小结

- 评测集 30~100 条、四层结构（常规/长文/边界/历史坏例），坏例持续回流。
- 期望分三级：结构断言（全自动）→ 要点断言（可自动）→ LLM 评分（有噪声但可规模）。
- 自动回归 + 基线拦截，输出有随机性就压 temperature + 关键场景跑多次取交集。
- 每周人工抽评 10 条，保持对真实输出的手感；坏例三层归因，换模型复测是最快定位法。

---

## 练习

1. 为你的功能建评测集：12 常规 + 6 边界，期望全部用结构断言表达。
2. 写评测脚本，输出通过率和失败明细 JSON，接入 pre-push hook。
3. 构造一条 LLM-as-judge 评分 Prompt，跑 10 条样本，人工核对裁判打的分靠不靠谱。
4. 找一个线上坏例，走完"复现 → 归因（换模型复测）→ 修复 → 进评测集"闭环。
