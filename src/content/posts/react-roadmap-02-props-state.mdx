上一篇讲"组件是纯函数"，这一篇讲这些函数的**输入从哪来**：props（父给的）和 state（自己记的）。

新手 90% 的结构混乱，根源不是不会写 `useState`，而是**把状态放错了地方**。所以这篇的重点不是 API，是判断标准。

## props 与 state 的边界

| | props | state |
|---|---|---|
| 谁拥有 | 父组件 | 组件自己 |
| 能否修改 | 只读（改了是 bug） | 用 setter 改 |
| 变化来源 | 父组件重渲染 | 内部事件 / 副作用 |
| 用于 | 配置、数据、回调 | 用户交互产生的、需要跨渲染记住的值 |

一句话：**props 是"别人给的现状"，state 是"我自己的记忆"。** 把别人的东西抄进自己的 state 是万恶之源：

```tsx
// ❌ 反模式：把 props 复制进 state
function UserCard({ user }: { user: User }) {
	const [name, setName] = useState(user.name); // 父组件的 user 变了，这里永远不更新
	...
}

// ✅ 直接用 props，需要改就是父组件的事
function UserCard({ user }: { user: User }) {
	return <p>{user.name}</p>;
}
```

这类 bug 的典型症状：**编辑弹窗第二次打开还是上一次的数据**。因为 `useState` 的初始值只在首次挂载时求值。

## 三条状态设计规则

### 规则 1：能算出来的，不要存（派生值不进 state）

```tsx
// ❌ 两个真值来源，必然不同步
const [items, setItems] = useState<Item[]>([]);
const [count, setCount] = useState(0);
// 每次增删都要记得同步 setCount —— 总有一处忘

// ✅ 渲染时算
const [items, setItems] = useState<Item[]>([]);
const count = items.length;
// 贵的话再 useMemo（见 06）
const filtered = useMemo(() => items.filter(match), [items, keyword]);
```

哪些属于派生值：`length`、`filtered`、`total`、`isValid`、`hasError`、`canSubmit`。**如果它完全由现有 state/props 决定，它就不该是 state。**

代价：每次渲染都重算。所以规则有个后缀——**昂贵的派生值用 `useMemo` 缓存，但仍然是"算"出来的，不是"存"下来的**。

### 规则 2：状态放在"最近的共同祖先"

两个组件都要读同一个值 → 提升到它们的共同父级，再把值和 setter 一起传下去。这叫**状态提升（lifting state up）**。

```tsx
// 兄弟组件要共享 keyword：提到父级
function Page() {
	const [keyword, setKeyword] = useState("");
	return (
		<>
			<SearchBox value={keyword} onChange={setKeyword} />
			<ResultList keyword={keyword} />
		</>
	);
}
```

反过来，**只被一个子组件用的状态就别往上提**——那会让父组件无谓地重渲染。

### 规则 3：能不存就不存，能下放就下放

```tsx
// ❌ 搜索框的值放在 Page 里，每敲一个字整个列表都重渲染
function Page() {
	const [keyword, setKeyword] = useState("");
	return (
		<>
			<input value={keyword} onChange={e => setKeyword(e.target.value)} />
			<HeavyList />   {/* 它不需要 keyword，却跟着重渲染 */}
		</>
	);
}

// ✅ 输入框自己管自己，只在"提交"时把值交出去
function SearchBar({ onSearch }: { onSearch: (q: string) => void }) {
	const [value, setValue] = useState("");
	return (
		<form onSubmit={e => { e.preventDefault(); onSearch(value); }}>
			<input value={value} onChange={e => setValue(e.target.value)} />
		</form>
	);
}
```

## 状态更新的本质：快照 + 引用比较

这一段是全篇最关键的。两条铁律：

**铁律一：`state` 是本次渲染的快照，不会"立刻变"。**

```tsx
function Counter() {
	const [n, setN] = useState(0);
	return (
		<button onClick={() => {
			setN(n + 1);
			setN(n + 1);
			setN(n + 1);
			console.log(n); // 0
		}}>
			{n}  {/* 点一次变成 1，不是 3 */}
		</button>
	);
}
```

因为三次都是 `0 + 1`，后两次被"覆盖"（更准确说：React 拿最终值 `1` 去渲染）。要累加必须用**函数式更新**：

```tsx
setN(prev => prev + 1);
setN(prev => prev + 1); // 队列里依次执行：0→1→2
```

**凡是新值依赖旧值，一律用 `prev =>`。** 这不是风格问题，而是唯一正确的写法——尤其在有异步、闭包、批处理的时候。

**铁律二：只有"引用变了"才会触发重渲染。**

```tsx
const [obj, setObj] = useState({ a: 1 });
obj.a = 2;
setObj(obj);          // ❌ 同一个引用，Object.is 相等 → 不渲染

setObj({ ...obj, a: 2 }); // ✅ 新对象
```

React 判等用的是 `Object.is`，**浅比较**。所以：

- 数组：`push` / `splice` 原地改 → 不渲染；`[...arr, x]`、`arr.filter()`、`arr.map()` → 新数组。
- 对象：改属性 → 不渲染；展开创建新对象 → 渲染。
- `Map`/`Set`：`new Map(prev).set(k, v)`。

这条规则在 06 的 `useMemo`/`memo`、09 的 Query 缓存、12 的性能优化里会反复出现。

## 受控与非受控

```tsx
// 受控：值来自 state，React 是唯一真值来源
<input value={value} onChange={e => setValue(e.target.value)} />

// 非受控：值在 DOM 里，用 ref 读
const ref = useRef<HTMLInputElement>(null);
<input ref={ref} defaultValue="初始" />
// 读：ref.current?.value
```

| | 受控 | 非受控 |
|---|---|---|
| 真值来源 | React state | DOM |
| 能做什么 | 实时校验、联动、格式化、禁用按钮 | 简单表单、文件上传、非 React 库集成 |
| 代价 | 每次输入都重渲染 | 取值时机要自己管 |

**默认用受控**；但表单字段超过 10 个时，每个字段一个 `useState` 会让整个表单每次按键全量重渲染——这时要么用 `useReducer` 收成一个状态树，要么用 React Hook Form（非受控 + ref，见 10）。

## 单向数据流：子改父只能靠回调

React 没有双向绑定。子组件想改父的状态，只能调用父传下来的函数：

```tsx
function Child({ onChange }: { onChange: (v: string) => void }) {
	return <input onChange={e => onChange(e.target.value)} />;
}
```

这个约束看着麻烦，实际是 React 最好用的部分：**数据流向永远可追踪**——状态只可能在"拥有它的那个组件"里被改，调试时不用满世界找谁改了值。

## 常见坑

| 现象 | 根因 | 解法 |
|---|---|---|
| 改了对象/数组，UI 不动 | 原地修改，引用没变 | 用展开/`filter`/`map` 创建新引用 |
| 连续 `setN(n+1)` 只加 1 | 快照，三次都基于同一个 `n` | `setN(prev => prev + 1)` |
| 弹窗第二次打开是旧数据 | `useState` 初始值只在挂载时求值 | 用 `key` 强制重挂载，或把数据提到父级 |
| 输入框完全无法输入 | `value` 有值但没有 `onChange` | 补 `onChange`，或改 `defaultValue` |
| 子组件改了 props 报错 | props 只读 | 通过回调让父组件改 |
| 派生值不同步 | 存了两份真值 | 删掉 state，渲染时计算 |

## 拦路的几道题

1. 一个购物车有 `items`、`total`、`count`、`hasDiscount`，其中后三个都能由 `items` 算出。写出正确的 state 设计。
2. 下面为什么点一次只加 1？改成加 3 并说明原因：

```tsx
const [n, setN] = useState(0);
const inc = () => { setN(n + 1); setN(n + 1); setN(n + 1); };
```

3. 写一个 `TodoList`：新增、切换完成、删除。要求 `items` 的更新全部不可变，并说明每处为什么是新引用。
4. 有一个"筛选 + 列表"页面，`keyword` 应该放在哪？如果列表有 5000 项且渲染很慢，怎么避免每敲一个字都重渲染？
5. 判断：把 `props.user` 复制进 `useState` 以便"本地编辑"，什么时候是合理的？(提示：需要"取消编辑"时)

**自检标准**：第 2 题能说出"三次都用同一个 `n` 快照"；第 5 题能说出"需要草稿态、且能丢弃"时把 props 复制进 state 是合理的，但要配 `key` 或同步逻辑。
