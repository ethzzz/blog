## Webpack 核心

### Q1: Webpack 的构建流程？⭐⭐ 🔥

**答：**

```
初始化参数
    ↓
创建 Compiler 对象
    ↓
注册所有插件（plugins）
    ↓
确定入口（entry）
    ↓
从入口开始构建模块图（Module Graph）
    ↓
Loader 转换每个模块
    ↓
递归处理依赖模块
    ↓
生成 Chunk（代码块）
    ↓
输出 Bundle 到文件系统
```

```javascript
// webpack.config.js 核心配置
module.exports = {
  entry: './src/index.js',       // 入口
  output: {                       // 输出
    path: path.resolve(__dirname, 'dist'),
    filename: '[name].[contenthash].js',
  },
  module: {
    rules: [                      // Loader 规则
      { test: /\.js$/, use: 'babel-loader' },
      { test: /\.css$/, use: ['style-loader', 'css-loader'] },
    ]
  },
  plugins: [                      // 插件
    new HtmlWebpackPlugin(),
    new MiniCssExtractPlugin(),
  ],
  optimization: {                 // 优化
    splitChunks: { chunks: 'all' },
    minimize: true,
  },
};
```

**追问链：**

- **「Compiler 和 Compilation 有什么区别？」⭐⭐⭐**
  答：**Compiler 是全局唯一**的编译实例，贯穿整个 watch 生命周期（启动时创建一次，配置、插件、文件系统都在它身上）；**Compilation 是一次构建过程**，每次改动都会新建一个（`compiler.hooks.watchRun` 之后 `newCompilation()`）。所以插件里要拿「本次构建的模块图/产物」用 `compilation`，要拿「全局配置/长期状态」用 `compiler`。说错这一层，说明没真写过插件。
- **「Webpack 的插件机制靠什么实现？」**
  答：Tapable 的发布订阅（hooks）。`compiler.hooks.emit.tapAsync(...)` 就是往 emit 这个 AsyncSeriesHook 上挂回调。三种 tap：`tap`（同步）、`tapAsync`（回调式异步）、`tapPromise`（Promise 式异步）。所以「写插件 = 找对 hook + 在正确时机改 compilation」。
- **「Loader 为什么必须从右到左执行？」**
  答：不是设计偏好，是**数据流方向**决定的。Loader 是「源码进、转换后代码出」的管道，右侧的 `sass-loader` 把 SCSS 变成 CSS，左侧的 `css-loader` 才能接着解析 CSS——反过来喂 CSS 给 sass-loader 直接报错。写成数组是为了让阅读顺序与书写习惯一致，执行顺序仍是链式从尾到头。

### Q2: Loader 和 Plugin 的区别？⭐ 🔥

**答：**

| 特性 | Loader | Plugin |
|:--|:--|:--|
| 作用 | 转换单个文件 | 扩展构建功能 |
| 时机 | 模块解析阶段 | 整个构建生命周期 |
| 本质 | 函数（接收源码，返回转换后代码） | 类（监听 Compiler 事件） |
| 示例 | babel-loader、css-loader | HtmlWebpackPlugin、DefinePlugin |

```javascript
// Loader 本质：一个函数
function myLoader(source) {
  // source 是文件内容字符串
  return source.replace(/console\.log\(.*?\);?/g, '');
}
module.exports = myLoader;

// Plugin 本质：一个类，监听 Compiler hooks
class MyPlugin {
  apply(compiler) {
    // 监听 emit 事件（输出文件前）
    compiler.hooks.emit.tapAsync('MyPlugin', (compilation, callback) => {
      // 修改 compilation.assets
      callback();
    });
    
    // 监听 done 事件（构建完成）
    compiler.hooks.done.tap('MyPlugin', (stats) => {
      console.log('Build complete!');
    });
  }
}
```

### Q3: 常见 Loader 有哪些？执行顺序？⭐⭐

**答：**

```javascript
// 常见 Loader
// babel-loader    -> ES6+ 转 ES5
// css-loader      -> 解析 CSS 中的 @import 和 url()
// style-loader    -> 将 CSS 插入到 <style> 标签
// sass-loader     -> 编译 Sass/SCSS
// postcss-loader  -> 自动添加浏览器前缀（autoprefixer）
// file-loader     -> 处理图片/字体文件
// url-loader      -> 小文件转 base64
// ts-loader       -> 编译 TypeScript
// vue-loader      -> 解析 Vue SFC

// 执行顺序：从右到左，从下到上
module: {
  rules: [{
    test: /\.scss$/,
    use: [
      'style-loader',    // 4. 插入 DOM
      'css-loader',      // 3. 解析 CSS
      'postcss-loader',  // 2. 添加前缀
      'sass-loader',     // 1. 编译 Sass（先执行）
    ]
  }]
}
```

### Q4: 常见 Plugin 有哪些？⭐⭐

**答：**

```javascript
const HtmlWebpackPlugin = require('html-webpack-plugin');
const MiniCssExtractPlugin = require('mini-css-extract-plugin');
const CssMinimizerPlugin = require('css-minimizer-webpack-plugin');
const TerserPlugin = require('terser-webpack-plugin');
const { CleanWebpackPlugin } = require('clean-webpack-plugin');
const DefinePlugin = require('webpack').DefinePlugin;
const CopyWebpackPlugin = require('copy-webpack-plugin');

plugins: [
  // 自动生成 HTML 并注入 bundle
  new HtmlWebpackPlugin({ template: './src/index.html' }),
  
  // 提取 CSS 为单独文件（生产环境）
  new MiniCssExtractPlugin({ filename: 'css/[name].[contenthash].css' }),
  
  // 清空 dist 目录
  new CleanWebpackPlugin(),
  
  // 定义全局变量（环境变量注入）
  new DefinePlugin({
    'process.env.API_URL': JSON.stringify(process.env.API_URL)
  }),
  
  // 复制静态文件
  new CopyWebpackPlugin({ patterns: [{ from: 'public', to: '' }] }),
],

optimization: {
  minimizer: [
    new TerserPlugin({ parallel: true }),       // 压缩 JS
    new CssMinimizerPlugin(),                    // 压缩 CSS
  ]
}
```

## 模块系统

### Q4b: ESM 和 CommonJS 到底差在哪？⭐⭐ 🔥

**答：** 不只是 `import` 和 `require` 的写法差异，是**两套语义**：

| 维度 | CommonJS | ESM |
|:--|:--|:--|
| 加载时机 | **运行时**加载（执行到 require 才读文件） | **编译期**确定依赖图，执行前已完成链接 |
| 导出内容 | `module.exports` 对象的**值拷贝**（基本类型） | 导出的**活绑定（live binding）**，只读引用 |
| 顶层 this | `module.exports` | `undefined` |
| 顶层 await | 不支持 | 支持（ES2022） |
| 缓存 | 缓存 `module.exports` 对象 | 缓存模块实例，绑定共享 |
| 动态性 | `require(变量)` 合法 | `import()` 动态，静态 import 必须顶层字面量 |

**活绑定是最高频追问：**

```javascript
// counter.mjs
export let count = 0;
export function inc() { count++; }

// main.mjs
import { count, inc } from './counter.mjs';
console.log(count); // 0
inc();
console.log(count); // 1 ← ESM 拿到的是「绑定」，源模块改了这边跟着变
// count = 5;       // ❌ TypeError：导入的绑定只读

// counter.cjs
let count = 0;
module.exports = { count, inc: () => count++ };
// main.cjs
const m = require('./counter.cjs');
m.inc();
console.log(m.count); // 0 ← CJS 导出时就拷贝了值，之后源模块改不到这里
```

**循环依赖的表现也不同：**

```javascript
// CJS：a 先执行，require b 时 b 又 require a，
// 拿到的是 a「已执行部分」的 exports（可能是不完整对象）→ 不报错但值缺失
// ESM：链接期就建好绑定，函数声明被提升可用；
// 但访问「尚未初始化的 let/const」会抛 ReferenceError（TDZ）
```

**追问链：**

- **「为什么 Node 里 `require` 一个 ESM 包会报错？」** 答：CJS 是同步加载模型，而 ESM 允许顶层 await（异步），同步 API 无法等待——所以 Node 22 之前 `require(esm)` 直接抛错，只能 `import()`。Node 22+ 开始支持 require 无顶层 await 的 ESM，但**有顶层 await 的仍然不行**，这是模型冲突不是实现偷懒。
- **「`__dirname` 在 ESM 里为什么没了？」** 答：CJS 的 `__dirname/__filename/require` 都是模块包装函数注入的参数，ESM 没有这层包装。替代：`import.meta.dirname`（Node 20.11+）或 `fileURLToPath(import.meta.url)`。
- **「打包器怎么处理两套混用？」** 答：靠**互操作层**——CJS 模块被包成「default 导出 = module.exports」的 ESM；这也是 `import x from 'cjs-pkg'` 能拿到整个 exports、而 `import { foo }` 有时失败的原因（具名导出要靠静态分析 cjs 源码猜，猜不中就只能 default）。Vite 预构建、Rollup 的 commonjs 插件干的就是这件事。

## Tree Shaking

### Q5: Tree Shaking 的原理？⭐⭐ 🔥

**答：**

Tree Shaking 是基于 **ES Module 静态分析** 的特性，在编译时移除未使用的代码。

```javascript
// utils.js
export function add(a, b) { return a + b; }
export function subtract(a, b) { return a - b; } // 未使用
export const PI = 3.14159;

// main.js
import { add } from './utils'; // 只导入 add
console.log(add(1, 2));

// Tree Shaking 后，subtract 和 PI 会被移除
```

**为什么需要 ESM？**

```javascript
// ESM：静态分析（编译时确定）
import { foo } from './module'; // 结构固定

// CommonJS：动态加载（运行时确定）
const module = require(condition ? './a' : './b'); // 无法静态分析
```

**Tree Shaking 失效的常见情况：**

```javascript
// 1. 副作用代码
// package.json 中声明
{ "sideEffects": false } // 允许 Tree Shaking
{ "sideEffects": ["*.css"] } // CSS 文件有副作用，保留

// 2. Babel 将 ESM 转换为 CJS（破坏静态分析）
// babel.config.js
{
  "presets": [["@babel/preset-env", { "modules": false }]] // 保留 ESM
}

// 3. 导入整个对象
import * as utils from './utils'; // 无法 Tree Shaking

// 4. 类方法
class MyClass {
  usedMethod() {}
  unusedMethod() {} // 类方法无法被 Tree Shaking
}
```

**追问链：**

- **「为什么 ESM 能静态分析，CommonJS 就不行？」**
  答：ESM 的 import/export 必须是**顶层声明**，且导入导出的绑定名在语法解析阶段就确定，不需要执行代码——所以打包器在「还没运行任何代码」时就能画出模块依赖图并标记未使用导出。CJS 的 `require` 是普通函数调用，参数可以是运行时表达式，导出对象可以被任意改写（`module.exports.x = ...` 动态挂载），打包器无法在编译期确定「到底用了什么」。一句话：**ESM 的静态性来自语法约束，而不是工具能力**。
- **「sideEffects: false 写错了会怎样？」⭐⭐⭐ 真实事故题**
  答：`sideEffects: false` 告诉打包器「这个包里的模块被 import 但未使用导出时，可以整模块删除」。如果某个模块 import 只为执行副作用（注册全局样式、`@babel/polyfill`、自定义元素注册、`import './global.css'`），就会被误删——典型症状是**线上样式丢失或 polyfill 没生效，本地 dev 正常**（dev 不做 DCE）。正确写法是声明白名单：`"sideEffects": ["*.css", "./src/register.ts"]`。这是我在项目里真踩过的坑，也是这道题最好的答法。
- **「usedExports 和 sideEffects 各管什么？」**
  答：`usedExports`（标记哪块代码被用）解决「导出没用就别留」，由 Terser 在压缩阶段真正删除，属于**语句级 DCE**；`sideEffects` 解决「整个模块能不能跳过」，属于**模块级 DCE**，能在不解析模块内容的前提下直接剪掉依赖。两者叠加才是完整 Tree Shaking。

## 代码分割

### Q6: Webpack 代码分割的方式？⭐⭐ 🔥

**答：**

```javascript
// 1. 多入口（entry）
entry: {
  app: './src/app.js',
  admin: './src/admin.js',
}

// 2. 动态导入（懒加载）
const LazyComponent = () => import('./components/Lazy.vue');
// React
const LazyComponent = React.lazy(() => import('./Lazy'));

// 3. splitChunks（提取公共代码）
optimization: {
  splitChunks: {
    chunks: 'all', // async | initial | all
    cacheGroups: {
      // 提取第三方库
      vendor: {
        test: /[\\/]node_modules[\\/]/,
        name: 'vendors',
        chunks: 'all',
        priority: 10,
      },
      // 提取公共模块
      common: {
        minChunks: 2,
        name: 'common',
        chunks: 'all',
        priority: 5,
        reuseExistingChunk: true,
      },
    },
  },
}

// 4. runtimeChunk（提取 Webpack 运行时代码）
optimization: {
  runtimeChunk: 'single', // 单独提取 runtime
}
```

### Q7: contenthash 的作用？⭐⭐

```javascript
// contenthash：根据文件内容生成 hash
// 只有文件内容变化，hash 才变化，利用浏览器缓存
```

## HMR (热模块替换)

### Q8: HMR 的原理？⭐⭐⭐ 🔥

**答：**

```
HMR 工作流程：

1. Webpack 监听文件变化，重新编译修改的模块
2. Webpack Dev Server 通过 WebSocket 通知浏览器
3. 浏览器 HMR Runtime 接收更新信息
4. HMR Runtime 下载新的模块代码（JSONP）
5. 执行模块的 accept handler，替换旧模块
6. 如果没有 accept handler，则冒泡到父模块
7. 如果冒泡到入口还未处理，则整页刷新
```

```javascript
// HMR API
if (module.hot) {
  module.hot.accept('./component.js', () => {
    // 组件更新时执行
    renderComponent();
  });
  
  module.hot.dispose(() => {
    // 模块卸载时清理
    cleanup();
  });
}

// Vue 中（vue-loader 自动处理）
// React 中（react-hot-loader / Fast Refresh）
```

**追问链：**

- **「Vue 的 HMR 为什么天然好做，React 却要 Fast Refresh？」⭐⭐⭐**
  答：本质差异在**状态存储位置**。Vue 的组件状态在组件实例（响应式对象）里，vue-loader 的 accept handler 能「换掉 render 函数、保留实例」，所以改模板时组件状态不丢。React 的函数组件状态在 Fiber 的 hooks 链表里，函数本身被重新定义后 hooks 顺序必须能对齐——Fast Refresh 靠**给每个组件打签名**（函数名 + hooks 顺序哈希）判断能否原地替换：签名一致就保留 state，签名变了（改了 hooks 数量/顺序）就强制卸载重建，状态丢失。这也是「改 hooks 顺序后页面状态突然清空」的原因。
- **「HMR 会内存泄漏吗？」**
  答：会。每次热替换都会在旧模块上执行 `module.hot.dispose`；如果模块里有全局监听、定时器、WebSocket、`addEventListener` 却没在 dispose 里清理，旧实例的引用一直挂着。症状是开发时页面越改越卡、内存曲线只涨不降。这也是「HMR 卡了就重启 dev server」的经验来源，但正确做法是补 dispose 清理。

## Vite

### Q9: Vite 为什么比 Webpack 快？⭐⭐ 🔥

**答：**

| 对比项 | Webpack | Vite |
|:--|:--|:--|
| 冷启动 | 打包全部模块再启动 | 直接启动 Dev Server |
| HMR | 重新打包受影响模块链 | 直接 ESM 模块替换 |
| 依赖预构建 | 无 | esbuild（Go 语言，极快） |
| 生产构建 | Webpack 打包 | Rollup 打包 |

**Vite 开发模式原理：**

```
浏览器请求 index.html
        ↓
Vite Dev Server 拦截请求
        ↓
按需编译请求的模块（不打包）
        ↓
以 ESM 格式返回给浏览器
        ↓
浏览器通过 <script type="module"> 加载
        ↓
遇到 import 再向 Vite 请求（按需加载）
```

```javascript
// Vite 开发模式：浏览器原生 ESM
// index.html
<script type="module" src="/src/main.js"></script>

// main.js（Vite 直接返回，不打包）
import { createApp } from 'vue';  // 浏览器请求 /node_modules/.vite/vue.js
import App from './App.vue';       // 浏览器请求 /src/App.vue（Vite 编译）
```

**依赖预构建（esbuild）：**

```javascript
// vite.config.js
export default {
  optimizeDeps: {
    include: ['lodash-es', 'axios'], // 强制预构建
    exclude: ['my-local-lib'],        // 排除预构建
  },
  // 预构建作用：
  // 1. 将 CJS 转为 ESM
  // 2. 将多文件模块合并（减少 HTTP 请求）
  // 3. esbuild 比 Webpack 快 10-100x
};
```

**追问链（Vite 的题必须答到「代价」才算过关）：**

- **「Vite 在生产构建上还快吗？」⭐⭐⭐**
  答：不快多少。生产构建走 Rollup，是**完整打包**，冷构建时间与 Webpack 同量级（大项目甚至更慢，因为 Rollup 的插件生态对某些场景不如 Webpack 成熟）。Vite 的优势集中在**开发态**：不打包 → 冷启动秒级；按需编译 → 改哪个模块编哪个模块。所以正确表述是「Vite 赢在开发体验，不赢在生产构建」——只背「Vite 比 Webpack 快 100 倍」会被追问穿。
- **「Vite 开发模式有哪些反直觉的坑？」**
  答：三个高频：① **请求瀑布**：浏览器原生 ESM 意味着每个 `import` 一次请求，依赖深的模块图首屏会发几百个请求，靠预构建合并缓解，但项目写得太碎（`import` 大量小文件）仍会慢；② **预构建失效整页刷新**：发现新依赖要重新 optimize，Vite 会 reload 整个页面，第一次跑起来看到「莫名其妙刷新一次」就是这个；③ **CJS 依赖**：只能在预构建阶段转成 ESM，动态 `require` 的包（少数老库）会直接报错，需要 `optimizeDeps.include` 手动兜。
- **「那大项目该怎么选？Rspack / Turbopack 是什么定位？」**
  答：先说结论——**Rspack（Rust 重写 Webpack）是「无痛迁移」路线**，配置与 Webpack 高度兼容（loader/plugin 生态大量复用），构建速度提升一个量级，适合存量 Webpack 大仓平滑替换；**Turbopack（Rust，Vercel）绑定 Next.js**，增量编译做到极致，但独立使用生态还在补齐。选型看约束：存量配置重、插件多 → Rspack；新项目 + Next.js → Turbopack / Vite；库开发 → Vite/tsup 足够。这类题的分值在「说清迁移成本」，不在背速度数字。

### Q9b: Vite 的 HMR 和 Webpack 的 HMR 有什么不同？⭐⭐⭐

**答：** 通知链路相似（文件变化 → WebSocket 推送 → 浏览器拉新模块），**替换机制完全不同**：

```text
Webpack HMR：模块被打包进 chunk → 更新以「模块 ID + 新工厂函数」下发
             → runtime 替换模块缓存 → 沿 accept 边界冒泡
Vite HMR：   模块本来就是浏览器里的独立 ESM → 直接 import 带时间戳的新 URL
             → import.meta.hot.accept 回调里用新模块替换旧引用
```

```javascript
// Vite HMR API（对比 Webpack 的 module.hot）
if (import.meta.hot) {
  import.meta.hot.accept('./render.js', (newModule) => {
    newModule.render(); // 拿到的是新 ESM 模块对象
  });
  import.meta.hot.dispose(() => {
    cleanup(); // 旧模块失效前清理副作用
  });
  import.meta.hot.invalidate(); // 主动放弃接受，让更新向上传播
}
```

**三个关键差异（追问高发区）：**

1. **更新速度与项目规模解耦**：Webpack 要重编译「受影响模块链」再打 patch，项目越大越慢；Vite 无论项目多大，**只编译被改的那一个文件**，HMR 耗时基本恒定——这是「Vite 大项目体验不衰减」的根因。
2. **边界传播规则**：两者都是「没人 accept 就向上冒泡，冒到顶就整页刷新」。但 Vite 里 Vue/React 插件已自动写好组件级 accept（配合 Fast Refresh/vue-loader 的状态保留逻辑），业务代码很少手写；手写 `import.meta.hot` 主要出现在**非组件模块**（store、工具单例）需要自定义替换/清理时。
3. **CSS 是天然 HMR**：Vite 里 CSS 也是 ESM 模块，改样式直接替换 `<style>`/link，不刷新页面、不丢状态；Webpack 需要 style-loader 配合，抽离 CSS 后 dev 会失效（见坑速查表）。

**追问：「为什么 Vite 偶尔还是整页刷新？」** 答：三类——① 改的文件不在任何 accept 边界内（如纯工具函数被多处引用且无插件接管）；② 依赖预构建重跑（发现新依赖）；③ `vite.config` / `.env` 变化触发 server restart。**能区分「模块级更新失败」和「server 级重启」，说明真观察过终端日志。**

### Q12b: 发版后用户报 ChunkLoadError / Loading chunk failed，链路是什么？怎么兜？⭐⭐⭐ 🔥

**答：** 这是**前端发版最高频的线上事故**，先把链路讲清：

```text
① 用户打开页面，加载了旧 index.html（引用旧 hash 的 chunk 清单）
② 期间你发了新版：新 HTML 上线，旧 chunk 被清理/CDN 回源 404
③ 用户在旧页面里点了懒加载路由 → 按旧清单请求旧 chunk → 404
④ import() reject → ChunkLoadError → 路由白屏
```

**三层防线（缺一层都会被追问）：**

```javascript
// ① 加载失败重试 + 强制刷新（兜住「新旧交替窗口期」）
function lazyWithRetry(importer, retries = 2) {
  return () =>
    importer().catch((err) => {
      if (retries > 0) {
        return new Promise((r) => setTimeout(r, 500)).then(() =>
          lazyWithRetry(importer, retries - 1)()
        );
      }
      // 重试仍失败：大概率是发版导致旧资源没了 → 带防死循环标记刷新
      if (!sessionStorage.getItem('chunk-reloaded')) {
        sessionStorage.setItem('chunk-reloaded', '1');
        location.reload(); // 拿到新 HTML + 新清单
      }
      throw err;
    });
}
const Page = React.lazy(lazyWithRetry(() => import('./Page')));

// ② 版本探测：构建时注入版本号，轮询/路由切换时对比
//    发现服务端版本更新 → 提示「有新版本，点击刷新」而不是突然白屏
// ③ 发布侧：旧版产物保留至少一个发布周期（见工程化篇发布顺序）
```

**追问链：**

- **「为什么不能 catch 到就无脑 reload？」** 答：如果 404 是 CDN 故障/网络问题而非发版，reload 后还是 404 → **无限刷新死循环**。所以必须带「本次会话已刷新过」的标记（sessionStorage），一次为限。
- **「HTML 不是不缓存吗，怎么还会拿到旧的？」** 答：三个来源——浏览器内存里的**已打开页面**（最常见，HTML 缓存策略管不到它）、CDN 边缘节点残留、Service Worker 缓存。所以「HTML no-cache」只解决新打开的页面，**已打开页面的懒加载**必须靠重试/版本探测兜。
- **「怎么在监控里把这类错误和普通 JS 错误分开？」** 答：按 `error.name === 'ChunkLoadError'` 或 message 匹配 `Loading chunk`/`Failed to fetch dynamically imported module`（Vite/Rollup 的报错文案不同）单独归类，告警阈值和「发版事件」关联——发版后 5 分钟内这类错误上涨是预期窗口，持续上涨才是事故。

### Q13: Babel 的编译流程？⭐⭐

**答：**

```
源代码 (JS/JSX/TS)
    ↓
解析 (Parse) → AST（抽象语法树）
    ↓
转换 (Transform) → 新 AST（插件处理）
    ↓
生成 (Generate) → 目标代码
```

```javascript
// babel.config.js
module.exports = {
  presets: [
    ['@babel/preset-env', {
      targets: '> 0.25%, not dead', // 目标浏览器
      useBuiltIns: 'usage',          // 按需引入 polyfill
      corejs: 3,                     // core-js 版本
      modules: false,                // 保留 ESM（Tree Shaking）
    }],
    '@babel/preset-react',            // JSX 支持
    '@babel/preset-typescript',       // TS 支持
  ],
  plugins: [
    '@babel/plugin-transform-runtime', // 避免全局污染
    ['@babel/plugin-proposal-decorators', { legacy: true }], // 装饰器
  ],
};
```

### Q13b: esbuild / SWC 为什么比 Babel 快？能完全替代吗？⭐⭐ 🔥

**答：** 快的来源是三层叠加，**不是单一原因**：

1. **语言层**：Go（esbuild）/ Rust（SWC）编译型语言 vs Babel 的 JS 解释执行，且无 GC 停顿；
2. **并行层**：原生多线程充分利用多核；Babel 单线程（thread-loader 只是进程级补丁）；
3. **架构层**：esbuild 一次遍历完成 parse/transform/print，**不生成可遍历的 JS 对象 AST**（Babel 的 AST 是海量 JS 对象，创建+遍历+GC 是大头）；且不做 Babel 那套「插件逐个遍历 AST」的通用管线。

**但「快」是有代价的，替代边界必须说清：**

| 能力 | Babel | esbuild / SWC |
|:--|:--|:--|
| 语法降级 + JSX/TS 剥离 | ✅ | ✅（快 10-100x） |
| **类型检查** | ❌（本来就不做） | ❌（都不做，tsc 单独跑） |
| 任意自定义 AST 插件 | ✅ 生态最全 | ⚠️ esbuild 插件 API 受限；SWC 有插件但生态小 |
| 老提案/装饰器 legacy 等边角语法 | ✅ | ⚠️ 部分不支持或语义有差 |
| polyfill 按需注入（useBuiltIns: usage） | ✅ core-js 集成 | ❌ 需另配 |

**工程结论（面试要落在这句）**：主流做法是**分层**——转译交给 esbuild/SWC（Vite dev、Next.js、tsup 都已默认），类型检查交给 `tsc --noEmit` 在 CI 单独跑，需要 Babel 独有插件的模块单独走 babel-loader。**「用 SWC 就不需要 tsc 了」是错误表述**——它们都不检查类型，类型门禁不能省。

### Q13c: Sourcemap 的原理？生产环境该怎么配？⭐⭐⭐ 🔥

**答：** Sourcemap 是一份 **JSON 映射文件**，记录「产物位置 → 源码位置」：`sources`（源文件列表）、`sourcesContent`（源码内容，可选）、`mappings`（**VLQ 编码**的位置映射：产物每一行每一列对应哪个源文件的哪行哪列）。浏览器/错误平台拿它把压缩后的栈还原成源码栈。

**常见类型与取舍：**

| devtool / 类型 | 产物 | 特点 |
|:--|:--|:--|
| `source-map` | 独立 .map + 末尾注释 | 完整映射，**注释会暴露 map 地址** |
| `hidden-source-map` | 独立 .map，**无注释** | 产物不含指向，map 只给错误平台用 |
| `inline-source-map` | map 内联进 bundle | 体积暴涨，仅调试用 |
| `cheap-module-source-map` | 只到行不到列 | 更快更小，loader 转换前的源码 |
| `eval-cheap-module-source-map` | eval 包裹 | dev 重建快，Vite/Webpack dev 常用 |

**生产标准姿势（三步）：**

```javascript
// ① 构建：生成 map 但不暴露
// webpack
devtool: 'hidden-source-map'
// vite
build: { sourcemap: 'hidden' }

// ② CI：把 .map 上传到 Sentry/自建错误平台，然后从发布产物里删除
//    sentry-cli releases files <version> upload-sourcemaps dist/
//    find dist -name '*.map' -delete   ← 部署包里不留 map

// ③ 错误平台用 map 还原堆栈；普通用户拿不到源码
```

**追问链：**

- **「为什么不能直接把 map 发到线上？」** 答：`.map` 里有 `sourcesContent` 时**等于公开全部源码**（含内部注释、接口路径、甚至误打包的密钥）。`hidden` 只解决「产物不指向 map」，**map 文件本身若还在 CDN 上，猜路径也能下载**——所以必须「上传后删除」，两步缺一不可。
- **「不上传 map，线上报错还能排查吗？」** 答：能但很痛——只有压缩后的行列号，靠本地同版本构建产物手动对位。所以「发版必传 map」要写进 CI 流程，而不是靠人记得。
- **「dev 和 prod 的 sourcemap 为什么策略不同？」** 答：dev 要**重建快**（eval/cheap 系，映射精度换速度）；prod 要**还原准 + 不泄露**（hidden 完整映射）。把 dev 配置带到 prod（inline/eval）是体积事故，把 prod 配置带到 dev（hidden 完整）是重建慢事故。

| 症状 | 先量什么 | 工具 | 常见根因 |

> 面试要给的回答结构：**先定指标（构建时长 / 首屏体积 / 缓存命中率）→ 用工具定位到具体模块 → 改一项 → 复测对比**。只说「我配了 splitChunks 所以快了」是没说服力的。

## 常见坑速查表

| 现象 | 根因 | 解法 |
|:--|:--|:--|
| 线上样式丢失，本地正常 | `sideEffects: false` 误删了只做副作用导入的模块 | 改白名单 `["*.css"]` |
| 发版后用户拿着新旧混杂的 chunk 报错 | HTML 与 chunk 缓存策略不一致 / 旧 chunk 被清 | HTML 不缓存 + 保留上一版产物（或 `output.clean` 谨慎用） |
| Tree Shaking 完全不生效 | Babel 把 ESM 转成了 CJS | `@babel/preset-env` 设 `modules: false` |
| 每次构建 hash 都变 | 模块 ID 不稳定 | `moduleIds/chunkIds: 'deterministic'` |
| dev 正常、build 报 `window is not defined` | 服务端/预渲染阶段执行了浏览器代码 | 浏览器 API 放到 `onMounted`/动态 import 内 |
| Vite 大依赖报 CJS 错误 | 未走预构建 | `optimizeDeps.include` 显式声明 |
| HMR 改样式无效但改逻辑有效 | CSS 被 `MiniCssExtractPlugin` 抽离（dev 也开） | dev 用 `style-loader`，仅 prod 抽取 |
| 构建内存 OOM | 大项目 sourcemap + 并行压缩 | 调 `--max-old-space-size`、拆分 chunk、关 dev sourcemap |
| `require()` 一个 ESM 包抛错 | CJS 同步模型等不了顶层 await | 改 `import()`；Node 22+ 可 require 无 TLA 的 ESM |
| `import { foo } from 'cjs包'` 拿不到 | CJS 具名导出靠静态分析猜 | 用 default 导入整个 exports，或换 ESM 包 |
| 线上堆栈全是压缩行列号 | 没传 sourcemap 到错误平台 | CI 里 upload-sourcemaps 后再删 map |
| 源码被公开下载 | .map 随产物上了 CDN | hidden + 上传后删除，两步缺一不可 |
| catch 到 chunk 404 就 reload 死循环 | 非发版原因的 404 刷新也没用 | sessionStorage 标记，一次会话只刷一次 |

## 深水区追问（2026 补充）

**Q：Vite 的 dev 走 esbuild 转换、prod 走 Rollup 打包，这种双管线会带来哪些「dev 正常、build 炸」的差异？**

答：五个高危差异：① dev 不做 Tree Shaking 与副作用分析，未被引用的死代码照样被求值，所以「build 后某个模块整段消失」的问题在 dev 永远复现不了；② 常量替换语义不同（`define` / `import.meta.env` 在 dev 是即时替换，prod 由打包器做静态替换），`typeof process !== "undefined"` 这类判断在两端结论可能相反；③ CJS 互操作：dev 能靠运行时包装跑通 `require` 动态调用，prod 是静态 ESM 分析，直接报「X is not exported」；④ 压缩差异：dev 不压缩，语法/作用域问题被掩盖，prod 开启 minify 后才暴露（典型是循环依赖导致的变量暂时为 `undefined`）；⑤ CSS 层叠顺序：dev 按导入顺序注入 `style`，prod 提取合并成单文件，两者顺序可能不同，表现为样式覆盖关系翻转。所以「本地看着对」不能作为发布依据，至少要跑一次 `vite build && vite preview`。

**Q：`manualChunks` 为什么容易切出「chunk 之间互相 import」？按什么维度划分才稳？**

答：`manualChunks` 是**静态规则**，它不感知模块图，只按包名/路径把模块塞进某个 chunk。你把 `react` 放进 `vendor`，而业务 chunk 又反向被 `vendor` 里的某个工具函数依赖时，两个 chunk 就形成环——运行时表现为 `Cannot access before initialization`，或者干脆多出一份重复代码。稳定划分的三个维度：① 按**更新频率**（runtime / vendor / 业务），vendor 只放「很久不变且不被业务反向依赖」的库；② 按**加载边界**（路由懒加载点），chunk 边界尽量与路由边界重合，别把同屏渲染的组件拆到两个 chunk；③ 按**体积与命中率**取舍，宁可 vendor 大一点也不要切碎——碎片化会放大请求数与 HTTP 开销。另外 `runtimeChunk: 'single'` 必开，否则每次发版 runtime 跟着业务 chunk 变，hash 全抖。

**Q：`/*#__PURE__*/` 注解是干什么的？`export default` 一个大对象为什么删不掉？**

答：Terser/Rollup 默认把「函数调用」当成有副作用——`const x = createThing()` 即使结果没人用也不能删。`/*#__PURE__*/` 就是告诉压缩器「这次调用无副作用，结果没人用就整句删掉」；库作者通常用 babel/rollup 插件在构建期自动打标，所以你看源码里没有、产物里到处都是。而 `export default { a, b }` 是一个**整体对象字面量**：属性不是独立导出，打包器无法在模块级切掉单个属性，只能整块保留（同理 `enum`、`namespace`、装饰器编译出的 IIFE 也都会让 DCE 失效）。工程结论：库要按具名导出写，消费者才能按需摇；`export default` 只适合「本来就要整体用」的模块。

**Q：Module Federation 的「运行时共享」和 npm 依赖共享有什么本质差别？版本冲突时怎么选？**

答：npm 共享是**编译期**确定一份代码，MF 共享是**运行时**从共享作用域里挑一份已加载的模块。差异集中在三点：① 版本仲裁——`shared` 里声明 `singleton: true` 后，宿主与远程按 semver 选出「能满足所有消费者的最高版本」，选不出来就各用各的，于是同一页面加载两份 React，报 `Invalid hook call`；② 构建顺序解耦——remote 可以先发布、host 后接入，但 remote 未发布或契约变更时运行时报错，需要 `strictVersion` 之类的显式拒载策略；③ Context / 全局状态必须落在单例里，否则跨应用 `Provider` 不生效。所以「是否需要独立部署」才是 MF 的判断标准：monorepo 内多个包共享依赖，用 workspace 统一版本 + 构建缓存更简单；只有多团队独立发版时才值得引入 MF 的复杂度。
