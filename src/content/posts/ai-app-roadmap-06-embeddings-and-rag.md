> [!NOTE]
> 模型不知道你公司的内部文档、不知道你昨天写的笔记。RAG 的思路很朴素：**先检索相关片段，塞进上下文，让模型看着材料回答**。它是 AI 应用里性价比最高的架构——不需要训练模型，全是你熟悉的工程活。这篇基于我给自托管知识库搭"全文问答"的完整踩坑史。

## 知识地图

- embedding：把文本变成可比较的向量
- 分块：chunk 大小与重叠的实践参数
- 向量库选型：从 SQLite 到专用引擎
- 召回与重排：两段式检索提升精度

## 1. Embedding：文本的坐标

Embedding 模型把任意文本映射成一个高维向量（比如 1024 维的浮点数组），**语义相近的文本，向量距离就近**。"如何配置 Nginx 缓存"和"nginx 反向代理设置"字面差异很大，但向量距离会很近——这是关键词搜索做不到的。

用法是两段式：

```ts
// 1. 离线：文档入库时算向量
const docVector = await embed(chunkText);

// 2. 在线：用户提问时算问题向量，找最近邻
const queryVector = await embed(question);
const topK = nearestNeighbors(docVectors, queryVector, 5);
```

调用姿势跟 chat 接口一样是 HTTP API（Qwen text-embedding-v3、OpenAI text-embedding-3-small 等）。几个工程要点：

- **embedding 也有计费**，但便宜得多（大约是 chat 的几十分之一），批量文档入库一次性成本可控
- **输入有长度上限**（比如 8K token），超长文本必须切块——自然引出下一节
- **换 embedding 模型 = 全量重算向量**。不同模型的向量空间不通用，选型时想清楚，别轻易换

## 2. 分块策略：决定 RAG 上限的一步

检索的最小单位是 chunk，**分块分得好不好，直接决定能不能检索到**。我的知识库最初用"每 500 字符硬切"，检索质量惨不忍睹：一个完整的概念被从中间砍断，两半都检索不到。

### 2.1 分块四原则

1. **按语义边界切，不按字符数硬切**。优先在标题、段落之间切；Markdown 文档先按 `##` 分节，节内超长再按段落切。我写的切分器第一件事就是识别 Markdown 结构。
2. **chunk 大小：300~800 token 是甜点区**。太小则上下文残缺，模型拿到碎片没法回答；太大则一个 chunk 里混了多个主题，检索时"什么都沾一点但都不准"，还费上下文。我的知识库最终落在 ~500 token。
3. **加重叠（overlap）**：相邻 chunk 保留 10%~15% 重叠，避免关键句恰好骑在边界上。
4. **带上元信息**：每个 chunk 附带文档标题、所属章节路径。回答"部署步骤是什么"时，"《部署指南》> 3.2 Docker 部署"这个路径本身就是强信号。

### 2.2 元数据增强：一个立竿见影的技巧

给每个 chunk 拼一个"上下文前缀"再算 embedding：

```ts
const embedInput = `《${doc.title}》 > ${sectionPath}\n${chunkText}`;
```

这样"如何在 Docker 里部署"这个问题，能对上正文只写了具体命令、而标题写了 Docker 部署的 chunk。就这一行代码，我的召回质量肉眼可见地提升。

## 3. 向量库选型

| 方案 | 适合 | 我的评价 |
| --- | --- | --- |
| SQLite + 内存暴力检索 | < 5 万 chunk | 个人项目首选，别急着上中间件 |
| pgvector | 已有 PostgreSQL | 一个扩展解决，运维零新增 |
| 专用向量库（Qdrant/Milvus） | 百万级以上 | 有运维成本，确认需要再上 |
| 云服务托管向量库 | 不想运维 | 记得算钱，按量存储+查询费 |

我的知识库大约 1.2 万 chunk，用 SQLite 存向量 + 暴力余弦相似度计算，单次查询 20ms 出头——**这个量级根本不需要专用向量库**。新手最大的误区是上来就装 Milvus，最后花在运维上的时间超过做功能本身。经验法则：**十万 chunk 以内，任何方案的暴力检索都够快**。

余弦相似度的暴力检索代码也就二十行，核心是每次查询把所有向量取出来点积一遍，向量归一化后点积即余弦相似度。

## 4. 召回与重排：两段式检索

单轮向量检索的痛点：向量相似 ≠ 真的相关。用户问"缓存怎么配"，向量会把所有提到"缓存"的 chunk 都排前面，但其中一半语义上答非所问。

### 4.1 两段式：先粗召回，再精排序

```ts
async function retrieve(query: string): Promise<Chunk[]> {
  // 第一段：向量粗召回，k 取大一点（20~50）
  const candidates = await vectorSearch(embed(query), 30);

  // 第二段：重排模型精排，取 top 3~5
  const reranked = await rerank(query, candidates);
  return reranked.slice(0, 4);
}
```

重排（rerank）用一个专门的交叉编码模型（Qwen 有 gte-rerank，Cohere 有 rerank 系列），它把"问题 + 候选文本"成对打分，精度远高于向量近似检索，但慢且贵——所以只对粗召回的小集合用。**加一层重排后，我的问答准确率提升显著，是我 RAG 链路里性价比最高的一次升级。**

### 4.2 混合检索：向量 + 关键词

纯向量检索对**专有名词、代码标识符**很弱（"zod parse 报错"里的 `zod` 可能被向量化得很模糊）。补一路关键词检索（SQLite FTS5 就够），两路结果按 rank 融合（RRF，倒数排名融合，十几行代码），专名类问题的召回立刻改善。

### 4.3 最后拼 Prompt

```ts
const context = chunks
  .map((c, i) => `[${i + 1}] ${c.meta.path}\n${c.text}`)
  .join("\n---\n");

const system = `基于以下资料回答问题。只使用资料中的信息，
资料不足以回答时明确说"资料中没有相关内容"。

${context}`;
```

"资料不足时明确说没有"这句是防幻觉的关键（03 篇讲过的失败出口），同时回答里标注来源编号 `[1]`，用户可以点回去看原文——**可溯源是 RAG 产品信任感的核心**。

## 5. 检索失败排查清单：比调优更先做的事

RAG 效果不好时，大多数人第一反应是"调分块参数"或"换 embedding 模型"，但我的经验是：**先搞清楚失败发生在哪个环节**。整条链路是"分块 → 向量化 → 召回 → 重排 → 拼接 → 生成"，每一环都可能出问题，对症下药才有效。这张排查清单建议照着走：

1. **召回环节就有答案吗？** 直接打印 top5 chunk 看内容。答案都不在 top5 里 → 问题在召回之前（分块、embedding、检索词），往下查；答案在 top5 但回答仍错 → 问题在生成环节，往下查。
2. **分块是否切碎了概念？** 打开失败 query 对应的源文档，人工看"答案所在段落"有没有被切到边界外。我的知识库出过一次"所有表格相关的提问全部失败"，最后发现表格被按行切散，任何一块都不完整——修复方式是切分器识别表格，整表作为一个 chunk。
3. **检索词和文档的"语言鸿沟"？** 用户问"部署失败怎么办"，文档里写的是"启动异常排查"。同义改写（让模型先把用户问题改写成 2-3 个检索词变体，每个都查一遍取并集）能显著缓解，成本是多两次廉价调用。
4. **生成环节是不是没读上下文？** 检查模型回答是否引用了错误的 chunk，或者无视了"只使用资料中的信息"的约束。前者说明重排顺序有问题，后者要检查 system prompt 的位置（资料放 system 还是 user 消息，不同模型表现不同，我目前统一放 system 尾部，效果最稳）。
5. **量级问题**：如果文档总量很大，确认检索没有因为实现疏忽只扫了部分库（我见过分库分表之后只查了第一张表的 bug，表现为"新文档永远检索不到"）。

这张清单的价值在于把"RAG 不准"这种模糊抱怨，拆解成可以逐项排除的具体问题。我的知识库问答从 60% 准确率到 90%+，走的正是这条排查路径，而不是某次神奇的调参。

## 6. 元数据过滤：被低估的检索精度杠杆

第 2 节讲了把元信息拼进 embedding 输入，这一节讲它的进阶用法：**结构化元数据 + 检索时过滤**。给每个 chunk 建立结构化字段——文档类型（教程/随笔/笔记）、发布时间、语言、技术栈标签——然后在检索前先按用户语境过滤：

```ts
// 检索范围缩小，精度自然上升
const scope = { type: "tutorial", tags: ["docker"] };
const candidates = vectorSearch(embed(query), 30, scope);
```

适用场景非常具体：用户在"教程"页面提问，就没必要检索全部随笔；问"最新的部署方式"，时间权重就该向前倾斜（我按 chunk 时间做了简单的分数衰减，半年前的 chunk 乘 0.8 系数）。这些手段没有一个是 AI，全是数据库查询，但它们对最终问答质量的贡献不输任何模型侧的调优——**检索系统的精度，一半靠模型，一半靠把"我们已经知道的信息"用起来。**

元数据过滤还有一个隐藏收益：权限边界。多用户知识库场景下，chunk 必须带 owner 字段，检索时强制过滤"当前用户可见的文档"——这一条不是优化，是安全底线（12 篇的"最小权限"原则在 RAG 里的直接落点）。漏了它的后果是 A 用户的问题召回 B 用户的私有文档，模型再把内容复述出来，一次数据泄漏事故就成了。

### 4.4 检索质量的最小验收流程

重排和混合检索做完之后，怎么知道整体链路确实变好了？我用的最小验收流程：固定 20 个测试问题（10 个答案明确在文档里、5 个答案部分覆盖、5 个文档里根本没有答案），每个问题人工判定 top5 chunk 是否命中，同时记录"文档里没有答案"的问题是否被模型诚实拒绝。

这个流程看起来原始，但它有一个不可替代的价值：**它同时检验检索和生成分界线的诚实度**。很多 RAG 系统的问题不是检索不准，而是检索不到时模型硬编——验收集里的 5 个"无答案"问题就是专门钓这个的。我的知识库在加"资料不足时明确说没有"约束前后，这 5 个问题的幻觉率从 5/5 降到 1/5，剩下那 1 条是模型把部分相关的内容脑补成了完整答案，属于灰色地带，靠重排相关性的阈值调整压到了可接受范围。20 个问题、半小时人工判定，换来对整条链路的量化认知，这是我做过的性价比最高的验收动作。

## 小结

- RAG = 检索 + 塞上下文，不需要训练模型，是性价比最高的 AI 应用架构。
- 分块按语义边界切、300~800 token、留 10% 重叠、带章节路径元信息；给 chunk 拼上下文前缀再算向量。
- 十万 chunk 以内 SQLite/Postgres 就够，别过早引入专用向量库。
- 向量粗召回 → 重排精排的两段式，加上关键词混合检索，是召回质量的两级火箭。
- Prompt 里给失败出口 + 回答标注来源，防幻觉且可溯源。

## 练习

1. 给你手头 10 篇文档跑一遍"入库 → 提问 → 检索"全流程，观察 top5 chunk 的相关性。
2. 对比 chunk 300 / 500 / 1000 token 三档的检索质量，记录你的数据集上的最优值。
3. 实现"上下文前缀"增强（2.2 节），重算向量并对比前后召回差异。
4. 加一路 SQLite FTS5 关键词检索 + RRF 融合，用一个专有名词问题验证提升。
