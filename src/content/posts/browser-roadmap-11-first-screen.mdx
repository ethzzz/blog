## 别再"优化首屏"，先拆开它

LCP 是一个合成结果，四段耗时相加：

```text
TTFB            资源加载延迟        资源加载时长        元素渲染延迟
[服务器响应]  →  [发现资源的时间]  →  [下载完的时间]  →  [画到屏幕]
```

每一段的对策完全不同。**不分段就动手，80% 是在优化不痛的那一段。**

| 段 | 怎么测 | 对策 |
| --- | --- | --- |
| TTFB | Network 里首个字节时间；或 `responseStart - requestStart` | CDN、服务端缓存、减少重定向、流式 SSR |
| 资源加载延迟 | LCP 元素是 `<img>` 时：`loadTime - startTime` 与 HTML 解析时间差 | `preload`、`fetchpriority=high`、别 lazy、别让它被 CSS/JS 挡住 |
| 资源加载时长 | 资源 `duration` | 换格式（AVIF）、压尺寸、CDN、Brotli |
| 元素渲染延迟 | 资源到位到 LCP 上报之间的差 | 减少阻塞 CSS/字体、避免长任务 |

## 一个真实案例：4.2s → 1.8s

背景：内容型页面，移动端 4G 限速，hero 图是 LCP 元素，P75 LCP = 4.2s。

| 步骤 | 改了什么 | LCP | 差值 |
| --- | --- | --- | --- |
| 基线 | — | 4.2s | — |
| 1 | `index.html` 从 `max-age=600` 改成 `no-cache`（拿掉旧 HTML 导致的二次请求） | 3.9s | -0.3s |
| 2 | hero 图 480KB JPEG → 160KB AVIF（尺寸按 DPR 出图） | 3.3s | -0.6s |
| 3 | hero 图去掉 `loading="lazy"`，加 `fetchpriority="high"` + `<link rel=preload>` | 2.6s | -0.7s |
| 4 | 中文字体 6MB → 280KB 子集 + `font-display: swap` | 2.2s | -0.4s |
| 5 | 首屏 JS 从 310KB(gz) 砍到 145KB（图表/编辑器改动态导入） | 2.0s | -0.2s |
| 6 | TTFB 320ms → 90ms（上 CDN + 服务端缓存） | **1.8s** | -0.2s |

关键点：**第 2、3 步合计贡献 1.3s，占全部收益的一半以上**——它们都作用在"资源加载"这一段。如果一开始就去优化 JS（很多人第一反应），只能拿到 0.2s。

## 四段的通用动作清单

### TTFB

- 静态资源上 CDN，HTML 走边缘缓存；
- 服务端渲染首屏（SSR/SSG），别让前端等接口再渲染；
- 去掉多余重定向（`http→https`、`/→/index`、域名跳转）；
- 数据库慢查询（这是最常见的隐藏原因）。

### 资源加载延迟（最容易忽略的一段）

- LCP 元素是图片：**必须**有 `fetchpriority="high"`，且不能 `loading="lazy"`；
- 用 `<link rel="preload">` 提前发现（只给这一个）；
- 确认它没被大 CSS 挡住（CSS 阻塞渲染，也推迟图片发现）；
- 不要在 `<head>` 塞同步脚本。

### 资源加载时长

- 图片格式与尺寸（`srcset` 按 DPR 出图）；
- 字体子集化；
- 压缩（Brotli）+ HTTP/2；
- 减少首屏请求数里的"大块头"。

### 元素渲染延迟

- 字体阻塞（`font-display: swap`）；
- 首屏 JS 里不要有长任务（>50ms 会推迟绘制）；
- 避免"先渲染骨架再替换"造成的二次布局（会推后 LCP）。

## 怎么确认"改对了"

**一次只改一项，改完立刻量**。用同一条件：

```bash
# 固定条件：4G 限速 + CPU 4x 降速 + 清缓存，跑 5 次取中位数
```

```js
// 用 PerformanceObserver 精确记录 LCP 与元素
new PerformanceObserver((list) => {
  const last = list.getEntries().at(-1);
  console.log('LCP', Math.round(last.startTime), 'ms', last.element?.tagName, last.url);
}).observe({ type: 'largest-contentful-paint', buffered: true });
```

`last.element` 很有用：**你以为的 LCP 元素可能不是真正的 LCP 元素**（比如标题比图更大）。

## 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 优化了 JS 但 LCP 没动 | LCP 元素与 JS 无关 | 先看 `last.element` 是什么 |
| 首屏图加了 lazy | 浏览器延迟发现 | 去掉 lazy + `fetchpriority=high` |
| 加了 preload 没用 | 元素不是 LCP，或 preload 被低优先级挤掉 | 用 `last.element` 确认 |
| Lighthouse 分数高、线上差 | 模拟环境太乐观 | 用 RUM 的 P75 判断 |
| 骨架屏让 LCP 变差 | 骨架先绘制、真实内容后到 | 骨架尺寸与内容一致，或直接服务端渲染内容 |
| 改完指标波动大 | 单次测量噪声 | 固定环境跑 5 次取中位 |

## 练习

1. **找出真正的 LCP 元素**：用上面的 observer 打印 `element.tagName` 与 `url`，对比你原本以为的那个。  
   *自检*：如果两者不一致，说明你之前优化错了对象。
2. **做一次四段拆解**：在 Network 里算 TTFB、资源发现延迟、下载时长、渲染延迟四个数，加起来接近 LCP。  
   *自检*：能指出最大的一段，并说出对应的一条手段。
3. **单变量验证**：只把首屏图换成 AVIF（其它不动），跑 5 次对比。  
   *自检*：给出体积变化与 LCP 变化两个数字；若 LCP 没动，解释原因（可能不是 LCP 元素）。
