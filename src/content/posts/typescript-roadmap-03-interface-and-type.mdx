## 别背表格，理解"能不能被重新打开"

`interface` 和 `type` 在 90% 的场景下可以互换。真正决定选择的只有一件事：**这个类型定义能不能被别处"再打开"一次**。

```ts
// interface：同名声明会合并（declaration merging）
interface User { id: string }
interface User { name: string }
// 结果：User 有两个字段，而且没有任何报错

// type：同名声明直接冲突
type User = { id: string };
type User = { name: string };   // ❌ Duplicate identifier
```

**这个差异既是特性也是地雷**：

- 特性：给第三方库的类型"打补丁"（`declare module` 里扩字段）、在全局注入（`Window` 加属性）。
- 地雷：两个模块不小心都定义了 `interface Config`，字段会**静默合并**成一个谁都不认识的类型，报错位置离现场很远。

---

## 差异对照

| 维度 | `interface` | `type` |
| --- | --- | --- |
| 声明合并 | ✅ | ❌ |
| 扩展方式 | `extends A, B` | 交叉 `A & B` |
| 能表达联合 | ❌ | ✅ `A \| B` |
| 能表达元组/字面量/条件类型 | ❌ | ✅ |
| 能表达映射类型 | ❌ | ✅ |
| 报错可读性 | 略好（名字保留在报错里） | 复杂交叉类型会展开成一大坨 |
| 性能 | 略好（TS 内部对接口有缓存） | 复杂组合时可能变慢 |

**实践建议**（团队统一比"正确答案"重要）：

- **对象形状**：用 `interface`，尤其对外导出的公共类型（可扩展、报错好看）；
- **联合、映射、条件、工具类型**：只能 `type`；
- **一个文件里别混着用两种风格描述同一层概念**，否则 review 时谁也说不清。

## 可选、只读、索引签名

```ts
interface Task {
  readonly id: string;        // 创建后不可改（编译期保证）
  title: string;
  done?: boolean;             // 可选：类型是 boolean | undefined
  tags: readonly string[];    // 只读数组，避免被 push 污染
}
```

⚠️ `readonly` 是**浅层**的：`readonly tags: string[]` 只能阻止重新赋值 `task.tags = []`，仍能 `task.tags.push('x')`。要深层只读得用 `readonly string[]` 或 `Readonly<T>` 逐层套。

### 索引签名：方便的代价

```ts
interface Dict { [key: string]: number }

const d: Dict = { a: 1 };
d.b = 2;         // ✅ 任何 key 都合法
d['不存在的键'];  // 类型是 number —— 但运行时是 undefined ⚠️
```

这就是索引签名最大的问题：**类型说谎**。开 `noUncheckedIndexedAccess` 后它会变成 `number | undefined`（务必开）。

更好的替代：

```ts
// 1) 键已知 → 用映射类型，键受约束
type PageMeta = Record<'home' | 'about' | 'post', { title: string }>;

// 2) 键未知但要安全 → 用 Map（取值自带 undefined）
const cache = new Map<string, number>();

// 3) 从常量推导键 → as const satisfies
const ROUTES = { home: '/', post: '/p' } as const;
type RouteKey = keyof typeof ROUTES;
```

### `{}`、`object`、`Record<string, never>` 的区别

| 写法 | 含义 | 常见误用 |
| --- | --- | --- |
| `{}` | **任何非 null/undefined 的值**（包括 `'abc'`、`123`） | 想表达"空对象"却写它 |
| `object` | 任何非原始类型 | 不能索引取值 |
| `Record<string, never>` | 真正的"空对象" | 过于严格，很少需要 |
| `Record<string, unknown>` | 任意键值 | 取值要判空 |

`{}` 的语义最反直觉：它**不表示"没有属性"**，而是"任何有值的类型"。要表达空对象，用 `Record<string, never>`。

## 交叉类型：注意"不可能的交叉"

```ts
type A = { kind: 'a'; a: number };
type B = { kind: 'b'; b: string };
type AB = A & B;      // kind 同时是 'a' 和 'b' → 实际是 never
```

`A & B` 不会报错，但它是一个**永远无法构造**的类型。这类"不可能类型"往往在深层才暴露，症状是"某个变量类型是 `never`，赋值怎么都不对"。

判断技巧：交叉里有**同名字段且类型互斥**时，结果就是 `never`。遇到时先检查是不是该用联合（`A | B`）而不是交叉。

## namespace：新代码别用

```ts
// ❌ 老写法：编译后生成真实对象，不能 tree-shake，还和 ESM 打架
namespace Utils {
  export function foo() {}
}
```

三个理由：

1. **它会产生运行时对象**，与"类型在编译期消失"的直觉冲突；
2. **与 ESM 混用会冲突**（同一个名字既是命名空间又是模块导出，容易 `Cannot redeclare`）；
3. **现代替代方案更简单**：一个文件就是一个模块，要分组就用目录。

`namespace` 唯一还有价值的场景：**全局 `.d.ts` 里给旧库补类型**（`declare global { namespace JSX {...} }`）——那是"描述已有结构"，不是"组织自己的代码"。

## 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 两个文件定义了同名 interface，字段莫名多出来 | 声明合并 | 改用 `type`，或给 interface 加前缀 |
| `Record<string, T>` 取不存在的键不报错 | 索引签名 + 未开 `noUncheckedIndexedAccess` | 开严格索引检查；或用 `Map` |
| `{}` 类型接受字符串/数字 | `{}` 语义是"非空值" | 用 `Record<string, never>` 或具体字段 |
| `A & B` 之后类型变 `never` | 同名字段互斥 | 检查是否该用 `\|` |
| `readonly arr: string[]` 仍能被 push | readonly 是浅层 | 用 `readonly string[]` |
| `Cannot redeclare block-scoped variable` | namespace 与模块同名 | 删掉 namespace，改文件模块 |

## 验收清单

- [ ] 团队有明确约定：什么情况用 `interface`、什么情况用 `type`
- [ ] 没有"同名 interface 意外合并"的地方（`grep` 一下重名）
- [ ] 索引签名的类型不是"说谎的"（开了 `noUncheckedIndexedAccess`，或改用 `Map`）
- [ ] 没有 `namespace`（除了 `.d.ts` 里补全局类型）
- [ ] 能说清 `{}`、`object`、`Record<string, never>` 三者的区别
- [ ] 交叉类型里没有互斥同名字段（不产生 `never` 类型）

## 练习

1. **制造一次声明合并**：在两个文件里各写一个 `interface Config { ... }`，在第三个文件里导入使用，观察类型变成"两者的并集"且无报错。  
   *自检*：能说出"为什么这种 bug 在 CI 里查不出来"（它不报错，只是类型变宽）。
2. **修一个说谎的索引签名**：把 `Record<string, Task>` 改成 `Map<string, Task>`，对比取值时的类型提示与判空要求。  
   *自检*：能说明 `Map.get` 返回 `T | undefined` 是"诚实的类型"。
3. **验证 `{}` 的语义**：写 `function f(x: {}) {}`，分别传 `'abc'`、`123`、`null`，看哪些能过。  
   *自检*：能解释"`{}` 只是排除了 null/undefined"。
