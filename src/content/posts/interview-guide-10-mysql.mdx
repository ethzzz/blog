## 索引

### Q1: MySQL 索引的类型？⭐ 🔥

**答：**

| 索引类型 | 说明 |
|:--|:--|
| 主键索引 (PRIMARY KEY) | 唯一标识，不允许 NULL |
| 唯一索引 (UNIQUE) | 值唯一，允许 NULL |
| 普通索引 (INDEX) | 最基本的索引 |
| 联合索引 (COMPOSITE) | 多列组合索引 |
| 全文索引 (FULLTEXT) | 文本搜索 |

```sql
-- 创建索引
CREATE INDEX idx_username ON users(username);
CREATE UNIQUE INDEX idx_email ON users(email);
CREATE INDEX idx_name_age ON users(name, age);  -- 联合索引

-- 查看索引
SHOW INDEX FROM users;

-- 删除索引
DROP INDEX idx_username ON users;
```

### Q2: 为什么使用 B+ 树而不是 B 树？⭐⭐⭐ 🔥

**答：**

```
B 树：
        [30|60]
       /   |   \
   [10|20] [40|50] [70|80]
   (数据存储在内部节点)

B+ 树：
        [30|60]           ← 内部节点只存键值
       /   |   \
   [10|20] [40|50] [70|80]
      ↓       ↓       ↓
   [data]  [data]  [data]  ← 叶子节点存数据
      ↔       ↔       ↔    ← 叶子节点链表相连
```

**B+ 树优势：**

| 特性 | B 树 | B+ 树 |
|:--|:--|:--|
| 数据存储位置 | 所有节点 | 只在叶子节点 |
| 叶子节点链表 | 无 | 有（便于范围查询） |
| 查询稳定性 | 不稳定（可能在内部节点找到） | 稳定（必须到叶子节点） |
| 磁盘 I/O | 较多 | 较少（内部节点更小） |
| 范围查询 | 需要中序遍历 | 链表顺序扫描 |

**追问链（把这几问接住，B+ 树才算真懂）：**

- **「为什么常说单表 2000 万行就该考虑分表？」**
  答：来自 B+ 树高度的经验估算。InnoDB 页 16KB，假设主键 8 字节 + 指针 6 字节，一个非叶子节点页能放约 1170 个索引项；叶子页每行 1KB 能放约 16 行。三层树容量 ≈ 1170 × 1170 × 16 ≈ 2000 万行。再涨就要 4 层，每次查询多一次磁盘 I/O。这不是硬阈值——行很窄可以到几千万，行很宽（大字段多）几百万就要拆——面试要说清「2000 万是 3 层树的估算值，不是魔数」。
- **「主键为什么推荐自增 ID，UUID 有什么问题？」**
  答：InnoDB 是聚簇索引，数据按主键**物理有序**存储。自增 ID 永远追加到 B+ 树最右侧页，写满就开新页，顺序写、页利用率高。UUID 无序，新行随机插到树中间，导致**页分裂**（挪数据、产生碎片）、缓存命中率低、写放大。同理，业务主键（如订单号）做主键时，通常还是配一个内部自增列当聚簇键。
- **「为什么联合索引区分度高的列放前面？」**
  答：不只区分度——先看**查询模式**再定列序：等值条件的列放前面，范围条件的列放最后（范围之后的列都用不上索引的定位能力）。区分度只决定「过滤效率」，查询模式决定「能不能命中」。

### Q3: 聚簇索引和非聚簇索引的区别？⭐⭐ 🔥

**答：**

```
聚簇索引（InnoDB 主键）：
┌─────────────────────────────────┐
│  B+ 树叶子节点存储完整行数据    │
│  数据即索引，索引即数据         │
└─────────────────────────────────┘

非聚簇索引（二级索引）：
┌─────────────────────────────────┐
│  B+ 树叶子节点存储主键值        │
│  需要"回表"查询完整数据         │
└─────────────────────────────────┘
```

```sql
-- 回表示例
SELECT * FROM users WHERE name = 'Tom';
-- 1. 在 name 索引树找到主键 id = 100
-- 2. 在主键索引树找到 id = 100 的完整行数据（回表）

-- 避免回表：覆盖索引
SELECT id, name FROM users WHERE name = 'Tom';
-- name 索引已包含 id 和 name，无需回表
```

**追问链：**

- **「回表为什么慢？覆盖索引怎么设计？」**
  答：回表 = 二级索引树上找到主键后，再去主键树查一次，随机 I/O 翻倍。覆盖索引的设计套路：把 `SELECT` 里出现的列**追加进联合索引**，让索引「顺便」带上要查的数据。例如高频查询 `SELECT id, name FROM users WHERE email = ?`，建 `(email, name)` 联合索引即覆盖。代价是索引变宽、写入变慢——所以只给高频查询做覆盖索引，不做无脑大宽索引。
- **「`SELECT *` 除了慢还有什么坏处？」**
  答：堵死覆盖索引的可能、网络传输变大、后端 ORM 映射出无用字段、加列后语义漂移。一句话：`SELECT *` 让优化器没有任何腾挪空间。

### Q4: 最左前缀原则？⭐⭐ 🔥

**答：**

联合索引 `(a, b, c)` 的查询规则：

```sql
-- ✅ 命中索引
WHERE a = 1                    -- 命中 a
WHERE a = 1 AND b = 2          -- 命中 a, b
WHERE a = 1 AND b = 2 AND c = 3 -- 命中 a, b, c

-- ❌ 不命中或部分命中
WHERE b = 2                    -- 不命中（缺少最左列 a）
WHERE c = 3                    -- 不命中
WHERE b = 2 AND c = 3          -- 不命中

-- ⚠️ 范围查询后停止
WHERE a = 1 AND b > 2 AND c = 3  -- 命中 a, b（c 不命中，范围后停止）

-- ✅ 索引下推（MySQL 5.6+）
WHERE a = 1 AND b LIKE '%test%' AND c = 3
-- ICP 优化：在索引层过滤 b，减少回表
```

### Q5: 索引失效的情况？⭐⭐ 🔥

```sql
-- 1. 对索引列使用函数
WHERE YEAR(create_time) = 2024        -- ❌ 失效
WHERE create_time >= '2024-01-01'     -- ✅ 命中

-- 2. 隐式类型转换
WHERE phone = 13800138000             -- ❌ phone 是 varchar，数字会转换
WHERE phone = '13800138000'           -- ✅ 命中

-- 3. LIKE 以 % 开头
WHERE name LIKE '%Tom'                -- ❌ 失效
WHERE name LIKE 'Tom%'                -- ✅ 命中

-- 4. OR 条件有非索引列
WHERE name = 'Tom' OR age = 20        -- ❌ age 无索引，全表扫描

-- 5. != 和 NOT IN
WHERE status != 1                     -- ❌ 可能失效
WHERE status NOT IN (1, 2)            -- ❌ 可能失效

-- 6. IS NULL / IS NOT NULL（视数据分布）
WHERE name IS NULL                    -- 可能失效

-- 7. 联合索引不满足最左前缀
-- 见上题
```

## 事务

### Q6: 事务的 ACID 特性？⭐ 🔥

**答：**

| 特性 | 说明 | 实现机制 |
|:--|:--|:--|
| **A** (Atomicity) 原子性 | 事务要么全成功，要么全失败 | undo log |
| **C** (Consistency) 一致性 | 事务前后数据状态一致 | 其他三个特性保证 |
| **I** (Isolation) 隔离性 | 并发事务互不干扰 | 锁 + MVCC |
| **D** (Durability) 持久性 | 提交后数据永久保存 | redo log |

```sql
-- 事务示例
START TRANSACTION;

UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;

COMMIT;  -- 或 ROLLBACK;
```

### Q6b: redo log、undo log、binlog 各干什么？两阶段提交在保什么？⭐⭐⭐ 🔥

**答：** 三大日志分工一句话：**redo 保崩溃恢复（D）、undo 保回滚与 MVCC（A+I）、binlog 保复制与归档**。

| 日志 | 层级 | 内容 | 写入方式 | 用途 |
|:--|:--|:--|:--|:--|
| redo log | InnoDB 引擎层 | 物理日志：「某数据页某偏移改了什么」 | 循环写、固定大小（WAL） | 崩溃后重放，保证已提交事务不丢 |
| undo log | InnoDB 引擎层 | 逻辑日志：反向操作（insert→delete） | 随事务生成， purge 线程回收 | 回滚 + MVCC 版本链 |
| binlog | Server 层 | 逻辑日志：语句或行变更 | 追加写、不覆盖 | 主从复制、时间点恢复 |

**为什么需要两阶段提交（2PC）？** redo 和 binlog 是两个独立日志，如果先写一个再写另一个，中间崩溃就会不一致：

```
事务提交的真实顺序：
1. 写 redo log，标记 prepare 状态
2. 写 binlog（落盘）
3. 写 redo log，标记 commit 状态

崩溃恢复时的裁决规则：
- redo 是 commit → 直接恢复
- redo 是 prepare：
    binlog 完整 → 补提交（从库可能已经同步了这条，主库必须认）
    binlog 不完整 → 回滚（从库没有这条，主库也不能有）
```

**追问链：**

- **「WAL 是什么？为什么先写日志比直接刷数据页快？」**
  答：Write-Ahead Logging——修改先顺序追加到 redo log，数据页可以晚点再刷脏。顺序写远快于随机写，且崩溃后靠 redo 重放就能恢复，不必每次提交都把随机分布的数据页刷盘。
- **「binlog 三种格式的区别？」**
  答：`statement` 记原始 SQL（省空间，但 NOW()/RAND() 等不确定函数会导致主从不一致）；`row` 记每行变更前后值（最安全，默认推荐，缺点是批量更新日志量大）；`mixed` 折中自动切换。生产基本都用 row。
- **「redo log 写满了会怎样？」**
  答：它是环形缓冲（write pos 追 checkpoint），写满意味着脏页还没刷盘腾不出空间，MySQL 会**阻塞所有更新**直到刷脏推进 checkpoint——线上表现为「写入突然全部卡住」，要查 `innodb_io_capacity` 与磁盘 IOPS 是否匹配。

### Q7: 事务隔离级别？⭐⭐ 🔥

**答：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|:--|:--|:--|:--|
| READ UNCOMMITTED | ✅ | ✅ | ✅ |
| READ COMMITTED | ❌ | ✅ | ✅ |
| REPEATABLE READ (MySQL默认) | ❌ | ❌ | ✅* |
| SERIALIZABLE | ❌ | ❌ | ❌ |

```sql
-- 查看隔离级别
SELECT @@transaction_isolation;

-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

**并发问题解释：**

```sql
-- 脏读：读到未提交的数据
-- 事务A修改数据但未提交，事务B读到了修改后的值

-- 不可重复读：同一事务内两次读取结果不同
-- 事务A读取数据，事务B修改并提交，事务A再次读取发现变了

-- 幻读：同一事务内两次查询行数不同
-- 事务A查询10行，事务B插入新行，事务A再查询变成11行
```

**MVCC（多版本并发控制）：**

```
MySQL InnoDB 通过 MVCC 实现 REPEATABLE READ 下的非锁定读：

每行数据隐藏列：
- trx_id：最后修改的事务ID
- roll_pointer：指向 undo log 的指针

读取时根据 Read View 判断可见性：
- 事务开始时创建 Read View
- 读取时沿着 roll_pointer 找到可见版本
```

**追问链（隔离级别的高频深挖）：**

- **「MySQL 的 REPEATABLE READ 下幻读到底解决了没有？」⭐⭐⭐**
  答：说「部分解决」最准确。**快照读**（普通 SELECT）靠 MVCC：事务全程用同一个 Read View，新插入的行对当前事务不可见，不会幻读。**当前读**（SELECT ... FOR UPDATE / UPDATE / DELETE）靠**间隙锁 + 临键锁**：锁住已存在的行和行之间的空隙，其他事务无法在范围内插入。但漏网场景存在：事务内先快照读、后当前读混用时（先 SELECT 再 FOR UPDATE），两次看到的行集可能不一致。能主动说出这个混用边界，比背结论高一个档位。
- **「为什么很多互联网公司反而把隔离级别调成 READ COMMITTED？」**
  答：RR 的间隙锁在并发写入时锁范围大、死锁率高，高并发场景代价明显。RC 只有行锁（语句级快照），死锁少、并发好；代价是不可重复读——多数业务（订单、支付状态机）靠「单行当前读 + 乐观锁版本号」就够了，不依赖事务级快照一致性。AliSQL 系默认 RC 就是这个原因。
- **「RC 和 RR 的 Read View 差别是什么？」**
  答：RC **每条语句**都创建新的 Read View（所以能看到别人已提交的最新数据）；RR 整个事务只用**第一条快照读时**创建的那份。这一句是两种级别所有行为差异的根。

## SQL 优化

### Q8: 如何分析慢 SQL？⭐⭐ 🔥

**答：**

```sql
-- 1. 开启慢查询日志
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;  -- 超过1秒记录

-- 2. EXPLAIN 分析执行计划
EXPLAIN SELECT * FROM users WHERE name = 'Tom';

-- 关键字段
-- id: 查询序号
-- select_type: 查询类型（SIMPLE/PRIMARY/SUBQUERY）
-- table: 表名
-- type: 访问类型（性能从好到差）
--   system > const > eq_ref > ref > range > index > ALL
-- possible_keys: 可能使用的索引
-- key: 实际使用的索引
-- rows: 预估扫描行数
-- Extra: 额外信息
--   Using index: 覆盖索引（好）
--   Using where: 需要过滤
--   Using filesort: 需要额外排序（差）
--   Using temporary: 使用临时表（差）
```

### Q9: SQL 优化技巧？⭐⭐ 🔥

```sql
-- 1. 避免 SELECT *
SELECT id, name, email FROM users;  -- ✅ 只查需要的列

-- 2. 使用 LIMIT 分页
SELECT * FROM orders ORDER BY id LIMIT 100000, 10;  -- ❌ 深分页慢
-- 优化：延迟关联
SELECT o.* FROM orders o
INNER JOIN (SELECT id FROM orders ORDER BY id LIMIT 100000, 10) t
ON o.id = t.id;  -- ✅

-- 3. 小表驱动大表
-- IN 适合子查询结果集小
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders WHERE amount > 100);
-- EXISTS 适合外表小
SELECT * FROM users u WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- 4. 批量操作
INSERT INTO users (name, age) VALUES ('A', 20), ('B', 21), ('C', 22);  -- ✅ 批量
-- 而不是循环单条插入

-- 5. 使用连接查询替代子查询
SELECT u.*, o.amount FROM users u
JOIN orders o ON u.id = o.user_id;  -- ✅ 通常比子查询快

-- 6. 合理使用索引
-- WHERE、ORDER BY、GROUP BY 的列加索引
-- 联合索引把区分度高的列放前面

-- 7. 避免大事务
-- 大事务占用锁时间长，影响并发
```

### Q9b: count(*)、count(1)、count(列) 有什么区别？大表计数怎么优化？⭐⭐ 🔥

```sql
-- 语义差异（先说清语义，再谈性能）
SELECT COUNT(*) FROM users;          -- 统计总行数（含 NULL 行）
SELECT COUNT(1) FROM users;          -- 与 COUNT(*) 完全等价
SELECT COUNT(name) FROM users;       -- 只统计 name 非 NULL 的行
SELECT COUNT(DISTINCT name) FROM users;  -- 去重计数，最贵

-- InnoDB 下 COUNT(*) 的执行：
-- 优化器会选最小的可用二级索引树遍历（叶子只存索引列+主键，比聚簇树小得多）
-- 没有二级索引才扫聚簇索引 → 所以「给大表建个窄索引」也能加速 count
```

**性能排序（InnoDB）：** `count(*) ≈ count(1) > count(主键) > count(普通列)`。前两者优化器同等对待，别信「count(1) 比 count(*) 快」的传言；`count(列)` 要逐行判 NULL 且可能走更宽的索引，最慢。

**为什么 MyISAM 的 count(*) 是 O(1) 而 InnoDB 不是？** MyISAM 把总行数存在元信息里（无事务、无 MVCC，一个全局计数就够）；InnoDB 因为 MVCC，**同一时刻不同事务看到的行数可能不同**，不存在一个对所有事务都正确的全局计数，只能实时遍历。

**大表计数的工程方案：**

| 方案 | 精确性 | 适用 |
|:--|:--|:--|
| `EXPLAIN` 的 rows 估算 | 估算值 | 监控大盘、允许误差 |
| Redis 计数（incr/decr） | 最终一致 | 高频读、可容忍短暂偏差 |
| 计数表（业务事务内同步更新） | 精确 | 需要精确且读多写少 |
| 定时任务离线统计 | 延迟精确 | 报表类 |

**追问：** `SELECT COUNT(*) FROM t WHERE status = 1` 怎么优化？—— 给 status 建索引让它走窄索引扫描；如果 status 区分度低（一半行都是 1），索引收益有限，考虑把高频计数沉淀到计数表/缓存，别每次实时算。

## 锁机制

### Q10: MySQL 有哪些锁？⭐⭐

**答：**

| 锁类型 | 粒度 | 说明 |
|:--|:--|:--|
| 表锁 | 表 | 开销小，并发低 |
| 行锁 | 行 | 开销大，并发高（InnoDB） |
| 共享锁 (S) | 行/表 | 读锁，允许并发读 |
| 排他锁 (X) | 行/表 | 写锁，阻塞其他读写 |
| 间隙锁 (Gap) | 范围 | 防止幻读 |
| 临键锁 (Next-Key) | 行+间隙 | InnoDB 默认 |

```sql
-- 共享锁（读锁）
SELECT * FROM users WHERE id = 1 LOCK IN SHARE MODE;

-- 排他锁（写锁）
SELECT * FROM users WHERE id = 1 FOR UPDATE;

-- 死锁示例
-- 事务A：UPDATE users SET ... WHERE id = 1;
-- 事务B：UPDATE users SET ... WHERE id = 2;
-- 事务A：UPDATE users SET ... WHERE id = 2;  -- 等待B
-- 事务B：UPDATE users SET ... WHERE id = 1;  -- 等待A，死锁！

-- InnoDB 自动检测死锁，回滚代价小的事务
```

**追问链：**

- **「行锁是加在『行』上的吗？」⭐⭐⭐ 这题最能筛掉背题的人**
  答：InnoDB 的行锁**加在索引项上**。如果 WHERE 条件走不到索引，InnoDB 无法精确定位，只能全表扫描并把**所有行都锁上**（近似锁表）——这就是「UPDATE 没走索引引发全表锁等待」的经典线上事故。同理，`WHERE name = 'Tom' FOR UPDATE` 若 name 无索引，并发下等于互锁大面积行。
- **「线上出现死锁怎么排查？」**
  答：`SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 段落能看到两个事务各自持有的锁和等待的锁、最后的 SQL。治理三板斧：**统一加锁顺序**（按主键升序更新）、缩小事务范围（大事务拆小）、给热点行更新加索引避免锁放大。死锁本质不是 bug，是并发访问顺序没约定。
- **「`SELECT ... FOR UPDATE` 用的什么读？」**
  答：当前读，读最新已提交版本（不是 MVCC 快照），并且加排他锁。这也是前面说的「间隙锁防幻读」生效的场合。

## 常见坑速查表

| 现象 | 根因 | 解法 |
|:--|:--|:--|
| 查询走索引却还是很慢 | 回表次数太多 | 覆盖索引（SELECT 列并入联合索引） |
| UPDATE 卡住整片业务 | 条件没走索引，行锁放大到全表 | 给 WHERE 列建索引；上线前 EXPLAIN |
| `WHERE phone = 138...` 不走索引 | varchar 列被隐式转成数字比较 | 值加引号，类型与列一致 |
| 深分页 `LIMIT 100000, 10` 越翻越慢 | 扫描并丢弃前 10 万行 | 延迟关联 / 游标分页（`WHERE id > last_id`） |
| 隐患：索引建了一堆写入变慢 | 二级索引都要同步维护 | 按查询频率收敛索引；冗余索引合并 |
| count(*) 很慢 | 全索引扫描 | 精确计数用计数表/缓存；业务允许用估算 |
| 主从延迟读不到新数据 | 从库回放滞后 | 关键读走主库；或写后短窗口内强制主库 |
| 死锁频发 | 事务加锁顺序不一致 | 统一按主键序加锁 + 缩小事务 |
| `count(列)` 比总行数少 | 该列有 NULL，count(列) 只数非 NULL | 数总行数用 `count(*)` |
| 写入高峰全库更新卡住 | redo log 写满，等刷脏腾空间 | 调 `innodb_io_capacity` 匹配磁盘 IOPS |

## 深水区追问（2026 补充）

**Q：间隙锁到底锁的是哪一段？`id = 5` 与范围条件两种当前读分别锁了什么？**

答：InnoDB 的 next-key lock 是「记录锁 + 该记录前面的间隙」，按索引顺序成段加锁。分三种情况：① `id` 是唯一索引且 `id = 5` 命中唯一值时，next-key lock 退化为**纯记录锁**，不锁间隙（唯一等值不可能幻读出第二行）；② 条件列是**非唯一索引**做等值时，除了命中记录本身，还会锁到「下一个不满足条件的值之前」的间隙，防止别人插入同值行；③ 范围条件（如大于某个 id）会锁住扫描到的每条记录及其间隙，直到第一个不满足条件的记录为止。④ 关键推论：条件列**没有索引**时无法定位区间，只能全表扫描并锁住所有行与所有间隙，近似锁表；插入方被阻塞的是「插入意向锁」与既有间隙锁的冲突。

**Q：`UPDATE ... WHERE status = 1` 只用了二级索引，为什么可能同时锁住两棵 B+ 树？这如何制造死锁？**

答：InnoDB 的加锁对象是「**实际访问到的索引项**」：先在 `status` 的二级索引上定位并加锁，再按叶子里的主键回表、在聚簇索引上给对应主键加锁——一条 SQL 因此在两棵树上都留下锁。死锁就从这里来：两个事务各更新多行，如果「二级索引顺序」与「主键顺序」不一致，它们获取聚簇索引锁的顺序就相反，形成交叉等待。治理三条：① 让二级索引尽量**覆盖查询列**，减少回表（连 `id` 都在二级索引里，回表锁就省了）；② 批量更新按主键排序或分批提交，把加锁顺序固定下来；③ 缩小事务粒度，别让一个大事务持有一堆行锁跨多个网络往返。

**Q：同一张表、同一个索引，为什么有时 `ORDER BY` 能免排序，有时必须 `Using filesort`？**

答：免排序的前提是「索引自身的有序性，恰好等于你要的顺序」。四个条件缺一不可：① 排序方向一致（`a ASC, b DESC` 这类混合方向在 MySQL 8 之前无法直接利用联合索引）；② 排序列是索引的**最左连续前缀**，中间跳过一列就断；③ 该前缀之前的列必须是**等值条件**，范围条件之后的排序列不再有序；④ 排序列不能混入索引外的字段。还有一个容易误判的细节：`Extra` 同时出现 `Using index; Using filesort` 时，表示走了覆盖索引但排序仍在内存/磁盘做——只看 `Using index` 就宣布优化成功是错的。

**Q：慢查询日志里「扫描行数很少却耗时很长」的 SQL，瓶颈通常在哪？**

答：这类 SQL 的问题基本都不在执行计划，而在等待与 IO：① **锁等待**——`performance_schema.data_lock_waits` 或 `SHOW ENGINE INNODB STATUS` 看是否在等行锁，常见于长事务；② **刷脏页**——写入高峰时 redo/脏页落盘打满磁盘，`innodb_io_capacity` 与实际 IOPS 不匹配；③ **Buffer Pool 命中率低**——刚重启或大表把热数据挤出去，一次点查变成多次随机 IO；④ **大字段与行溢出**——`TEXT` / `BLOB` 走溢出页，行数少但读的页多；⑤ 从库回放延迟，读到的从库还在补日志。定位手段是 `EXPLAIN ANALYZE` 看实际耗时分布与 `performance_schema` 的阶段事件，而不是只盯 `rows` 这一列。

## 分库分表

### Q11: 什么时候需要分库分表？⭐⭐⭐

**答：**

| 场景 | 方案 |
|:--|:--|
| 单表数据量 > 2000万 | 水平分表 |
| 单库并发 > 2000 | 分库 |
| 读写比例悬殊 | 读写分离 |

```
垂直分库：按业务拆分
┌─────────────────┐    ┌──────┐ ┌──────┐ ┌──────┐
│   单一数据库    │ →  │用户库│ │订单库│ │商品库│
└─────────────────┘    └──────┘ └──────┘ └──────┘

水平分表：按规则分散数据
┌─────────────────┐    ┌────────┐ ┌────────┐ ┌────────┐
│   orders 表     │ →  │orders_0│ │orders_1│ │orders_2│
│   (1亿条)       │    │(hash)  │ │(hash)  │ │(hash)  │
└─────────────────┘    └────────┘ └────────┘ └────────┘

读写分离：
写 → 主库 → 同步 → 从库1（读）
                  → 从库2（读）
```

### Q11b: 主从复制的原理？延迟怎么产生的、怎么治？⭐⭐⭐ 🔥

```
复制链路（三个线程）：
主库                          从库
binlog ──→ [dump 线程] ──→ [I/O 线程] ──→ relay log ──→ [SQL 线程] ──→ 回放
           推送变更          拉取落盘中继日志            重放写入从库

1. 主库提交事务写 binlog
2. 从库 I/O 线程连主库，dump 线程把 binlog 推过来
3. 从库先写 relay log（中继日志），I/O 线程即可返回
4. SQL 线程读 relay log 回放 → 数据才真正可见
```

**延迟的根因（按出现频率）：**
1. **回放是单线程/并行度不足**：主库并发写，从库 SQL 线程回放跟不上（MySQL 5.7+ 基于组提交的并行复制、8.0 WRITESET 可大幅缓解）；
2. **大事务**：主库一个事务删百万行，从库要原样回放这么久，期间后续全部排队；
3. **从库机器差/负载高**：从库常被拿去跑报表、备份，IOPS 被抢；
4. **DDL 阻塞**：主库在线 DDL 完成后，从库回放同样的 DDL 会锁表。

**治理与兜底：**

```sql
-- 看延迟：Seconds_Behind_Master（粗略，大事务/空闲时会失真）
SHOW REPLICA STATUS\G   -- 8.0.22+；老版本 SHOW SLAVE STATUS

-- 更准：对比主从 GTID 位点
SELECT @@global.gtid_executed;
```

- 开启并行复制：`replica_parallel_type=LOGICAL_CLOCK` + `replica_parallel_workers=N`（8.0 用 WRITESET 提高并行度）；
- 大事务拆小批（每批几千行、批间 sleep）；
- **业务侧兜底**：写后立刻要读的请求强制走主库（「写后读窗口」），或前端提交成功后用本地乐观更新，不依赖从库即时可见。

**追问链：**

- **「异步复制、半同步、组复制的区别？」**
  答：异步——主库提交不等从库，主库宕机可能丢最后一段 binlog；半同步（`rpl_semi_sync`）——至少一个从库确认收到 binlog 才返回客户端成功，兼顾性能与安全（注意是「收到」不是「回放完」）；组复制（MGR）——基于 Paxos 的多节点强一致，代价是写延迟与运维复杂度。
- **「主从切换后怎么防数据回退？」**
  答：用 GTID 定位新主（执行过的事务集合最全者），切换后旧主降级为从库时靠 GTID 自动跳过已执行事务；没有 GTID 的时代靠 binlog 文件名+位点对齐，极易出错——这也是「为什么新项目一律开 GTID」的答案。
