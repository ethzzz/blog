> [!NOTE]
> 这是我写给自己（也写给你）的一份路线图。过去两年我以前端工程师的身份，把大模型塞进了公司知识库、翻译工具、摘要卡片这些真实产品里——封装过多 Key 轮询的 QwenClient，也走过阿里云 MaaS 网关的计费账单。这篇总览不教你任何具体技术，只回答三个问题：**这条路线长什么样、适合谁、从哪开始。**

## 知识地图

整条路线 14 篇（含本篇），分四个阶段 + 一个毕业项目：

| 阶段 | 篇目 | 主题 |
| --- | --- | --- |
| 基本功 | 01-05 | API 基础、客户端封装、Prompt、流式、结构化输出 |
| 进阶能力 | 06-08 | RAG、Agent、多模态 |
| 产品化 | 09-10 | 真实场景落地、评估与质量 |
| 工程化 | 11-12 | 网关基建、安全合规 |
| 毕业项目 | 13 | 把前面的零件拼成一个能上线的知识库问答 |

依赖关系很宽松：01-05 是地基，务必顺序学；06-08 相对独立，可以按需挑读；09-13 适合已经动手做过一两个功能之后回头补课——最后的毕业项目就是把这些零件真正串起来。

## 1. 前端工程师在 AI 应用里做什么

先泼一盆冷水：**绝大多数前端工程师做 AI 应用，不需要懂模型训练，也不需要懂数学。** 模型是别人训练好的，你拿到手的只是一个 HTTP 接口（或者一个 SDK）。你的工作，本质上和对接任何第三方服务没有区别——只是这个服务"返回什么"不完全可控。

一个典型 AI 应用前端的职责清单：

- **报文工程**：组装 messages、管理对话历史、裁剪上下文（01、03）
- **客户端健壮性**：多 Key、限流、重试、超时、降级（02）
- **体验工程**：流式打字机渲染、中断、断线续传（04）
- **契约工程**：让模型输出合法 JSON 并校验（05）
- **检索工程**：文档切分、向量召回、重排（06）
- **工具工程**：定义 tool、维护调用循环（07）

看出规律了吗？**全是前端最擅长的活**：异步、流、缓存、校验、状态机。所谓"AI 应用开发"，八成是工程问题，两成才是模型问题。

## 2. 这条路线适合谁

适合你，如果你符合以下任意一条：

- 前端/全栈工程师，公司让你"给产品加个 AI 功能"，但没人告诉你怎么做
- 有个人项目想接入大模型（知识库问答、翻译、写作助手），卡在"知道 API 但做不出产品"
- 已经调通过一次 `chat/completions`，但遇到 429、流式中断、输出不是合法 JSON 时束手无策
- 想搞清楚 RAG、Agent 这些词到底是不是玄学

再具体一点，可以对照这份"自测清单"：你能说清楚 messages 里 system 和 user 的分工吗？你知道一次 1000 字的翻译调用大概花多少钱吗？用户按了停止按钮之后，你的前端和后端分别该做什么？如果这三个问题你一个都答不上来，这条路线正适合你从头走；如果答得上来但说不透，也建议通读一遍——每个阶段的小节里都有我踩坑的细节，那些细节才是从"知道"到"做到"之间的距离。

**不适合**：想训练/微调模型、想转算法岗、想读懂 Transformer 论文的人。这条路线不覆盖那些内容。另外说明一下技术栈立场：示例以 TypeScript/Node 为主（我十年的主业是前端），但所有设计思想——重试策略、缓存设计、评估方法——与语言无关，用 Python 写服务端的读者照样能带走 90% 的内容。

前置要求只有三条：会 TypeScript（大量示例是 ts）、熟悉 fetch 和异步流、用过任意一种包管理器。不需要 Python。

## 3. 学习地图与阶段说明

### 3.1 基本功（01-05）

| 篇 | 内容 | 你将能 |
| --- | --- | --- |
| 01 | chat completions 报文、temperature/top_p、token 与计费、上下文窗口 | 读懂任何一家大模型 API 文档 |
| 02 | 自封装客户端 vs SDK、多 Key 池轮询、429 退避重试、超时降级 | 写出一个生产级 QwenClient |
| 03 | 系统提示词、few-shot、思维链、提示词版本管理 | 把 Prompt 当代码管理 |
| 04 | SSE 协议、fetch 流读取、打字机渲染、中断续传 | 做出 ChatGPT 级别的流式体验 |
| 05 | JSON mode、tool calling、Zod/JSON Schema 校验 | 让模型输出成为可编程契约 |

我的建议是**这五篇必须顺序学、必须动手**。02 和 04 是整条路线含金量最高的两篇——市面上 90% 的 AI 应用事故（重试风暴、流式中断）都出在这里。

### 3.2 进阶能力（06-08）

- **06 RAG**：embedding 原理、分块策略、向量库选型、召回与重排。适合知识库、文档问答场景。
- **07 Agent**：ReAct 模式、工具调用循环、记忆管理。以及很重要的——**什么时候别用 Agent**。
- **08 多模态**：图片理解、语音输入、文生图/文生视频 API 的前端接入。

### 3.3 产品化（09-10）

- **09 产品化**：翻译/摘要/卡片生成等真实场景的做法、成本控制、缓存、灰度开关。这是我自托管知识库里踩坑最多的一篇。
- **10 评估**：评测集建设、自动回归、人工评估、坏例分析。没有评估，你的 Prompt 改一次坏一次。

### 3.4 工程化（11-12）

- **11 网关与基建**：MaaS 平台对比、token-plan 计费、自建网关、用量统计。
- **12 安全合规**：提示词注入、内容审核、隐私脱敏、密钥管理。密钥进过一次 git 历史的人都会很重视这篇。

### 3.5 毕业项目（13）

- **13 知识库问答**：流式输出、结构化引用、RAG 检索、评估回归、成本闸门与注入防护，一条链路串完。默认带 mock LLM，不配 API Key 也能跑通全流程；换真模型只需接一个 `LlmProvider` 实现。

## 4. 我见过的三个误区

在动笔之前，先把三个我在同事和读者身上反复看到的误区摆出来，帮你少走弯路：

**误区一：把"会用 API"当成"会做 AI 应用"。** 调通一次 chat completions 只要十分钟，但让它在生产环境稳定跑一个月是另一回事。我见过有人第一周就上线了聊天功能，第二周就被一次限流事故打回原形——没有重试策略、没有降级、没有监控。这就是为什么这条路线把大量篇幅给了 02（客户端工程化）和 04（流式）这类"不性感"的内容。

**误区二：追新模型、追新框架，地基不打。** 每个月都有新模型发布、新框架刷屏，但底层的东西十年没变过：HTTP 接口、流式传输、结构化校验、缓存与重试。你把这些吃透了，任何新模型新框架到手都是半小时的事；反之，追一年热点还是只会复制官方 demo。

**误区三：从 RAG/Agent 入门。** 这两个词最有话题度，但它们是建立在基本功之上的架构模式。不会处理流式就去做 Agent，调一次工具循环卡半天是常态。我的顺序安排（先 01-05 再 06-08）不是随意的，是踩过坑之后总结出的依赖关系。

## 5. 我的两条学习心法

**第一，把模型当成"不可靠的下游服务"。** 你对接过一个随机超时、偶尔返回错误格式、计费按字符算的第三方 API 吗？AI 应用就是这样，只是更不稳定。所有你在高可用工程里学的东西——重试、降级、熔断、缓存、监控——在这里全部适用，而且价值被放大了。

**第二，成本意识从第一天就要有。** 我见过太多 demo 阶段不看的账单，上线后一个月几千块 token 费。每篇正文里我都会贴上计费相关的坑。

## 6. 怎么用这条路线：三个具体建议

**建议一：全程围绕一个真实项目。** 这条路线的每一篇都有练习，而练习的质量取决于你有没有一个真实的宿主项目。一个自托管的知识库、一个个人博客、一个团队内部工具，都可以。没有真实项目，你写出来的代码永远停留在"能跑通官方 demo"的水平，因为 demo 不需要面对真实数据的脏、真实用户的怪、真实账单的痛。我自己的所有经验，都来自给博客和知识库加功能这个持续两年的项目。

**建议二：每篇读两遍，第一遍只读不敲，第二遍边读边写。** 第一遍建立全局认知——知道这个环节解决什么问题、坑在哪，读完能给别人讲清楚就算过；第二遍把代码逐行敲出来、跑起来、改坏它再修好它。AI 应用的代码有个特点：看起来都对，跑起来全靠细节（流式的粘包、重试的抖动、缓存的版本号），只有亲手改坏过一次，你才真正拥有这段知识。

**建议三：建立自己的 snippet 库。** 这条路线出现的代码——KeyPool、withRetry、streamChat、Typewriter、robustJsonCall、agentLoop、gatewayChat——都是可以直接复用的零件。建议你每完成一篇，就把对应零件放进自己的代码仓库，加上你自己的注释和理解。一年后你会发现，这些零件拼起来就是一套属于你的 AI 应用脚手架，这才是学习路线的最终产出物。

## 7. 路线之外：保持信息源的清醒

最后聊聊怎么跟进行业变化。AI 领域的信息噪音极大，我的原则是**只看一手信息源，不看二手情绪文**：各平台的官方文档和 changelog（模型能力变化最先出现在这里）、你所用框架的 release note、以及少数真正在一线做落地的工程师的长文。至于"AI 将取代 XX"这类内容，一律跳过——能力预测不是工程师的工作，把当下能用的能力用稳才是。

模型在变、平台在变、价格在变，但这条路线的结构不会过时：报文、流式、校验、检索、循环、评估、安全——这些是 AI 应用的骨架。骨架稳了，任何新东西到来时你只需要替换其中一块零件，而不是推倒重来。

## 小结

- 这条路线面向前端工程师，覆盖 API → 封装 → Prompt → 流式 → 结构化 → RAG → Agent → 多模态 → 产品化 → 评估 → 网关 → 安全 → 毕业项目，共 13 阶段。
- 核心认知：AI 应用开发八成是工程问题，前端优势巨大。
- 基本功（01-05）顺序学且动手；其余按需选读。
- 两条心法：把模型当不可靠下游服务；成本意识第一天就有。
- 学完 01-12 后，用第 13 篇的毕业项目做一次完整交付：流式、RAG、评估、成本、安全缺一不可。

## 练习

1. 列出你手头正在做（或想做）的产品，写下 1-3 个可能受益于大模型的功能点。
2. 注册一个 MaaS 平台账号（阿里云百炼或 OpenAI Platform 均可），拿到 API Key，存进环境变量——注意，**不要**写进任何代码文件。
3. 用 curl 或 fetch 调一次最简单的 chat completions，把返回的 JSON 结构完整读一遍，为下一篇做准备。
