## 先定尺子：什么叫"TS 用明白了"

不是会写 `interface`，而是这五件事都做得到：

1. **改后端字段，编译期就报错**：不是等线上 `undefined` 才发现。
2. **看到 `as any` / `!` 能说出理由**：并且知道替代写法（判空、schema 校验、泛型约束）。
3. **读得懂别人的复杂类型**：`z.infer<typeof Schema>`、`Pick<T, K>`、Prisma 的 `select` 返回值——能讲出推断过程。
4. **团队项目的类型检查是"分钟级以内"**：5 万行代码 `tsc --noEmit` 超过 30 秒，就会有人开始绕过它。
5. **发布的库有人能用**：`d.ts` + `exports.types` + 类型测试三件套齐全。

第 1 条区分"会写 TS"和"把 TS 当 JS 注解"；第 4 条区分"个人习惯"和"团队工程"。

## L1：能写（01–05）

**目标：把"类型"当成设计工具，而不是应付编译器的注释。**

- **01 环境**：`tsc` / `tsx` / 打包器三条运行路径各管什么；`strict` 从第一天开（后开成本高 10 倍）。
- **02 基础类型**：`any` / `unknown` / `never` 的分工，`as const` 与 `satisfies` 的差别（这两个能解决 80% 的"类型太宽"问题）。
- **03 对象类型**：`interface` 与 `type` 的真实差异（声明合并 vs 不可变），索引签名与 `Record` 的取舍，以及**为什么新代码别用 `namespace`**。
- **04 函数类型**：重载、`this`、可选参数、回调参数的变型（为什么把函数传进库后会报错）。
- **05 类**：`implements` / `abstract` / `private` 与 `#` 的区别；装饰器只讲"读得懂框架源码"的程度。

> 读法：01→02→03→04 顺序读；05 若无 OOP 背景可先跳过，用到再回。

## L2：能表达契约（06–11）

**这一层才是 TS 的分水岭：从"给变量加类型"变成"用类型描述业务规则"。**

- **06 泛型基础**：约束（`extends`）、默认值、推断时机——写 `useState<T>` 这种签名不再是抄。
- **07 工具类型**：`keyof` / `typeof` / 映射类型 / `Partial` / `Pick` / `Omit`，并且能手写一遍（手写过才真懂）。
- **08 联合与守卫**：**判别联合 + `never` 穷尽检查**是 TS 里性价比最高的模式；断言函数（`asserts x is T`）。
- **09 条件类型与 infer**：`T extends U ? X : Y`、`infer`、分发条件类型；练到能读懂 `ReturnType` 的实现。
- **10 类型兼容性**：结构化类型、协变/逆变/双变、`strictFunctionTypes`——**这是"为什么这里报错"的终极答案**。
- **11 运行时校验**：类型在运行时不存在。API 响应、表单、环境变量、URL 参数四个边界必须用 schema 校验，并从 schema 反推类型（zod / valibot）。

> 读法：06→07→08 必读且连读；09 可以先跳（用到再学）；10、11 是"从会写到写对"的关键，别跳。

---

## L3：能落地（12–16）

**这一层决定你能不能在真实项目里推 TS，而不只是自己写。**

- **12 声明文件**：`.d.ts`、`declare module`、`@types` 生态、`skipLibCheck` 的代价。
- **13 从 JS 迁移**：`allowJs` + `checkJs` 渐进、`// @ts-expect-error` 治理、`any` 预算——**真实工作里最常见的任务**。
- **14 tsconfig 与性能**：`project references`、`incremental`、`skipLibCheck`；为什么类型检查会慢到没人跑。
- **15 类型测试与发布**：`tsd` / `expect-type` 写类型断言测试；`d.ts` 打包与 `exports.types`；API 破坏性变更怎么发现。
- **16 框架集成**：React（`ComponentProps`、泛型组件、事件类型）、Vue（`defineProps` 宏）、Node（`@types/node`、ESM/CJS 双出口）。

> 读法：13 是实战优先项（有存量项目就先看它）；12、15 是库作者必备；14 在你开始嫌 `tsc` 慢时读。

## 不同起点的读法

| 你的现状 | 建议路径 | 投入 |
| --- | --- | --- |
| **JS 熟练，没写过 TS** | 01 → 02 → 03 → 04 → 06 → 08 → 11 → 13 → 17 | 每篇 1.5–2 小时，两周 |
| **会写 TS，但常 `as any`** | 02（`unknown`/`satisfies`）→ 08（判别联合）→ 11（schema）→ 10（变型） | 三小时就能明显改变写法 |
| **要带团队推 TS** | 13 → 14 → 15 → 11 → 12 → 17 | 重点是迁移策略与门禁 |
| **写库 / 发 npm 包** | 06–09 → 12 → 15 → 17 | 类型即 API 文档 |

## 和「前端工程化」模块的分工

这两块内容容易重叠，界线是：

- **本模块（05/14）**：`tsconfig` 与类型检查**对代码本身**的影响（严格度、项目引用、性能）。
- **[工程化 05](/blog/posts/engineering-roadmap-05-babel-typescript/)**：类型检查**在流水线里的位置**（build 里必须有 `tsc --noEmit`、CI 门禁、与打包器别名同步）。

一句话：这里讲"怎么写对类型"，那边讲"怎么让错误进不来"。

## 我踩过最贵的三个坑

- **`strict` 后开**：3 万行项目从 `false` 切 `true`，一次性 800 个错误，最后只能关掉一半规则，等于白做。
- **接口类型当运行时校验**：`as User` 用了两年，后端某次把 `id` 从 number 改字符串，前端 5 个页面崩，全部无声（编译期完全通过）。
- **类型检查慢到没人跑**：`tsc` 要 90 秒，本地 hook 被注释掉，CI 里也没人看——**慢，等于没有**。

## 小结

TS 的价值不在"编译通过"，而在**把约束提前到写代码的时候**。
