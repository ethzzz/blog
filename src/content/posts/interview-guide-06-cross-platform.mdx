## 跨端方案概览

### Q1: 主流跨端方案有哪些？各自原理是什么？⭐⭐ 🔥

**答：**

| 方案 | 技术栈 | 渲染方式 | 性能 |
|:--|:--|:--|:--|
| **React Native** | JS + React | 原生组件（Bridge/JSI） | 接近原生 |
| **Flutter** | Dart | 自绘引擎（Skia） | 最接近原生 |
| **uniapp** | Vue | WebView / 原生（条件编译） | 中等 |
| **Taro** | React/Vue | 小程序 / H5 | 中等 |
| **Ionic** | JS + WebView | WebView | 一般 |
| **Weex** | Vue | 原生组件 | 接近原生（已停维） |

**渲染架构对比：**

```
React Native（新架构）
JS 线程 ←→ JSI (C++) ←→ 原生 UI 组件

Flutter
Dart 代码 → Skia 引擎 → GPU 直接绘制（不依赖原生组件）

uniapp（App 端）
Vue 代码 → WebView / 原生混合渲染
```

**追问链（面试官大概率接着问）：**

- **「Flutter 为什么要自绘，而不是像 RN 一样用原生组件？」**
  答：用原生组件意味着 UI 最终长什么样由系统决定——不同版本、不同厂商的控件外观和行为有差异，两端一致性难保证；而且布局结果要经过原生系统的测量流程，JS/Dart 侧无法完全控制。自绘（Skia/Impeller）把布局、绘制、合成全部拿在自己手里，iOS 和 Android 渲染像素级一致，动画也能稳定 60/120fps。代价是：包体积大（要内置引擎）、无障碍和系统级交互（如 iOS 原生文本选择菜单）需要额外桥接。
- **「自绘的代价具体指什么？」**
  答：三点——包体积（Flutter 空项目就比 RN 大好几 MB，因为要打包 Skia 和 Dart VM）；内存（自建渲染树，多一层与系统视图的映射）；系统能力接入成本（摄像头、推送、支付都要写平台通道 Platform Channel）。
- **「Taro 和 uniapp 都能写小程序，区别是什么？」**
  答：核心差别在**编译时 vs 运行时**的取舍。Taro 早期是编译时方案（把 React 语法编译成小程序 DSL，语法限制多），Taro 3 改成运行时方案（在小程序逻辑层实现一个类 React 的运行时，通过 setData 同步到视图层）。uniapp 以 Vue 语法为中心，编译时优化更激进，官方工具链（HBuilderX）一体化程度高。选型时看团队语法栈：React 系选 Taro，Vue 系选 uniapp。

### Q2: React Native 的通信机制？⭐⭐⭐

**答：**

**旧架构（Bridge）：**
```
JS Thread ←→ Bridge (异步 JSON 序列化) ←→ Native Thread
```
- 缺点：异步通信、序列化开销大、批量更新

**Bridge 三大缺点的展开（能说透就是加分项）：**

| 缺点 | 具体表现 | 典型症状 |
|:--|:--|:--|
| 异步 | JS 调原生拿不到同步返回值 | 需要「先拿设备信息再渲染」的页面首屏慢 |
| 序列化 | 每次通信都走 JSON 序列化/反序列化 | 长列表快速滚动时丢帧（每帧都在传数据） |
| 批量 | 通信按批次合并，无法控制时机 | 交互响应滞后，动画和手势跟手性差 |

**追问链：**

- **「为什么要换成 JSI？JSI 到底是什么？」**
  答：JSI 是一层用 C++ 写的轻量接口，让 JS 引擎（如 Hermes/JSC）**直接持有原生对象的引用**（HostObject）。调用原生方法时不需要序列化成 JSON 跨线程传递，而是同步的 C++ 方法调用。这解决了 Bridge 的三个问题：同步可拿返回值、无序列化开销、时机可控。
- **「新架构下列表滚动为什么更流畅了？」**
  答：Fabric 渲染器支持**同步布局与绘制**，滚动过程中 JS 侧的计算可以直接在当前帧完成，不用等下一批 Bridge 消息；同时 JSI 让图片尺寸测量等高频调用零开销，掉帧的根因被消掉了。
- **「Hermes 是什么，为什么默认启用了？」**
  答：Facebook 自研的 JS 引擎，核心差异是 **AOT 字节码**：打包时把 JS 预编译成字节码，App 启动跳过「解析 JS 源码」这一步，TTI（可交互时间）显著下降，内存占用也更低。代价是包体积略增、调试工具链有适配成本。

**新架构（JSI + TurboModules + Fabric）：**
```
JS Thread ←→ JSI (C++ 直接引用) ←→ Native
```
- JSI：JavaScript Interface，JS 可以直接调用 C++ 方法
- TurboModules：按需加载原生模块，懒加载
- Fabric：新渲染系统，支持同步布局

```javascript
// JSI 使用示例（C++ HostObject）
// JS 侧直接调用原生方法，无需 Bridge 序列化
global.nativeModule.doSomething(arg);
```

## uniapp

### Q3: uniapp 的跨端原理？⭐⭐ 🔥

**答：**

uniapp 使用 **条件编译** + **运行时适配** 实现跨端：

```javascript
// 条件编译
// #ifdef APP-PLUS
// App 端特有代码
uni.scanCode({ success: (res) => {} });
// #endif

// #ifdef H5
// H5 端特有代码
window.scrollTo(0, 0);
// #endif

// #ifdef MP-WEIXIN
// 微信小程序特有代码
wx.login({});
// #endif
```

**各端渲染方式：**

| 平台 | 渲染方式 |
|:--|:--|
| H5 | Vue → DOM |
| 小程序 | Vue → 小程序 DSL → 原生渲染 |
| App (iOS/Android) | WebView + 原生组件混合 |
| App (nvue) | Weex → 原生组件 |

**追问链：**

- **「小程序端为什么要搞逻辑层和视图层分离（双线程）？」**
  答：小程序把 JS 跑在一个独立的逻辑层（JSCore/V8）里，视图层跑在 WebView 里，两层之间靠桥通信。初衷是**安全和管控**：开发者拿不到 DOM/BOM，无法随意操作页面，平台才有审核和控制能力。代价是 `setData` 跨线程通信开销——这正是小程序长列表卡顿的根因，也是 Taro/uniapp 运行时方案要优化的重点（diff 结果最小化传输、批量 setData）。
- **「uniapp 的 nvue 是什么？什么时候用？」**
  答：nvue 是基于 Weex 的原生渲染页面，每个页面是一个独立原生视图，适合长列表、弹幕、直播这类 WebView 渲染会卡的场景。但组件和 CSS 支持受限（默认 flex 布局、不支持部分选择器），所以典型做法是**普通页面用 vue、性能瓶颈页用 nvue 混合**。
- **「条件编译是编译时还是运行时？」**
  答：编译时。`#ifdef` 代码块在构建阶段就被裁剪掉，产物里根本不存在其它端的代码，所以不影响包体积。这也是它和「运行时判断平台」的本质区别。

### Q4: uniapp 的生命周期？⭐⭐

**答：**

```javascript
// uniapp 有两套生命周期

// 1. 应用生命周期（App.vue）
export default {
  onLaunch(options) {},    // 应用初始化（全局只触发一次）
  onShow(options) {},      // 应用进入前台
  onHide() {},             // 应用进入后台
  onError(err) {},         // 应用报错
  onPageNotFound() {},     // 页面不存在
};

// 2. 页面生命周期（页面 .vue）
export default {
  // Vue 生命周期
  beforeCreate() {},
  created() {},
  mounted() {},
  
  // uniapp 页面生命周期
  onLoad(options) {},      // 页面加载（可获取路由参数）
  onShow() {},             // 页面显示
  onReady() {},            // 页面初次渲染完成
  onHide() {},             // 页面隐藏
  onUnload() {},           // 页面卸载
  onPullDownRefresh() {},  // 下拉刷新
  onReachBottom() {},      // 触底加载
  onShareAppMessage() {}, // 分享
};
```

### Q5: uniapp 路由和传参？⭐

```javascript
// 页面跳转
uni.navigateTo({ url: '/pages/detail?id=123' });
uni.redirectTo({ url: '/pages/detail' });   // 关闭当前页
uni.switchTab({ url: '/pages/home' });       // 跳转 tabBar
uni.navigateBack({ delta: 1 });              // 返回
uni.reLaunch({ url: '/pages/login' });       // 重启应用

// 接收参数
export default {
  onLoad(options) {
    console.log(options.id); // '123'
  }
};

// 复杂参数（序列化）
const data = encodeURIComponent(JSON.stringify({ a: 1, b: 2 }));
uni.navigateTo({ url: `/pages/detail?data=${data}` });

// 接收
onLoad(options) {
  const data = JSON.parse(decodeURIComponent(options.data));
}

// EventChannel（页面间通信）
uni.navigateTo({
  url: '/pages/detail',
  success: (res) => {
    res.eventChannel.emit('acceptData', { data: 'from prev page' });
  }
});
```

## Flutter

### Q8: Flutter 的架构和渲染原理？⭐⭐⭐

**答：**

```
Flutter 三层架构：

┌─────────────────────────────────┐
│      Framework (Dart)           │
│  Material/Cupertino/Widgets     │
├─────────────────────────────────┤
│      Engine (C++)               │
│  Skia 绘图 / Dart VM / Text     │
├─────────────────────────────────┤
│      Embedder (平台层)           │
│  iOS / Android / Web / Desktop  │
└─────────────────────────────────┘
```

**渲染流程：**
```
Widget (描述 UI) → Element (管理生命周期) → RenderObject (布局绘制)
```

```dart
// Widget 是不可变的描述
class MyWidget extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return Container(
      padding: EdgeInsets.all(16),
      child: Text('Hello Flutter'),
    );
  }
}

// StatefulWidget 管理状态
class CounterWidget extends StatefulWidget {
  @override
  _CounterState createState() => _CounterState();
}

class _CounterState extends State<CounterWidget> {
  int _count = 0;
  
  void _increment() {
    setState(() => _count++); // 触发重建
  }
  
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        Text('Count: $_count'),
        ElevatedButton(
          onPressed: _increment,
          child: Text('Increment'),
        ),
      ],
    );
  }
}
```

## 跨端方案对比与选型

### Q9: 跨端方案如何选型？⭐⭐ 🔥

**答：**

| 维度 | uniapp | React Native | Flutter |
|:--|:--|:--|:--|
| 学习成本 | 低（Vue） | 中（React） | 高（Dart） |
| 性能 | 中 | 高 | 最高 |
| 生态 | 小程序优 | 丰富 | 快速增长 |
| 包体积 | 小 | 中 | 大（~10MB） |
| 热更新 | 支持 | 支持 | 受限 |
| 原生能力 | 一般 | 强 | 强 |
| 适用场景 | 多端统一（含小程序） | 重交互 App | 高性能 UI |

**选型建议：**
- **需要小程序 + App + H5**：选 uniapp / Taro
- **重交互、接近原生体验**：选 React Native
- **高性能 UI、设计一致性**：选 Flutter
- **团队技术栈是 React**：React Native
- **团队技术栈是 Vue**：uniapp

**60 秒参考话术（选型题这么答才有层次）：**

> 「我先看三个约束：**端的目标组合**、**团队栈**、**性能敏感度**。如果产品要同时覆盖微信小程序和 App，那 RN 和 Flutter 都不在牌桌上（小程序支持是硬伤），基本就是 uniapp/Taro；如果只做双端 App、对体验要求高，React 团队选 RN 新架构，追求渲染一致性和复杂动画选 Flutter；如果团队规模小、招人难度大，语法栈就是第一约束，能力可以靠原生模块补。我们上一个是 XX 场景，选了 XX，原因是 XX，踩的坑是 XX。」——**给出自己的决策案例**是这道题从背书变成加分的关键。

### Q10: 跨端方案的热更新原理？⭐⭐⭐

**答：**

```
React Native 热更新：
1. 打包 JS Bundle（CodePush / 自建服务）
2. App 启动时检查版本
3. 下载新 Bundle 到本地
4. 重启加载新 Bundle

uniapp 热更新：
1. wgt 包（Widget 更新包）
2. 使用 plus.runtime.install 安装
3. 重启应用

Flutter 热更新（受限）：
1. Dart AOT 编译后无法直接热更新
2. 需要通过 Shorebird 等方案
3. 或者通过配置 + 服务端控制
```

```javascript
// RN CodePush 热更新示例
import codePush from 'react-native-code-push';

const codePushOptions = {
  checkFrequency: codePush.CheckFrequency.ON_APP_RESUME,
  installMode: codePush.InstallMode.ON_NEXT_RESTART,
};

function App() {
  useEffect(() => {
    codePush.sync({
      updateDialog: true,
      installMode: codePush.InstallMode.IMMEDIATE,
    });
  }, []);
  
  return <MainApp />;
}

export default codePush(codePushOptions)(App);
```

**追问链：**

- **「热更新有什么合规风险？」**
  答：Apple 审核条款（原 3.3.2）禁止下载执行**改变 App 用途**的代码。所以热更新只能走「资源/脚本解释执行」的灰区，且不能弹用户可见的更新对话框太张扬；RN 的 JS Bundle 更新业界普遍在做，但要控制下发的差异范围。Android 端约束宽松得多。被拒的真实案例通常是把热更新做成了「下载可执行文件」，这是红线。
- **「Flutter 为什么热更新受限？」**
  答：Release 模式下 Dart 是 **AOT 编译成机器码**的，不存在可以替换的解释层。Shorebird 的思路是打补丁级别的差异下发（code push for Dart），但仍受平台政策约束。所以 Flutter 项目通常用「配置驱动 + 服务端开关」来弥补热更新能力。

## 常见坑速查表

| 现象 | 根因 | 解法 |
|:--|:--|:--|
| RN 列表快速滚动掉帧 | 每帧都有 Bridge 通信（旧架构）+ 图片解码在 JS 线程 | FlatList + getItemLayout + FastImage；新架构升级 JSI |
| RN 首页白屏时间长 | JS Bundle 未加载完就渲染 | 启用 Hermes + 按需加载 + 启动图占位 + 安排非关键任务延后 |
| uniapp 小程序 setData 频繁卡顿 | 逻辑层/视图层跨线程通信 | 合并 setData、diff 最小化传输、长列表虚拟化 |
| nvue 页面样式全乱 | nvue 只支持受限 CSS（默认 flex） | 只在性能瓶颈页用 nvue，其余用 vue |
| Flutter 真机上文字显示异常 | 未集成系统字体/引擎内置字体缺字 | 配置字体回退链，中文场景显式声明字体 |
| iOS 审核因热更新被拒 | 下发了可执行代码，触碰 3.3.2 | 只走资源/脚本解释层，控制下发范围 |
| 双端 UI 不一致（RN） | 原生组件随系统版本差异 | 关键组件用一致性组件库或自绘 |
