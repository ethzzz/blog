> [!NOTE]
> 我第一次把项目部署到服务器，花了整个周末：Node 版本不对、MySQL 没装、nginx 配置写完发现端口被占。第二周换了一台机器，同样的坑又踩了一遍。容器解决的从来不是「怎么跑起来」，而是「**凭什么下次还能跑起来**」。这条路线是我把这件事从头到尾做对的过程。

---

## 1. 为什么前端也要学 Docker

三年前端工程师的日常里，Docker 出现的场景比想象中多：

- **环境一致性**：本地 Node 22、服务器 Node 18，`sharp` 编译失败；`npm ci` 在 CI 上能过，在自己机器上过不了。容器把「运行时」也纳入版本管理。
- **自托管**：博客、数据库、对象存储、监控，一个 `compose.yaml` 就能在一台 2 核 4G 的机器上起步，不用为每个服务写一套 systemd。
- **交付边界**：当你要把服务交给别人（同事、客户、下一家公司），镜像比一份 README 可靠得多。

更现实的一点：现在招聘 JD 里写「熟悉 Docker/K8s」的前端岗位越来越多。不是要你去当运维，而是**你要能独立把一个服务送上生产**。

## 2. 这条路线的知识地图

整条路线拆成 **10 个阶段**，分三段：先把容器跑起来（01–03），再把它交付出去（04–06），最后处理生产上的麻烦（07–10）。

| 阶段 | 主题 | 关键技能 | 预计投入 |
| :--: | :-- | :-- | :--: |
| 一 | 第一个容器 | `run` / `ps` / `logs` / `exec`、生命周期、与虚拟机的区别 | 1 天 |
| 二 | Dockerfile 与镜像分层 | 指令、层缓存、多阶段构建、基础镜像选型 | 2 天 |
| 三 | 数据卷与容器网络 | volume / bind mount、自定义网络、健康检查、资源限制 | 2 天 |
| 四 | Compose 编排 | 多服务编排、依赖顺序、profiles、开发态热更新 | 2 天 |
| 五 | 镜像仓库与 CI | tag 策略、push/pull、GitHub Actions 多架构构建、扫描 | 2 天 |
| 六 | 生产部署 | nginx 反代、HTTPS、日志、备份、回滚、零停机 | 3 天 |
| 七 | 排障 | 日志/状态/网络/磁盘的排查顺序、退出码语义 | 2 天 |
| 八 | 安全与瘦身 | 非 root、只读文件系统、secrets、镜像扫描 | 2 天 |
| 九 | 上 K8s 的边界 | 判据、概念映射、最小清单、探针、滚动发布 | 2 天 |
| 十 | NoteLab 实战 | 三仓 + 中间件的完整编排、从 pm2 迁移与回滚 | 3 天 |

按每天 2 小时算，完整走一遍大约 **三周**；只求能部署自己的项目，走完 01–06 就够（约一周）。

## 4. 先建立四个心智模型

概念不清时，命令背得再熟也会在出问题时抓瞎。这四个对照表建议先看一遍，遇到困惑再回来查。

### 4.1 容器不是「小虚拟机」

| 维度 | 虚拟机 | 容器 |
| :-- | :-- | :-- |
| 隔离的是 | 整台硬件（Hypervisor 虚拟化） | 进程（namespace + cgroup） |
| 内核 | 各自一套完整内核 | **共享宿主机内核** |
| 启动时间 | 几十秒到几分钟 | 毫秒到几百毫秒 |
| 镜像体积 | GB 级 | 几十 MB 到几百 MB |
| 隔离强度 | 强（硬件级） | 较弱（内核级，配置不当可逃逸） |

一句话：**容器是一个被限制了视野和资源的普通进程**。所以容器里 `uname -a` 看到的是宿主机内核；所以 Windows 上跑 Linux 容器需要 WSL2 或一台 Linux 虚拟机兜底。

### 4.2 镜像、容器、仓库

| 概念 | 类比 | 关系 |
| :-- | :-- | :-- |
| 镜像 image | 类 / 安装光盘 | 只读模板，由 Dockerfile 构建或从仓库拉取 |
| 容器 container | 实例 / 装好的系统 | 镜像 + 一层可写层，可启动、停止、删除 |
| 仓库 registry | npm registry | 存镜像，`docker push/pull` 与它打交道 |

容器删掉，可写层就没了——这是新手最常见的「数据怎么丢了」：**写进容器里的文件不会跟着镜像走，也不会自己留下来**。数据必须落到卷（阶段三）。

### 4.3 Dockerfile 与 Compose 不是一回事

- **Dockerfile** 描述「一个镜像怎么构建出来」：基础镜像、拷贝什么、装什么依赖、启动命令。
- **Compose** 描述「一组容器怎么一起跑」：几个服务、各自用哪个镜像、端口怎么映射、卷怎么挂、谁先启动。

前者是**构建期**，后者是**运行期编排**。很多人一开始就把两者混在一起，结果一个 Dockerfile 里塞 `docker run` 的参数，怎么都不生效。

### 4.4 Compose 与 Kubernetes 是同一层的东西

两者都在解决「多容器怎么编排」，只是规模不同：

| 维度 | Docker Compose | Kubernetes |
| :-- | :-- | :-- |
| 适用范围 | 单机、几个到十几个服务 | 多机集群、几十到几千个 Pod |
| 声明文件 | `compose.yaml` | 一组 YAML（Deployment/Service/...） |
| 自愈 | `restart` 策略 | 控制器持续调谐 |
| 学习成本 | 半天 | 几周起 |

**单机能跑就用 Compose**，别为了简历上写 K8s 把一台 2 核机器搞成事故现场。阶段九会给出更具体的判据。

## 5. 这条路线适合谁

**适合**：

- 写过 Node/Java 服务，能读懂 nginx 配置，但没系统用过容器
- 有自己的小项目要部署（博客、API、工具箱），受够了「换台机器就重装环境」
- 想把 CI/CD 走通，让 push 之后自动构建、自动上线

**不适合**：

- 想学容器编排平台运维（K8s 集群、CNI、Operator）——这条路线只到「知道什么时候该上、最小清单怎么写」
- 想学云厂商全家桶（ECS、SLB、ACK 的产品细节）——各平台差异太大，路线只讲通用部分

## 6. 几个常见的误区

**误区一：把容器当虚拟机用。** 在容器里装 systemd、装 sshd、跑多个进程——这不是不行，是方向错了。容器的最佳实践是**一个容器一个进程**，多进程交给编排层。

**误区二：镜像越小越好，不管可维护性。** 从 1.2GB 瘦到 180MB 很有成就感，但把 Node 换成 scratch、自己编静态二进制，最后连 `sh` 都没有，出问题只能靠猜。**先能排障，再谈极致瘦身**（阶段八）。

**误区三：数据放在容器里。** `docker compose down` 之后数据消失，然后开始怀疑人生。规则很简单：**容器无状态，状态进卷或外部服务**。

**误区四：本地能跑就等于线上能跑。** 本地 `docker run` 成功，线上仍然可能因为架构（arm64/amd64）、时区、文件权限、DNS 解析失败。阶段六和阶段七就是处理这些「本地看不见」的问题。

## 7. 怎么用这条路线

**建议一：全程围绕一个真实项目。** 拿你自己正在维护的服务（博客、API、工具箱都行），从写第一个 Dockerfile 开始，一路做到 compose 上线。没有真实项目，练习会退化成抄命令。

**建议二：每章的练习都做，并且留下产物。** 阶段二留下 Dockerfile，阶段四留下 `compose.yaml`，阶段六留下部署脚本。走完之后你得到的不是笔记，是一套能复用的部署模板。

**建议三：先手动，再自动化。** 先用 `docker run` 把服务跑起来，再用 compose 收敛，最后才接 CI。顺序反了，出问题时你不知道是哪一层坏的。

## 小结

- 容器是**被 namespace + cgroup 限制的进程**，共享宿主机内核，不是小虚拟机。
- 镜像只读、容器可写、仓库存镜像；容器删了，可写层和数据一起没。
- Dockerfile 管构建，Compose 管编排，K8s 是更大规模的编排——三者不在一个维度上。
- 这条路线 10 个阶段，01–06 能覆盖「把项目部署上线」，07–10 处理生产上的排障、安全与规模问题。
- 单机优先 Compose；上 K8s 要有明确判据，不要为了技术而技术。

## 练习

1. 用自己的话写下「镜像 / 容器 / 仓库」三者的关系，然后跑一个 `hello-world` 验证你的理解。
2. 列出你现在维护的一个项目在部署时依赖的所有环境（运行时版本、数据库、环境变量），标出哪些适合放进容器、哪些必须外置。
3. 打开一个你常用的开源项目的仓库，找到它的 `Dockerfile` 和 `compose.yaml`，试着说出每个服务的作用。
4. 给自己的项目估一个「容器化改造」的工作量：需要写几个 Dockerfile、几个服务、哪些数据要进卷。
