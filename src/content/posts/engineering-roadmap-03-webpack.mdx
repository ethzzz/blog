## 什么时候还该用 Webpack

新项目我会选 Vite。但 Webpack 仍然值得学，原因很实在：

- **存量项目**：大量企业项目、组件库、微前端基座还是 Webpack 5；
- **控制力**：复杂 loader 链、精细的 chunk 编排、老浏览器兼容，Webpack 更成熟；
- **面试与排障**：构建慢、内存爆、产物错，懂原理才能改配置而不是乱试。

这篇给你一份**能直接跑生产的配置**，而不是概念罗列。

## 四个核心概念，一句话各自说清

| 概念 | 作用 | 类比 |
| --- | --- | --- |
| `entry` | 依赖图的起点 | 从哪进这座城 |
| `output` | 产物落盘规则 | 出城后东西放哪、叫什么名 |
| `loader` | **把非 JS 文件变成模块**（一对一转换） | 城门安检：ts→js、css→js |
| `plugin` | **在生命周期钩子上做全局操作**（一对多/全局） | 城市管理局：抽 CSS、生成 HTML、压缩 |

记住这条边界：**能"转单个文件"用 loader，需要"知道全局/等所有产物"用 plugin**。

### loader 为什么从右往左执行

```js
{ test: /\.scss$/, use: ['style-loader', 'css-loader', 'sass-loader'] }
```

执行顺序：`sass-loader` → `css-loader` → `style-loader`。

原因：数据流是**管道**，源文件先要变成 CSS 字符串（sass），再变成 JS 模块（css-loader 处理 `@import`/`url()`），最后注入 DOM（style-loader）。写反了就会拿到"还没编译的 scss 文本"，报语法错。

> 口诀：**配置数组从右往左跑，等于处理流程从左往右流。**

## 一份能上生产的配置

```js
// webpack.config.js —— Webpack 5
const path = require('node:path');
const HtmlWebpackPlugin = require('html-webpack-plugin');
const MiniCssExtractPlugin = require('mini-css-extract-plugin');
const CssMinimizerPlugin = require('css-minimizer-webpack-plugin');

const isProd = process.env.NODE_ENV === 'production';

module.exports = {
  mode: isProd ? 'production' : 'development',
  entry: './src/main.tsx',
  devtool: isProd ? 'hidden-source-map' : 'eval-cheap-module-source-map',

  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: isProd ? 'js/[name].[contenthash:8].js' : 'js/[name].js',
    chunkFilename: isProd ? 'js/[name].[contenthash:8].chunk.js' : 'js/[name].chunk.js',
    // 每次构建前清空 dist（避免旧产物残留）
    clean: true,
    publicPath: '/',
  },

  resolve: {
    extensions: ['.tsx', '.ts', '.jsx', '.js'],
    alias: { '@': path.resolve(__dirname, 'src') },
  },

  module: {
    rules: [
      {
        test: /\.[jt]sx?$/,
        exclude: /node_modules/,
        use: {
          loader: 'esbuild-loader', // 比 babel-loader 快一个量级；需要老浏览器再换 babel
          options: { target: 'es2020', loader: 'tsx' },
        },
      },
      {
        test: /\.css$/,
        use: [isProd ? MiniCssExtractPlugin.loader : 'style-loader', 'css-loader', 'postcss-loader'],
      },
      {
        test: /\.(png|jpe?g|svg|webp)$/,
        type: 'asset',                 // < 8KB 自动转 base64，> 8KB 落文件
        parser: { dataUrlCondition: { maxSize: 8 * 1024 } },
        generator: { filename: 'img/[name].[contenthash:8][ext]' },
      },
    ],
  },

  plugins: [
    new HtmlWebpackPlugin({ template: './public/index.html' }),
    isProd && new MiniCssExtractPlugin({ filename: 'css/[name].[contenthash:8].css' }),
  ].filter(Boolean),

  optimization: {
    minimize: isProd,
    minimizer: ['...', new CssMinimizerPlugin()],
    // 持久化缓存：二次构建能快 5-10 倍（Webpack 5 最重要的性能开关）
    moduleIds: 'deterministic',
    chunkIds: 'deterministic',
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        react: {
          test: /[\\/]node_modules[\\/](react|react-dom|scheduler)[\\/]/,
          name: 'react',
          priority: 30,
        },
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendor',
          priority: 10,
          minSize: 30_000,
        },
      },
    },
    runtimeChunk: 'single', // 把 runtime 单独抽出来，业务 chunk 的 hash 更稳
  },

  // 关键：文件系统缓存（默认在 node_modules/.cache/webpack）
  cache: { type: 'filesystem' },

  stats: 'errors-warnings',
};
```

配套 `package.json`：

```json
{
  "scripts": {
    "dev": "webpack serve --hot",
    "build": "cross-env NODE_ENV=production webpack",
    "analyze": "cross-env NODE_ENV=production webpack --profile --json > stats.json && source-map-explorer 'dist/js/*.js'"
  }
}
```

三个容易被忽略、但直接决定线上表现的点：

1. **`contenthash`**：内容变才改名 → 用户缓存命中率高。用 `[hash]` 会让所有文件一起失效。
2. **`runtimeChunk: 'single'`**：runtime（模块映射表）单独出文件，否则每次构建都会污染业务 chunk 的 hash。
3. **`cache.type = filesystem`**：不加这个，中型项目热构建要 30–60 秒；加了通常 3–8 秒。

## HMR 为什么有时候不生效

```js
// webpack.config.js
devServer: {
  hot: true,
  port: 8080,
  historyApiFallback: true,      // SPA 路由刷新 404 的解药
  client: { overlay: { errors: true, warnings: false } },
  proxy: { '/api': { target: 'http://localhost:8001', changeOrigin: true } },
}
```

HMR 不生效的常见原因，按出现频率排：

1. 组件没被 `module.hot.accept` 关联（React 需 `react-refresh` + `@pmmmwh/react-refresh-webpack-plugin`）；
2. `devtool` 用了 `eval` 系列，但代码在 `node_modules` 里被排除在热更新之外；
3. 直接把整个 `store` 或工具函数模块导出成常量，热更新后引用还是旧的；
4. `style-loader` 换成了 `MiniCssExtractPlugin.loader`（生产模式），CSS 改动会触发整页刷新。

## 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 构建内存爆（`JavaScript heap out of memory`） | 一次性处理太多模块 / sourcemap 过大 | `NODE_OPTIONS=--max-old-space-size=4096`；生产用 `hidden-source-map` |
| 二次构建还是慢 | 没开 `cache.type: filesystem` | 开缓存，并保证 `cache.buildDependencies` 指向配置文件 |
| CSS 里 `url()` 图片 404 | `publicPath` 与实际部署路径不符 | 对齐 `output.publicPath` 与 nginx 子路径 |
| 循环依赖导致某模块为 `undefined` | CJS 循环引用 + 立即取值 | 改成函数内延迟取用；或用 ESM 活绑定 |
| 打包产物里有 2 份 React | 某依赖把 react 放进了 `dependencies` | `resolve.alias` 指向单份 + 提 issue |
| 改了 `tsconfig` 的 paths 但构建报找不到 | Webpack 不读 tsconfig 的 paths | 在 `resolve.alias` 里同步一份（或用 `tsconfig-paths-webpack-plugin`） |

## Webpack vs Vite：怎么选

| 维度 | Webpack 5 | Vite |
| --- | --- | --- |
| 开发启动 | 全量打包，项目越大越慢（几秒到几十秒） | 按需编译，通常 < 1s |
| 生产构建 | 成熟、可精细控制 | Rollup，配置更少，产物通常更小 |
| 生态 | 极全（各类 loader/plugin） | 插件接口新，个别老 loader 无替代 |
| 老浏览器（IE11） | 支持（配 babel + polyfill） | 不再支持 |
| 适合 | 存量项目、复杂定制、需要极致控制 | 新项目、现代浏览器、开发体验优先 |

## 练习

1. **从零手配**：不用 CRA/Vue CLI，用 Webpack 5 配一个 TS + CSS + 图片 + 代码分割的项目，产出一个 `dist` 能直接 `npx serve` 打开。
   *自检*：产物里 JS/CSS/图片分目录且有 hash；改一行代码后只有对应业务 chunk 变名。
2. **量化缓存收益**：删掉/打开 `cache: { type: 'filesystem' }`，各跑两次 `build`，记录耗时。
   *自检*：能说清"冷启动 vs 热构建"差在哪（模块解析结果与转译结果被复用）。
3. **制造 loader 顺序错误**：把 `['style-loader','css-loader','sass-loader']` 改成 `['sass-loader','css-loader','style-loader']`，看报错信息。
   *自检*：能解释报错来自"把 scss 语法当成 JS 解析"。
