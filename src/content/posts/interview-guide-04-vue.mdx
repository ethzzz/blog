export default {

</script>

## 响应式原理

### Q3: Vue2 响应式原理？⭐⭐⭐ 🔥

**答：**

Vue2 使用 `Object.defineProperty` 实现数据劫持。

```javascript
// 简化实现
function defineReactive(obj, key, val) {
  const dep = new Dep(); // 依赖管理器
  
  Object.defineProperty(obj, key, {
    enumerable: true,
    configurable: true,
    get() {
      if (Dep.target) {
        dep.addSub(Dep.target); // 依赖收集
      }
      return val;
    },
    set(newVal) {
      if (newVal === val) return;
      val = newVal;
      dep.notify(); // 派发更新
    }
  });
}

function observe(obj) {
  if (typeof obj !== 'object') return;
  
  Object.keys(obj).forEach(key => {
    defineReactive(obj, key, obj[key]);
    observe(obj[key]); // 递归监听
  });
}
```

**流程图：**
```
初始化 -> observe(data) -> defineReactive
                                |
    渲染 -> Watcher -> 读取数据 -> get 触发 -> 依赖收集
                                |
    修改数据 -> set 触发 -> dep.notify() -> Watcher.update() -> 重新渲染
```

**Vue2 响应式的缺陷：**

```javascript
const obj = { a: 1 };
observe(obj);

// 1. 无法检测对象属性的添加/删除
obj.b = 2;           // 不是响应式
delete obj.a;        // 不是响应式

// 解决：Vue.set / Vue.delete
Vue.set(obj, 'b', 2);
Vue.delete(obj, 'a');

// 2. 无法检测数组索引修改和长度变化
arr[0] = 'new';      // 不是响应式
arr.length = 0;      // 不是响应式

// 解决：变异方法
arr.splice(0, 1, 'new');
```

### Q4: Vue3 响应式原理？⭐⭐⭐ 🔥

**答：**

Vue3 使用 `Proxy` 替代 `Object.defineProperty`。

```javascript
// 简化实现
function reactive(target) {
  return new Proxy(target, {
    get(target, key, receiver) {
      const result = Reflect.get(target, key, receiver);
      track(target, key); // 依赖收集
      
      // 惰性代理嵌套对象
      if (typeof result === 'object' && result !== null) {
        return reactive(result);
      }
      return result;
    },
    set(target, key, value, receiver) {
      const oldValue = target[key];
      const result = Reflect.set(target, key, value, receiver);
      
      if (oldValue !== value) {
        trigger(target, key); // 触发更新
      }
      return result;
    },
    deleteProperty(target, key) {
      const result = Reflect.deleteProperty(target, key);
      trigger(target, key);
      return result;
    }
  });
}

// ref 实现（基本类型）
function ref(value) {
  const wrapper = {
    get value() {
      track(wrapper, 'value');
      return value;
    },
    set value(newVal) {
      if (newVal !== value) {
        value = newVal;
        trigger(wrapper, 'value');
      }
    }
  };
  
  Object.defineProperty(wrapper, '__v_isRef', { value: true });
  return wrapper;
}
```

**Vue3 响应式优势：**

| 特性 | Vue2 | Vue3 |
|:--|:--|:--|
| 对象新增/删除属性 | 不支持 | 支持 |
| 数组索引修改 | 不支持 | 支持 |
| 嵌套对象 | 初始化递归 | 惰性代理 |
| Map/Set | 不支持 | 支持 |
| 性能 | 初始化开销大 | 运行时开销小 |

**追问链（Vue3 响应式的三层结构必须能说清）：**

- **「依赖存在哪里？为什么用 WeakMap？」⭐⭐⭐**
  答：三级结构 `WeakMap<target, Map<key, Set<effect>>>`：

  ```text
  WeakMap
   └─ target(Object) → Map
        └─ key('count') → Set
             └─ effect(fn1, fn2, ...)   ← 依赖这个属性的所有副作用
  ```

  用 WeakMap 做最外层：组件卸载后 target 不再被引用时，整棵依赖树可以被 GC 回收；用 Map 会永久持有 target，等于泄漏。这正是「为什么不用普通对象存依赖」的答案。
- **「为什么 `trigger` 之后是异步更新？更新队列在哪？」**
  答：`trigger` 并不直接执行 effect，而是把 effect 推进一个**微任务队列**（`Promise.then` 派发），同一轮里多个数据变化会被去重并合并成一次组件更新。这和 React 的批处理是同一个目的：避免一次交互触发 N 次渲染。所以「改完数据后立刻读 DOM 拿到旧值」是正常现象，需要 DOM 就 `await nextTick()`。
- **「`computed` 和 `watch` 的区别，从依赖角度说？」**
  答：`computed` 是**惰性 + 缓存**的 effect：只有被读取时才求值，并把自身标记为「干净」；依赖变化只把标记置脏（dirty），下次读取才重算。`watch` 是**立即订阅**的 effect：依赖变化就把回调推进队列执行。所以「模板里用 computed 算三遍」不会算三次，而 watch 不读也在跑。

> ⚠️ 注意上面 `reactive()` 示例里的 `return reactive(result)` 是**教学简化**，真实实现用 `reactiveMap`/`readonlyMap` 缓存代理对象，保证同一个原始对象多次被访问时返回**同一个 proxy**。否则每次 `get` 都新建 proxy，会导致 `state.obj === state.obj` 为 false、`watch` 反复触发。

### Q5: ref 和 reactive 的区别？⭐⭐ 🔥

**答：**

| 特性 | `ref` | `reactive` |
|:--|:--|:--|
| 类型 | 任意类型 | 对象/数组 |
| 访问方式 | `.value` | 直接访问 |
| 实现原理 | getter/setter 包装 | Proxy 代理 |
| 模板中使用 | 自动解包 | 直接使用 |

```javascript
import { ref, reactive } from 'vue';

// ref
const count = ref(0);
count.value++; // 需要 .value
console.log(count.value); // 0

// reactive
const state = reactive({ count: 0 });
state.count++; // 直接访问
console.log(state.count); // 1

// 模板中使用（ref 自动解包）
// <div>{{ count }}</div>  不需要 .value

// reactive 的陷阱
const state = reactive({ list: [] });
state.list = [1, 2, 3];     // ✅ 可以
const { list } = state;      // ❌ 解构后失去响应式

// 解决：toRefs
import { toRefs } from 'vue';
const { list } = toRefs(state); // ✅ 保持响应式
```

**追问链（这几问决定你是「用过」还是「踩过」）：**

- **「`reactive` 对象整体被替换会怎样？」⭐⭐⭐**
  答：会丢响应式。`state = reactive({...})` 拿到的是 proxy，组件里持有的是这个 proxy 的引用；如果后续 `state = { ... }` 重新赋值，模板仍指向旧 proxy，视图不更新。所以约定是「**永远不整体替换 reactive 对象，只改它的属性**」；需要整体替换就用 `ref` 包一层（`state.value = {...}`，ref 的 `.value` 是可替换的）。
- **「什么时候必须用 `shallowRef` / `markRaw`？」**
  答：两类场景：① **大对象且只在整体替换时更新**（如一次性加载的图表数据、地图实例），用 `shallowRef` 避免深度代理的开销，只监听 `.value` 的替换；② **不需要也不允许被代理的对象**（第三方类实例、ECharts/Three 实例、复杂二进制结构），用 `markRaw` 打标记让 Vue 跳过代理——否则 proxy 会破坏这些库的内部判断（`instanceof`、私有字段），出现「图表渲染空白」「实例方法找不到」这类玄学 bug。
- **「`ref` 放进 `reactive` 里还要 `.value` 吗？」**
  答：不用。`reactive` 在 get 时会对「值为 ref 的属性」自动解包，所以 `state.count` 直接可用。但**数组/Map 里的 ref 不会自动解包**，`arr[0]` 仍是 ref 对象——这是最容易让人困惑的不一致，官方文档也明确标注了。

### Q5b: watch 和 watchEffect 的区别？flush 的三个时机怎么选？⭐⭐ 🔥

**答：**

| 维度 | `watch` | `watchEffect` |
|:--|:--|:--|
| 依赖来源 | **显式指定**源（ref/getter/数组） | **自动收集**回调里读到的所有响应式依赖 |
| 首次执行 | 默认不执行（`immediate: true` 才执行） | 立即执行一次（为了收集依赖） |
| 拿旧值 | 回调有 `(newVal, oldVal)` | 拿不到旧值 |
| 适用 | 精确监听某几个值、需要新旧对比 | 副作用依赖多且懒得逐个列 |

```javascript
// watch：精确监听 + 旧值
watch(() => state.count, (n, o) => console.log(o, '->', n));
watch([a, b], ([na, nb], [oa, ob]) => {});   // 多源

// watchEffect：自动追踪，立即跑一次
watchEffect(() => {
  console.log(state.count, state.name);  // 读了谁就追踪谁
});
```

**flush 三个时机（决定回调在渲染前还是后跑）：**

| flush | 执行时机 | 典型用途 |
|:--|:--|:--|
| `'pre'`（默认） | 组件更新**前** | 大多数场景；此时读 DOM 是旧的 |
| `'post'` | 组件更新**后**（DOM 已就绪） | 回调里要操作更新后的 DOM、测量尺寸 |
| `'sync'` | 数据一变**同步**执行 | 极少数必须同步的场景；**慎用**，失去批处理、易死循环 |

```javascript
// 回调里要读更新后的 DOM → 必须 post（等价于 nextTick 后再跑）
watch(source, () => {
  console.log(el.offsetHeight);   // 拿到新布局
}, { flush: 'post' });
```

**追问链：**

- **「watch 监听 reactive 对象，为什么默认拿不到深层变化？」**
  答：直接 `watch(obj, cb)` 时 Vue 会**自动开 deep**（监听整个代理），但 `watch(() => obj.a, cb)` 这种 getter 只追踪 `a`，`a` 内部嵌套变化不触发——要 `{ deep: true }` 或改成监听 `() => obj.a.b`。**「getter 返回对象才需要手动 deep」**是易混点。
- **「watchEffect 里条件分支读了依赖，会怎样？」**
  答：依赖收集是「运行时读到才算」。`if (flag) read(a) else read(b)` 只会追踪当前分支读到的那个，flag 切换后重新收集——所以它天然「按需追踪」，但也意味着**没读到的依赖变化不会触发**，别指望它监听所有字段。
- **「watch 的清理函数（onCleanup）解决什么？」**
  答：竞态。异步回调回来时源可能已变，用 `onCleanup` 注册取消逻辑（abort 上一次请求/置失效标志），Vue 会在下次回调前或停止监听时调用它——等价于 React useEffect 的 return 清理。

## 虚拟 DOM 与 Diff

### Q6: 什么是虚拟 DOM？⭐⭐ 🔥

**答：**

虚拟 DOM 是用 JavaScript 对象描述真实 DOM 的结构。

```javascript
// 真实 DOM
<div id="app" class="container">
  <h1>Hello</h1>
  <p>World</p>
</div>

// 虚拟 DOM
const vnode = {
  tag: 'div',
  props: { id: 'app', class: 'container' },
  children: [
    { tag: 'h1', props: null, children: 'Hello' },
    { tag: 'p', props: null, children: 'World' }
  ]
};
```

**虚拟 DOM 的优势：**
1. **性能优化**：批量操作，减少真实 DOM 操作
2. **跨平台**：可渲染到 DOM、Canvas、Native
3. **声明式编程**：状态驱动视图

**虚拟 DOM 不一定比直接操作 DOM 快**，但提供了更好的开发体验和可维护性。

### Q7: Vue 的 Diff 算法？⭐⭐⭐ 🔥

**答：**

Vue 采用**双端对比**策略（Vue2）和**最长递增子序列**（Vue3）。

**Vue2 双端 Diff：**

```
旧头 <---> 新头
旧尾 <---> 新尾
旧头 <---> 新尾
旧尾 <---> 新头
```

```javascript
// 简化流程
function patch(oldVnode, newVnode) {
  // 1. 同层比较，不同层直接替换
  if (oldVnode.tag !== newVnode.tag) {
    replaceNode(oldVnode, newVnode);
    return;
  }
  
  // 2. 文本节点直接更新
  if (!newVnode.tag) {
    if (oldVnode.text !== newVnode.text) {
      oldVnode.elm.textContent = newVnode.text;
    }
    return;
  }
  
  // 3. 子节点 Diff
  diffChildren(oldVnode.children, newVnode.children);
}

function diffChildren(oldCh, newCh) {
  let oldStartIdx = 0, oldEndIdx = oldCh.length - 1;
  let newStartIdx = 0, newEndIdx = newCh.length - 1;
  
  while (oldStartIdx <= oldEndIdx && newStartIdx <= newEndIdx) {
    // 四种比较方式
    if (sameVnode(oldCh[oldStartIdx], newCh[newStartIdx])) {
      patch(oldCh[oldStartIdx++], newCh[newStartIdx++]);
    } else if (sameVnode(oldCh[oldEndIdx], newCh[newEndIdx])) {
      patch(oldCh[oldEndIdx--], newCh[newEndIdx--]);
    } else if (sameVnode(oldCh[oldStartIdx], newCh[newEndIdx])) {
      patch(oldCh[oldStartIdx++], newCh[newEndIdx--]);
    } else if (sameVnode(oldCh[oldEndIdx], newCh[newStartIdx])) {
      patch(oldCh[oldEndIdx--], newCh[newStartIdx++]);
    } else {
      // 使用 key 查找
      const idxInOld = findIdxInOld(oldCh, newCh[newStartIdx]);
      if (idxInOld === -1) {
        // 新节点，插入
        insertBefore(oldCh[oldStartIdx].elm, newCh[newStartIdx]);
      } else {
        // 移动节点
        moveNode(oldCh[idxInOld], newCh[newStartIdx]);
      }
      newStartIdx++;
    }
  }
}
```

**key 的作用：**

```html
<!-- ❌ 不使用 key，可能导致就地复用 -->
<li v-for="item in list">{{ item.name }}</li>

<!-- ✅ 使用唯一 key，提高 Diff 效率 -->
<li v-for="item in list" :key="item.id">{{ item.name }}</li>

<!-- ❌ 使用 index 作为 key（列表会变化时） -->
<li v-for="(item, index) in list" :key="index">{{ item.name }}</li>
```

### Q7b: Vue3 的 Diff 到底怎么走？为什么要用最长递增子序列？⭐⭐⭐ 🔥

**答：** Vue3 把「子节点更新」拆成**五步**，前四步都是廉价的特判，只有真正乱序时才进入 O(n) 的 map 查找 + LIS。

```
① 同步前置：i 从 0 开始，新旧头节点逐个 patch，遇到不同就停
② 同步后置：e1/e2 从尾部往前，逐个 patch，遇到不同就停
③ 旧节点已遍历完（i > e1）→ 剩下的新节点全是新增，挂载
④ 新节点已遍历完（i > e2）→ 剩下的旧节点全是删除，卸载
⑤ 乱序（最复杂）：中间段建 key→index 映射，再求 LIS 决定谁「不用动」
```

**第 ⑤ 步的关键：为什么要 LIS？**

```text
旧中间段 key：[a, b, c, d, e]
新中间段 key：[a, e, b, c, d]      ← a 不动，b~e 整体后移

做法：按新顺序遍历，为每个新节点找到它在旧序列里的位置索引 → [0, 4, 1, 2, 3]
LIS([0,4,1,2,3]) = [0,1,2,3]（对应 a,b,c,d）

含义：a/b/c/d 保持相对顺序不变 → 只有 e 需要真正移动 DOM。
     其余节点只需 patch 内容，不需要 insertBefore。
```

```javascript
// Vue3 源码中的乱序处理（runtime-core/src/renderer.ts 简化）
const newIndexToOldIndexMap = new Array(toBePatched)

// 1. 建立 新索引 → 旧索引 的映射，顺带把「旧节点被复用」标记出来
for (let i = toBePatched - 1; i >= 0; i--) {
  const nextIndex = s2 + i
  const nextChild = c2[nextIndex]
  const anchor = nextIndex + 1 < l2 ? c2[nextIndex + 1].el : parentAnchor
  const key = nextChild.key
  const oldIndex = keyToNewIndexMap.get(key)

  if (oldIndex === undefined) {
    patch(null, nextChild, container, anchor)   // 新增
  } else {
    newIndexToOldIndexMap[i] = oldIndex + 1      // 记录，供 LIS 使用
    patch(c1[oldIndex], nextChild, ...)
  }
}

// 2. 求 LIS，得到「不需要移动」的索引集合
const increasingNewIndexSequence = getSequence(newIndexToOldIndexMap)

// 3. 从后往前遍历，只移动不在 LIS 里的节点
let j = increasingNewIndexSequence.length - 1
for (let i = toBePatched - 1; i >= 0; i--) {
  if (i !== increasingNewIndexSequence[j]) {
    insert(nextChild.el, container, anchor)      // 移动
  } else {
    j--                                           // 在 LIS 里，跳过
  }
}
```

**追问链：**

- **「不用 LIS，直接按新顺序全部移动行不行？」**
  答：功能正确，但 DOM 操作次数从「最少必要」变成「几乎全量」。DOM 的 `insertBefore` 会触发样式重算与布局，成本远高于 JS 计算（LIS 是 O(n log n)，几千个节点也就毫秒级）。所以 **LIS 是用一点 CPU 换掉大量 DOM 操作**。
- **「为什么 Vue2 的双端对比没有用到 LIS？」**
  答：双端对比是「四种首尾组合特判 + 中间乱序时逐个查找移动」，最优场景（头尾增删、单点移动）表现极好，但中间乱序的比例一高就退化成 O(n²) 级别的查找与移动。Vue3 的 map + LIS 在乱序场景是稳定 O(n log n)，**这是「大列表重排」场景 Vue3 明显更快的核心原因**。
- **「那 key 到底影响哪一步？」**
  答：只影响第 ⑤ 步的 map 查找与 LIS 结果。没有 key 时只能按索引对齐（就地复用），一旦顺序变了就是「内容全错位 + 全部重渲染」；用 index 做 key 等价于没有 key（因为索引永远连续），列表插入/删除时同样会错位。

### Q7c: Vue3 编译器做了哪些优化？PatchFlags / 静态提升 / Block Tree 是什么？⭐⭐⭐ 🔥

**答：** Vue3 快的核心不只是 Proxy 和 LIS，更是「**编译时就知道哪里会变，运行时只 diff 会变的部分**」——这叫**靶向更新（targeted update）**。三大手段：

**① 静态提升（Static Hoisting）**

```javascript
// 模板里的静态节点，编译后提到 render 函数外，只创建一次
const _hoisted_1 = /*#__PURE__*/_createElementVNode("p", null, "静态文字", -1 /* HOISTED */)

function render() {
  // 每次渲染复用 _hoisted_1，不再重新创建 vnode
  return (_openBlock(), _createElementBlock("div", null, [
    _hoisted_1,
    _createElementVNode("p", null, _toDisplayString(ctx.msg), 1 /* TEXT */)
  ]))
}
```

**② PatchFlags（补丁标记）—— 每个动态 vnode 带一个数字标记**

| Flag | 值 | 含义：运行时只需检查这一项 |
|:--|:--|:--|
| TEXT | 1 | 只有文本会变 |
| CLASS | 2 | 只有 class 会变 |
| STYLE | 4 | 只有 style 会变 |
| PROPS | 8 | 只有特定 props 会变（还附带动态 prop 名数组） |
| FULL_PROPS | 16 | 有 key 动态，需全量 diff props |
| STABLE_FRAGMENT | 64 | 子节点顺序不变的 fragment |

```javascript
// 运行时 patch 看到 flag=1，直接比文本，跳过 class/style/props 全部检查
if (patchFlag & 1 /* TEXT */) {
  if (n1.children !== n2.children) hostSetText(el, n2.children);
}
```

**③ Block Tree（区块树）—— 把「全树遍历」降为「只遍历动态节点」**

```
传统 diff：递归整棵 vnode 树，静态节点也要走一遍
Block Tree：
  每个「结构稳定」的节点（带 PatchFlag 或组件根）成为一个 Block
  Block 内部把所有动态后代收集进一个扁平数组 dynamicChildren
  更新时：只遍历 dynamicChildren，静态节点整棵跳过
```

**追问链：**

- **「为什么 `v-if`/`v-for` 会『切断』Block？」**
  答：Block 的前提是「结构稳定」。`v-if` 切换会增删节点、`v-for` 长度会变，结构不稳定就没法用扁平数组追踪——所以它们各自成为新的 Block 边界。这也是「`v-if` 和 `v-for` 别同用」之外的另一层编译原理。
- **「PatchFlags 和 React 的 memo 有什么本质不同？」**
  答：React 靠**运行时**比较 props（memo）或开发者手动声明依赖；Vue3 靠**编译时**分析模板，自动给每个节点打标记，开发者零心智负担。代价是 Vue 的优化强依赖模板编译——**手写 render 函数 / JSX 会丢失大部分编译优化**（没有静态分析），这是「为什么 Vue 推荐模板而非 JSX」的性能理由。
- **「`-1 /* HOISTED */` 和 `64 /* STABLE_FRAGMENT */` 这些负数/特殊值干嘛的？」**
  答：是编译器的内部标记：-1 表示已提升的静态节点（运行时直接跳过），-2 表示带缓存的静态 vnode。面试能说出「负数是跳过标记」即可，不用背全表。

### Q9b: nextTick 的实现原理？为什么改数据后要在 nextTick 里读 DOM？⭐⭐ 🔥

**答：** 因为 Vue 的更新是**异步批处理**的：`trigger` 把组件的更新 effect 推进微任务队列，同一轮里多次改数据只触发一次渲染。所以改完数据**同步读 DOM 拿到的是旧值**，`nextTick` 就是「等这次渲染完成后再执行」的钩子。

```javascript
count.value++;
console.log(el.textContent);        // 旧值！渲染还没发生
await nextTick();
console.log(el.textContent);        // 新值，渲染已完成
```

**实现原理（降级链）：**

```javascript
// 简化：nextTick 本质是把回调推进微任务队列，排在更新 effect 之后
const callbacks = [];
let pending = false;

function nextTick(cb) {
  callbacks.push(cb);
  if (!pending) {
    pending = true;
    // 优先 Promise.then（微任务），降级 MutationObserver → setImmediate → setTimeout
    Promise.resolve().then(flushCallbacks);
  }
}

function flushCallbacks() {
  pending = false;
  const copies = callbacks.slice(0);
  callbacks.length = 0;
  copies.forEach(cb => cb());
}
```

**关键：为什么 nextTick 的回调一定在渲染之后？**
因为更新 effect 先入队、nextTick 回调后入队，微任务按 FIFO 清空——更新先跑完，回调才执行。Vue3 里 `nextTick()` 不传回调时返回 Promise，就是 `await` 当前这轮微任务队列刷完。

**追问链：**

- **「nextTick 和 `flush: 'post'` 的 watch 什么关系？」**
  答：目的相同（DOM 更新后执行），机制不同：nextTick 是「手动等一轮」，post-watch 是「声明式地在每次更新后跑」。一次性操作用 nextTick，持续监听用 post-watch。
- **「Vue2 为什么用过 MutationObserver / setImmediate？」**
  答：历史降级链——早期要兼容不支持 Promise 的环境，且某些场景微任务优先级过高会饿死 I/O，曾尝试宏任务方案。Vue3 已统一为 Promise 微任务。**面试答「微任务 + 降级链」即可，不用背 MutationObserver 细节**。
- **「连续改三次数据，nextTick 回调执行几次？」**
  答：一次。三次 trigger 的更新 effect 被去重合并，nextTick 回调也只入队一次（同一轮 pending 期间不重复调度）——这正是批处理的意义。

### Q12b: keep-alive 的实现原理？LRU 缓存怎么工作？⭐⭐⭐

**答：** keep-alive 是 Vue 内置的**抽象组件**（不渲染真实 DOM、不出现在父组件链），它把被包裹组件的 **vnode 和组件实例缓存起来**，切换时不销毁而是「 deactivated → 重新 activated」。

```
首次进入 A：创建实例 → 渲染 → 缓存 { key: A, vnode, instance }
切到 B：A 不卸载，触发 onDeactivated，DOM 移入隐藏容器
切回 A：命中缓存 → 取出实例 → DOM 移回 → 触发 onActivated（不重新 created/mounted）
```

**LRU（最近最少使用）淘汰策略：**

```javascript
// keep-alive 内部简化：cache + keys 数组
const cache = new Map();   // key → vnode
const keys = new Set();    // 维护访问顺序

function cacheSubtree(key, vnode) {
  if (cache.has(key)) {
    keys.delete(key);      // 命中：移到最新
  } else if (keys.size >= max) {
    // 超上限：淘汰最久未用的（keys 里第一个）
    const oldest = keys.values().next().value;
    pruneCacheEntry(cache.get(oldest));   // 真正卸载该实例
    keys.delete(oldest);
    cache.delete(oldest);
  }
  cache.set(key, vnode);
  keys.add(key);
}
```

**三个属性 + 两个钩子：**

| 配置/钩子 | 作用 |
|:--|:--|
| `include` / `exclude` | 按组件名正则/数组/字符串决定缓存谁 |
| `max` | 缓存上限，触发 LRU 淘汰 |
| `onActivated` | 缓存组件重新进入时（替代 mounted 做刷新） |
| `onDeactivated` | 离开时（暂停定时器/视频，省资源） |

**追问链：**

- **「为什么 keep-alive 缓存后数据不刷新？」**
  答：因为切回时**不走 created/mounted**，只走 onActivated。如果拉数据写在 mounted 里，第二次进入就不执行了——要把刷新逻辑放 onActivated，或用 `:key` 强制重建。这是最高频的 keep-alive 坑。
- **「include 匹配的是什么？」**
  答：组件的 **name 选项**（`<script setup>` 里需用 `defineOptions({ name: 'X' })` 或额外 script 块声明），不是文件名/路由名。匹配不上就静默不缓存——「配了 include 却没缓存」多半是 name 没对上。
- **「keep-alive 缓存的组件会内存泄漏吗？」**
  答：会，如果不在 onDeactivated 里暂停定时器/监听/动画。缓存意味着实例长期存活，mounted 里注册的副作用不会随切换自动清理。max 也要设，否则路由越多缓存越多。

### Q13b: hash 模式和 history 模式的区别？为什么 history 要服务端配置？⭐⭐ 🔥

**答：**

| 维度 | hash 模式 | history 模式 |
|:--|:--|:--|
| URL 形态 | `example.com/#/user/1` | `example.com/user/1` |
| 原理 | `location.hash` + `hashchange` 事件 | `history.pushState/replaceState` + `popstate` |
| 是否发请求 | hash 变化**不发请求**（# 后不属于路径） | pushState 不发请求，但**刷新/直接访问会发请求** |
| 服务端配置 | 不需要 | **必须配 fallback** |
| SEO/美观 | # 不优雅，爬虫忽略 hash | 干净路径，SEO 友好 |

**为什么 history 模式刷新会 404？**

```
用户直接访问 example.com/user/1（或刷新）
→ 浏览器向服务器请求 /user/1 这个真实路径
→ 服务器上并没有 /user/1 这个文件/路由
→ 404

解法：服务端把所有「非静态资源」的请求都回退到 index.html，
让前端路由接管解析。
```

```nginx
# Nginx 配置（history 模式必备）
location / {
  try_files $uri $uri/ /index.html;   # 找不到文件就回 index.html
}
```

**追问链：**

- **「pushState 会触发 popstate 吗？」**
  答：不会。`pushState/replaceState` 只改 URL 和历史栈，**不触发 popstate**；只有用户点前进/后退（或 `history.back()`）才触发 popstate。所以前端路由要「主动监听 popstate + 拦截链接点击调 pushState」两条腿走路。
- **「hash 模式为什么 SEO 不友好？」**
  答：搜索引擎爬虫传统上忽略 `#` 后的内容（视为同一页面的锚点），所有 hash 路由在爬虫眼里都是同一个 URL。history 模式每个路径是独立 URL，可被分别收录——这也是 SSR/SSG 常配 history 的原因。
- **「history 模式的 base 路径怎么配？」**
  答：部署在子目录（如 `/app/`）时，`createWebHistory('/app/')` 要传 base，Nginx 的 fallback 也要指向 `/app/index.html`，否则资源路径和回退全错。

## 常见坑速查表

| 现象 | 根因 | 解法 |
|:--|:--|:--|
| 改了数据视图不更新 | 整体替换了 reactive 对象 / 解构丢了响应式 | 只改属性；解构用 `toRefs`；或换 `ref` |
| 图表/地图实例渲染空白或方法丢失 | 类实例被 Proxy 包住，内部判定失效 | `markRaw` 或 `shallowRef` |
| 列表插入后输入框内容错位 | 用 index 当 key | 用稳定业务 id |
| `watch` 监听不到嵌套对象变化 | 默认浅监听 | `{ deep: true }`，或用 `watch(() => obj.a, ...)` 精确监听 |
| `watch` 里改自己被监听的值导致死循环 | 回调里写回同一个源 | 加条件判断，或用 `flush: 'post'` + 只写别的状态 |
| 改数据后立刻取 DOM 是旧值 | 更新走微任务队列 | `await nextTick()` |
| `v-if` 和 `v-for` 同元素，条件取不到循环变量 | `v-if` 优先级更高（Vue3） | 外层包 `<template v-for>`，或先 computed 过滤 |
| provide 的值不是响应式 | provide 了普通值 | provide 一个 ref/reactive，或 `readonly` 包装响应式对象 |
| keep-alive 缓存后数据不刷新 | `onActivated` 没做重新拉取 | 用 `onActivated` 触发刷新，或用 `:key` 控制缓存粒度 |
| 大列表滚动卡顿 | 一次渲染全部节点 | 虚拟滚动（vue-virtual-scroller / vueuc） |
| history 模式刷新 404 | 服务器没有该真实路径 | Nginx `try_files ... /index.html` 回退 |
| watch 回调里读 DOM 是旧值 | 默认 flush:'pre' 在渲染前跑 | 改 `{ flush: 'post' }` 或 nextTick |
| keep-alive include 配了却不缓存 | 匹配的是组件 name 不是文件名 | `defineOptions({ name })` 声明组件名 |

## 深水区追问（2026 补充）

**Q：Proxy 代理不到哪些东西？为什么这类对象必须 `markRaw` 或 `shallowRef`？**

| 代理不到的对象 | 症状 | 处理 |
|:--|:--|:--|
| 带私有字段的类实例（`#x`） | 方法一调就抛「Cannot read private member」 | `markRaw`，或把方法 `bind` 回原始实例 |
| `Map` / `Set` / `Date` / `Promise` 等内建对象 | 方法读不到内部槽，报 `incompatible receiver` 或返回空 | `Map`/`Set` Vue 有专门 instrumentation，其余用 `shallowRef` / `markRaw` |
| 需要 `===` 判等的场景 | `proxy !== raw`，`includes` / `indexOf` 找不到 | 比较前 `toRaw`，或统一只存原始引用 |

根因是 Proxy 只拦截**属性访问**这一层：任何依赖「内部槽」或「this 必须是原始实例」的行为都会失效。所以第三方库实例（ECharts、Three、地图 SDK）一律 `markRaw`——这不是性能优化，是**正确性**要求。

**Q：`const { count } = defineProps()` 为什么曾经丢响应式？Vue 3.5 之后变了吗？**

`props` 是一个响应式代理对象，解构相当于**当场读一次值**存进局部变量，之后 props 更新也不会回写这个变量——这是 JS 解构语义，不是 Vue 的 bug。以前的标准解法是 `toRefs(props)` 或 `toRef(props, 'count')`。Vue 3.5 起，`<script setup>` 里 `defineProps` 的解构会被编译器**改写成 `props.count` 的属性访问**（默认值也编译成 `??` 表达式），所以响应性自动保留。两个限制仍在：只在编译宏场景生效（`this.$props`、运行时 API 声明无效）；解构出的变量**不能重新赋值**，编译器会报错。

**Q：SSR 直出后页面「先闪一下再归位」，hydration mismatch 通常来自哪三类代码？**

① **服务端取不到的值**：`Date.now()`、`Math.random()`、`localStorage`、`navigator.language`、窗口宽度——两次渲染结果不同，客户端 patch 时就得改 DOM。② **条件渲染依赖运行环境**：模板里判断 `typeof window` 是否存在，服务端渲染成 false、客户端首帧 true，结构直接对不上。③ **第三方组件在 setup 顶层就碰 DOM**：地图、编辑器、图表容器在 `onMounted` 之前实例化。修法统一：把环境相关取值挪进 `onMounted` / `onActivated`，或用 `ClientOnly` 组件把整块延后到客户端；`Teleport` 的目标节点必须服务端也存在，否则 hydration 时找不到容器。

**Q：`v-once`、`v-memo`、`shallowRef` 分别省掉什么？代价是什么？**

| 手段 | 省掉的成本 | 代价 |
|:--|:--|:--|
| `v-once` | 编译期标记静态，后续更新整棵子树跳过 diff | 里面的插值也永久冻结，只能用于真正不变的块 |
| `v-memo="[a, b]"` | 依赖数组不变时跳过该节点及其子树的 patch | 依赖漏写就是不更新，得自己判断「影响输出的全部输入」 |
| `shallowRef` | 跳过深层代理的创建与嵌套 get/set 拦截 | 内部属性 mutate 不触发更新，必须整体替换 `.value` |

三者治的都是「渲染与代理的固定开销」，不是「计算太慢」。真正的计算热点还是得靠 `computed` 缓存加虚拟滚动，别指望用 `v-memo` 救一个大列表的首屏。
