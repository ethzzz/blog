### 2. 响应外壳：code、message、data、traceId

四个字段各自有明确读者，不要混用。`code` 给前端做分支，`message` 给人看，`data` 只在成功时有意义，`traceId` 给排查用。

```java title="task-center/src/main/java/com/demo/taskcenter/common/ApiResponse.java"
package com.demo.taskcenter.common;

import org.slf4j.MDC;

public record ApiResponse<T>(int code, String message, T data, String traceId) {

    public static <T> ApiResponse<T> ok(T data) {
        return new ApiResponse<>(ErrorCode.OK.getCode(), "ok", data, MDC.get("traceId"));
    }

    public static <T> ApiResponse<T> fail(int code, String message) {
        return new ApiResponse<>(code, message, null, MDC.get("traceId"));
    }
}
```

`MDC` 是 SLF4J 的线程上下文映射，底层是 `ThreadLocal`。一个 HTTP 请求在 Tomcat 里由一个线程处理到底，所以只要在请求入口写入、在请求结束清理，`ApiResponse` 在任何深度都能取到同一个值。这也是为什么 traceId 必须在 Filter 里写，而不是在 Controller 里生成：Controller 抛出异常时，代码根本走不到你的那一行。

### 3. 业务码不是随便编的数字

```java title="task-center/src/main/java/com/demo/taskcenter/common/ErrorCode.java"
package com.demo.taskcenter.common;

import org.springframework.http.HttpStatus;

public enum ErrorCode {

    OK(0, HttpStatus.OK, "ok"),
    INVALID_PARAM(40000, HttpStatus.BAD_REQUEST, "参数不合法"),
    RESOURCE_NOT_FOUND(40400, HttpStatus.NOT_FOUND, "资源不存在"),
    TASK_NOT_FOUND(40401, HttpStatus.NOT_FOUND, "任务不存在"),
    TASK_TITLE_DUPLICATED(40901, HttpStatus.CONFLICT, "同名任务已存在"),
    UPLOAD_TOO_LARGE(41301, HttpStatus.PAYLOAD_TOO_LARGE, "文件超过大小限制"),
    MEDIA_TYPE_UNSUPPORTED(41500, HttpStatus.UNSUPPORTED_MEDIA_TYPE, "不支持的 Content-Type"),
    INTERNAL_ERROR(50000, HttpStatus.INTERNAL_SERVER_ERROR, "服务器开小差了，请稍后再试");

    private final int code;
    private final HttpStatus status;
    private final String message;

    ErrorCode(int code, HttpStatus status, String message) {
        this.code = code;
        this.status = status;
        this.message = message;
    }

    public int getCode() {
        return code;
    }

    public HttpStatus getStatus() {
        return status;
    }

    public String getMessage() {
        return message;
    }
}
```

五位数的规则是「HTTP 状态 × 100 + 两位序号」：`40401` 是 404 段的第 1 个业务原因，`40901` 是 409 段的第 1 个。这样网关按前三位做告警分级，前端按完整五位数决定文案和后续动作，两边都不用维护一张对照表。枚举把状态码和业务码写在同一个常量里，避免了「异常里抛 404、响应里写 500」这种最常见的不一致。

```java title="task-center/src/main/java/com/demo/taskcenter/common/BusinessException.java"
package com.demo.taskcenter.common;

public class BusinessException extends RuntimeException {

    private final ErrorCode errorCode;

    public BusinessException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
    }

    public BusinessException(ErrorCode errorCode, String message) {
        super(message);
        this.errorCode = errorCode;
    }

    public ErrorCode getErrorCode() {
        return errorCode;
    }
}
```

业务异常继承 `RuntimeException`，不是为了省 `throws`，而是因为它必须能穿过 Service 的方法签名到达 MVC 的异常解析器。受检异常在每一层都要声明，最后往往被就地吞掉或包成 500，契约就散了。

### 4. traceId 由 Filter 统一发放

```java title="task-center/src/main/java/com/demo/taskcenter/common/TraceIdFilter.java"
package com.demo.taskcenter.common;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.util.UUID;
import org.slf4j.MDC;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter extends OncePerRequestFilter {

    public static final String TRACE_HEADER = "X-Trace-Id";
    public static final String TRACE_KEY = "traceId";

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String traceId = request.getHeader(TRACE_HEADER);
        if (traceId == null || traceId.isBlank() || traceId.length() > 64) {
            traceId = UUID.randomUUID().toString().replace("-", "");
        }
        MDC.put(TRACE_KEY, traceId);
        response.setHeader(TRACE_HEADER, traceId);
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.remove(TRACE_KEY);
        }
    }
}
```

三个细节值得停留一下。第一，接受上游传来的 `X-Trace-Id` 并限制长度，是为了让网关、前端、后端串成一条链；不限制长度等于允许别人往你的日志里塞任意内容。第二，`finally` 里的 `MDC.remove` 不能省：Tomcat 复用线程，不清掉就会把上一个请求的 traceId 带给下一个。第三，`OncePerRequestFilter` 保证一次请求只执行一次，转发和 include 不会重复写入。

### 5. 异常收口：一个 Advice 管十类

```java title="task-center/src/main/java/com/demo/taskcenter/common/GlobalExceptionHandler.java"
package com.demo.taskcenter.common;

import jakarta.validation.ConstraintViolationException;
import java.util.stream.Collectors;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.http.ResponseEntity;
import org.springframework.http.converter.HttpMessageNotReadableException;
import org.springframework.web.HttpMediaTypeNotSupportedException;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.MissingServletRequestParameterException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.method.annotation.MethodArgumentTypeMismatchException;
import org.springframework.web.multipart.MaxUploadSizeExceededException;
import org.springframework.web.servlet.resource.NoResourceFoundException;

@RestControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    /** 请求体校验失败：字段名与消息逐条列出，按字段名排序保证输出稳定 */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiResponse<Void>> onInvalidBody(MethodArgumentNotValidException e) {
        String message = e.getBindingResult().getFieldErrors().stream()
                .sorted((a, b) -> a.getField().compareTo(b.getField()))
                .map(err -> err.getField() + ": " + err.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return fail(ErrorCode.INVALID_PARAM, message);
    }

    /** 方法参数校验：Service 上的 @Validated 与 @RequestParam 上的约束走这里 */
    @ExceptionHandler(ConstraintViolationException.class)
    public ResponseEntity<ApiResponse<Void>> onConstraint(ConstraintViolationException e) {
        String message = e.getConstraintViolations().stream()
                .map(v -> v.getPropertyPath() + ": " + v.getMessage())
                .sorted()
                .collect(Collectors.joining("; "));
        return fail(ErrorCode.INVALID_PARAM, message);
    }

    @ExceptionHandler(HttpMessageNotReadableException.class)
    public ResponseEntity<ApiResponse<Void>> onUnreadable(HttpMessageNotReadableException e) {
        log.warn("unreadable body traceId={}", MDC.get(TraceIdFilter.TRACE_KEY));
        return fail(ErrorCode.INVALID_PARAM, "请求体不是合法 JSON，或字段类型不匹配");
    }

    @ExceptionHandler(MissingServletRequestParameterException.class)
    public ResponseEntity<ApiResponse<Void>> onMissingParam(MissingServletRequestParameterException e) {
        return fail(ErrorCode.INVALID_PARAM, e.getParameterName() + ": 缺少必填参数");
    }

    @ExceptionHandler(MethodArgumentTypeMismatchException.class)
    public ResponseEntity<ApiResponse<Void>> onTypeMismatch(MethodArgumentTypeMismatchException e) {
        return fail(ErrorCode.INVALID_PARAM, e.getName() + ": 参数类型不正确");
    }

    @ExceptionHandler(HttpMediaTypeNotSupportedException.class)
    public ResponseEntity<ApiResponse<Void>> onMediaType(HttpMediaTypeNotSupportedException e) {
        return fail(ErrorCode.MEDIA_TYPE_UNSUPPORTED,
                "Content-Type 需为 application/json 或 multipart/form-data");
    }

    @ExceptionHandler(MaxUploadSizeExceededException.class)
    public ResponseEntity<ApiResponse<Void>> onTooLarge(MaxUploadSizeExceededException e) {
        return fail(ErrorCode.UPLOAD_TOO_LARGE, ErrorCode.UPLOAD_TOO_LARGE.getMessage());
    }

    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ApiResponse<Void>> onBusiness(BusinessException e) {
        log.info("business rejected code={} traceId={}",
                e.getErrorCode().getCode(), MDC.get(TraceIdFilter.TRACE_KEY));
        return fail(e.getErrorCode(), e.getMessage());
    }

    /** 路径没匹配到任何接口：静态资源处理器抛出的异常要还原成 404 */
    @ExceptionHandler(NoResourceFoundException.class)
    public ResponseEntity<ApiResponse<Void>> onNoResource(NoResourceFoundException e) {
        return fail(ErrorCode.RESOURCE_NOT_FOUND, ErrorCode.RESOURCE_NOT_FOUND.getMessage());
    }

    /** 兜底：只回一句通用文案，堆栈进日志 */
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiResponse<Void>> onUnknown(Exception e) {
        log.error("unhandled error traceId={}", MDC.get(TraceIdFilter.TRACE_KEY), e);
        return fail(ErrorCode.INTERNAL_ERROR, ErrorCode.INTERNAL_ERROR.getMessage());
    }

    private ResponseEntity<ApiResponse<Void>> fail(ErrorCode code, String message) {
        return ResponseEntity.status(code.getStatus())
                .body(ApiResponse.fail(code.getCode(), message));
    }
}
```

排序那一行不是洁癖。`getFieldErrors()` 的返回顺序由 Hibernate Validator 的校验顺序决定，同一个 DTO 改一个字段就可能变；接口测试断言整段 message 时会莫名其妙红一次。按字段名排序后，输出可以逐字符比对。

```java title="task-center/src/main/java/com/demo/taskcenter/task/dto/TaskQuery.java"
package com.demo.taskcenter.task.dto;

import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;

public record TaskQuery(

        @Min(value = 1, message = "page 最小为 1")
        Integer page,

        @Min(value = 1, message = "size 最小为 1")
        @Max(value = 100, message = "size 最大为 100")
        Integer size,

        Boolean done,

        @Size(max = 40, message = "keyword 最长 40 个字符")
        String keyword,

        @Pattern(regexp = "priority|createdAt|id", message = "sort 只支持 priority、createdAt、id")

        size = size == null ? 20 : size;

        return (page - 1) * size;

}
```

```java title="task-center/src/main/java/com/demo/taskcenter/task/TaskMapper.java"
package com.demo.taskcenter.task;

import java.util.List;
import org.apache.ibatis.annotations.Insert;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Options;
import org.apache.ibatis.annotations.Param;
import org.apache.ibatis.annotations.Select;
import org.apache.ibatis.annotations.Update;

@Mapper
public interface TaskMapper {

    @Select("SELECT * FROM task WHERE id = #{id}")
    Task findById(@Param("id") long id);

    @Select("SELECT COUNT(*) FROM task WHERE title = #{title}")
    long countByTitle(@Param("title") String title);

    @Select("""
        SELECT COUNT(*) FROM task
        WHERE (#{done} IS NULL OR done = #{done})
          AND (#{keyword} IS NULL OR title LIKE CONCAT('%', #{keyword}, '%'))
        """)
    long count(@Param("done") Boolean done, @Param("keyword") String keyword);

    @Select("""
        SELECT * FROM task
        WHERE (#{done} IS NULL OR done = #{done})
          AND (#{keyword} IS NULL OR title LIKE CONCAT('%', #{keyword}, '%'))
        ORDER BY ${sort} DESC, id DESC
        LIMIT #{limit} OFFSET #{offset}
        """)
    List<Task> page(@Param("done") Boolean done,
                    @Param("keyword") String keyword,
                    @Param("sort") String sort,
                    @Param("limit") int limit,
                    @Param("offset") int offset);

    @Insert("""
        INSERT INTO task(title, done, priority, due_at, remark, estimate_minutes)
        VALUES(#{title}, #{done}, #{priority}, #{dueAt}, #{remark}, #{estimateMinutes})
        """)
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int insert(Task task);

    @Update("""
        UPDATE task
        SET title = #{title},
            done = #{done},
            priority = #{priority},
            due_at = #{dueAt},
            remark = #{remark},
            estimate_minutes = #{estimateMinutes}
        WHERE id = #{id}
        """)
    int update(Task task);
}
```

`ORDER BY` 后面是 `${sort}`，因为它必须是列名，占位符做不到。这是整篇文章里唯一一处字符串拼接 SQL 的地方，安全由两道闸保证：`TaskQuery` 的 `@Pattern` 白名单，以及 Service 里把 camelCase 映射成列名时的 `switch` 默认分支。

```java title="task-center/src/main/java/com/demo/taskcenter/task/TaskService.java"
package com.demo.taskcenter.task;

import com.demo.taskcenter.task.dto.TaskQuery;
import com.demo.taskcenter.task.dto.TaskSaveReq;
import java.util.List;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class TaskService {

    private final TaskMapper mapper;

    public TaskService(TaskMapper mapper) {
        this.mapper = mapper;
    }

    @Transactional(rollbackFor = Exception.class)
    public Task create(TaskSaveReq req) {
        if (mapper.countByTitle(req.title().trim()) > 0) {
            throw new BusinessException(ErrorCode.TASK_TITLE_DUPLICATED);
        }
        Task task = new Task();
        task.setTitle(req.title().trim());
        task.setDone(false);
        task.setPriority(req.priority() == null ? 3 : req.priority());
        task.setDueAt(req.dueAt());
        task.setRemark(req.meta().remark());
        task.setEstimateMinutes(req.meta().estimateMinutes());
        mapper.insert(task);
        return task;
    }

    @Transactional(rollbackFor = Exception.class)
    public Task update(long id, TaskSaveReq req) {
        Task task = mapper.findById(id);
        if (task == null) {
            throw new BusinessException(ErrorCode.TASK_NOT_FOUND);
        }
        task.setTitle(req.title().trim());
        task.setPriority(req.priority() == null ? task.getPriority() : req.priority());
        task.setDueAt(req.dueAt());
        task.setRemark(req.meta().remark());
        task.setEstimateMinutes(req.meta().estimateMinutes());
        mapper.update(task);
        return task;
    }

    public PageResult<Task> page(TaskQuery query) {
        long total = mapper.count(query.done(), query.keyword());
        List<Task> items = total == 0
                ? List.of()
                : mapper.page(query.done(), query.keyword(), sortColumn(query.sort()),
                        query.size(), query.offset());
        return new PageResult<>(items, query.page(), query.size(), total);
    }

    private String sortColumn(String sort) {
        return switch (sort) {
            case "priority" -> "priority";
            case "createdAt" -> "created_at";
            default -> "id";
        };
    }
}
```

`total == 0` 时直接返回空列表，避免了一次必然空的 `LIMIT/OFFSET` 查询。这不是性能优化，是契约清晰：`total` 为 0 时 `items` 一定是空数组，前端不用判断 `null`。

重复标题的检查是「先查后插」，两个请求同时提交仍可能都通过。真正的兜底是给 `title` 加唯一索引，并把插入时的 `DuplicateKeyException` 翻译成 40901；索引与并发留到阶段十五，本篇先把错误码定下来，让后续改动不用动前端。

### 9. 时间格式只在一处定义

```java title="task-center/src/main/java/com/demo/taskcenter/config/JacksonConfig.java"

import com.fasterxml.jackson.datatype.jsr310.ser.LocalDateTimeSerializer;
import java.time.format.DateTimeFormatter;
import java.util.TimeZone;
import org.springframework.boot.autoconfigure.jackson.Jackson2ObjectMapperBuilderCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class JacksonConfig {

    public static final String DATE_TIME_PATTERN = "yyyy-MM-dd'T'HH:mm:ss";

    @Bean
    public Jackson2ObjectMapperBuilderCustomizer contractCustomizer() {
        DateTimeFormatter formatter = DateTimeFormatter.ofPattern(DATE_TIME_PATTERN);
        return builder -> builder
                .serializers(new LocalDateTimeSerializer(formatter))
                .deserializers(new LocalDateTimeDeserializer(formatter))
                .timeZone(TimeZone.getTimeZone("Asia/Shanghai"));
    }
}
```

选 `yyyy-MM-dd'T'HH:mm:ss` 不是审美问题：带 `T` 的字符串是 ECMAScript 规范保证能被 `new Date()` 解析的格式，带空格的那种在部分浏览器里直接得到 `Invalid Date`。秒后面的纳秒被截掉，是因为 MySQL 的 `DATETIME` 默认就是秒精度，保留纳秒只会让前后端对不上。

## 二、机制：一个请求在容器里怎么走

很多「注解不生效」的困惑，本质是不知道代码停在了哪一步。下面这条链是 Spring MVC 处理一次请求的完整顺序，异常会从任意一步跳到最后一步。

```text
Tomcat 工作线程
└── FilterChain
    ├── TraceIdFilter        MDC、响应头
    ├── 编码 / CORS / 安全    （阶段十六会加）
    └── DispatcherServlet
        ├── getHandler()          HandlerMapping 选中 HandlerMethod + 拦截器链
        ├── getHandlerAdapter()   RequestMappingHandlerAdapter
        ├── preHandle()           拦截器（此时方法参数还没解析）
        ├── 参数解析              ArgumentResolver 按注解取数据
        ├── 校验                  @Valid / @Validated，失败抛 MethodArgumentNotValidException
        ├── 方法调用              AOP 代理 -> Controller 方法体
        ├── 返回值处理            ReturnValueHandler -> HttpMessageConverter 写 JSON
        ├── afterCompletion()     拦截器收尾（异常也会走到）
        └── 异常路径              HandlerExceptionResolver 链
```

**第一层：Filter 在 Servlet 容器里。** `DispatcherServlet` 本身就是一个 Servlet，映射到 `/`。Filter 在它之前执行，拿到的是原始 `HttpServletRequest`，不知道最终会落到哪个方法。这也解释了一个高频问题：在 Filter 里抛出的异常，`@RestControllerAdvice` 接不住。因为此时还没进入 `DispatcherServlet.doDispatch` 的 `try` 块，异常被容器交给 `/error`，返回的是 `BasicErrorController` 的响应，格式和你的 `ApiResponse` 完全不同。

**第二层：HandlerMapping 决定「谁来处理」。** `RequestMappingHandlerMapping` 按路径、方法、`consumes`、`produces`、`params`、`headers` 六个条件匹配。多个映射同时匹配时，更具体的条件胜出；如果两个映射同样具体，启动阶段就会因为歧义失败，不会等到运行时报错。

**第三层：HandlerAdapter 决定「怎么调用」。** `RequestMappingHandlerAdapter` 持有一组 `HandlerMethodArgumentResolver`，按顺序询问谁能处理这个参数。`@RequestBody` 交给 `RequestResponseBodyMethodProcessor`，它用 `HttpMessageConverter` 把字节流读成对象；`@PathVariable` 交给 `PathVariableMethodArgumentResolver`；没有注解的复杂类型默认落到 `@ModelAttribute` 那条路。

**第四层：校验发生在方法体之前。** 参数解析完、反射调用前，框架会检查参数上的注解名是否以 `Valid` 开头，是就调用校验器。所以 Controller 方法体第一行永远可以假设「`req.title()` 不为空白」——这个假设由框架保证，不靠人记得写 `if`。

**第五层：返回值也要过一遍转换器。** `@RestController` 等价于 `@ResponseBody`，返回值交给 `RequestResponseBodyMethodProcessor`，再由 Jackson 写出去。`ResponseEntity` 让你额外控制状态码和响应头，这也是创建接口返回 201 的方式。

**第六层：异常由三个解析器接力。** `ExceptionHandlerExceptionResolver` 先找 `@ControllerAdvice` 里匹配的 `@ExceptionHandler`；找不到就交给 `ResponseStatusExceptionResolver` 处理 `@ResponseStatus`；再找不到交给 `DefaultHandlerExceptionResolver`，它把 Spring 标准异常映射成状态码，但**不写响应体**。这就是为什么没写 handler 的 415 会返回空 body——不是 Bug，是兜底解析器的行为。想统一格式，就得像上一节那样把 `HttpMediaTypeNotSupportedException` 显式接住。

**404 有两种来源，处理方式不同。** 第一种是完全没有匹配的映射：`getHandler` 返回 `null`，`DispatcherServlet` 直接 `sendError(404)`，不经过异常解析器。第二种更常见：请求 `/api/tasksx` 不会匹配任何 Controller，却会匹配到 `/**` 的静态资源处理器；从 Spring Boot 3.2（Spring 6.1）起，它找不到文件时抛的是 `NoResourceFoundException`，而不是直接 `sendError(404)`。这个异常会一路走到 `@ExceptionHandler(Exception.class)`，于是「接口不存在」变成了 500。给 advice 补一个 `NoResourceFoundException` 分支，才能让 404 保持 404；这也是兜底 handler 必须谨慎的原因——它能接住一切，包括本来不该由它接的东西。

## 三、参数绑定：四个注解，四种来源

四个注解不是风格选择，而是四个不同的数据来源。选错来源的典型症状是「参数永远是 null」。

| 注解 | 数据来源 | 适合 | 常见错配 |
| :-- | :-- | :-- | :-- |
| `@PathVariable` | URI 模板 | 资源定位、层级关系 | 把筛选条件塞进路径；路径变量里带点号或斜杠需要额外的匹配配置 |
| `@RequestParam` | query 或表单的单值 | 筛选、分页、开关 | 用它接 JSON 体，得到 null 或 400 |
| `@RequestBody` | 请求体，经 `HttpMessageConverter` | 创建、更新、批量提交 | 一个方法写两个；漏写 `Content-Type` |
| `@ModelAttribute` | query 或表单，按属性名绑定 | GET 列表的查询对象 | 直接绑实体，被多传字段覆盖 |

**`@PathVariable` 的两个边界。** 名字可以不写，前提是编译时保留了参数名——Spring Boot 的 Maven 插件默认加 `-parameters`，手工 `javac` 不加就会报「Name for argument of type not specified」。类型转换失败（`/api/tasks/abc`）抛 `MethodArgumentTypeMismatchException`，我们已经在 advice 里接住，返回 400 而不是 500。

**`@RequestParam` 的默认值语义。** `required` 默认是 `true`，缺失抛 `MissingServletRequestParameterException`；写了 `defaultValue` 就相当于 `required=false`。布尔转换由 `StringToBooleanConverter` 完成，`true`、`1`、`on`、`yes` 都算真，`done=abc` 则是 400。前端传来 `done=`（空串）不会当成 false，会被当成空值——需要空值语义时，用包装类型并在 DTO 里显式归一。

**`@RequestBody` 只能有一个。** 请求体是一个流，读一次就没了，所以不存在两个 `@RequestBody` 参数。反序列化失败有两种：JSON 语法错误，和 JSON 合法但字段类型不匹配（比如把 `"priority":"高"` 塞给 `Integer`），两者都抛 `HttpMessageNotReadableException`，消息里不区分——因为区分了也没用，前端都得改请求。另外，Jackson 默认对未知字段不报错，`titel` 会静默变 null；打开 `fail-on-unknown-properties` 后才会 400。

**`@ModelAttribute` 是 GET 列表的正确答案，也是批量赋值的入口。** 它按属性名逐字段绑定，record 走构造器绑定（Spring 6.1 起支持，对应 Spring Boot 3.2 及以上；更早的版本只能绑普通 JavaBean）。危险之处在于：如果参数类型是实体 `Task` 而不是 `TaskQuery`，前端多传一个 `id` 或 `done` 就能改到不该改的字段。契约的第一步不是加注解，是**为每个入口定义独立的 DTO**。

四种来源也可以组合：路径给资源 ID，查询串给分页，请求体给内容。组合本身没问题，问题是同一个字段出现两次——`PUT /api/tasks/1?title=x` 加请求体里的 `title`，谁赢取决于代码先读哪个，这种接口一定要在评审时砍掉。

## 四、@Valid、分组与嵌套级联

`@Valid` 与 `@Validated` 经常被当成同义词，实际分工不同：`@Valid` 是 Bean Validation 标准注解，主要用来**开启级联**；`@Validated` 是 Spring 的注解，多了 `value` 用来指定分组，还能标在类上做方法级校验。在 MVC 参数上两者都能触发校验，因为框架判断的是「注解名是否以 Valid 开头」，而不是具体类型。

**分组不是可选项，而是「默认组不会自动生效」。** 一旦在参数上写了 `@Validated(Create.class)`，校验器只跑 `Create` 组的约束，`Default` 组的约束一条都不跑。所以 DTO 里的每个约束都必须显式写出分组，否则就是「注解写了，错误没报」。这也是新手最常踩的坑：只在 `@NotNull` 上写了 `groups`，其他注解忘了写，结果只有一条错误生效。

**嵌套对象必须加 `@Valid`，而且分组会一路传下去。** `TaskSaveReq` 的 `meta` 字段上有 `@Valid`，校验器才会进入 `TaskMeta` 内部；分组 `Create` 也会传进嵌套对象，所以 `TaskMeta` 的约束同样声明了 `Create` 和 `Update`。如果不想在嵌套类型里重复写分组，可以在 `meta` 上加 `@ConvertGroup(from = Create.class, to = Default.class)`，把外层分组映射成内层默认组；多个分组用 `@ConvertGroup.List` 包一层。这个注解来自 `jakarta.validation.groups`，不是 Spring 提供的。

**错误信息映射到字段，靠的是属性路径。** `MethodArgumentNotValidException` 里的 `FieldError.getField()` 返回的是属性路径，嵌套字段是 `meta.estimateMinutes`，不是 `estimateMinutes`。前端拿到这个路径就能精确高亮输入框；如果只返回一句「参数错误」，前端只能整表单飘红。这也是我们在 advice 里保留字段名的原因——可定位比可读更重要。

**校验只在入口做一次，Service 不重复。** 但 Service 的方法参数也可能被其他入口调用，所以关键方法上仍可加 `@Validated` 和约束，这类失败抛的是 `ConstraintViolationException`，属性路径形如 `create.arg0.title`。两个异常类型都要有 handler，否则一个 400 会变成 500。

## 五、统一错误：业务异常、参数异常、系统异常

三种失败必须有三种处理方式，混在一起的直接后果是告警失效。

| 层 | 典型异常 | HTTP | 业务码 | 前端应该做什么 |
| :-- | :-- | :-- | :-- | :-- |
| 参数层 | `MethodArgumentNotValidException`、`HttpMessageNotReadableException` | 400 | 40000 | 高亮字段、修正后重发 |
| 参数层 | `MaxUploadSizeExceededException` | 413 | 41301 | 提示换小文件，不重试 |
| 参数层 | `HttpMediaTypeNotSupportedException` | 415 | 41500 | 修请求头，属于联调问题 |
| 业务层 | `BusinessException(TASK_NOT_FOUND)` | 404 | 40401 | 提示资源不存在，回列表 |
| 业务层 | `BusinessException(TASK_TITLE_DUPLICATED)` | 409 | 40901 | 提示改名，可重试 |
| 系统层 | 任何未预期异常 | 500 | 50000 | 提示稍后重试，并上报 traceId |

**HTTP 状态码与业务码不是二选一。** 状态码的读者是网关、浏览器、监控和重试库：502 会触发重试，401 会触发跳登录，5xx 会触发告警。业务码的读者是前端业务代码：它需要区分「任务不存在」和「同名已存在」，而这两者都是 4xx，光看状态码分不出来。所以规则是：**同一业务码永远对应同一个 HTTP 状态，HTTP 状态永远不撒谎。**

**「全部返回 200，用 code 判断」为什么不行。** 因为中间层不认你的 code。监控看到 200 就认为健康，重试库看到 200 就不会重试，浏览器缓存看到 200 可能缓存错误页。更隐蔽的是告警：所有失败都 200，5xx 告警永远不响，等到用户投诉才发现。

**日志分级要和状态码对齐。** 4xx 用 `warn` 且不打堆栈——它们是正常的业务输入，打堆栈只会淹没有用信息；5xx 用 `error` 并打完整堆栈，因为这是代码或依赖出了问题。业务拒绝用 `info` 记一行 code 即可，方便统计某个业务码的突增。

**兜底 handler 只回一句话。** `Exception.class` 的 handler 里绝不能返回 `e.getMessage()`：那可能是 SQL 片段、表名、内网地址。细节进日志，响应给一句通用文案加 traceId，让用户报障时能对上日志。

## 六、Filter、Interceptor、AOP：三层拦截

三层都能「在方法前后做点事」，但位置决定了能力边界。

| 维度 | Filter | Interceptor | AOP |
| :-- | :-- | :-- | :-- |
| 作用位置 | Servlet 容器，DispatcherServlet 之前 | DispatcherServlet 内部，参数解析前后 | Bean 方法调用处（代理） |
| 能否拿到方法参数 | 不能，只有原始请求 | 不能，只能拿到 `HandlerMethod` 和原始请求 | 能，`JoinPoint.getArgs()` |
| 能否改返回值 | 不能，只能包装响应 | 不能 | 能，`@Around` 可替换返回值 |
| 异常能否被 `@RestControllerAdvice` 处理 | 不能 | 能 | 能 |
| 相对 Controller 的执行顺序 | 最先，在 DispatcherServlet 之前 | 其次，参数解析之前 | 最后，方法调用处 |
| 典型用途 | traceId、编码、CORS、安全过滤链 | 登录态、权限、耗时统计 | 事务、审计、重试 |

```java title="task-center/src/main/java/com/demo/taskcenter/config/SlowApiInterceptor.java"
package com.demo.taskcenter.config;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;
import org.springframework.web.method.HandlerMethod;
import org.springframework.web.servlet.HandlerInterceptor;

@Component
public class SlowApiInterceptor implements HandlerInterceptor {

    private static final Logger log = LoggerFactory.getLogger(SlowApiInterceptor.class);
    private static final long WARN_NANOS = 200_000_000L;

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        request.setAttribute("startAt", System.nanoTime());
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {
        Object start = request.getAttribute("startAt");
        if (!(handler instanceof HandlerMethod method) || start == null) {
            return;
        }
        long costNanos = System.nanoTime() - (long) start;
        if (costNanos >= WARN_NANOS) {
            log.warn("slow api {}.{} cost={}ms", method.getBeanType().getSimpleName(),
                    method.getMethod().getName(), costNanos / 1_000_000);
        }
    }
}
```

```java title="task-center/src/main/java/com/demo/taskcenter/config/WebConfig.java"
package com.demo.taskcenter.config;

import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class WebConfig implements WebMvcConfigurer {

    private final SlowApiInterceptor slowApiInterceptor;

    public WebConfig(SlowApiInterceptor slowApiInterceptor) {
        this.slowApiInterceptor = slowApiInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(slowApiInterceptor).addPathPatterns("/api/**");
    }
}
```

阈值 `200_000_000` 纳秒是配置值，不是实测数据；上线前应按真实 p99 调整，否则要么全是噪音，要么一条都不报。`afterCompletion` 在异常路径上也会执行，所以统计耗时不依赖方法是否成功。

**执行顺序要背下来：** Filter 前置 → `preHandle` → 参数解析 → 校验 → AOP 前置 → 方法体 → AOP 后置 → 返回值处理 → `afterCompletion` → Filter 后置。由此推出两个结论：

1. **鉴权拦截器跑在参数校验之前。** 未登录的请求会先拿到 401，而不是先因为 `title` 为空拿到 400。这既是安全要求，也避免了「用 400 的错误信息探测接口结构」。
2. **AOP 管不到参数解析阶段的失败。** 想给所有请求记审计日志，写在 AOP 里会漏掉 400；写在 Filter 或拦截器里才完整。

**一个容易漏掉的边界：** Filter 里也可以用 `try/catch` 自己生成 JSON 错误响应，但那就绕过了 `ApiResponse` 的统一构造和 MDC 清理逻辑，两套格式迟早会漂移。所以 Filter 只做「一定会成功」的事——写 traceId、设置编码、校验签名；需要业务语义的判断放到拦截器。

## 七、文件上传：multipart 的三道闸

上传不是「收个文件存起来」，而是三道互不替代的限制：容器层的大小限制、应用层的类型与名字检查、存储层的路径与原子性。

第一道在配置里，`max-file-size` 是单文件上限，`max-request-size` 是整个请求（多文件加表单字段的总和）上限。超过时 Tomcat 中断请求，Spring 包装成 `MaxUploadSizeExceededException`，我们的 advice 把它映射成 413。但这里有个坑：Tomcat 默认只「吞掉」2MB 的剩余请求体以便返回错误，超出就直接断连接，客户端看到的是连接重置而不是 413。`max-swallow-size: -1` 让 Tomcat 读完整个请求体再回错误，代价是攻击者可以让你读一个超大 body——所以它只应该在前面有网关限流时开启。

```java title="task-center/src/main/java/com/demo/taskcenter/task/TaskAttachmentController.java"
package com.demo.taskcenter.task;

import com.demo.taskcenter.common.ApiResponse;
import com.demo.taskcenter.common.BusinessException;
import com.demo.taskcenter.common.ErrorCode;
import java.io.IOException;
import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.Paths;
import java.nio.file.StandardCopyOption;
import java.util.Locale;
import java.util.Set;
import java.util.UUID;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestPart;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.multipart.MultipartFile;

@RestController
@RequestMapping("/api/tasks")
public class TaskAttachmentController {

    private static final Set<String> ALLOWED_EXT = Set.of("png", "jpg", "jpeg", "pdf", "txt");
    private static final long MAX_BYTES = 5L * 1024 * 1024;

    private final TaskMapper mapper;
    private final Path root;

    public TaskAttachmentController(TaskMapper mapper,
                                    @Value("${app.upload-dir}") String uploadDir) {
        this.mapper = mapper;
        this.root = Paths.get(uploadDir).toAbsolutePath().normalize();
    }

    @PostMapping(value = "/{id}/attachments", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
    public ApiResponse<String> upload(@PathVariable long id,
                                      @RequestPart("file") MultipartFile file) throws IOException {
        if (mapper.findById(id) == null) {
            throw new BusinessException(ErrorCode.TASK_NOT_FOUND);
        }
        if (file.isEmpty()) {
            throw new BusinessException(ErrorCode.INVALID_PARAM, "文件为空");
        }
        if (file.getSize() > MAX_BYTES) {
            throw new BusinessException(ErrorCode.UPLOAD_TOO_LARGE);
        }

        // 1. 只取最后一段，同时兼容 Windows 的反斜杠
        String original = file.getOriginalFilename();
        String base = original == null ? "" : original.replace('\\', '/');
        String safeName = base.substring(base.lastIndexOf('/') + 1).trim();
        if (safeName.isEmpty() || safeName.startsWith(".") || safeName.length() > 120) {
            throw new BusinessException(ErrorCode.INVALID_PARAM, "文件名不合法");
        }

        // 2. 扩展名白名单，取最后一个点之后的部分并转小写
        int dot = safeName.lastIndexOf('.');
        String ext = dot < 0 ? "" : safeName.substring(dot + 1).toLowerCase(Locale.ROOT);
        if (!ALLOWED_EXT.contains(ext)) {
            throw new BusinessException(ErrorCode.INVALID_PARAM, "只允许 png、jpg、pdf、txt");
        }

        // 3. 落盘名与客户端无关，路径必须落在 root 之内
        String stored = UUID.randomUUID().toString().replace("-", "") + "." + ext;
        Path target = root.resolve(stored).normalize();
        if (!target.startsWith(root)) {
            throw new BusinessException(ErrorCode.INVALID_PARAM, "文件名不合法");
        }

        Files.createDirectories(root);
        Path tmp = Files.createTempFile(root, "upload-", ".part");
        try (InputStream in = file.getInputStream()) {
            Files.copy(in, tmp, StandardCopyOption.REPLACE_EXISTING);
        }
        Files.move(tmp, target, StandardCopyOption.ATOMIC_MOVE);
        return ApiResponse.ok(stored);
    }
}
```

**为什么要 `replace('\\', '/')` 再取最后一段。** `Paths.get("../../etc/passwd").getFileName()` 在 Linux 上只返回 `passwd`，看起来安全；但 `Paths.get("..\\..\\evil.png").getFileName()` 在 Linux 上返回的是整个带反斜杠的字符串——因为反斜杠不是 Linux 的路径分隔符。同一个上传代码在 Windows 上开发、Linux 上运行，结论可能相反。统一替换再截取，是跨平台确定性最高的写法。

**为什么不用 `getContentType()` 判断类型。** 它和文件名一样由客户端提供，改个请求头就能绕。真正的校验要么读魔数（PNG 前 8 字节是固定的 `89 50 4E 47 0D 0A 1A 0A`），要么交给图像库解码一次。扩展名白名单只解决「不会存成 .jsp 被执行」，不解决「内容是恶意文件」。

**流式落盘的两个要点。** 不要 `file.getBytes()`，那会把整个文件读进堆内存，10 个并发 5MB 就是 50MB 的瞬时占用；`getInputStream()` 配合 `Files.copy` 是固定缓冲区。先写临时文件再 `ATOMIC_MOVE`，是为了避免「文件只写了一半就被读到」——同名覆盖场景下，读者永远只会看到完整文件。

```bash
printf '接口契约草稿' > /tmp/note.txt

# 正常上传
curl -s -i -X POST http://127.0.0.1:8081/api/tasks/1/attachments \
  -H 'X-Trace-Id: demo-0005' \
  -F 'file=@/tmp/note.txt'

# 客户端伪造目录穿越的文件名：会被截成 evil.txt，落盘名仍是 UUID
curl -s -X POST http://127.0.0.1:8081/api/tasks/1/attachments \
  -F 'file=@/tmp/note.txt;filename=../../evil.txt'

# 扩展名不在白名单
curl -s -X POST http://127.0.0.1:8081/api/tasks/1/attachments \
  -F 'file=@/tmp/note.txt;filename=evil.sh'
```

正常上传返回 `code` 为 0、`data` 是形如 `8f3a...c1.txt` 的存储名；穿越请求同样成功但文件名被换成 UUID，目录里不会出现 `evil.txt`；`evil.sh` 返回 400 与 40000。任务不存在时第一条就返回 404 与 40401——资源检查放在大小检查之前，是为了让「任务不存在」这个更根本的错误优先暴露。

## 八、Long 与时区：两处静默失真

这两类问题有个共同点：本地自测全对，上线后偶发，日志里看不出异常。

**先说 Long。** task 表的 `id` 是自增，现在只有个位数，序列化成字符串看不出必要性；但同一套序列化规则会复制到阶段二十的工单表，那里的编号由雪花算法生成，19 位，量级在 1.8×10^18。JavaScript 的 `Number` 是双精度浮点，能精确表示的整数上限是 `2^53 - 1`，即 `9007199254740991`，16 位；在这个量级上，相邻可表示值的间隔是 256。

```js
const id = '1839661200473890847';
JSON.parse('{"id":' + id + '}').id   // 1839661200473890800
Number(id)                            // 1839661200473890800
```

服务端返回的工单号是 `...847`，前端拿到的是 `...800`（其精确值实际是 `1839661200473890816`），差 31。用这个值去查详情，要么 404，要么读到另一张工单——后者更可怕，因为它在测试环境里大概率不会发生。

字段级修法就是 `Task.java` 里的那一行：把 `@JsonSerialize(using = ToStringSerializer.class)` 加在 `id` 字段上，类型保持 `Long`，只有这个字段被写成字符串。

全局修法是在 `Jackson2ObjectMapperBuilderCustomizer` 里加两行：`builder.serializerByType(Long.class, ToStringSerializer.instance).serializerByType(Long.TYPE, ToStringSerializer.instance);`。`long` 和 `Long` 都要注册，只注册前者，包装类型仍然输出数字。

| 方案 | 影响范围 | 代价 |
| :-- | :-- | :-- |
| 字段级 `@JsonSerialize` | 只有标注的字段 | 新增 ID 字段时容易忘；适合 ID 少的场景 |
| 全局 `serializerByType` | 所有 `Long`，包括 `total`、计数、金额分 | 一次配置永不遗漏，但前端要把计数当字符串处理 |

本项目选了字段级：分页的 `total` 是数字，前端可以直接比较；只有 `id` 是字符串。如果哪天 `total` 也接近 `2^53`，那不是精度问题，是分页设计出了问题。反序列化方向不用特殊处理，Jackson 能把字符串 `"123"` 直接读成 `Long`。前端侧只有一条纪律：**ID 全程当字符串，不 `+`、不 `parseInt`、不和数字比较。**

**再说时区。** `LocalDateTime` 不带时区，它只是「墙上时间」：`2026-12-01T18:00:00` 没有说明这是北京还是柏林的 18 点。正因为不带，Jackson 输出时不会做任何时区换算，`spring.jackson.time-zone: Asia/Shanghai` 对它**没有效果**——那个配置影响的是 `java.util.Date`、`Calendar` 这类带瞬时语义的类型。

`spring.jackson.date-format` 同样只作用于 `java.util.Date`，对 `LocalDateTime` 无效。这是「配置了但没生效」的经典来源：想让 `LocalDateTime` 变格式，只能像前面的 `JacksonConfig` 那样注册 `LocalDateTimeSerializer`，或者在字段上写 `@JsonFormat(pattern = "yyyy-MM-dd'T'HH:mm:ss")`。

前端解析也有边界：

```js
new Date('2026-12-01T18:00:00')   // 本地时间 18:00，符合规范
new Date('2026-12-01 18:00:00')   // 部分浏览器 Invalid Date
```

ECMAScript 只保证 ISO 8601 形式（带 `T`）的解析结果，空格分隔的形式属于实现自由。所以接口统一输出带 `T` 的格式，前端不需要写 `replace(' ', 'T')` 这种补丁。

如果接口需要跨时区正确，比如海外用户看到的是自己本地时间，那就不要用 `LocalDateTime`，改成 `OffsetDateTime` 或 `Instant`，让 JSON 里带上 `+08:00` 或 `Z`。此时 `spring.jackson.time-zone` 才真正有用：它决定 `Date` 序列化成哪个偏移。数据库侧同理：`DATETIME` 存的是墙上时间，不做换算；`TIMESTAMP` 会按会话时区转换。连接串里的 `connectionTimeZone=Asia/Shanghai` 决定驱动如何解释 `TIMESTAMP`，它默认不会修改 MySQL 会话的 `time_zone`；而 `CURRENT_TIMESTAMP` 是按会话时区求值的。容器时区、会话时区、驱动时区三者不一致时，默认值写入的墙上时间就会偏 8 小时。

## 常见坑

| 现象 | 根因 | 解法 |
| :-- | :-- | :-- |
| 空标题返回 500 而不是 400 | 参数上漏了 `@Validated`，或 advice 里没接 `MethodArgumentNotValidException` | 两个都检查：注解在参数上，handler 在 advice 里 |
| 分组校验完全不生效 | 只写了 `@Validated(Create.class)`，字段约束留在 Default 组 | 每个约束显式声明分组，或把公共约束同时写进两个组 |
| 嵌套对象永远校验通过 | 嵌套字段漏了 `@Valid`，校验器不会进入对象内部 | 加 `@Valid`，并让内层约束声明同一分组 |
| Filter 里抛异常返回一坨 HTML | 异常发生在 DispatcherServlet 之前，advice 接不到 | Filter 只做不会失败的事，业务判断放拦截器 |
| 415 的响应体是空的 | `DefaultHandlerExceptionResolver` 只写状态码不写 body | 显式接 `HttpMediaTypeNotSupportedException` |
| 访问不存在的接口返回 500 | 静态资源处理器抛 `NoResourceFoundException`，被兜底 handler 接住 | advice 里显式把 `NoResourceFoundException` 映射回 404 |
| 上传超限时连接被重置 | Tomcat 默认只吞 2MB 剩余请求体 | 网关层限流，或调 `max-swallow-size` 并接受代价 |
| 前端拿到的 ID 末几位变了 | 19 位雪花 ID 超过 JS 安全整数 | ID 序列化成字符串，前端全程当字符串 |
| 时间差 8 小时 | 用 `Date` 却按 `LocalDateTime` 理解，或连接时区与库不一致 | 统一 `LocalDateTime` 加固定格式，连接串固定时区 |
| `spring.jackson.date-format` 不生效 | 它只作用于 `java.util.Date` | `LocalDateTime` 用序列化器或 `@JsonFormat` |
| `ORDER BY ${sort}` 被注入 | 直接拼客户端传来的字符串 | DTO 白名单加 Service 的 `switch` 双保险 |

## 验收清单

- [ ] `POST /api/tasks` 合法请求返回 201，`data.id` 是带引号的字符串而不是数字。
- [ ] 空标题请求返回 400 与 40000；一次提交四个非法字段时，`message` 含 `title`、`dueAt`、`meta.estimateMinutes`、`priority` 四条且顺序固定。
- [ ] 坏 JSON 返回 400 与 40000，响应体是 JSON 而不是 Whitelabel 页面。
- [ ] `curl -d` 发 JSON 返回 415 与 41500，而不是空 body。
- [ ] `GET /api/tasks?size=1000` 返回 400，消息指明 `size` 最大为 100。
- [ ] `sort` 传非白名单值返回 400，SQL 日志里看不到拼接进去的原文。
- [ ] 响应头 `X-Trace-Id` 与 body 的 `traceId` 相同，且能在日志里 grep 到同一行。
- [ ] 不存在的任务上传附件返回 404 与 40401；`evil.sh` 返回 400，目录里没有可疑文件。

## 练习

1. 给更新接口加 PATCH 语义：只传 `title` 时不得清空 `priority`。
   **自检：** 先 `GET` 记下 `priority`，再 PATCH 只带 `title`，返回的 `priority` 不变；把 `title` 换成空串，返回 400 且错误里只有 `title` 一个字段。

2. 把 ID 序列化方案临时改成全局 `Long` 转字符串。
   **自检：** `total` 从数字变成字符串，前端 `Number(data.total)` 后分页逻辑仍正确；还原字段级方案后 `total` 又变回数字，两次 `id` 的值都不变。

3. 上传两个文件：`filename=../../evil.png` 和 `filename=evil.exe`。
   **自检：** 前者返回 0 且落盘名是 UUID，`find data/uploads -name 'evil*'` 无输出；后者返回 400 与 40000，两次的响应 `code` 不同。

4. 把 `spring.jackson.time-zone` 改成 `UTC`，重启后再创建一次任务。
   **自检：** `createdAt` 的字符串逐字符不变；把某个字段临时换成 `java.util.Date`，同一时刻的输出会随配置变化。用这两次结果解释「为什么 `LocalDateTime` 不受它影响」。

5. 删掉 `TaskSaveReq` 里 `meta` 字段上的 `@Valid`，重启后提交 `meta.estimateMinutes` 为 `-5` 的请求。
   **自检：** 请求从 400 变成 201，数据库里出现负的预估工时；恢复注解后同一请求重新返回 400。这条负向实验用来确认级联校验真的在工作。

## 小结

- 一个接口的契约由四样东西组成：DTO、校验分组、统一响应体、错误码表，缺一样就会出现「有时候 200 有时候 500」。
- DispatcherServlet 的顺序是 Filter、拦截器、参数解析、校验、Controller、返回值转换、异常解析；知道顺序才知道异常被谁接住。
- 校验发生在方法体之前，所以 Controller 可以信任入参；但分组要显式写全，嵌套要加 `@Valid`。
- 业务码不等于 HTTP 状态：状态码给基础设施，业务码给前端分支，两者必须同向。
- Filter 适合不该失败的事，拦截器适合需要方法信息的判断，AOP 适合已经拿到参数之后的行为。
- 上传的安全边界在文件名、扩展名和落盘路径三处，流式读写加原子移动是基本要求。
- Long 和 `LocalDateTime` 是两个静默失真的高发区：一个丢精度，一个丢时区。
- 本步在 task-center 只加列、加 DTO、加错误码、加统一返回；认证留给 16，索引留给 15，缓存留给 18。
