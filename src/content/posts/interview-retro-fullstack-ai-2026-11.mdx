## 面试背景

岗位是全栈开发工程师，方向偏 Web 产品 + Node BFF + AI 应用。面试前半段围绕 JavaScript、Node、React 和 AI 工程化提问，后半段是面试官介绍团队和业务。

整场下来，我的感受是：**基础题能接住，但一往深里问，回答就停在概念层**。下面按被问到的顺序复盘。

## 一、浏览器事件循环：答对了，但只答了一层

我的回答大概是：

> JS 是单线程的，异步任务交给浏览器 Web API 处理，完成后放进任务队列，主线程空闲时通过事件循环调度执行。

这句话不算错，但它只是第一层。面试官如果继续问「微任务和宏任务谁先」「Promise 和 setTimeout 谁先」「Node 有什么不同」，就会卡住。

完整的浏览器事件循环是：

```text
同步代码
  ↓
清空微任务队列（Promise.then、queueMicrotask、MutationObserver）
  ↓
浏览器渲染（样式、布局、绘制、合成）
  ↓
取下一个宏任务（setTimeout、I/O、UI 事件）
  ↓
重复
```

一段常见的输出题：

```js
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

queueMicrotask(() => console.log('4'));

console.log('5');

// 1 5 3 4 2
```

Node 又不一样：它由 libuv 驱动，分 timers、pending callbacks、poll、check、close 等阶段，每个阶段后清 `process.nextTick` 和 Promise 微任务，而且 `nextTick` 优先于 Promise。

**复盘**：我以前把「事件循环」当成一道背诵题，实际它决定的是「回调为什么延迟」「服务端为什么被一个同步任务卡住」。下次回答时，我会主动补上微任务、渲染时机和 Node 差异，而不是停在「单线程 + 任务队列」。

## 二、Node 中间件：分类背出来了，执行顺序没讲透

我被问到 Node 中间件的分类，回答是：应用级、路由级、错误处理、内置、第三方五类。

分类是对的，但面试官更想听的是：

- 中间件按什么顺序执行？
- `next()` 之后还会继续执行当前中间件吗？
- 异步错误怎么捕获？
- Koa 的洋葱模型具体怎么走？

Express 是线性执行：

```js
app.use((req, res, next) => {
  console.log('A before');
  next();
  console.log('A after');
});

app.use((req, res, next) => {
  console.log('B');
  next();
});

// A before → B → A after
```

Koa 是洋葱模型：

```js
app.use(async (ctx, next) => {
  console.log('A before');
  await next();
  console.log('A after');
});

app.use(async (ctx, next) => {
  console.log('B before');
  await next();
  console.log('B after');
});

// A before → B before → B after → A after
```

Express 4 还有一个经典坑：**async 函数里抛出的错误不会自动进入错误中间件**，必须 `try/catch` 后 `next(err)`，或者统一用 `asyncHandler` 包一层。错误中间件必须是 4 个参数，Express 才认得。

**复盘**：分类是「知道」，执行顺序和错误传播才是「理解」。下次我会用一段可运行的顺序题来回答，而不是只报五类。

## 三、Node 项目：最容易被追问穿的一段

面试官问 Node 项目实践，我的回答里有这么一句：

> 系统架构由技术组长搭建，本人负责功能实现层面。

这句话可能是整场面试里最伤的一句。它本身是事实，但听起来像「我只是执行者」。面试官接着问「你设计过什么、遇到过什么高并发问题」，就很难接。

正确的讲法不是否认骨架是别人搭的，而是讲清楚**你在里面做了什么决策**：

> 那个服务的骨架是组长搭的，但我负责了三个模块的接口和缓存设计：用 Redis 做了热点缓存和空值缓存，解决了峰值时重复查库；用 log4js 做了分级日志和请求 trace；补了连接池和优雅退出。后来又把两个接口做了聚合，减少前端往返。如果重做，我会先补限流和熔断。

同样的经历，后一种讲法有四个东西：**我做了什么决策、解决什么问题、结果是什么、如果重来会改什么**。

**复盘**：项目经历不是「我参与过」，而是「我在约束下做了什么判断」。这一点比多背十个 API 更重要。

## 四、React Fiber：优先级那题，我说得太粗

我回答了 Fiber 解决旧版同步渲染阻塞主线程的问题，通过时间片实现可中断渲染。这部分是对的。

但我说优先级「从高到低分 5 级：立即执行、用户交互、普通更新、低延迟、非必要渲染」，这就把 **Scheduler 的优先级**和 **Fiber 内部的 Lane 模型**混在一起了。

更准确的说法是：

- Scheduler 层有 5 个优先级：Immediate、UserBlocking、Normal、Low、Idle，用来决定时间切片顺序；
- Fiber 内部用 Lane 表示更细的优先级，按位运算合并；
- `startTransition` 走 transition lane，可以被更高优先级打断；
- commit 阶段同步、不可中断，保证 DOM 变更的原子性。

Fiber 的工作循环可以简化成：

```text
while (nextUnitOfWork && !shouldYield()) {
  nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
}
```

`performUnitOfWork` 里向下 `beginWork`、向上 `completeUnitOfWork`，时间片到期或来了更高优先级就 yield。commit 阶段不能中断，因为 DOM 不能只改一半。

**复盘**：5 级不是完全错，但它只是 Scheduler 的视角。面试官如果继续问 Lane、transition、commit，就会露馅。下次回答要先说「分两层：Scheduler 和时间切片；Fiber 用 Lane 表示优先级」，再展开。

## 五、AI 工程化：方向对，但只有「做法」，没有「体系」

这场面试里，AI 工程化问得比传统八股多。我讲了：

- 针对不同项目制定提示词规范；
- 明确技术栈、可修改文件、验收标准和边界；
- 用工具库生成测试用例校验结果；
- 通过 MCP 读取需求文档和设计稿。

方向是对的，但如果面试官继续问「怎么度量」「怎么保证 AI 不改测试」「团队怎么推广」，我的答案就不够系统了。

一个更完整的 AI 工程化体系至少包含五层：

**1. 契约层**

每做一个需求，先写 spec：目标、输入输出、状态、边界、非目标、验收标准。spec 不清楚，AI 一定会自由发挥。

**2. 约束层**

规则文件写清技术栈、可改目录、只读模块、命令、禁止事项。例如：

```md
# AGENTS.md
- 技术栈：React 18 + TypeScript + Next.js
- 可改目录：src/features/**
- 只读：src/components/ui/**、src/lib/auth/**
- 命令：pnpm typecheck / pnpm test / pnpm build
- 禁止：改测试断言、写生产库、提交密钥
- 验收：类型通过、测试通过、包体积不超预算
```

**3. 测试层**

先写失败测试，再让 AI 实现到通过。测试是验收标准，不是装饰；review 时要单独看测试 diff，防止「为了让测试过而改断言」。

**4. 门禁层**

CI 卡类型、lint、单测、e2e、视觉回归、包体积、无障碍。AI 生成的代码缺陷分布和手写不同，门禁要更自动化，而不是更宽松。

**5. 度量层**

看一次通过率、返工率、缺陷率、review 轮次、交付周期，不数代码行。没有度量，就无法判断这套流程是真的有效，还是只是「大家都在用」。

MCP 在这里的角色，是把内部系统（需求文档、设计稿、权限注册）标准化成工具，让 AI 在受控范围内调用；工具要有参数校验、权限白名单和审计，不能把数据库写权限直接暴露给模型。

一句话总结我的观点：**AI 提升的是吞吐，不替代判断。质量不能靠模型自觉，要靠工程系统。**

## 六、面试官介绍的团队信息，比题目更值得记

后半段面试官介绍了团队情况，有几个信号我印象很深：

1. **AI 生成代码占比很高**，团队已经形成两条路径：固定页面全链路 AI 生成、复杂 H5 渐进式 AI 开发。
2. **质量门禁是流水线化的**：代码管控、单元测试、e2e 测试多层卡口，大部分问题在自动化环节处理，最后人工确认合并。
3. **Node 的选择和业务有关**：社群业务高并发、前后端人员配比、降低跨角色沟通成本。
4. **后端统一 Java**，需求迭代周期两周。

这些信息透露出一个判断：这类团队要的不是「会调 AI 补代码」的人，而是**能建规范、能 review、能兜住线上的人**。

两条 AI 路径也值得单独想：

- **固定页面全链路生成**：模板化、约束强、门禁全，适合标准页面；关键是模板和验收标准要足够稳定。
- **复杂 H5 渐进式开发**：人主导拆分，AI 做局部；关键是拆分粒度和中间验收，不能一次让 AI 生成整页。

如果面试官问「你怎么看这两种路径」，我的回答会是：路径不同，spec 的粒度和门禁的强度不同；复杂页面不能一次生成，必须先把交互和状态拆清楚。

## 七、我的五个缺口

这场面试让我看清了五个缺口：

| 缺口 | 具体表现 | 下一步 |
|---|---|---|
| Node 架构 | 只讲功能实现，没有架构、并发、可运维证据 | 独立做一个 BFF，补缓存、限流、日志、优雅退出 |
| React 原理 | Fiber 优先级说得太粗，Lane 没讲清 | 补 Lane / Scheduler / commit，做一个小 demo |
| AI 工程化 | 有做法，缺指标和门禁体系 | 写 spec、搭 MCP 工具、设计 CI 门禁和度量 |
| Java 协作 | 公司后端 Java，面试没体现 | 能读 Spring Boot / MyBatis，能写简单接口 |
| 面试表达 | 自我介绍泛、离职原因负面、ownership 弱 | 重写 5 个项目故事，录音复盘 |

## 九、给同样在面试的人五条建议

1. **不要只背分类，要讲执行顺序和失败模式。** 中间件五类谁都会背，`next()` 之后发生什么才是分水岭。
2. **每个项目都准备「我做了什么决策」。** 不是「我参与了」，而是「我在约束下选了什么、代价是什么」。
3. **不会就承认，但给机制和验证路径。** 「我没在生产做过，但我理解链路，如果让我做会先……」比硬编安全。
4. **AI 时代，判断力比打字速度值钱。** 能 review、能验收、能兜底的人，比会生成代码的人稀缺。
5. **一场面试只是一个样本。** 它暴露的是表达和深度，不是你的全部能力；把缺口拆成可执行的动作，比自我否定有用。

## 最后

这场面试没有让我觉得自己「什么都不会」，反而让我更清楚：**我做过的东西是真的，但我还没把它们讲到别人能看见的深度。**

接下来要做的，不是再背十页八股，而是把 Node 架构、React 原理、AI 工程化各做出一个能跑、能讲、能扛追问的东西。

如果这篇复盘对你有用，欢迎对照自己的面试记录，也做一份「问题 → 原因 → 补法」的清单。比收藏一堆面经更有用的，是下一次能讲清楚一个点。
