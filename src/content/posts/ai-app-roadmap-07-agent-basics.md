> Agent 是这两年被讲得最玄的词，剥开包装只剩一个循环：**模型决定调什么工具 → 代码执行工具 → 结果喂回模型 → 重复，直到模型认为完成**。这篇讲透这个循环的实现与工程细节，最后花一整节讲"什么时候别用 Agent"——这可能是全文最有价值的一节。

## 1. ReAct：Agent 的最小心智模型

ReAct（Reasoning + Acting）就是 05 篇 function calling 的"循环版"：

```
用户: 帮我查一下知识库里关于 Docker 部署的文章，做个摘要

模型思考: 我需要先检索 → 行动: search("Docker 部署")
代码执行: 返回 3 篇文章
模型思考: 逐篇摘要 → 行动: summarize(doc1) / summarize(doc2) / summarize(doc3)
代码执行: 返回 3 段摘要
模型思考: 信息齐了 → 最终回答: 以下是 3 篇文章的摘要……
```

关键认知：**模型不执行任何东西，它只是"点菜"**。05 篇的 function calling 返回 `tool_calls` 后流程就结束了；Agent 只是把执行结果作为新的 `role: "tool"` 消息塞回去，再问一次模型，如此往复。所谓"自主性"，就是模型可以连续点几轮菜。

## 2. 工具循环实现

```ts
interface ToolDef {
  name: string;
  description: string;
  parameters: object; // JSON Schema
  run: (args: unknown) => Promise<string>;
}

async function agentLoop(
  messages: ChatMessage[],
  tools: ToolDef[],
  opts: { maxTurns?: number } = {},
): Promise<string> {
  const maxTurns = opts.maxTurns ?? 8;
  const toolSpecs = tools.map((t) => ({
    type: "function" as const,
    function: {
      name: t.name,
      description: t.description,
      parameters: t.parameters,
    },
  }));

  for (let turn = 0; turn < maxTurns; turn++) {
    const res = await chat(messages, { tools: toolSpecs });
    const msg = res.choices[0].message;

    // 没有 tool_calls → 模型认为任务完成，输出最终回答
    if (!msg.tool_calls?.length) return msg.content ?? "";

    // 有调用请求 → 执行并回填
    messages.push(msg); // assistant 消息（含 tool_calls）必须原样回传
    for (const call of msg.tool_calls) {
      const tool = tools.find(
        (t) => t.name === call.function.name,
      );
      let result: string;
      if (!tool) {
        result = `错误：未知工具 ${call.function.name}`;
      } else {
        try {
          result = await tool.run(JSON.parse(call.function.arguments));
        } catch (e) {
          result = `工具执行失败：${String(e)}`; // 错误也要喂回去
        }
      }
      messages.push({
        role: "tool",
        tool_call_id: call.id,
        content: result,
      });
    }
  }
  return "已达最大轮次限制，任务未完成。";
}
```

几个必须记住的细节：

1. **`maxTurns` 必须设**。没有上限的循环，模型可能陷入"查了又查"的死循环，token 哗哗烧。我设 8，任务复杂的单独调。
2. **assistant 消息要原样回传**。带 `tool_calls` 的 assistant 消息和对应 tool 结果是配对的，丢了配对直接报 400。
3. **工具报错也喂回去**，而不是抛出终止。模型看到"文件不存在"会自己调整策略，这正是 Agent 的价值。

### 2.1 工具设计的三条纪律

- **工具名和 description 是模型的路标**。`search_knowledge_base` 比万能的 `query` 好得多；描述里写清楚什么时候该用、什么时候不该用。
- **参数宁少勿多**。可选参数一多，模型乱填的概率陡增。
- **返回值要有错误信息含量**。"成功"两个字的返回值等于浪费一轮；"已创建卡片 id=42"能让模型接着引用。

## 3. 记忆管理

Agent 循环里 messages 会快速膨胀（工具结果动辄上千 token）。我的分层做法：

| 层 | 内容 | 生命周期 |
| --- | --- | --- |
| 系统层 | 人设 + 规则 + 工具使用注意事项 | 永久 |
| 任务层 | 当前任务目标 + 关键约束 | 整个任务 |
| 工作层 | 工具调用与结果 | **用完即压缩** |
| 对话层 | 用户历史会话 | 按需裁剪（01 篇的 truncateMessages） |

工作层的压缩技巧：**工具结果回填前先做摘要**。搜索返回 5 篇文章全文（每篇 2000 token）？只回填标题 + 前 200 字 + "详情可调用 get_article(id) 获取"。模型需要细节时会自己再点菜——**用"按需取用"替代"一次全塞"**，这是控制上下文的根本手段。

对超长任务，还可以在每轮结束时把当前进度写一条"任务笔记"进任务层，相当于给 Agent 一个便签本，防止 20 轮之后忘了最初目标。

## 4. 什么时候别用 Agent

这是我付出真金白银学到的。Agent 的每次循环都是一次完整的 LLM 调用，**延迟以十秒计、成本以循环数翻倍计、失败率随轮次指数增长**。以下场景请老老实实写确定性代码：

| 场景 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 固定流程（翻译→入库→通知） | Agent 自由编排 | 一个普通函数按序调用 |
| 单一工具可解决 | 套 Agent 循环 | 一次 function calling |
| 输出格式严格 | Agent 中途发挥 | JSON mode + 校验（05 篇） |
| 低延迟交互 | 多轮 Agent | 预计算/缓存/单轮 |

判断标准就一条：**路径是否可预测**。可预测的路径用代码写死；只有"下一步真的取决于上一步结果、且无法枚举"的任务才值得 Agent。我的知识库里，"文章问答"是 RAG 单轮，"帮我整理本周新增文章并生成周报"才用 Agent——因为它要先查列表、再逐篇读、最后汇总，步数和内容都不可预知。

另一个实战教训：**能给 Agent 的工具越少越好**。我最初挂了 7 个工具，模型经常选错或过度调用；砍到 3 个职责清晰的工具后，行为稳定多了。工具多到需要"工具的路标"时，先想想是不是功能本身该拆分。

## 5. 一次真实 Agent 任务的完整轨迹

为了让循环不再是抽象代码，我把知识库"整理周报"任务的一次真实执行轨迹完整记录如下（token 数字为实测）：

```
[第 1 轮] 模型 → 调用 list_recent_articles({ since: "2026-10-07" })
          工具返回: 9 篇文章的 id + 标题列表（约 200 token）
[第 2 轮] 模型 → 调用 get_article({ id: "a1" }) × 4（并行点菜）
          工具返回: 每篇返回 标题+前200字摘要版（各约 250 token）
          ※ 这里体现了第 3 节的"按需取用"：全文各 3000 token，
            摘要版只回填 250，需要细节时模型才会再点菜
[第 3 轮] 模型 → 调用 summarize({ ids: ["a1","a2","a3","a4"] })
          工具返回: 4 条摘要（约 400 token）
[第 4 轮] 模型 → 对剩余 5 篇重复第 2-3 轮的动作
[第 6 轮] 模型 → 不再调用工具，输出最终周报正文
```

从这条轨迹能读出几个设计决策的回报：

- **工具结果瘦身**（全文 3000 → 摘要 250）让 6 轮循环的总上下文控制在 8000 token 以内；如果回填全文，第 4 轮就逼近窗口上限，还会显著拉高每轮的输入计费。
- **`maxTurns: 8` 的余量刚好**：这个任务实际用 6 轮，留 2 轮容错。有次文章列表异常多，任务在第 8 轮被截断——截断信息会返回给用户而不是静默失败，用户可以点"继续"，把已有进度作为上下文重新起一轮。
- **并行点菜**（第 2 轮同时要 4 篇文章）把总耗时从串行的 4 次往返压到 1 次。实现上就是模型一次返回多个 tool_calls，我的循环里用 `Promise.all` 并发执行——这是循环代码里容易忽略的免费优化。

这个任务如果不用 Agent 写死成固定流水线可不可以？可以，但"哪些文章值得进周报、摘要取哪些角度"每次都不一样，写死就会越来越僵化。**路径不可预测 + 每步依赖上一步结果**——这正是第 4 节判定标准的一个正面样本，和它对照着理解，标准就活了。

## 6. Agent 任务的评估：循环多了怎么测

10 篇会系统讲评估，这里先解决 Agent 场景的特殊性：单轮功能评的是"一次输出对不对"，Agent 评的是"整个任务流程成没成"，评估维度完全不同。我的 Agent 评估指标有三层：

| 层 | 指标 | 判定方式 |
| --- | --- | --- |
| 结果层 | 任务是否完成、最终输出是否正确 | 固定 10 个任务脚本 + 结构断言 |
| 过程层 | 轮次数、工具调用数、token 消耗 | 从 ledger 表直接统计（11 篇） |
| 行为层 | 有没有多余调用、死循环、错误工具 | 人工看轨迹，抽评 |

结果层是底线：我给"整理周报"任务写了 10 个固定输入（不同数量/类型的文章组合），每次改 Prompt 或换模型就跑一遍，最终周报的断言包括"提到的文章都在输入列表内"和"没有编造不存在的文章"。过程层几乎免费——网关本来就在记账，把 Agent 任务的轮次数和 token 消耗拉出来看趋势，轮次数莫名上涨通常意味着 Prompt 或工具描述退化。行为层最费人力，但对 Agent 最有价值：我通过抽评轨迹发现过模型对某个工具的过度调用（10 轮任务里调了 7 次 search），最后在工具描述里加了一句"同一问题已调用过则不要重复调用"，轮次立刻降下来。

这三层指标的成本递增、价值也递增。如果只做一层，做结果层；有余力就加过程层——它不要人肉，却能提前发现 80% 的退化。

### 2.2 工具的幂等性与重入安全

Agent 循环里有个隐蔽但危险的工程问题：**模型可能对同一个工具发起重复调用**（重试、误解、或单纯抽风）。如果工具不是幂等的——比如"创建卡片"调两次就生成两张重复卡片——重复调用就是真实事故。我的对策分三步：

1. **写操作尽量幂等**：`create_summary_card({ docId })` 内部先查"该 docId 是否已有卡片"，有则直接返回已有 id。把去重逻辑藏在工具实现里，模型的重复调用自然无害。
2. **真不幂等的操作加确认门**：确需一次性的动作（如发送通知），工具返回前打一层"同参数 5 分钟内已执行"的内存去重。
3. **轨迹留痕**：每次工具调用记入 ledger（11 篇），重复调用在报表上一眼可见。我通过轨迹统计发现过某工具 3% 的调用是 1 秒内的完全重复，顺着查出了模型对某类输入的解析抖动。

这个问题的本质和 02 篇的重试安全是同一个：**在会重复触发的系统里，副作用必须能自愈**。前端工程师对"请求可能重复发送"早有肌肉记忆（防抖、幂等键），把它带进 Agent 工具设计即可，不需要新知识。

## 小结

- Agent = function calling 的循环版：模型点菜、代码执行、结果回填、直到没有 tool_calls。
- 必须设 maxTurns；assistant 消息与 tool 结果配对回传；工具报错也要喂回去。
- 记忆分层管理：工作层结果先摘要再回填，用"按需取用"替代"一次全塞"。
- 路径可预测的任务别用 Agent——写确定性代码更快、更便宜、更可靠；工具宁少勿多。
