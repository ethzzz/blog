## 一张图定生死

```text
┌──────────────────────── 一轮事件循环 ────────────────────────┐
│ 1. 取出一个宏任务执行（script / setTimeout / 事件回调 / I/O） │
│ 2. 执行期间产生的微任务全部执行完（Promise.then / queueMicrotask / MutationObserver）│
│ 3. 如果需要，执行渲染（样式 → 布局 → 绘制）                  │
│ 4. 取下一个宏任务…                                          │
└──────────────────────────────────────────────────────────────┘
```

三条关键结论，所有顺序题都由它们推出：

1. **微任务在"当前宏任务结束后"立刻清空**，不等下一个宏任务；
2. **微任务里再产生的微任务，仍在同一轮里执行完**（可能饿死渲染）；
3. **渲染发生在微任务清空之后**，所以"改了状态但 DOM 还没变"是正常的。

## 经典顺序题，逐行拆

```js
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

queueMicrotask(() => console.log('4'));

console.log('5');
```

输出：`1 5 3 4 2`。

拆解：

- 同步代码先跑完 → `1`、`5`；
- 当前宏任务结束，清空微任务队列（按入队顺序）→ `then` 的 `3`、`queueMicrotask` 的 `4`；
- 进入下一轮，取宏任务 → `2`。

## `setTimeout(fn, 0)` 到底多久

规范里 `0` 会被当作 `4ms`（嵌套超过 5 层后强制最小 4ms）。实际延迟取决于：

- 当前宏任务与微任务的执行时长；
- 浏览器是否在做渲染/垃圾回收；
- 后台标签页会被节流（可能几十秒）。

```js
// 想"尽快执行但让出主线程"：用 0 可以，但别指望精确
// 想"下一帧执行"：用 requestAnimationFrame
// 想"空闲时执行"：用 requestIdleCallback
```

所以 `setTimeout(fn, 0)` 的真实语义是"**排到下一个宏任务**"，不是"立即"。

## `async/await` 在队列里怎么排

```js
async function a() {
  console.log('a1');
  await null;                 // 让出一次（相当于 then 的回调）
  console.log('a2');
}

console.log('s1');
a();
console.log('s2');
```

输出：`s1 a1 s2 a2`。

原因：`await` 之后的代码**被放进微任务队列**。`await null` 相当于 `Promise.resolve(null).then(...)`。

两道易错题：

```js
// 题 1
async function f() {
  console.log('f1');
  await g();        // g 是 async，返回 promise
  console.log('f2');
}
async function g() { console.log('g'); }
f();
console.log('end');
// 输出：f1 g end f2
```

```js
// 题 2：微任务里产生微任务，仍在同一轮
Promise.resolve().then(() => {
  console.log('A');
  Promise.resolve().then(() => console.log('B'));
});
setTimeout(() => console.log('C'), 0);
// 输出：A B C  （B 在渲染前就被执行了）
```

## "await 之后 DOM 还没更新"是怎么回事

```js
const [list, setList] = useState([]);

async function load() {
  const data = await fetchList();
  setList(data);
  console.log(document.querySelectorAll('.item').length);   // 旧的！
}
```

因为 React 的更新是异步调度（可能批量、可能并发），`setList` 之后 DOM 还没变。要拿"渲染后"的状态：

```js
useEffect(() => {
  console.log(document.querySelectorAll('.item').length);   // ✅ 这次渲染之后
}, [list]);
```

纯 JS 里同理：改了样式要等下一帧才上屏，需要 `requestAnimationFrame` 之后再读。

## 微任务会饿死渲染

```js
function loop() {
  Promise.resolve().then(loop);   // ❌ 无限微任务
}
loop();   // 页面直接卡死，连渲染机会都没有
```

因为微任务队列不清空就不进入渲染。**长任务用宏任务切片，不要用微任务递归**：

```js
// ✅ 每轮让出一次，给渲染留机会
function chunk(tasks, handle) {
  let i = 0;
  const run = () => {
    const end = Math.min(i + 200, tasks.length);
    for (; i < end; i++) handle(tasks[i]);
    if (i < tasks.length) setTimeout(run, 0);   // 宏任务切片
  };
  run();
}
```

## 渲染相关的三个 API

| API | 时机 | 用途 |
| --- | --- | --- |
| `requestAnimationFrame` | 下一帧渲染前 | 动画、读布局前的批量读 |
| `requestIdleCallback` | 浏览器空闲时 | 埋点上报、非关键初始化 |
| `queueMicrotask` | 当前宏任务后立刻 | 需要在渲染前完成的收尾逻辑 |

```js
// 典型用法：先写样式，下一帧读结果
el.style.transform = 'translateX(100px)';
requestAnimationFrame(() => {
  console.log(getComputedStyle(el).transform);   // 已生效
});
```

## Node 的差异（只记差别）

| | 浏览器 | Node |
| --- | --- | --- |
| 宏任务队列 | 一个 | **多个阶段**（timers / poll / check / close） |
| `process.nextTick` | 无 | 比微任务**更优先** |
| 渲染 | 每轮可能渲染 | 无渲染 |
| `setImmediate` | 无 | check 阶段执行 |

日常写业务代码不用记这些，但**看到 `nextTick` 与 `Promise.then` 混用**时要小心：`nextTick` 先执行。

## 常见坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 顺序题猜错 | 把微任务当成下一轮 | 记住"当前宏任务结束立刻清空微任务" |
| `setTimeout(0)` 很久才执行 | 前面有长任务/微任务 | 用 rAF 或切片 |
| 页面卡死但没网络请求 | 微任务无限递归 | 改宏任务切片 |
| `await` 之后读 DOM 是旧值 | 渲染还没发生 | 在 `useEffect`/`rAF` 里读 |
| 后台标签页定时器不执行 | 浏览器节流 | 改用 `visibilitychange` + 补偿 |
| Node 里顺序和浏览器不同 | `nextTick` 优先级更高 | 混用时显式改结构 |

## 练习

1. **预测五连**：写一段含 `setTimeout`、`Promise.then`、`queueMicrotask`、`await` 的代码，先写答案再跑。  
   *自检*：每个输出都能指出它来自哪个队列。
2. **制造微任务饿死**：用 `Promise.resolve().then(loop)` 递归 1 秒后停止，观察页面是否卡住；改成 `setTimeout` 切片对比。  
   *自检*：能说明"渲染要等微任务清空"。
3. **验证渲染时机**：改一个元素的宽度后立刻读 `offsetWidth`（强制同步，能读到新值）与在 `rAF` 里读，比较差异。  
   *自检*：能解释"强制同步布局"与"正常渲染"的区别。
