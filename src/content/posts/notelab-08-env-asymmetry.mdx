> 结论先行：不要把环境不齐当待修复的缺陷，把它当已知约束来设计工作流。我花在实际排查"为什么本地不能验证"上的时间，远多于花在想清楚"该在哪台机器验证"上的时间。

## 知识地图

```text
三个仓库 × 三台机器的能力矩阵（这才是真实的开发环境）
                 本机(Windows)      服务器(4GB/2vCPU)
notelab-java     ❌ 无 JDK          ✅ 唯一能编译的地方
notelab-b        ⚠️ 只有 tsc 预检    ✅ 完整构建
notelab-c        ❌ 无 node_modules  ✅ 唯一可信的 tsc + 构建
```

## 一、四个不对称，以及它们各自逼出的决策

| 不对称 | 事实 | 逼出的决策 |
|---|---|---|
| 本机没有 JDK | Java 改动无法本地编译验证 | Java 必须**第一个**推上去并确认构建通过，它晚一步，B/C 的改动就没有可验证的契约 |
| B 端有依赖、C 端没有 | 同一个命令在两个仓里的可信度不同 | 预检命令按仓选择，不做"统一脚本"；C 端的类型检查只在服务器跑 |
| 服务器内存小 | `npm run build` 与 `mvn package` 都很吃内存 | **两个仓的构建绝不并发**，串行且看日志收尾标记 |
| 配置与凭据按 CWD 读 | `.env` 是按当前工作目录读的 | pm2 的 `cwd` 必须等于仓目录；改了启动配置还要 `pm2 save`，否则重启后又回退 |

第一行值得多说一句：**"Java 是内容管线源头"不只是架构描述，它是工作顺序**。我现在的流程是 Java 推上去 → 确认它真的构建过并起了 → 再动 B 端表单和 C 端消费。反过来做的后果是：B 端页面做完了，接口字段对不上，而你在本地根本没法验证到底哪边错了。

## 二、「本地能验证什么」要写下来，不要靠记忆

环境能力会漂移（装过什么、删过什么、哪次升级改了什么），靠记忆判断最容易出事——[第七篇](/blog/posts/notelab-07-false-green-checks/) 里那个假 `tsc` 就是这么来的。我的办法是把结论写成一张表放在仓库里，而不是记在脑子里：

```markdown
| 检查项 | 本机 | 服务器 | 备注 |
| 类型检查 | b 可（有依赖）/ c 不可（无依赖） | 全部可 | c 本机 npx tsc 会拉假包 |
| 完整构建 | 不可（沙箱删除保护） | 可 | 串行，勿并发 |
| Java 编译 | 不可 | 唯一 | 先推先验 |
| 接口冒烟 | 可（走公网域名） | 可（本地更快） | 匿名与鉴权各一条 |
| 视觉验收 | 可（headless Chrome + CDP） | 不可 | 必须禁代理、独立 profile |
```

这张表真正的价值不在省命令，而在**阻止你在错的地方做验证**：本地跑不出来的东西，跑出来"没问题"这件事本身没有信息量。

## 三、一个绕不过的坑：本地构建被安全策略拦住

B 端在本地 `next build` 会失败，报错看起来像代码问题，其实是 Next 启动时要清理 `.next/trace`（约 50 个文件），撞上了沙箱的批量删除保护阈值。

三种处理方式我都试过：

- **绕过**（给足权限）：能跑通，但把本机环境的差异藏起来了，下次换机器照样炸；
- **本地只预检**（`tsc --noEmit`），完整构建交给服务器：这是我最后稳定下来的做法——本地拿"类型没问题"这个结论，服务器上拿"产物能生成"这个结论；
- **删掉 `.next` 再构建**：反而更慢，而且丢掉了增量缓存。

顺带一条同类的：**改完 pm2 的启动配置一定要 `pm2 save`**。`restart` 不会刷新快照，你会看到"明明改了，重启又变回去"，然后怀疑代码。

## 四、命令穿过 ssh 时的引号，是另一类环境不对称

`ssh myapp "cmd \"x\" && VARS=\$Y"` 这种嵌套引号，`\$` 会原样传到远端变成字面反斜杠，命令在你的 shell 里"看着是对的"，到远端就错了。踩过几次后我的规矩是：**只要不是单条简单命令，就用 heredoc 送**，把远端脚本当成一个完整程序而不是一个字符串。

```bash
ssh myapp << 'EOF'
cd /root/Notelab/notelab-b
git log -1 --format='%h %cd' --date=iso
stat -c '%y' .next/BUILD_ID
EOF
```

引号用单引号包住 heredoc 标记（`<< 'EOF'`），本地完全不展开，远端拿到的是原文。这条能消掉一整类"命令在本地能跑"的假象。

## 五、凭据与配置的存放，也是环境的一部分

三条被事故教出来的约定：

1. **凭据必须落文件**，不要指望它在某个 shell 里存在。数据库密码写在服务器上的 `.env`，而 `.env` 按 CWD 读，所以「pm2 的 cwd 等于仓目录」不是洁癖，是配置能不能被读到的开关。
2. **改生产数据库结构前先备份**。一条 `mysqldump` 换一个不可回滚的操作，这笔账怎么算都划算。
3. **容器内的密钥是另一个命名空间**。只在容器 env 里的东西（比如我那个朗读用的模型服务），在宿主机上 `echo` 是空的——排查"是不是没配"之前先确认你在哪一层。

## 六、由此得到的四条工作顺序约束

1. **Java 先推、先确认构建**，再动两个前端；
2. **本地只做类型预检**，凡是结论依赖"产物"，就去服务器；
3. **构建串行**，并且判据看脚本的收尾标记而不是日志尾部（见第七篇）；
4. **验收分层**：接口冒烟走公网域名（匿名 + 鉴权各一条）、视觉验收在本地 headless，两层的失败含义不同，别混着看。

这四条写下来之后，"本地复现不了"这类问题的处理时间从半天缩到了几分钟——不是环境问题解决了，是**我不再问环境问题，只问该在哪台机器验证**。

## 小结

- 环境不对称是常态，试图把它抹平（到处装依赖、到处给权限）通常只是把差异藏到更深的地方。
- 真正的资产是一张写下来的能力矩阵 + 由它推出的执行顺序。
- 三个反复出现的坑：`.env` 按 CWD 读、`pm2 save` 漏掉、ssh 引号穿透。它们都不属于代码，但都足以让一次正确的改动被判成失败。
- 「本地跑不通」和「改动是错的」是两个独立命题，别让第一个污染第二个。

## 练习

1. 给你手上多仓/多端的项目写一张「检查项 × 机器」能力矩阵，贴在仓库里，然后按它跑一遍你最近一次改动，看有没有哪步其实在不该验证的地方验证了。
2. 把部署流程里的 Java/后端改动提到前端之前，观察你因此省掉了哪类返工，写下来。
3. 把你常用的那条远程核查命令改写成 heredoc 形式，并故意构造一次嵌套引号失败来对照差异。
4. 检查你的进程管理器配置：`cwd` 是否等于仓目录、改了启动参数之后是否做过快照持久化。
