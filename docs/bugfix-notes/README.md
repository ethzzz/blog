# Bug 修复留档

> 用途：把「排查费过劲、根因不显然」的 bug 固定成可复用经验，避免下次从零再查一遍。
> 位置：`docs/` 不参与构建，这里的内容不会出现在博客正文里，也不进 Pagefind / sitemap。

## 1. 什么时候该记一条

满足任意两条即可记：

- 影响用户可见行为（闪屏、错位、功能不可用），而不是纯内部清理。
- 根因不在报错信息里，需要采样 / 打断点 / 读源码才能定位。
- 踩到了某个库的隐式行为（初始化会搬 DOM、hook 执行顺序、缓存语义……）。
- 修法有取舍，且取舍理由不写下来下次会重新纠结（例：`paused` 还是 `none`）。
- 结论是「排除法」得来的（例：证明了不是整页重载），这类结论最容易被重复怀疑。

不记：拼写错误、漏加 `await`、一次性的配置调整 —— `git log` 已经够了。

## 2. 文件命名与位置

```
docs/bugfix-notes/
  README.md                      ← 本文件（索引 + 模板）
  YYYY-MM-DD-短横线英文描述.md   ← 一条 bug 一个文件
```

日期用**修复/定稿当天**（不是发现日）。文件名带日期是为了按目录排序时天然成时间线；
标题写在正文 `# ` 一级标题里，用中文，方便搜。

## 3. 模板

复制下面骨架，删掉用不上的小节。**「证据」和「可复用经验」是重点**，
其余部分写短句即可 —— 代码本身已经在 git 里，这里只留判断过程。

```markdown
# <一句话现象>（<涉及模块>）

> 日期：YYYY-MM-DD ｜ 提交：`<sha>` ｜ 涉及文件：`path:行号`

## 1. 现象

用户看到什么、什么时候出现、复现条件（机型 / 视口 / 页面类型 / 网络）。

## 2. 先排除什么

列出被验证为「无关」的怀疑，以及排除它的那条证据。
（例：不是整页重载 —— 计数器仍然是 1。）

## 3. 根因

机制级别，不是「改了这里就好了」。指向具体文件与行号。

## 4. 证据

能复现的观测：逐帧数值、调用栈、请求列表、前后对比。写清楚怎么采的。

## 5. 修法

改了什么 + **为什么选这个方案**（对比被否掉的方案）。

## 6. 验证

跑了哪些场景，各自结果。区分「机器可判定」与「肉眼确认」。

## 7. 可复用经验

脱离本项目也成立的 3~6 条。这一节是留档的真正目的。
```
